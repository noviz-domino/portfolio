## 0. 이 문서 사용법 (AI에게 구현을 맡길 때)

이 문서는 사람이 설계를 끝낸 결과물이다. AI(Sonnet 등)에게 코드를 맡길 때는
**"무엇을 만들지 생각해줘"가 아니라 "이 문서의 N절을 그대로 구현해줘"** 형태로 요청한다.

작업 요청 예시:

```
기획서.md의 7-1절 add_transaction 명세를 보고,
5절 반환 규약과 6절 검증 규칙을 지켜서 함수를 작성해줘.
지금은 노트북 셀에 붙여넣을 코드만 주면 돼.
```

**AI가 지켜야 할 제약**
- 함수 이름, 매개변수 이름, 반환 키 이름을 이 문서와 다르게 바꾸지 말 것
- 이 문서에 없는 기능을 임의로 추가하지 말 것
- 설계를 바꾸는 게 낫다고 판단되면, 코드를 고치지 말고 **먼저 이유를 설명하고 물어볼 것**

## 1. 프로젝트 개요

사용자가 **자연어로** 수입·지출을 기록하고 예산을 관리하는 AI Agent.

Gemini의 **Function Calling**을 이용해, 모델이 사용자의 요청을 이해하고
적절한 Python 도구를 스스로 선택·호출하여 실제 작업을 수행한다.

**이 프로젝트의 목적은 금융 계산기가 아니라 "도구를 쓰는 Agent"를 만드는 것이다.**

핵심 동작 예시:

| 사용자 발화 | Agent가 하는 일 |
|---|---|
| "오늘 점심으로 12,000원 썼어" | 지출을 식비 카테고리로 등록 |
| "8월 27일 카페에서 쓴 금액을 4,500원으로 수정해줘" | 검색 → ID 확인 → 수정 (도구 2회 연속 호출) |
| "이번 달 식비 예산 얼마나 남았어?" | 예산과 지출을 조회해 잔액 안내 |

## 2. 개발 원칙 및 제약

### 2-1. 사용 기술
- Python 3
- `google-genai` SDK (`from google import genai`)
- `client.interactions.create()` 방식 — **과제 `260826_김민석_function_calling.ipynb`와 동일한 패턴을 사용한다**
- 모델: 환경변수 `GEMINI_MODEL` (기본값 `gemini-3.6-flash`)
- 외부 DB 없음. 데이터는 메모리 + JSON 파일

### 2-2. 개발 순서 원칙 (⭐ 중요)

```
Python 함수 구현 → 직접 호출해 결과 확인 → Gemini에 도구로 등록 → Agent loop
```

**Gemini를 먼저 붙이지 않는다.** 함수가 검증되지 않은 상태에서 Agent를 붙이면
에러가 났을 때 함수 문제인지 Agent 문제인지 구분할 수 없다.

### 2-3. 개발은 노트북에서, 완성 후 .py로 분리

**1단계 — 노트북에서 전부 완성한다.**
`main.ipynb` 안에서 클래스·도구 함수·schema·Agent loop를 모두 작성하고,
실제로 대화가 동작하는 것까지 확인한다.
이 기간 동안 `.py` 파일은 만들지 않는다. **코드의 원본은 노트북 하나뿐이다.**

**2단계 — 동작이 확인되면 `.py`로 이사한다.**
- `BudgetManager` 클래스 → `budget_manager.py`
- 도구 schema + Agent loop + `main()` → `agent.py`
- 옮긴 뒤 **노트북의 해당 정의 셀은 삭제하고 `import`로 교체한다**
  (같은 함수를 두 곳에 남겨두면 어느 쪽이 최신인지 알 수 없게 된다)

이사 후 노트북 첫 셀:

```python
%load_ext autoreload
%autoreload 2          # .py를 수정하면 자동으로 다시 불러온다 (없으면 옛 코드가 계속 쓰임)

from budget_manager import BudgetManager
manager = BudgetManager()
```

**주의 — 데이터 파일 충돌**
이사한 뒤 노트북과 `python agent.py`를 동시에 실행하면, 둘 다 `data.json` 전체를
덮어쓰기 때문에 나중에 저장한 쪽이 상대의 변경분을 지운다.
동시에 쓸 일이 있다면 노트북 쪽만 별도 파일을 사용한다.

```python
manager = BudgetManager(data_file="test_data.json")
```

## 4. 데이터 구조 명세

### 4-1. 거래 1건 (딕셔너리)

```python
{
    "id": 1,                    # int  — 1부터 자동 증가, 고유
    "type": "지출",              # str  — "수입" 또는 "지출" 둘 중 하나
    "category": "식비",          # str  — 해당 type의 카테고리 목록 안의 값
    "amount": 12000,            # int  — 0보다 큰 정수 (원 단위)
    "description": "점심",       # str  — 없으면 빈 문자열 ""
    "date": "2026-08-27"        # str  — "YYYY-MM-DD" 형식
}
```

> ⚠️ **이름 주의**: 딕셔너리 키는 `"type"`이지만,
> 함수 매개변수 이름은 `transaction_type`이다.
> (`type`은 파이썬 내장 함수 이름이라 매개변수로 쓰면 위험)
> 함수 안에서 `{"type": transaction_type}` 으로 매핑한다.

### 4-2. BudgetManager가 들고 있는 상태

```python
class BudgetManager:
    def __init__(self, data_file: str = "data.json"):
        self.data_file = data_file
        self.transactions = []          # list[dict] — 거래 목록
        self.next_id = 1                # int — 다음에 부여할 거래 ID
        self.expense_categories = ["식비", "교통비", "주거비", "문화생활", "기타"]
        self.income_categories  = ["월급", "용돈", "부수입", "기타"]
        self.budgets = {}               # dict — 아래 4-3 참고
        self._load()                    # 시작 시 JSON에서 자동 복원
```

**카테고리를 상수(파일 상단 대문자 변수)로 두지 않고 인스턴스 속성으로 두는 이유:**
나중에 `add_category` 기능을 붙일 때 JSON에 함께 저장·복원되어야 하기 때문이다.
상수로 두면 실행 중 추가해도 재실행 시 사라진다.

**예산은 지출에만 설정할 수 있다.** (`expense_categories`만 허용)
"월급 예산 300만원" 같은 말이 안 되는 요청을 코드로 차단하기 위함이다.

### 4-3. 예산 구조

```python
self.budgets = {
    "2026-08": {"식비": 300000, "교통비": 50000},
    "2026-09": {"식비": 400000}
}
```

월(`"YYYY-MM"`) → 카테고리 → 금액의 2단계 딕셔너리.
월별로 다른 예산을 설정할 수 있다.

### 4-4. JSON 저장 형식 (`data.json`)

```json
{
  "transactions": [
    {"id": 1, "type": "지출", "category": "식비", "amount": 12000,
     "description": "점심", "date": "2026-08-27"}
  ],
  "next_id": 2,
  "expense_categories": ["식비", "교통비", "주거비", "문화생활", "기타"],
  "income_categories": ["월급", "용돈", "부수입", "기타"],
  "budgets": {"2026-08": {"식비": 300000}}
}
```

- 저장: `json.dump(..., ensure_ascii=False, indent=2)` — 한글이 깨지지 않게, 사람이 읽을 수 있게
- 불러오기: 파일이 없으면 **에러가 아니라 기본값으로 시작**한다 (첫 실행)
- `next_id`도 반드시 저장한다. 저장하지 않으면 재실행 시 ID가 1부터 다시 시작해 중복이 생긴다.

## 5. 반환 형식 규약 (⭐ 모든 도구가 지킨다)

명세서 요구사항: *"모든 도구는 실행 성공 여부와 실행 결과 또는 오류 정보를 반환해야 한다."*

### 5-1. 성공

```python
{
    "ok": True,
    "data": { ... },                       # 도구별로 다른 실제 결과
    "message": "식비 12,000원을 등록했습니다."   # 사람이 읽을 한국어 문장
}
```

### 5-2. 실패

```python
{
    "ok": False,
    "error": "INVALID_AMOUNT",              # 오류 종류 코드 (개발자/로그용)
    "message": "금액은 0보다 큰 숫자여야 합니다."  # 사용자에게 보여줄 설명
}
```

**키 이름을 `ok`로 정한 이유:** 과제 코드의 `execute_tool_call()`이 예외 발생 시
이미 `{"ok": False, "error": ...}`를 반환하고 있다. 도구도 같은 키를 써야
Agent loop가 성공/실패를 한 가지 방법으로만 판단할 수 있다.

### 5-3. 오류 코드 목록

| 코드 | 의미 | 발생 상황 |
|---|---|---|
| `INVALID_TYPE` | 거래 유형 오류 | `transaction_type`이 "수입"/"지출"이 아님 |
| `INVALID_CATEGORY` | 카테고리 오류 | 해당 유형의 카테고리 목록에 없는 값 |
| `INVALID_AMOUNT` | 금액 오류 | 정수로 변환 불가 / 0 이하 |
| `INVALID_DATE` | 날짜 오류 | "YYYY-MM-DD" 형식이 아니거나 존재하지 않는 날짜 |
| `INVALID_MONTH` | 월 오류 | "YYYY-MM" 형식이 아님 |
| `NOT_FOUND` | 대상 없음 | 해당 ID의 거래가 존재하지 않음 |
| `NOTHING_TO_UPDATE` | 수정 항목 없음 | update 호출 시 수정할 값이 하나도 주어지지 않음 |
| `NO_BUDGET_SET` | 예산 미설정 | 조회한 월·카테고리에 설정된 예산이 없음 |
| `NO_DATA` | 데이터 없음 | 보고서 생성 시 해당 월 거래가 하나도 없음 |

## 6. 공통 검증 규칙 (내부 헬퍼 함수)

도구가 아니라 **클래스 내부에서만 쓰는 보조 함수**다. Gemini에 등록하지 않는다.
(이름 앞의 `_`는 "외부에서 쓰지 말라"는 파이썬 관례다.)

### 6-1. `_validate_amount(amount) -> int | None`

LLM은 금액을 `12000`(int), `"12000"`(str), `12000.0`(float) 중 아무거나 보낼 수 있다.
셋 다 정수로 변환을 시도하고, 실패하거나 0 이하면 `None`을 반환한다.

```python
# 처리해야 할 입력 예시
12000      -> 12000
"12000"    -> 12000
12000.0    -> 12000
"만이천원"  -> None   (INVALID_AMOUNT)
-500       -> None   (INVALID_AMOUNT)
0          -> None   (INVALID_AMOUNT)
```

### 6-2. `_validate_date(date_str) -> bool`

```python
from datetime import datetime

def _validate_date(self, date_str):
    try:
        datetime.strptime(date_str, "%Y-%m-%d")
        return True
    except (ValueError, TypeError):
        return False
```

`strptime`은 형식이 틀리거나 **존재하지 않는 날짜**(예: `"2026-02-30"`, `"2026-13-01"`)도
`ValueError`로 잡아준다. 직접 자릿수를 세는 것보다 훨씬 정확하다.

### 6-3. `_validate_month(month_str) -> bool`

같은 방식으로 `"%Y-%m"` 형식을 검사한다.

### 6-4. `_validate_category(category, transaction_type) -> bool`

`transaction_type`이 `"지출"`이면 `self.expense_categories`,
`"수입"`이면 `self.income_categories`에 포함되는지 검사한다.

### 6-5. `_save()` / `_load()`

- `_save()`: 4-4의 형식으로 `data.json`에 덮어쓴다.
  **데이터를 변경하는 모든 도구의 마지막에 호출한다.**
  (`add_transaction`, `update_transaction`, `delete_transaction`, `set_budget`)
- `_load()`: `__init__`에서 호출. 파일이 없으면 조용히 기본값 유지.

## 7. 도구 함수 명세

> 모든 도구는 `BudgetManager`의 **메서드**로 구현한다.
> Gemini에 연결할 때는 인스턴스를 하나 만들어 그 메서드를 등록한다 (9-2절 참고).

### 7-1. `add_transaction` — 거래 등록 [필수]

```python
def add_transaction(
    self,
    transaction_type: str,      # "수입" 또는 "지출"
    category: str,              # 해당 유형의 카테고리
    amount: int,                # 0보다 큰 정수
    date: str,                  # "YYYY-MM-DD"
    description: str = ""       # 선택 — 없으면 빈 문자열
) -> dict:
```

**동작 순서**
1. `transaction_type` 검증 → 실패 시 `INVALID_TYPE`
2. `amount` 검증 → 실패 시 `INVALID_AMOUNT`
3. `date` 검증 → 실패 시 `INVALID_DATE`
4. `category` 검증 → 실패 시 `INVALID_CATEGORY` (메시지에 **사용 가능한 카테고리 목록을 함께 넣는다**)
5. `self.next_id`로 거래 dict 생성 → `transactions`에 추가 → `next_id += 1`
6. `_save()` 호출
7. 성공 반환

**성공 반환 예시**
```python
{
    "ok": True,
    "data": {"id": 1, "type": "지출", "category": "식비",
             "amount": 12000, "description": "점심", "date": "2026-08-27"},
    "message": "[1] 2026-08-27 식비 지출 12,000원을 등록했습니다."
}
```

> 💡 `message`에 **ID를 함께 넣는 것이 중요하다.** Gemini가 사용자에게 ID를 알려주면
> 이후 "1번 거래 수정해줘" 같은 대화가 가능해진다.

### 7-2. `search_transactions` — 거래 검색 [필수]

```python
def search_transactions(
    self,
    date: str = None,           # 특정 날짜 "YYYY-MM-DD"
    start_date: str = None,     # 기간 시작
    end_date: str = None,       # 기간 끝
    category: str = None,       # 카테고리
    keyword: str = None         # description에 포함된 단어
) -> dict:
```

**동작**
- 주어진 조건들을 **AND로 모두 만족**하는 거래를 찾는다.
- 조건이 하나도 없으면 전체 거래를 반환한다.
- `date`와 `start_date`/`end_date`가 함께 오면 `date`를 우선한다.
- 날짜 문자열은 `"YYYY-MM-DD"` 형식이므로 **문자열 비교(`<=`, `>=`)로 기간 판정이 가능하다.**
  (형식이 고정 자릿수라 사전순 = 날짜순)
- `keyword`는 대소문자 구분 없이 부분 일치(`in`)로 검사한다.
- 결과는 날짜 오름차순, 같으면 ID 오름차순으로 정렬한다.

**성공 반환**
```python
{
    "ok": True,
    "data": {
        "count": 1,
        "transactions": [ {...거래 dict...} ]
    },
    "message": "조건에 맞는 거래 1건을 찾았습니다."
}
```

- 검색 결과가 0건이어도 **실패가 아니다.** `ok: True`, `count: 0`으로 반환한다.
  (검색은 성공했고, 결과가 없을 뿐이다)
- `count`를 별도로 넣는 이유: Gemini가 "여러 건이니 되물어야겠다"를 쉽게 판단하게 하기 위함.

---

### 7-3. `update_transaction` — 거래 수정 [필수]

```python
def update_transaction(
    self,
    transaction_id: int,        # 필수 — 수정할 거래의 ID
    amount: int = None,
    category: str = None,
    description: str = None,
    date: str = None
) -> dict:
```

**동작**
1. `transaction_id`로 거래를 찾는다. 없으면 → `NOT_FOUND`
2. `amount`~`date`가 **전부 `None`이면** → `NOTHING_TO_UPDATE`
3. 주어진 항목만 검증 후 수정한다. (`None`인 항목은 건드리지 않는다)
   - `category` 검증 시에는 **해당 거래의 기존 `type`** 기준으로 검사한다
4. `_save()` 호출

**`transaction_type`은 수정할 수 없다.** 수입을 지출로 바꾸는 것은 사실상 다른 거래이므로,
삭제 후 재등록이 올바른 방법이다.

**성공 반환 — `before`/`after`를 함께 담는다**
```python
{
    "ok": True,
    "data": {
        "before": {"id": 3, "amount": 5000, ...},
        "after":  {"id": 3, "amount": 4500, ...}
    },
    "message": "[3]번 거래의 금액을 5,000원에서 4,500원으로 수정했습니다."
}
```

> 💡 `before`/`after`를 둘 다 주면 Gemini가 "무엇이 어떻게 바뀌었는지" 정확히 설명할 수 있다.
> 시연에서도 변화가 눈에 보여 효과적이다.

### 7-4. `set_budget` — 예산 설정 [필수]

```python
def set_budget(
    self,
    month: str,                 # "YYYY-MM"
    category: str,              # expense_categories 중 하나
    amount: int                 # 0보다 큰 정수
) -> dict:
```

**동작**
1. `month` 검증 → `INVALID_MONTH`
2. `category`가 `expense_categories`에 있는지 검증 → `INVALID_CATEGORY`
   (수입 카테고리를 넣으면 여기서 걸린다. 메시지로 "예산은 지출 카테고리에만 설정할 수 있습니다" 안내)
3. `amount` 검증 → `INVALID_AMOUNT`
4. `self.budgets`에 저장 (해당 월 키가 없으면 만든다). 이미 있으면 **덮어쓴다**
5. `_save()` 호출

```python
{"ok": True,
 "data": {"month": "2026-08", "category": "식비", "amount": 300000},
 "message": "2026년 8월 식비 예산을 300,000원으로 설정했습니다."}
```

### 7-5. `get_budget_status` — 예산 현황 조회 [필수]

```python
def get_budget_status(
    self,
    month: str,                 # "YYYY-MM"
    category: str = None        # 없으면 해당 월 전체 카테고리
) -> dict:
```

**동작**
1. `month` 검증 → `INVALID_MONTH`
2. 해당 월에 설정된 예산이 하나도 없으면 → `NO_BUDGET_SET`
3. `category`가 주어졌는데 그 카테고리 예산이 없으면 → `NO_BUDGET_SET`
4. 예산이 설정된 각 카테고리에 대해 계산:
   - `spent` = 해당 월 + 해당 카테고리 + **type이 "지출"인** 거래들의 `amount` 합계
     (⚠️ 수입을 섞어 계산하지 않도록 반드시 type을 필터링한다)
   - `remaining` = `budget - spent` (음수 가능 — 초과 지출)
   - `usage_rate` = `round(spent / budget * 100, 1)`
5. "해당 월"의 판정: 거래의 `date`가 `month`로 시작하는지 (`date.startswith(month)`)

**성공 반환**
```python
{
    "ok": True,
    "data": {
        "month": "2026-08",
        "items": [
            {"category": "식비", "budget": 300000, "spent": 112000,
             "remaining": 188000, "usage_rate": 37.3, "over_budget": False}
        ]
    },
    "message": "2026년 8월 식비: 예산 300,000원 중 112,000원 사용, 188,000원 남았습니다."
}
```

`over_budget`(초과 여부)을 별도 키로 주면 Gemini가 경고 문구를 붙이기 쉬워진다.

## 8. Gemini 도구 schema

과제와 동일한 형식(딕셔너리)으로 작성한다. **`name`은 파이썬 함수 이름과 정확히 일치해야 한다.**

### 8-1. 작성 원칙

- `description`에 **언제 이 도구를 쓰는지**를 쓴다 (무엇을 하는지만 쓰면 부족하다)
- 각 매개변수의 `description`에 **형식과 예시**를 적는다 (`"YYYY-MM-DD 형식. 예: 2026-08-27"`)
- 카테고리는 `enum`으로 값을 제한한다 → LLM이 "식비/음식/밥값"처럼 제멋대로 만드는 것을 막는다
- `required`에는 **기본값이 없는 매개변수만** 넣는다

### 8-2. 예시 — `add_transaction`

```python
add_transaction_tool = {
    "type": "function",
    "name": "add_transaction",
    "description": (
        "사용자가 돈을 쓰거나 벌었다고 말할 때, 수입 또는 지출 거래를 새로 등록합니다. "
        "예: '점심 12000원 썼어', '월급 300만원 들어왔어'"
    ),
    "parameters": {
        "type": "object",
        "properties": {
            "transaction_type": {
                "type": "string",
                "enum": ["수입", "지출"],
                "description": "거래 유형. 돈이 나갔으면 '지출', 들어왔으면 '수입'",
            },
            "category": {
                "type": "string",
                "description": (
                    "카테고리. 지출: 식비, 교통비, 주거비, 문화생활, 기타 / "
                    "수입: 월급, 용돈, 부수입, 기타"
                ),
            },
            "amount": {"type": "integer", "description": "금액(원). 0보다 큰 정수"},
            "date": {
                "type": "string",
                "description": "거래 날짜. YYYY-MM-DD 형식. 예: 2026-08-27",
            },
            "description": {
                "type": "string",
                "description": "거래 내용 메모. 예: 점심, 카페, 택시",

        },
        "required": ["transaction_type", "category", "amount", "date"],
    },
}
```

나머지 도구도 같은 형식으로 작성한다. 전체 목록:

```python
TOOLS = [
```

> ⚠️ `search_transactions`와 `update_transaction`의 `description`은 특히 신경 써야 한다.
> "ID를 모르면 먼저 검색해서 ID를 알아낸 뒤 수정하라"는 힌트를 넣어야
> 연속 도구 호출이 안정적으로 일어난다. (과제 3번의 `get_order` 설명과 같은 원리)

## 10. 시스템 프롬프트

**오늘 날짜는 도구가 아니라 프롬프트로 알려준다.** 항상 참인 배경 정보를 도구로 만들면

> 코드가 아니라 **프롬프트로 구현되는 요구사항**이라는 점에 주의.

## 11. Agent loop

과제의 `run_agent`를 기반으로 하되, **콘솔 출력을 추가**한다
(명세서 필수 기능: *"Agent가 호출한 도구와 실행 결과를 콘솔에서 확인"*).

### 11-1. 구조

```python
def execute_tool_call(step) -> dict:
    """도구 하나를 안전하게 실행한다."""
    tool_function = TOOL_FUNCTIONS.get(step.name)
    if tool_function is None:
        return {"ok": False, "error": "UNKNOWN_TOOL",
                "message": f"허용되지 않은 도구: {step.name}"}
    try:
        return tool_function(**step.arguments)
    except TypeError as error:
        return {"ok": False, "error": "INVALID_ARGUMENTS",
                "message": f"잘못된 인자: {error}"}
    except Exception as error:
        return {"ok": False, "error": "TOOL_FAILED",
                "message": f"도구 실행 실패: {type(error).__name__}"}


def run_agent(user_input: str, max_turns: int = 5) -> dict:
    next_input = user_input
    previous_interaction_id = None
    logs = []

    for turn in range(1, max_turns + 1):
        request = {
            "model": model,
            "input": next_input,
            "tools": TOOLS,
            "system_instruction": SYSTEM_INSTRUCTION,
            "store": True,
        }
        if previous_interaction_id is not None:
            request["previous_interaction_id"] = previous_interaction_id

        interaction = client.interactions.create(**request)
        function_calls = [s for s in interaction.steps if s.type == "function_call"]

        # 도구 요청이 없으면 최종 답변이다
        if not function_calls:
            return {"ok": True, "answer": interaction.output_text,
                    "turns": turn, "tool_logs": logs}

        next_input = []
        for step in function_calls:
            print_tool_call(step)                    # ← 콘솔 출력 (11-2)
            result = execute_tool_call(step)
            print_tool_result(result)                # ← 콘솔 출력
            write_log(turn, step, result)            # ← 로그 파일 (선택)

            logs.append({"turn": turn, "tool": step.name,
                         "arguments": step.arguments, "result": result})
            next_input.append({
                "type": "function_result",
                "name": step.name,
                "call_id": step.id,
                "result": [{"type": "text",
                            "text": json.dumps(result, ensure_ascii=False)}],
            })

        previous_interaction_id = interaction.id

    return {"ok": False, "answer": None, "turns": max_turns,
            "tool_logs": logs, "error": "최대 반복 횟수를 초과했습니다."}
```

**`max_turns = 5`로 정한 이유:** 이 프로젝트에서 가장 긴 작업이 "검색 → 수정"의 2단계다.
5는 충분한 여유이면서, 모델이 도구 호출을 반복하며 비용이 무한히 커지는 것을 막는다.

### 11-2. 콘솔 출력 형식

```
────────────────────────────────────────
🔧 [도구 호출] search_transactions
   인자: {"date": "2026-08-27", "keyword": "카페"}
✅ [실행 결과] 조건에 맞는 거래 1건을 찾았습니다.

   인자: {"transaction_id": 3, "amount": 4500}
```

### 11-4. 대화 실행부 (`agent.py`의 `main`)

```python
def main():
    print("개인 예산 관리 비서입니다. 종료하려면 '종료'를 입력하세요.")
    while True:
        user_input = input("\n나: ").strip()
        if user_input in ("종료", "exit", "quit"):
            print("종료합니다.")
            break
        if not user_input:
            continue
        result = run_agent(user_input)
        print(f"\n💬 {result['answer'] if result['ok'] else result['error']}")

if __name__ == "__main__":
    main()
```

## 13. 필수 시연 시나리오

각 시나리오는 **콘솔에 도구 호출이 보이는 상태로** 실행하고 캡처한다.

### 시나리오 1 — 한 문장으로 지출 등록
```
나: 오늘 점심으로 12000원 썼어

기대: add_transaction 1회 호출
      transaction_type="지출", category="식비", amount=12000, date=오늘
      → ID를 포함한 등록 완료 안내
```

### 시나리오 2 — 자연어 조건 검색
```
나: 8월에 식비로 쓴 거 보여줘

기대: search_transactions 1회 호출
      start_date="2026-08-01", end_date="2026-08-31", category="식비"
      → 건수와 목록 안내
```

### 시나리오 3 — 검색 후 수정 (⭐ 연속 도구 호출)
```
사전 준비: 8월 27일 카페 지출을 1건만 등록해 둔다 (반드시 1건)

나: 2026년 8월 27일 카페에서 쓴 금액을 4500원으로 수정해줘

기대: search_transactions → update_transaction 순서로 2회 호출
      콘솔에 두 번의 도구 호출이 순서대로 찍혀야 한다
```

### 시나리오 4 — 예산 설정 및 조회
```
나: 이번 달 식비 예산을 30만원으로 설정해줘
기대: set_budget 호출

나: 이번 달 식비 얼마나 남았어?
기대: get_budget_status 호출 → 예산/사용/잔액 안내
```

### 시나리오 5 — 오류 처리
```
나: 999번 거래 금액을 5000원으로 바꿔줘

기대: update_transaction 호출 → ok=False, error="NOT_FOUND"
      → Agent가 "999번 거래를 찾을 수 없습니다"라고 안내
      → 프로그램이 죽지 않고 대화가 계속되어야 한다
```

**추가로 확인하면 좋은 것 (명세서 요구사항)**
```
나: 카페에서 쓴 거 수정해줘     (카페 거래가 여러 건인 상태에서)
기대: Agent가 임의로 고르지 않고, 목록을 보여주며 날짜 등을 되물음
```

포트폴리오에서는 코드보다 README를 먼저 본다. 30초 안에 파악되게 쓴다.

```markdown
# 개인 예산 관리 AI Agent

자연어로 가계부를 관리하는 AI Agent.
Gemini Function Calling으로 사용자의 말을 이해하고 적절한 도구를 스스로 선택해 실행한다.

## 데모
(실행 화면 캡처 2~3장 — 특히 연속 도구 호출 장면)

## 주요 기능
- 자연어 수입·지출 등록 / 조건 검색 / 수정 / 삭제
- 카테고리별 월 예산 설정 및 잔액 조회
- 검색 → 수정으로 이어지는 연속 도구 호출
- JSON 자동 저장 (재실행 후에도 데이터 유지)
- 월별 Markdown 보고서 생성

## 실행 방법
1. `pip install google-genai python-dotenv`
2. `.env` 파일 생성 후 `GEMINI_API_KEY=your_key` 작성
3. `python agent.py`

## 구조
| 파일 | 역할 |
|---|---|
| budget_manager.py | 데이터 관리와 도구 함수 (Gemini와 무관한 순수 로직) |
| agent.py | 도구 등록, Agent loop, 실행 진입점 |
| main.ipynb | 개발 과정과 함수 단위 테스트 기록 |

## 설계 포인트
- 모든 도구가 `{ok, data/error, message}` 형식으로 통일 반환 → Agent loop 처리 코드 단일화
- 오늘 날짜는 도구가 아닌 시스템 프롬프트로 주입 (호출 누락 위험 제거)
- 검색 결과가 여러 건이면 임의 선택 대신 사용자에게 재질의
- 최대 반복 횟수를 둔 Agent loop로 무한 호출 방지
```

## 15. 자주 발생하는 문제와 대비

| 문제 | 원인 | 대비 |
|---|---|---|
| `.py`를 고쳤는데 노트북에 반영 안 됨 | 모듈이 한 번만 로드됨 | 첫 셀에 `%autoreload 2`, 안 되면 커널 재시작 |
| 재실행 시 ID가 1부터 다시 시작 | `next_id`를 저장 안 함 | JSON에 `next_id` 포함 (4-4절) |
| 예산 사용액이 이상하게 큼 | 수입까지 합산 | `get_budget_status`에서 `type == "지출"` 필터 필수 |
| LLM이 금액을 문자열로 보냄 | JSON 스키마와 실제 출력 불일치 | `_validate_amount`에서 형변환 시도 (6-1절) |
| 카테고리가 제멋대로 생성됨 | 목록을 안 알려줌 | schema의 `description`과 시스템 프롬프트에 목록 명시 |
| 검색 후 수정이 한 번에 안 됨 | 단발 호출 코드 사용 | 반드시 `run_agent` 루프로 실행 |
| 한글이 `식비`로 저장됨 | 인코딩 옵션 누락 | `json.dump(..., ensure_ascii=False)`, 파일은 `encoding="utf-8"` |
| GitHub에 API 키가 올라감 | `.gitignore` 누락 | **최초 커밋 전에** `.gitignore`에 `.env` 추가 |

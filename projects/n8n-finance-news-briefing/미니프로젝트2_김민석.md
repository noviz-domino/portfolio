## 2. 전체 흐름

```
  ⏰ 매일 아침 8시 30분 (자동)
            ↓
  ① 구글 시트에서 지금까지 보낸 기사 목록 읽기
            ↓
  ② 뉴스 3곳에서 기사 수집 (연합뉴스 / 한국경제 / 매일경제)
            ↓
  ③ 3곳 기사를 하나로 합치기
            ↓
  ④ 주소 정리 + 24시간 이내 기사만 남기기
            ↓
  ⑤ 이미 보낸 기사 빼기  +  금융 기사만 남기기      ← AI 부르기 전!
            ↓
  ⑥ AI에 보낼 기사 40건 추리고 10건씩 묶기
            ↓
  ⑦ AI(Gemini)가 요약 + 중요도(1~5) + 분야 매기기
            ↓
  ⑧ AI 답이 이상하면 걸러내기
            ↓
  ⑨ 실제로 보낼 기사 확정 + 메시지 만들기
            ↓
  ⑩ 구글 시트에 기록
            ↓
  ⑪ 디스코드로 한 통 발송
```

## 4. 요구사항 체크

### ✅ REQ-01 :: 수집 (RSS)

**요구: 서로 다른 매체의 RSS를 최소 2개 연결**

3개를 연결했습니다.

| 매체 | 주소 | 성격 |
| --- | --- | --- |
| 연합뉴스 | `https://www.yna.co.kr/rss/economy.xml` | 종합지 경제면 (정책·거시) |
| 한국경제 | `https://www.hankyung.com/feed/economy` | 경제지 (증시·기업) |
| 매일경제 | `https://www.mk.co.kr/rss/30100041/` | 경제지 (기업·산업) |

**3개로 한 이유**

경제지 2곳만 쓰면 기업·증시 기사에 치우칩니다. 종합지인 연합뉴스 경제면을 넣어 정책·금리 쪽 기사도 확보했습니다.

**한 곳이 죽어도 멈추지 않는 장치**

RSS 노드 3개 모두 아래처럼 설정했습니다.

- `On Error` = **Continue** → 이 언론사가 응답을 안 해도 워크플로우가 멈추지 않고 계속 진행
- `Always Output Data` = ON → 빈 결과라도 내보내서 다음 노드가 기다리지 않게 함
- `Retry On Fail` = ON (2회) → 일시적 오류면 한 번 더 시도

실제로 RSS 주소 3개를 일부러 틀리게 바꿔 테스트했을 때, 워크플로우가 끝까지 완주하고 "수집 0건" 메시지가 도착하는 것을 확인했습니다.

### ✅ REQ-03 :: 중복 발송 방지 (가장 신경 쓴 부분)

**요구: 어제 보낸 기사가 오늘 브리핑에 다시 들어가면 안 됨. 고유값과 그 근거를 문서에 쓸 것. 반드시 LLM 호출 이전에 차단할 것.**

#### 기사를 구분하는 고유값: **정리한 주소(URL)를 SHA-256으로 바꾼 값**

시트의 `url_hash` 컬럼에 저장됩니다.

**먼저 주소를 이렇게 정리합니다**

| 순서 | 정리 내용 | 예시 |
| --- | --- | --- |
| 1 | `http` → `https`로 통일 | `http://a.com/1` → `https://a.com/1` |
| 2 | 대문자 → 소문자, `www.` 제거 | `WWW.A.com` → `a.com` |
| 3 | `#` 뒤 부분 제거 | `/1#comment` → `/1` |
| 4 | 광고 추적용 꼬리표 제거 (`utm_`, `fbclid` 등) | `/1?utm_source=naver` → `/1` |
| 5 | 남은 옵션들 순서를 가나다순으로 정렬 | `?b=2&a=1` → `?a=1&b=2` |
| 6 | 맨 끝 `/` 제거 | `/1/` → `/1` |
| 7 | 이 결과를 SHA-256으로 변환 (64자리 문자) | |

**왜 이걸 고유값으로 골랐나**

후보가 세 가지 있었습니다.

| 후보 | 판단 |
| --- | --- |
| RSS가 주는 `guid` | 언론사마다 형식이 제각각입니다. 어떤 곳은 주소를 그대로, 어떤 곳은 내부 번호를 넣습니다. 기사를 수정하면 값이 바뀌는 곳도 있어서 언론사를 추가할 때마다 예외 처리가 늘어납니다. **탈락** |
| 제목 | 주소가 바뀌어도 잡히는 장점이 있지만, "코스피 마감 시황"처럼 **매일 똑같은 제목**을 쓰는 기사가 있습니다. 그러면 오늘의 새 기사를 어제 것으로 착각해서 안 보내게 됩니다. 놓치는 게 더 큰 손해라 **탈락** |
| **정리한 주소** | 기사 주소는 발행할 때 정해지고 나중에 잘 안 바뀝니다. 같은 기사가 다른 문자열로 보이는 이유는 대부분 광고 꼬리표나 대소문자 차이인데, 이건 위 정리 규칙으로 확실히 없앨 수 있습니다. **채택** |

**주소를 그대로 안 쓰고 굳이 SHA-256으로 바꾼 이유**

- 주소는 200자가 넘기도 하는데, 해시로 바꾸면 항상 64자로 고정됩니다. 시트에 넣고 비교하기 편합니다.
- 긴 주소를 시트에 저장하면 구글 시트가 자동으로 링크로 바꾸거나 공백을 붙이는 일이 있어서, 글자 비교가 어긋날 수 있습니다. 해시는 그런 변형이 없습니다.
- 대신 원래 주소도 `original_url` 컬럼에 같이 저장해서, 사람이 시트를 볼 때 불편하지 않게 했습니다.

#### 어디까지 대조하나: 최근 7일

시트는 계속 쌓이지만, 매번 읽을 때는 **최근 7일치만** 비교합니다.

RSS는 보통 최근 2~3일치 기사만 보여주기 때문에 7일이면 충분합니다. 전체를 다 읽으면 몇 달 뒤 수천 줄이 되어 매일 아침 실행이 느려집니다.

#### ★ LLM 호출 이전에 차단

이게 요구사항의 핵심이라 노드 순서로 확실히 보장했습니다.

```
중복대조+키워드필터  →  상한+배치  →  통과건 있음?  →  LLM 요약+중요도
      (차단 지점)                                        (AI 호출)
```

중복 제거를 하는 `중복대조+키워드필터` 노드가 AI 노드보다 **앞**에 있습니다. 순서 자체가 바뀌지 않는 한 AI가 중복 기사를 보는 일은 없습니다.

**실제 검증**

워크플로우를 연속 두 번 실행했습니다.

| | 1회차 | 2회차 |
| --- | --- | --- |
| 필터 통과 기사 | 16건 | **0건** |
| AI 호출 횟수 | 2회 | **0회** |
| 시트 중복 여부 | 없음 | 없음 |

2회차에서 AI가 아예 실행되지 않았습니다. 시트에서 `=COUNTA(C2:C)-COUNTA(UNIQUE(C2:C))` 로 확인했을 때도 결과가 `0`(중복 없음)이었습니다.

### ✅ REQ-04 :: 금융 키워드 필터

**요구: 금융 관련 기사만 남길 것. 필터를 LLM 앞에 둘지 뒤에 둘지 판단하고 이유를 쓸 것.**

#### 필터 위치: **LLM 앞**

| | LLM 앞 (선택) | LLM 뒤 |
| --- | --- | --- |
| AI 호출 건수 | 필터 통과분만 | 수집한 전부 |
| 비용 | 낮음 | 3~5배 |
| 속도 | 빠름 | 느림 |

**앞에 둔 이유**

종합지 RSS에는 연예·스포츠·사건사고 기사가 섞여 있습니다. 이걸 전부 AI에 넣는 건 **쓰레기를 돈 내고 분류하는 것**과 같습니다.

게다가 중요도 기준에 이미 `1 = 브리핑에 넣을 필요 없는 기사`가 있어서, **AI가 자연스럽게 2차 필터 역할**을 합니다. 즉 키워드 필터가 조금 느슨해서 애매한 기사를 통과시켜도, AI가 중요도 1~2를 주면 어차피 브리핑에서 빠집니다.

그래서 1차 키워드 필터는 **놓치지 않는 것 우선(느슨하게), 정확한 판단은 AI에 맡기는** 방향으로 만들었습니다.

#### 필터 방식: 3단계 점수제

**1단계 — 차단 단어 (하나라도 있으면 바로 탈락)**

```
연예, 아이돌, 드라마, 예능, 배우, 가수, 열애, 결혼설, 이혼,
프로야구, 축구, 야구, 골프, 올림픽, 월드컵, 리그, 선수단,
날씨, 미세먼지, 폭염, 한파, 음주운전, 살인, 운세, 로또 당첨번호 ...
```

**2단계 — 확실한 금융 단어 (STRONG, 하나당 2점)**

```
기준금리, 금통위, 한국은행, 연준, FOMC, 코스피, 코스닥, 증시, 주가,
환율, 원달러, 국채, 채권, 금리, 영업이익, 순이익, 실적, 인수합병,
물가, GDP, 부동산, 집값, 분양, 금융위, 금감원, ETF, 국민연금 ...
```

**3단계 — 애매한 단어 (WEAK, 하나당 1점)**

```
투자, 자금, 시장, 경기, 경제, 산업, 수출, 기업, 정부, 정책,
대출, 예금, 은행, 보험, 반도체, 배터리, 바이오, 건설 ...
```

**통과 기준**

```
차단 단어가 있으면 → 탈락
확실한 금융 단어(STRONG)가 하나도 없으면 → 탈락
점수 = (STRONG 개수 × 2) + (WEAK 개수 × 1)
제목에도 STRONG 단어가 있으면 → +1점
점수가 2점 이상이면 → 통과
```

**"STRONG 단어 필수" 조건을 나중에 추가한 이유**

처음에는 점수만 봤는데, 저희가 쓰는 피드 3개가 **전부 경제면**이라 "시장", "경제", "기업" 같은 WEAK 단어만으로도 거의 모든 기사가 통과했습니다. 필터가 사실상 작동하지 않은 셈입니다. 그래서 "확실한 금융 단어가 최소 1개는 있어야 한다"는 조건을 넣어 실질적인 필터가 되게 했습니다.

### ✅ REQ-05 :: LLM 요약과 중요도 분류

**요구: 4개 필드를 JSON으로 반환. 중요도 기준을 프롬프트에 명시. 중요도 4 이상만 발송.**

#### 사용 모델

Google Gemini (`Basic LLM Chain` + `Google Gemini Chat Model` 노드)

#### JSON 형식 강제

`Structured Output Parser` 노드에 아래 형식을 지정해서, AI가 정해진 모양으로만 답하게 했습니다.

```json
{
  "results": [
    {
      "id": 1,
      "summary": "3문장 이하 요약",
      "importance": 5,
      "category": "증시"
    }
  ]
}
```

| 필드 | 타입 | 허용값 |
| --- | --- | --- |
| `summary` | 문자열 | 3문장 이하 |
| `importance` | 숫자 | 1~5 정수 |
| `category` | 문자열 | 증시 / 금리 / 환율 / 부동산 / 기업 / 정책 / 기타 |
| `needs_review` | 참/거짓 | 검증 실패 시 참 |

> `needs_review`는 AI가 아니라 **시스템이 검사해서 채웁니다.** AI에게 스스로 "내 답이 틀렸다"고 판단하라고 하는 건 신뢰할 수 없기 때문입니다.

#### 중요도 기준 (프롬프트에 그대로 넣음)

```
5 :: 시장 전체를 흔드는 사건. 금리 결정, 대형 정책 발표, 급락과 급등
4 :: 특정 업종이나 대형 기업에 직접 영향. 실적 발표, 대형 인수합병
3 :: 참고할 만한 동향. 지표 발표, 업계 전망
2 :: 일반적인 소식
1 :: 브리핑에 넣을 필요 없는 기사
```

여기에 더해, AI가 중요도를 너무 후하게 주는 문제가 있어서 아래 지침을 추가했습니다.

```
[중요도 4 이상은 엄격하게 판정하십시오]
아래는 '3 :: 참고할 만한 동향'에 해당하므로 3 이하를 부여합니다.
- 증권사 투자의견 변경, 목표주가 조정
- 개별 종목의 단순 주가 등락 보도 ([특징주] 류)
- 시장 예상 범위 안의 실적 발표
- 이미 예고돼 있던 정기 지표 발표
- 정책 변화를 담지 않은 원론적 발언 인용

[4를 부여하는 조건]
한 기업의 소식이라도 그 기업이 속한 '업종 전체' 또는 '지수'에
파급되는 경우여야 합니다.

- 하루치 기사 중 4 이상은 소수입니다. 대부분의 기사는 2 또는 3입니다.
```

#### 검증 안전판 (7가지 검사)

형식을 지정해도 AI가 이상하게 답하는 경우가 있어서, `검증 안전판` 노드에서 한 번 더 확인합니다.

| 검사 | 문제 상황 | 처리 |
| --- | --- | --- |
| V-1 | AI 호출 자체가 실패 | 중요도 1, 분야 기타로 처리 후 발송 제외 |
| V-2 | 요약이 비었거나 10자 미만 | 발송 제외 |
| V-3 | 요약이 4문장 이상 | 앞 3문장만 남기고 발송 제외 |
| V-4 | 중요도가 1~5 정수가 아님 | 1로 바꾸고 발송 제외 |
| V-5 | 분야가 정해진 7개가 아님 | '기타'로 바꾸고 발송 제외 |
| V-6 | 요약에 코드 기호나 URL이 섞임 | 지우고 발송 제외 |
| V-7 | 10건 묶어 보냈는데 답이 9건만 옴 | 빠진 기사를 발송 제외 |

문제가 발견된 기사는 `needs_review = TRUE`로 시트에 남기고, **브리핑에는 넣지 않습니다.** 나중에 시트에서 이 값만 걸러보면 어떤 기사에서 AI가 실수했는지 바로 알 수 있어서, 프롬프트를 고칠 때 참고할 수 있습니다.

#### 중요도 4 이상만 발송

`발송선별` 노드에서 이렇게 거릅니다.

```javascript
const MIN_IMPORTANCE = 4;
const candidates = items.filter(j =>
  j.needs_review !== true && Number(j.importance) >= MIN_IMPORTANCE);
```

### ✅ REQ-06 :: 디스코드 브리핑 발송

**요구: 여러 기사를 메시지 1개로 묶을 것. 제목·요약·링크·카테고리가 기사마다 들어갈 것. 중요 기사가 없는 날의 경로도 설계할 것.**

#### ① 메시지는 항상 1개

`발송선별`에서 모든 기사를 문자열 하나로 합치고, `브리핑 조립`이 **아이템 1개만** 내보냅니다.

```javascript
return [{ json: { content } }];
```

n8n은 들어온 아이템 수만큼 HTTP 요청을 보내기 때문에, **1개로 줄이는 것이 곧 메시지 1개**가 됩니다.

> **여기서 실수했다가 고친 부분**
>
> 처음에는 RSS 노드 3개를 다음 노드에 바로 연결했습니다. 그런데 n8n은 한 노드에 연결이 여러 개 들어오면 합치는 게 아니라 **연결 수만큼 뒷부분 전체를 반복 실행**합니다. 그래서 디스코드 메시지가 언론사별로 3통씩 왔습니다.
>
> `RSS 병합`(Merge, Append, 입력 3개) 노드를 넣어 한 줄기로 합쳐서 해결했습니다.

#### ② 기사마다 들어가는 정보

```
[1] ⭐5 증시 | 코스피, 4~5%대로 낙폭확대…매도 사이드카 발동
  6일 코스피가 장중 4~5%대의 급락을 기록하며 낙폭을 확대했다.
  📰 연합뉴스 🔗 https://www.yna.co.kr/view/AKR20260806057851008
```

| 요구 항목 | 위치 |
| --- | --- |
| 카테고리 | `증시` |
| 제목 | `코스피, 4~5%대로 낙폭확대…` |
| 요약 | 두 번째 줄 |
| 원문 링크 | `🔗 https://...` |

여기에 **중요도(⭐)** 와 **매체명(📰)** 을 추가로 넣어 읽기 편하게 했습니다. 기사 사이에는 빈 줄을 넣어 구분되게 했습니다.

#### ③ 중요 기사가 없는 날 ← 요구사항의 핵심

그냥 "없습니다"만 보내면 **시스템 고장과 구분이 안 됩니다.** RSS가 하나도 안 와도 똑같은 메시지가 나가기 때문입니다.

그래서 **각 단계에서 몇 건이 걸러졌는지 숫자를 함께 보여줍니다.**

```
📭 오늘의 금융 브리핑 (2026-08-06)
중요도 4 이상 기사가 없습니다.

수집 220건 → 시간창 204건 → 중복제외 120건 → 금융필터 62건 → 중요도4+ 0건
```

받는 사람은 이 한 줄로 상황을 구분할 수 있습니다.

| 숫자 모양 | 뜻 |
| --- | --- |
| `수집 220건 → … → 중요도4+ 0건` | **정상.** 오늘은 큰 뉴스가 없는 날 |
| `수집 0건 → … → 중요도4+ 0건` | **고장.** RSS 3곳이 모두 실패 |
| `수집 220건 → 중복제외 0건 → …` | **의심.** 시트를 못 읽고 있음 |
| 메시지가 아예 안 옴 | **고장.** 스케줄이나 디스코드 문제 |

두 상황을 실제로 만들어서 테스트했습니다.

- 발송 기준을 일부러 6으로 올려 실행 → `수집 220건 → … → 중요도4+ 0건`
- RSS 주소 3개를 일부러 틀리게 하고 실행 → `수집 0건 → … → 중요도4+ 0건`

메시지 모양이 확실히 달라서 구분됩니다.

#### ④ 메시지 길이 관리

디스코드 메시지는 **2,000자 제한**이 있고, 넘으면 발송 자체가 실패합니다. 그래서 안전장치를 넣었습니다.

| 항목 | 값 |
| --- | --- |
| 요약 표시 | 첫 문장만, 90자까지 |
| 최대 기사 수 | 15건 |
| 최종 안전장치 | 1,950자를 넘으면 뒤에서부터 기사를 하나씩 빼며 다시 만듦 |

기사가 잘렸을 때는 `… 외 N건은 길이 제한으로 생략`이라고 알려주고, 그 기사들은 시트에 `sent=FALSE`로 남아 있어 나중에 확인할 수 있습니다.

### ✅ REQ-07 :: 발송 이력 기록

**요구: 발송한 기사를 구글 시트에 자동으로 누적. 어떤 항목을 남길지 설계할 것.**

`이력 기록` 노드(Google Sheets - Append Row)가 매번 자동으로 줄을 추가합니다.

#### 시트 구조 (`sent_log` 탭, 16개 컬럼)

| 열 | 컬럼명 | 무엇을 남기나 | 왜 필요한가 |
| --- | --- | --- | --- |
| A | `run_date` | 실행 날짜 | **7일치만 읽을 때 기준이 되는 값** |
| B | `run_id` | n8n 실행 번호 | 문제 생겼을 때 그날 실행 기록 찾기 |
| C | `url_hash` | 주소 해시 | **중복 판정에 쓰는 핵심 값** |
| D | `normalized_url` | 정리된 주소 | 나중에 정리 규칙을 바꿔도 다시 계산할 수 있게 |
| E | `original_url` | 원래 주소 | 사람이 클릭해서 확인 |
| F | `title` | 제목 | 사람이 보고 어떤 기사인지 알기 |
| G | `source` | 매체명 | 어느 언론사 기사가 많이 뽑히는지 확인 |
| H | `published_at` | 발행 시각 | 24시간 필터가 잘 되는지 검증 |
| I | `category` | 분야 | 분야별 분포 확인 |
| J | `importance` | 중요도 | 중요도 분포를 보고 기준 조정 |
| K | `summary` | AI 요약 | 다시 보내지 않고도 내용 확인 |
| L | `needs_review` | 검증 실패 여부 | **AI가 실수한 기사 찾기** |
| M | `review_flags` | 실패한 검사 이름 | 어떤 종류의 실수인지 파악 |
| N | `sent` | 실제 발송 여부 | 몇 건이 실제로 나갔는지 확인 |
| O | `filter_score` | 키워드 점수 | 필터 기준을 조정할 때 참고 |
| P | `matched_keywords` | 걸린 키워드 | "왜 이 기사가 들어왔지?" 설명 가능 |

#### 항목을 이렇게 정한 이유

중복 판정에 꼭 필요한 건 `url_hash` 하나뿐입니다. 나머지는 **운영하면서 생길 질문에 답하기 위해** 넣었습니다.

- `run_date`가 없으면 "최근 7일치만 읽기"를 할 수 없습니다.
- `normalized_url`이 있어야 나중에 주소 정리 규칙을 바꿨을 때 예전 기록을 다시 계산할 수 있습니다. 해시만 있으면 규칙을 바꾸는 순간 과거 기록이 전부 쓸모없어집니다.
- `needs_review`와 `review_flags`가 없으면 AI 프롬프트를 개선할 근거가 사라집니다.
- `filter_score`와 `matched_keywords`가 있으면 "이 기사가 왜 브리핑에 들어왔는지" 바로 설명할 수 있습니다.
- `sent`는 중요도 1~3 기사까지 시트에 남기기 때문에, 실제로 나간 것과 아닌 것을 구분하려고 넣었습니다.

#### 어떤 기사까지 기록하나

**금융 필터를 통과해서 AI가 평가한 기사는 전부** 기록합니다. 중요도 1~3이라 발송 안 된 기사도 남깁니다.

**그 이유**는, 발송된 것만 기록하면 어제 중요도 3을 받아 안 보낸 기사가 오늘 또 수집됐을 때 **AI를 한 번 더 호출**하게 되기 때문입니다. 매일 수십 건씩 낭비되는 구조라, 필터를 통과한 시점부터 기록해서 한 기사가 AI를 딱 한 번만 타게 했습니다.

#### 기록 순서: 발송보다 먼저

`이력 기록`은 `Discord 발송`보다 **앞**에 있습니다.

발송 후에 기록하면, 디스코드로는 갔는데 시트 저장이 실패하는 순간 **내일 같은 기사가 또 발송**됩니다. 반대로 기록을 먼저 하면 최악의 경우 "기록은 됐는데 발송이 안 된 기사"가 생기는데, 이건 재시도(3회)와 실행 기록으로 확인할 수 있습니다.

REQ-03의 목적이 재발송 방지이므로, **기록을 먼저 하는 쪽**을 골랐습니다.

## 5. 만들면서 겪은 문제와 해결

실제로 돌려보며 발견한 문제들입니다.

### 문제 1 :: 디스코드 메시지가 3통씩 왔다

**증상**: 한 번 실행했는데 연합뉴스분·한국경제분·매일경제분이 따로 왔습니다.

**원인**: n8n은 한 노드의 같은 입력에 연결이 여러 개 들어오면 **합치는 게 아니라 뒷부분 전체를 연결 수만큼 반복 실행**합니다. RSS 3개를 다음 노드에 바로 연결한 것이 문제였습니다.

**해결**: `RSS 병합`(Merge / Append / 입력 3개) 노드를 넣어 한 줄기로 합쳤습니다.

### 문제 2 :: Gemini 429 오류 (호출 횟수 초과)

**증상**: `429 Too Many Requests`, 무료 티어는 분당 5회 제한.

**원인**: 기사 한 건마다 AI를 한 번씩 불러서 하루 수십~수백 번 호출됐습니다.

**해결**: `상한+배치` 노드를 추가했습니다.

- 하루에 AI로 보낼 기사를 **40건**으로 제한 (키워드 점수 높은 순)
- **10건씩 묶어서** 한 번에 요청 → 호출 횟수가 **4회 이하**로 줄어듦
- 재시도 대기 시간을 65초로 설정

### 문제 3 :: 실제로 안 보낸 기사가 "보냄"으로 기록됐다

**증상**: 브리핑에는 8건이 왔는데 시트에는 `sent=TRUE`가 17건이었습니다.

**원인**: `이력 기록`이 `브리핑 조립`보다 먼저 실행돼서, 시트에 쓸 때는 **길이 제한에 몇 건이 잘릴지 알 수 없었습니다.** 그래서 중요도만 보고 17건 전부를 `TRUE`로 찍었습니다.

**해결**: `발송선별` 노드를 새로 만들어 **실제로 보낼 기사를 먼저 확정한 뒤** 시트에 기록하도록 순서를 바꿨습니다.

```
[전] 검증 안전판 → 이력 기록 → 브리핑 조립 → Discord
[후] 검증 안전판 → 발송선별 → 이력 기록 → 브리핑 조립 → Discord
                   ↑ 발송분 확정
```

### 문제 4 :: 필터가 사실상 작동하지 않았다

**증상**: 금융 필터를 통과하는 기사가 수집한 것의 거의 전부였습니다.

**원인**: 피드 3개가 모두 경제면이라 "시장", "경제", "기업" 같은 애매한 단어(WEAK)만으로도 점수 2점이 쉽게 넘었습니다.

**해결**: "확실한 금융 단어(STRONG)가 최소 1개는 있어야 통과"라는 조건을 추가했습니다.

### 문제 5 :: 잘린 기사를 다음 날 보내려다 요구사항을 어길 뻔했다

길이 제한에 잘린 중요 기사를 다음 날 다시 보내려고 시간 범위를 48시간으로 넓혔는데, 이러면 **어제 기사가 오늘 브리핑에 섞입니다.** 매일 아침 최신 뉴스를 받는 시스템에서는 맞지 않아 **24시간으로 되돌렸습니다.**

같은 사건이 정말 중요하다면 오늘 새 기사로 다시 보도되고, 그 기사는 주소가 다르니 중복에 걸리지 않고 오늘 기준으로 새로 평가받습니다.

## 1. 프로젝트 개요

### 1.1 문제 정의

자산운용사 리서치팀은 매일 아침 여러 뉴스 사이트를 개별적으로 순회합니다. 이로 인해 (1) 팀원 간 정보 비대칭, (2) 비금융 기사 선별에 드는 시간 낭비, (3) 동일 기사 반복 열람이 발생합니다.

### 1.2 해결 방식

매일 08:30에 자동 실행되는 n8n 워크플로우가 복수 매체의 RSS를 수집해, 이미 본 기사를 제거하고, 금융 기사만 남긴 뒤, LLM으로 요약·중요도를 매겨, 중요 기사만 **하나의 Discord 메시지**로 묶어 발송합니다.

### 1.3 성공 기준

| 기준 | 측정 방법 |
| --- | --- |
| 아무 조작 없이 08:30에 브리핑 도착 | 3일 연속 자동 실행 로그 확인 |
| 어제 발송된 기사가 오늘 브리핑에 없음 | 이틀 연속 실행 후 `url_hash` 교집합 = 0 |
| 브리핑에 비금융 기사 0건 | 3일치 브리핑 육안 검수 |
| 기사 N건이 메시지 1건으로 도착 | Discord 채널 메시지 수 확인 |
| 조용한 날과 고장난 날이 구분됨 | 강제 0건 시나리오 테스트 |

### 2.1 설계 원칙

1. **LLM 호출은 파이프라인 최말단에.** 중복 제거와 키워드 필터를 모두 앞에 두어 유료 호출 건수를 최소화합니다. (REQ-03·REQ-04 요구사항이자 비용 설계의 핵심)
2. **Code 노드에 로직을 모은다.** n8n의 IF/Filter 노드를 여러 개 늘어놓는 대신 Code 노드 하나에 규칙을 담아, 규칙 변경 시 수정 지점이 한 곳이 되도록 합니다.
3. **어느 단계에서 몇 건이 떨어졌는지 항상 센다.** 최종 메시지에 파이프라인 카운트를 노출해 무음(無音)과 장애를 구분합니다.
4. **한 소스가 죽어도 브리핑은 나간다.** RSS 노드 3개는 각각 실패를 허용합니다.

## 3. 트리거 설계 (REQ-02)

### 3.1 노드: `① Schedule Trigger`

| 설정 | 값 |
| --- | --- |
| Trigger Rule | Days |
| Days Between Triggers | 1 |
| Trigger at Hour | 8 |
| Trigger at Minute | 30 |

### 3.2 타임존 주의

n8n의 Schedule Trigger는 **워크플로우 설정의 타임존**을 따릅니다. 반드시 확인할 것:

- `Workflow Settings → Timezone` = `Asia/Seoul`
- 인스턴스 기본값(`GENERIC_TIMEZONE`)이 UTC면 08:30 UTC = 17:30 KST로 발송됩니다. 이 프로젝트에서 가장 흔한 사고 지점입니다.

### 3.3 검증 방법

정식 운영 전에는 다음 순서로 확인합니다.

1. 워크플로우 상단 `Execute Workflow`로 수동 실행 → 전 구간 동작 확인
2. Schedule Trigger를 임시로 `Minutes / every 5`로 바꿔 자동 실행 경로 확인 (이때 Discord 알림이 5분마다 오므로 테스트용 웹훅 URL 사용 권장)
3. 08:30으로 되돌리고 워크플로우 `Active` 토글 ON
4. 다음 날 아침 도착 확인

> **주의**: `Active` 토글을 켜지 않으면 스케줄이 동작하지 않습니다. 수동 실행만으로는 REQ-02 충족이 아닙니다.

| `yna` | 연합뉴스 (경제) | `https://www.yna.co.kr/rss/economy.xml` | 종합지 경제면 — 정책·거시 |
| `hankyung` | 한국경제 | `https://www.hankyung.com/feed/economy` | 경제지 — 증시·기업 |
| `mk` | 매일경제 | `https://www.mk.co.kr/rss/30100041/` | 경제지 — 기업·산업 |

> 피드 URL은 매체 개편 시 변경될 수 있습니다. 구축 첫 단계에서 각 URL을 브라우저로 열어 XML이 반환되는지 확인하고, 실패하면 해당 매체의 RSS 안내 페이지에서 대체 URL을 찾습니다. 구성상 URL만 교체하면 되며 다른 노드는 영향받지 않습니다.

### 4.2 피드를 3개 쓰는 이유

요청서는 최소 2개를 요구합니다. 3개로 정한 이유는 두 가지입니다.

- **커버리지**: 경제지 2곳만 쓰면 기업·증시 기사에 치우칩니다. 종합지(연합뉴스) 경제면을 넣어 정책·금리 계열 기사를 확보합니다.
- **장애 격리**: RSS는 매체 사정으로 종종 502를 반환하거나 빈 응답을 줍니다. 2개 중 1개가 죽으면 커버리지가 절반이 되지만, 3개 중 1개가 죽으면 2/3가 남습니다.

### 4.3 노드: `② RSS Read` × 3

각 노드 설정:

| 설정 | 값 |
| --- | --- |
| URL | 위 표의 피드 URL |
| Node Name | `RSS - 연합뉴스` / `RSS - 한국경제` / `RSS - 매일경제` |
| **Settings → On Error** | **`Continue (using error output)`** 또는 `Continue` |
| Settings → Always Output Data | ON |
| Settings → Retry On Fail | ON, Max Tries 2, Wait 1000ms |

> **On Error를 반드시 `Continue`로 둘 것.** 기본값(`Stop Workflow`)이면 한 매체의 일시 장애가 브리핑 전체를 취소시킵니다. 이것이 REQ-01이 말하는 "안전장치"의 실제 구현 지점입니다.

### 4.3.1 ★ Merge 노드는 필수 (v1.3 정정)

세 RSS 노드는 **`RSS 병합`(Merge, mode=Append, Number of Inputs=3)** 을 거쳐 `③ 정규화`로 들어갑니다.

> **v1.2까지의 설계 오류**: 초안은 "n8n이 여러 입력 연결을 순차 병합하므로 Merge 노드가 필요 없다"고 적었습니다. **틀렸습니다.**
>
> n8n은 한 노드의 **같은 입력에 연결이 여러 개 들어오면 병합하지 않고, 연결 수만큼 하류 체인 전체를 반복 실행**합니다. RSS 3개를 `③`에 직결하면 `③ → ⑤ → ⑤b → ⑧ → ⑨ → ⑩ → ⑪ → ⑫`가 **3번씩** 돌고, 결과적으로 **Discord 메시지가 매체별로 3통** 발송됩니다. REQ-06("메시지 1개")의 정면 위반입니다.
>
> 실기동에서 캔버스 노드 배지에 `✓3`이 표시되고 Discord에 `수집 120건` / `수집 50건` / `수집 50건` 세 통이 도착해 확인됐습니다.

| 설정 | 값 |
| --- | --- |
| Mode | **Append** |
| Number of Inputs | **3** |
| 입력 연결 | 연합뉴스 → Input 1, 한국경제 → Input 2, 매일경제 → Input 3 |

Append 모드는 세 입력이 모두 도착할 때까지 기다렸다가 아이템을 이어 붙여 **한 줄기로** 내보냅니다. 따라서 하류 체인은 정확히 1회만 실행됩니다.

RSS 노드에 `Always Output Data = ON`이 켜져 있어야 합니다. 한 피드가 실패해 아무 아이템도 내보내지 않으면 Merge가 그 입력을 계속 기다릴 수 있습니다. 빈 아이템이라도 도착해야 Append가 진행되며, 빈 아이템은 `③ 정규화`가 `link`/`title` 부재로 걸러냅니다.

> Merge 노드의 입력 개수는 `Number of Inputs`로 3개 이상 지정할 수 있습니다. "Merge는 입력 2개 제한"이라는 초안의 서술도 함께 정정합니다.

### 4.4 RSS 노드 출력 필드

| 개념 | 가능한 필드명 |
| --- | --- |
| 링크 | `link`, `guid`, `id` |
| 제목 | `title` |
| 발행시각 | `isoDate`, `pubDate`, `pubdate`, `date` |
| 본문요약 | `contentSnippet`, `content`, `description`, `summary` |

## 5. 정규화 및 시간 창 (노드 ③)

### 5.1 노드: `③ Code: 정규화 + 시간창`

- 노드 타입: **Code**
- Mode: **Run Once for All Items**
- 언어: JavaScript

이 노드가 하는 일은 5가지입니다.

1. 매체별 상이한 필드를 하나의 스키마로 통일
2. URL 정규화 (§7.1의 규칙)
3. `url_hash` 생성
4. 시간 창 필터 (A-01)
5. **같은 실행 안에서의 중복 제거** (동일 기사가 같은 매체 피드에 2번 실릴 때)

### 5.2 시간 창 필터 (A-01)

```
window_start = 실행시각 - 24시간
window_end   = 실행시각
조건: window_start <= published_at <= window_end
```

`published_at` 파싱에 실패한 기사는 **버리지 않고 통과**시킵니다. 일부 매체가 비표준 날짜 포맷을 쓰기 때문이며, 어차피 중복 제거가 뒤에 있어 재발송 위험은 없습니다. 대신 `pub_parsed=false` 플래그를 달아 시트에 기록합니다.

### 5.3 통일 스키마

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| `url_hash` | string | 정규화 URL의 SHA-256 (64자 hex) |
| `normalized_url` | string | 정규화된 URL |
| `original_url` | string | 피드가 준 원본 URL |
| `title` | string | 제목 (앞뒤 공백 제거) |
| `source` | string | `연합뉴스` / `한국경제` / `매일경제` |
| `published_at` | string | ISO 8601 (KST 오프셋) |
| `snippet` | string | 본문 발췌 (최대 1,200자로 절단) |
| `pub_parsed` | boolean | 발행시각 파싱 성공 여부 |
| `run_id` | string | 실행 식별자 (`{{$execution.id}}`) |
| `run_date` | string | `YYYY-MM-DD` (KST) |

### 5.4 코드

```javascript
// ③ Code: 정규화 + 시간창 + 실행내 중복제거
// Mode: Run Once for All Items

const WINDOW_HOURS = 24;          // A-01: "오늘 기사"의 정의
const SNIPPET_MAX  = 1200;        // LLM 입력 토큰 절약

// --- SHA-256 (n8n Code 노드는 crypto 전역을 제공) ---
function sha256(str) {
  try {
    return crypto.createHash('sha256').update(str).digest('hex');
  } catch (e) {
    // 샌드박스에서 crypto가 막힌 경우의 폴백: FNV-1a 64bit 2회
    let h1 = 0xcbf29ce484222325n, h2 = 0x84222325cbf29ce4n;
    const P = 0x100000001b3n, M = 0xFFFFFFFFFFFFFFFFn;
    for (const ch of str) {
      const c = BigInt(ch.codePointAt(0));
      h1 = ((h1 ^ c) * P) & M;
      h2 = ((h2 ^ (c + 7n)) * P) & M;
    }
    return (h1.toString(16).padStart(16, '0') + h2.toString(16).padStart(16, '0'));
  }
}

// --- URL 정규화 (§7.1 규칙) ---
const TRACKING_PREFIXES = ['utm_', 'fbclid', 'gclid', 'igshid', 'spm', '_ga'];
const TRACKING_EXACT = new Set([
  'ref', 'src', 'source', 'cid', 'mid', 'sid', 'from', 'inputkey',
  'utm', 'nav', 'page_no_dummy'
]);

function normalizeUrl(raw) {
  if (!raw) return '';
  let s = String(raw).trim();
  try {
    const u = new URL(s);
    u.protocol = 'https:';                                  // http/https 통일
    u.hostname = u.hostname.toLowerCase().replace(/^www\./, ''); // 호스트 소문자 + www 제거
    u.hash = '';                                            // #앵커 제거
    const keep = [];
    for (const [k, v] of u.searchParams.entries()) {
      const lk = k.toLowerCase();
      if (TRACKING_PREFIXES.some(p => lk.startsWith(p))) continue;
      if (TRACKING_EXACT.has(lk)) continue;
      keep.push([k, v]);
    }
    keep.sort((a, b) => a[0].localeCompare(b[0]));          // 파라미터 순서 무관하게
    u.search = keep.length
      ? '?' + keep.map(([k, v]) => `${k}=${v}`).join('&')
      : '';
    let out = u.toString();
    out = out.replace(/\/+$/, '');                          // 끝 슬래시 제거
    return out;
  } catch (e) {
    return s.toLowerCase().replace(/[#?].*$/, '').replace(/\/+$/, '');
  }
}

// --- 매체명 매핑 (RSS 노드 이름으로 판별) ---
function sourceOf(item) {
  const n = (item.json.$source || item.json.sourceName || '').toString();
  if (n) return n;
  const link = String(item.json.link || '');
  if (link.includes('yna.co.kr')) return '연합뉴스';
  if (link.includes('hankyung.com')) return '한국경제';
  if (link.includes('mk.co.kr')) return '매일경제';
  return '기타';
}

const now = new Date();
const windowStart = new Date(now.getTime() - WINDOW_HOURS * 3600 * 1000);
const runDate = new Intl.DateTimeFormat('sv-SE', { timeZone: 'Asia/Seoul' }).format(now);
const runId = String($execution.id);

const seen = new Set();
const out = [];
const counters = { raw: 0, out_of_window: 0, dup_in_run: 0, no_link: 0 };

for (const item of $input.all()) {
  counters.raw++;
  const j = item.json;

  const rawLink = j.link || j.guid || j.id || '';
  if (!rawLink) { counters.no_link++; continue; }

  const normalized = normalizeUrl(rawLink);
  const hash = sha256(normalized);

  // 실행 내 중복 (같은 피드에 두 번 실린 경우 / guid만 다른 동일 링크)
  if (seen.has(hash)) { counters.dup_in_run++; continue; }
  seen.add(hash);

  // 시간 창
  const rawDate = j.isoDate || j.pubDate || j.pubdate || j.date || null;
  const d = rawDate ? new Date(rawDate) : null;
  const parsed = d instanceof Date && !isNaN(d.getTime());
  if (parsed && (d < windowStart || d > now)) { counters.out_of_window++; continue; }

  const snippetRaw = j.contentSnippet || j.content || j.description || j.summary || '';
  const snippet = String(snippetRaw)
    .replace(/<[^>]*>/g, ' ')      // 태그 제거
    .replace(/&[a-z]+;/gi, ' ')    // 엔티티 제거
    .replace(/\s+/g, ' ')
    .trim()
    .slice(0, SNIPPET_MAX);

  out.push({
    json: {
      url_hash: hash,
      normalized_url: normalized,
      original_url: String(rawLink),
      title: String(j.title || '').replace(/\s+/g, ' ').trim(),
      source: sourceOf(item),
      published_at: parsed ? d.toISOString() : '',
      pub_parsed: parsed,
      snippet,
      run_id: runId,
      run_date: runDate,
      _counters: counters,   // 마지막 아이템 기준으로 뒤에서 참조
    },
  });
}

// 수집 0건이어도 후속 노드가 카운트를 읽을 수 있도록 빈 신호 아이템 유지
if (out.length === 0) {
  return [{ json: { _empty: true, run_id: runId, run_date: runDate, _counters: counters } }];
}
return out;
```

> `_counters`는 모든 아이템에 같은 객체 참조가 들어가므로 마지막에 확정된 값이 전 아이템에 반영됩니다. 최종 메시지 조립 노드에서 이 값을 읽어 파이프라인 통계를 출력합니다.

## 6. LLM 요약·중요도 설계 (REQ-05)

> 순서상 중복 제거(§7)와 키워드 필터(§7.4)가 먼저 실행되지만, 문서 흐름상 LLM 설계를 여기에 먼저 서술합니다. 실제 노드 순서는 §2 다이어그램을 따릅니다.

### 6.1 일일 상한과 배치 요약 (v1.2)

#### 문제

초안(v1.1)은 기사당 1회 호출이었습니다. 실기동해 보니 **필터 통과 188건 → LLM 호출 188회**가 되어 첫 배치부터 `429 Too Many Requests`가 났습니다.

```
[GoogleGenerativeAI Error]: [429 Too Many Requests] You exceeded your current quota
Quota exceeded for metric: generate_content_free_tier_requests, limit: 5, model: gemini-2.5-flash
```

`limit: 5`는 **분당 5요청**입니다. 188회를 건별로 보내면 38분이 걸리고, 무료 티어 일일 한도(250회)에도 부딪힙니다. 재시도나 대기로는 해결되지 않고 **호출 수 자체를 줄여야** 합니다.

#### 대응 (노드 `⑤b 상한+배치`)

| 상수 | 값 | 역할 |
| --- | --- | --- |
| `LLM_MAX` | `40` | 하루 LLM 대상 상한. `filter_score` 내림차순 → 최신순으로 정렬해 상위 40건만 선발 |
| `BATCH_SIZE` | `10` | 한 프롬프트에 넣을 기사 수 |
| `SNIPPET_MAX` | `600` | 배치 프롬프트용 본문 발췌 상한 (10건 × 600자 = 약 6,000자) |

결과: **188회 → 4회.** 분당 5회 한도 안에 들어오고, 일일 한도(250회) 대비 여유가 큽니다.

#### 배치의 대가와 그 방어

배치는 실패 격리를 잃습니다. 한 호출이 깨지면 10건이 함께 사라지고, LLM이 10건 중 6건만 반환하는 부분 누락도 발생합니다. 두 가지로 막습니다.

1. **id 기반 되짚기**: 배치 노드가 각 기사에 배치 내 지역 `id`(1~10)를 부여하고, 프롬프트에 "results는 정확히 N개, id는 입력 id와 일치"를 명시합니다. `⑨`는 반환된 `results`를 `id`로 인덱싱해 원본 기사와 짝지웁니다.
2. **V-7 누락 검사**: `id`에 대응하는 결과가 없으면 그 기사만 `needs_review=true`, `review_flags=V7_missing_in_batch`로 처리합니다. **배치 전체를 잃지 않고 누락된 건만 격리**됩니다.

오프라인 검증에서 "10건 중 6건만 반환 + 다른 배치 하나는 통째 실패" 상황을 넣었을 때, 출력 기사 수는 입력과 같은 40건을 유지했고 플래그 분포는 `정상 26 / V7_missing_in_batch 4 / V1_llm_error 10`으로 정확히 나왔습니다.

#### 재시도 설정

`LLM 요약+중요도` 노드의 `Retry On Fail`을 **Max Tries 3 / Wait 65,000ms**로 둡니다. 429의 `retryDelay`가 보통 49초이므로 65초를 기다리면 분당 한도 창이 리셋된 뒤 재시도합니다. 기본값 2초로는 재시도가 전부 같은 429를 받습니다.

> **v1.1 변경 (유지)**: `Loop Over Items(Batch Size 1)`는 제거했습니다. `Basic LLM Chain`이 입력 아이템마다 자동 실행되므로 루프 노드 없이도 배치당 1회 호출이 됩니다.
>
> LLM 노드 출력에는 `output`만 남고 원본 기사 메타(`url_hash`, `title` 등)가 사라지므로, `⑨ 검증 안전판`에서 `$('상한+배치').itemMatching(i)`로 배치 원본을 복원합니다.

### 6.2 노드: `⑧ Basic LLM Chain` + `Google Gemini Chat Model`

| 설정 | 값 |
| --- | --- |
| Chat Model | `Google Gemini Chat Model` (등록된 자격증명 사용) |
| Model | `gemini-2.5-flash` (요약·분류 용도에 충분, 저비용) |
| Temperature | `0.2` (분류 일관성 우선) |
| Output Parser | **Structured Output Parser** 연결 |
| Settings → On Error | **`Continue (using error output)`** |
| Settings → Retry On Fail | ON, Max Tries 2 |

`On Error`를 `Continue`로 두어야 특정 기사에서의 API 실패가 브리핑 전체를 죽이지 않습니다. 실패한 아이템은 §6.4 검증 안전판이 `needs_review=true`로 흡수합니다.

### 6.3 프롬프트 전문

> REQ-05는 중요도 판정 기준을 **"프롬프트에 명시할 것"** 으로 요구합니다. 따라서 아래 `importance` 항목의 5줄은 **요청서 원문 그대로** 유지합니다. v1.5까지는 제가 임의로 확장한 문장이 들어가 있어 v1.6에서 원문으로 되돌렸고, 해석을 좁히는 내용은 별도 섹션으로 분리했습니다.

**System / 상단 지시문**

```
당신은 자산운용사 리서치팀을 위해 뉴스를 정리하는 애널리스트입니다.
입력으로 여러 건의 기사가 '### id: N' 구분자와 함께 주어집니다.
각 기사를 독립적으로 분석해, results 배열에 기사 수만큼의 객체를 담아 JSON 하나만 반환합니다.
설명, 인사말, 코드펜스를 절대 붙이지 마십시오.

[절대 규칙]
- 입력 기사가 N건이면 results도 정확히 N개여야 합니다. 건너뛰거나 합치지 마십시오.

### 6.4 검증 안전판

Structured Output Parser가 있어도 다음이 발생합니다: 파서 통과 후에도 `summary`가 4문장이거나, `importance`가 문자열 `"4"`거나, 노드 자체가 에러 출력으로 빠지는 경우입니다. Code 노드에서 한 번 더 잡습니다.

**노드: `⑨ Code: 검증 안전판`** — Mode: Run Once for All Items

**검증 항목과 조치**

| # | 검사 | 실패 시 조치 |
| --- | --- | --- |
| V-1 | LLM 노드가 에러 출력으로 나옴 | `importance=1`, `category=기타`, `summary=""`, `needs_review=true` |
| V-2 | `summary`가 비었거나 10자 미만 | `needs_review=true` |
| V-3 | `summary`가 4문장 이상 | 앞 3문장만 남기고 `needs_review=true` |
| V-4 | `importance`가 정수 1~5가 아님 | 숫자 변환 시도 → 실패하면 `1`, `needs_review=true` |
| V-5 | `category`가 허용 7종이 아님 | `기타`로 보정, `needs_review=true` |
| V-6 | `summary`에 URL/코드펜스 잔여 | 제거 후 `needs_review=true` |

**D-10 확정 정책**: `needs_review=true`인 기사는 **발송 대상에서 제외**하되, 시트에는 전부 기록합니다. 오작동한 LLM 출력이 브리핑 본문을 오염시키지 않게 하면서, 나중에 시트에서 `needs_review=TRUE` 필터만 걸면 프롬프트 개선 대상을 즉시 뽑을 수 있습니다.

```javascript
// ⑨ Code: 검증 안전판
// Mode: Run Once for All Items

const CATEGORIES = new Set(['증시','금리','환율','부동산','기업','정책','기타']);

function sentenceTrim(text, max = 3) {
  const parts = String(text).split(/(?<=[.!?。])\s+/).filter(s => s.trim());
  return { text: parts.slice(0, max).join(' ').trim(), over: parts.length > max };
}

const out = [];

for (const item of $input.all()) {
  const j = item.json;

  // LLM 결과는 Basic LLM Chain의 output 위치가 버전에 따라 다름 → 폴백 체인
  const llm = j.output ?? j.data ?? j.result ?? j;

  // 원본 기사 메타는 Loop 입력 아이템에서 유지되어 함께 흘러옴
  const base = {
    url_hash:       j.url_hash,
    normalized_url: j.normalized_url,
    original_url:   j.original_url,
    title:          j.title,
    source:         j.source,
    published_at:   j.published_at,
    run_id:         j.run_id,
    run_date:       j.run_date,
    _counters:      j._counters,
  };

  let needsReview = false;
  let summary = '';
  let importance = 1;
  let category = '기타';
  const flags = [];

  // V-1: LLM 자체 실패
  if (j.error || !llm || (typeof llm !== 'object')) {
    needsReview = true;
    flags.push('V1_llm_error');
    out.push({ json: { ...base, summary, importance, category, needs_review: true,
                       review_flags: flags.join('|') } });
    continue;
  }

  // summary
  summary = String(llm.summary ?? '').trim();
  // V-6: 코드펜스/URL 잔여물 제거
  const cleaned = summary.replace(/```[a-z]*\n?/gi, '').replace(/https?:\/\/\S+/g, '').trim();
  if (cleaned !== summary) { needsReview = true; flags.push('V6_artifact'); }
  summary = cleaned;

  // V-2
  if (summary.length < 10) { needsReview = true; flags.push('V2_too_short'); }

  // V-3
  const st = sentenceTrim(summary, 3);
  if (st.over) { needsReview = true; flags.push('V3_too_many_sentences'); }
  summary = st.text;

  // V-4
  const impNum = Number(llm.importance);
  if (!Number.isInteger(impNum) || impNum < 1 || impNum > 5) {
    importance = 1; needsReview = true; flags.push('V4_bad_importance');
  } else {
    importance = impNum;
  }

  // V-5
  const cat = String(llm.category ?? '').trim();
  if (!CATEGORIES.has(cat)) {
    category = '기타'; needsReview = true; flags.push('V5_bad_category');
  } else {
    category = cat;
  }

  out.push({
    json: {
      ...base,
      summary,
      importance,
      category,
      needs_review: needsReview,
      review_flags: flags.join('|'),
    },
  });
}

return out;
```

## 7. 중복 발송 방지 설계 (REQ-03) — 핵심

### 7.1 중복 판정 고유값: `url_hash` (REQ-03)

**결정: 정규화된 기사 URL의 SHA-256 해시를 고유값으로 삼는다. (D-01)**

#### 정규화 규칙

| 순서 | 규칙 | 예 |
| --- | --- | --- |
| 1 | 프로토콜을 `https`로 통일 | `http://a.com/1` → `https://a.com/1` |
| 2 | 호스트 소문자화 + `www.` 제거 | `WWW.A.com` → `a.com` |
| 3 | `#` 앵커 제거 | `/1#comment` → `/1` |
| 4 | 추적 파라미터 제거 (`utm_*`, `fbclid`, `gclid`, `ref`, `src`, `from`, `cid` 등) | `/1?utm_source=naver` → `/1` |
| 5 | 남은 쿼리 파라미터를 키 사전순 정렬 | `?b=2&a=1` → `?a=1&b=2` |
| 6 | 끝 슬래시 제거 | `/1/` → `/1` |
| 7 | 위 결과를 SHA-256 해시 (64자 hex) |  |

#### 왜 이 값인가 (제출 문서용 근거)

기사를 식별하는 후보는 셋이었습니다.

- **RSS `guid`**: 피드가 제공하는 공식 식별자지만, 매체마다 형식이 제각각입니다. 어떤 매체는 URL을 그대로 넣고, 어떤 매체는 내부 시퀀스를 넣으며, 일부 CMS는 기사 수정 시 `guid`를 재발급합니다. 매체가 늘어날 때마다 예외 처리가 붙습니다.
- **제목 해시**: URL이 바뀌어도 잡히는 장점이 있으나, "코스피 마감 시황" 같은 정형 제목이 매일 반복되는 매체가 있어 **다른 날의 다른 기사를 같은 기사로 오판**합니다. 오탐은 누락으로 직결되므로 단독 키로 부적합합니다.
- **정규화 URL 해시** (채택): 기사 URL은 매체가 발행 시점에 확정하고 이후 바꾸지 않는 것이 원칙입니다. 실무에서 같은 기사가 다른 문자열로 나타나는 원인은 대부분 추적 파라미터와 대소문자·슬래시 차이인데, 이는 정규화로 결정론적으로 제거됩니다.

해시를 쓰는 이유는 별도입니다.

- **길이 고정**: 원본 URL은 200자를 넘기도 합니다. 시트 셀·비교 연산·로그 모두 64자 고정이 다루기 쉽습니다.
- **비교 안정성**: 시트에 긴 URL을 저장하면 Google Sheets가 하이퍼링크로 변환하거나 앞뒤 공백을 다루는 방식 때문에 문자열 비교가 어긋날 수 있습니다. hex 문자열은 그런 변형이 없습니다.
- **대조 시 원본 URL도 함께 저장**하므로 사람이 시트를 열어 확인할 때의 가독성은 잃지 않습니다.

#### 한계 (명시)

같은 사건을 세 매체가 각각 보도하면 URL이 다르므로 3건 모두 통과합니다. 이는 **D-04에서 이번 범위 밖으로 합의**한 사항이며, 요청서 REQ-03이 요구하는 "어제 보낸 기사의 재발송 방지"와는 다른 문제입니다. §12에 대응 방안을 기록해 둡니다.

### 7.2 이력 기록 범위 (REQ-03 & REQ-07)

**결정: 금융 키워드 필터를 통과한 기사 전부를 기록한다. 발송 여부는 `sent` 컬럼으로 구분한다. (D-02)**

| 단계 | 시트 기록 여부 |
| --- | --- |
| RSS 수집 원본 | ✗ |
| 시간 창 통과 | ✗ |
| 중복 제거 통과 | ✗ |
| **키워드 필터 통과** | **✓ (여기부터 전부 기록)** |
| LLM 처리 완료 | ✓ (같은 행에 요약·중요도 채움) |
| 중요도 4+ 발송 | ✓ `sent=TRUE`, `sent_at` 기록 |
| 중요도 1~3 미발송 | ✓ `sent=FALSE` |

**이유**: 중복 차단은 시트에 기록된 것만 걸러냅니다. 만약 발송된 기사(중요도 4+)만 기록하면, 어제 중요도 3으로 평가돼 미발송된 기사가 오늘 피드에 다시 뜰 때 **LLM을 또 호출**합니다. 매일 수십 건씩 낭비되는 구조입니다. 필터 통과 시점부터 기록하면 그 기사는 평생 한 번만 LLM을 탑니다.

수집 전체를 기록하지 않는 이유는, 금융 필터에서 탈락한 연예·스포츠 기사까지 넣으면 시트가 하루 수백 행씩 커지고 §7.3의 7일 조회 비용이 급증하기 때문입니다. 필터 탈락 기사는 내일 다시 와도 어차피 필터에서 다시 탈락하므로 LLM 비용이 발생하지 않습니다.

#### v1.2 보완: 상한 초과분은 기록하지 않는다 (D-13)

v1.2에서 일일 LLM 상한 40건이 생겼으므로, "필터는 통과했으나 상한에 밀려 LLM을 타지 못한 기사"라는 제3의 상태가 생겼습니다. **이들은 시트에 기록하지 않습니다.**

기록하면 `url_hash`가 시트에 남아 중복 키가 되고, 그 기사는 **내일 다시 평가받을 기회가 영영 사라집니다.** 오늘 41위였던 기사가 내일은 상위권일 수 있는데, 한 번 밀렸다는 이유로 영구 배제되는 것은 명백한 손실입니다.

기록하지 않으면 내일 피드에 그대로 있을 때 다시 경쟁합니다. 24시간 시간 창(A-01) 밖으로 나가면 그때 자연스럽게 사라지므로, 무한히 재평가되지도 않습니다.

오프라인 검증에서 확인된 실제 동작:

| 실행 | 필터 통과 | LLM 대상 | 상한 제외 | 다음 실행에서 |
| --- | --- | --- | --- | --- |
| 1회차 | 55건 | 40건 (기록됨) | 15건 (미기록) | — |
| 2회차 | 55건 중 **40건 중복 차단** → 15건 | 15건 | 0건 | 어제 밀린 15건이 오늘 LLM을 탐 ✓ |

**대가**: 상한에 걸린 기사가 어떤 것이었는지 시트에 흔적이 남지 않습니다. 대신 브리핑 하단 카운트 줄에 `LLM대상 40건(상한제외 15)`으로 노출해, 받는 사람이 "오늘은 후보가 넘쳤다"는 사실만은 알 수 있게 했습니다.

### 7.3 이력 조회 범위: 7일 (D-03)

시트는 무제한 누적하되, **매 실행 시 최근 7일치 행만 읽어** 메모리에 올립니다.

- RSS 피드는 통상 최근 20~50건, 길어야 2~3일치만 노출합니다. 7일이면 재발송 방지에 충분한 여유입니다.
- 전체 조회 방식은 운영 몇 달 뒤 수천~수만 행이 되어 매일 아침 읽기 지연과 Sheets API 쿼터 부담을 만듭니다.
- 시트가 커지면 `A:N` 전체 읽기 대신 최근 N행만 읽도록 범위를 좁힐 수 있습니다(§7.3.1).

#### 7.3.1 노드: `④ Google Sheets - 이력 조회`

| 설정 | 값 |
| --- | --- |
| Resource / Operation | Sheet Within Document → **Get Row(s)** |
| Document | `금융뉴스브리핑_발송이력` |
| Sheet | `sent_log` |
| Filters | 사용하지 않음 (날짜 필터는 Code 노드에서 수행) |
| Combine Filters | — |
| Settings → Always Output Data | **ON** (첫 실행 시 빈 시트여도 워크플로우가 멈추지 않게) |
| Settings → On Error | `Continue` |

> **시트가 커졌을 때**: Get Row(s)의 `Range`를 `A1:N1` + 최근 2,000행으로 좁히거나, 월별 시트 분리(`sent_log_2026_08`)로 전환합니다. 후자는 조회 노드가 2개(이번 달 + 지난 달)로 늘어나는 대신 조회량이 항상 일정합니다.

#### 7.3.2 `④`의 배치 위치 (v1.1 변경)

`⑤`는 `$('이력 조회').all()`로 시트 이력을 참조합니다. 따라서 **`⑤`가 실행되는 시점에 `④`가 이미 끝나 있어야** 합니다.

초안은 트리거에서 `②` RSS와 `④`를 나란히 분기시켰으나, n8n `executionOrder: v1`은 분기를 깊이 우선으로 실행하므로 **RSS → ③ → ⑤가 ④보다 먼저 끝날 수 있습니다.** 이 경우 `⑤`에서 `node not executed` 에러가 나거나(try/catch로 흡수되면) 이력 0건으로 간주돼 **중복 차단이 통째로 무력화**됩니다. 눈에 잘 띄지 않는 치명적 실패라 배선으로 원천 차단합니다.

**확정 배선**: `① → ④ 이력 조회 → Limit(1) → ② RSS ×3`

- `④`가 `②`의 상류에 있으므로 실행 순서가 배선으로 강제됩니다.
- `Limit` 노드(Max Items 1)가 필요한 이유: `④`가 이력 300행을 내보내면 그 뒤 RSS 노드가 **300번 실행**됩니다. 아이템 수를 1로 줄여 각 RSS를 정확히 1회만 돌립니다.
- `④`는 `Always Output Data = ON`이므로 시트가 비어 있어도 빈 아이템 1개를 내보내 체인이 끊기지 않습니다.
- `③ 정규화`는 입력 아이템 중 `link`/`title`이 모두 없는 것을 건너뛰므로, `Limit`을 타고 넘어온 빈 아이템이 기사로 오인되지 않습니다.

### 7.4 노드: `⑤ Code: 중복 대조` + 금융 키워드 필터

**두 로직을 한 Code 노드에 합칩니다.** 순서는 **중복 대조 → 키워드 필터**입니다. 중복 제거가 더 싸고(집합 조회 O(1)) 더 많이 걸러내므로 앞에 둡니다.

#### 금융 키워드 필터 설계 (REQ-04)

**필터 위치: LLM 호출 앞. (요청서가 근거 제출을 요구한 항목)**

| 비교 항목 | LLM 앞에 필터 (채택) | LLM 뒤에 필터 |
| --- | --- | --- |
| LLM 호출 건수 | 필터 통과분만 (대략 수집의 20~40%) | 수집 전량 |
| 비용 | 낮음 | 3~5배 |
| 실행 시간 | 짧음 | 김 |
| 애매한 기사 판별 정확도 | 키워드 규칙에 의존 (오탐·누락 존재) | LLM 문맥 이해로 더 정확 |
| 실패 지점 | 키워드 목록 관리 필요 | API 실패 위험이 전 기사에 노출 |

**채택 이유**: 종합지 RSS의 상당수는 연예·스포츠·사건사고입니다. 이걸 전부 LLM에 넣는 것은 "쓰레기를 유료로 분류하는" 구조입니다. 게다가 요청서 REQ-05의 중요도 기준 `1 = 브리핑에 넣을 필요 없는 기사`가 이미 존재하므로, **LLM은 2차 필터로 자연스럽게 작동**합니다. 즉 키워드 필터가 다소 느슨해서 비금융 기사를 통과시켜도 LLM이 중요도 1~2를 부여해 브리핑에서 제외합니다. **2단 필터 구조**이므로 1단(키워드)을 비용 절감 목적의 거친 체로 두는 것이 합리적입니다.

반대로 키워드 필터를 지나치게 엄격하게 잡으면 LLM이 볼 기회조차 없이 중요 기사가 사라집니다. 따라서 **재현율(recall) 우선, 정밀도는 LLM에 위임**이 이 설계의 방침입니다.

#### 키워드 규칙

3단 구조입니다.

**(1) 차단 키워드 (BLOCK)** — 하나라도 걸리면 즉시 탈락. 금융 키워드보다 먼저 평가합니다.

```
연예, 아이돌, 드라마, 예능, 배우, 가수, 열애, 결혼설, 이혼,
프로야구, 축구, 야구, 골프, 올림픽, 월드컵, 리그, 선수단, 감독 선임,
날씨, 미세먼지, 폭염, 한파, 태풍 경로,
음주운전, 살인, 성폭행, 마약 투약,
운세, 별자리, 로또 당첨번호
```

**(2) 강한 금융 키워드 (STRONG)** — 하나만 있어도 통과 (가중치 2점)

```
기준금리, 금통위, 한국은행, 연준, FOMC, 파월,
코스피, 코스닥, 나스닥, S&P, 다우, 지수, 증시, 주가, 상장, 공모주, IPO,
환율, 원달러, 달러화, 엔화, 위안화, 외환보유액,
국채, 회사채, 채권, 금리, 스프레드,
영업이익, 순이익, 실적, 어닝, 분기 실적, 매출,
인수합병, M&A, 지분 인수, 유상증자, 자사주,
물가, 소비자물가, CPI, PPI, GDP, 경상수지, 무역수지,
부동산, 아파트값, 집값, 전세, 분양, 청약, 재건축,
금융위, 금감원, 기재부, 세제 개편, 규제 완화,
펀드, ETF, 연기금, 국민연금, 기관 순매수, 외국인 순매도
```

**(3) 약한 금융 키워드 (WEAK)** — 2개 이상이면 통과 (각 1점)

```
투자, 자금, 자본, 시장, 경기, 경제, 산업, 수출, 수입, 성장률,
기업, 대기업, 중소기업, 스타트업, 상장사, 계약, 수주,
정부, 정책, 대출, 예금, 은행, 보험, 증권사, 카드사,
반도체, 배터리, 바이오, 조선, 철강, 자동차, 유통, 건설
```

**판정식 (v1.2 강화)**

```
if (BLOCK 매칭 있음)     → 탈락
if (STRONG 매칭 개수 = 0) → 탈락      ← v1.2 추가
score = (STRONG 매칭 개수 × 2) + (WEAK 매칭 개수 × 1)
if (score >= 2) → 통과
else → 탈락
```

#### v1.2에서 STRONG 필수로 바꾼 이유

초안은 STRONG 없이 WEAK 2개만으로도 통과시켰습니다. "종합지 RSS에는 연예·스포츠가 많으니 필터는 거칠게 두고 LLM이 2차 필터 역할을 하게 한다"는 전제였습니다.

**전제가 틀렸습니다.** 실제로 선정한 피드 3개(연합뉴스 경제면, 한국경제, 매일경제)는 **모두 경제 섹션 전용**입니다. WEAK 목록의 `시장 / 경제 / 기업 / 산업 / 정부`는 경제 기사라면 거의 반드시 등장하므로, 필터가 사실상 아무것도 걸러내지 못하고 **188건이 전량 통과**했습니다.

STRONG 1개 이상을 요구하면 `기준금리 / 코스피 / 환율 / 영업이익` 같은 **구체적 금융 용어**가 최소 하나는 있어야 합니다. 검증 데이터(STRONG 포함 55건 + WEAK만 30건 + 연예 1건)에서 **31건이 정확히 탈락**했습니다.

재현율 손실은 감수 가능합니다. STRONG 목록에 없는 표현만 쓴 중요 기사는 놓칠 수 있으나, 그런 기사는 대개 제목에 지수·금리·기업명이 들어가므로 실제 누락은 드뭅니다. 운영 중 놓친 사례가 나오면 그 키워드를 STRONG에 추가하는 것이 정상적인 튜닝 경로입니다.

매칭 대상 텍스트는 `title + ' ' + snippet`입니다. **제목에서 매칭되면 가중치를 1점 추가**해 제목 신호를 우대합니다.

#### 코드

```javascript
// ⑤ Code: 중복 대조 + 금융 키워드 필터
// Mode: Run Once for All Items
// ※ 중복 대조를 먼저 수행 (더 싸고 더 많이 걸러냄)

const HISTORY_DAYS = 7;   // D-03
const SCORE_MIN    = 2;

const BLOCK = ['연예','아이돌','드라마','예능','배우','가수','열애','결혼설','이혼',
  '프로야구','축구','야구','골프','올림픽','월드컵','리그','선수단','감독 선임',
  '날씨','미세먼지','폭염','한파','태풍 경로',
  '음주운전','살인','성폭행','마약 투약','운세','별자리','로또 당첨번호'];

const STRONG = ['기준금리','금통위','한국은행','연준','FOMC','파월',
  '코스피','코스닥','나스닥','S&P','다우','지수','증시','주가','상장','공모주','IPO',
  '환율','원달러','달러화','엔화','위안화','외환보유액',
  '국채','회사채','채권','금리','스프레드',
  '영업이익','순이익','실적','어닝','매출',
  '인수합병','M&A','지분 인수','유상증자','자사주',
  '물가','소비자물가','CPI','PPI','GDP','경상수지','무역수지',
  '부동산','아파트값','집값','전세','분양','청약','재건축',
  '금융위','금감원','기재부','세제 개편','규제 완화',
  '펀드','ETF','연기금','국민연금','순매수','순매도'];

const WEAK = ['투자','자금','자본','시장','경기','경제','산업','수출','수입','성장률',
  '기업','대기업','중소기업','스타트업','상장사','계약','수주',
  '정부','정책','대출','예금','은행','보험','증권사','카드사',
  '반도체','배터리','바이오','조선','철강','자동차','유통','건설'];

// --- 1) 시트 이력을 Set으로 ---
const cutoff = new Date(Date.now() - HISTORY_DAYS * 86400 * 1000);
const historySet = new Set();
let historyRowsRead = 0;

let historyItems = [];
try {
  historyItems = $('④ Google Sheets - 이력 조회').all();
} catch (e) {
  historyItems = [];   // 첫 실행: 시트가 비어 노드 출력이 없을 수 있음
}

for (const h of historyItems) {
  const hj = h.json || {};
  const hash = String(hj.url_hash || '').trim();
  if (!hash) continue;
  historyRowsRead++;
  const rd = hj.run_date ? new Date(String(hj.run_date) + 'T00:00:00+09:00') : null;
  if (rd && !isNaN(rd.getTime()) && rd < cutoff) continue;   // 7일 초과분은 무시
  historySet.add(hash);
}

// --- 2) 필터링 ---
const inputs = $input.all().filter(i => !i.json._empty);
const counters = (inputs[0]?.json?._counters) || {};
const stats = {
  ...counters,
  collected: inputs.length,
  history_rows: historyRowsRead,
  history_active: historySet.size,
  dup_blocked: 0,
  keyword_blocked: 0,
  passed: 0,
};

const out = [];

for (const item of inputs) {
  const j = item.json;

  // (a) 중복 대조 — LLM 이전 (REQ-03)
  if (historySet.has(j.url_hash)) { stats.dup_blocked++; continue; }

  // (b) 금융 키워드 필터 — LLM 이전 (REQ-04)
  const title = String(j.title || '');
  const body  = title + ' ' + String(j.snippet || '');

  if (BLOCK.some(k => body.includes(k))) { stats.keyword_blocked++; continue; }

  const strongHits = STRONG.filter(k => body.includes(k));
  const weakHits   = WEAK.filter(k => body.includes(k));
  let score = strongHits.length * 2 + weakHits.length;
  if (strongHits.some(k => title.includes(k))) score += 1;   // 제목 신호 우대

  if (score < SCORE_MIN) { stats.keyword_blocked++; continue; }

  stats.passed++;
  out.push({
    json: {
      ...j,
      filter_score: score,
      matched_keywords: [...strongHits, ...weakHits].slice(0, 8).join(','),
      _stats: stats,
    },
  });
}

// 통과 0건이어도 뒤쪽 "정상 동작 메시지" 경로가 통계를 읽어야 함
if (out.length === 0) {
  return [{ json: { _empty: true, run_id: inputs[0]?.json?.run_id || '',
                    run_date: inputs[0]?.json?.run_date || '', _stats: stats } }];
}
return out;
```

> `_empty` 아이템은 **⑥ IF 노드**로 분기시켜 LLM을 건너뛰고 `⑪ 브리핑 조립`으로 직행시킵니다. IF 조건: `{{ !!$json._empty }}` is true → true 분기는 ⑪로, false 분기는 ⑧(LLM)으로.

## 8. Discord 발송 설계 (REQ-06)

### 8.1 노드: `⑪ Code: 브리핑 메시지 조립`

- Mode: **Run Once for All Items**
- 하는 일: 중요도 4+ 필터 → 카테고리·중요도 정렬 → 단일 문자열 조립 → 0건 분기 처리

**정렬 규칙**: 중요도 내림차순 → 카테고리 고정 순서(`금리 > 정책 > 증시 > 환율 > 기업 > 부동산 > 기타`) → 발행시각 내림차순.

금리·정책을 앞에 두는 이유는 거시 이벤트가 나머지 기사의 해석 맥락이 되기 때문입니다.

### 8.2 메시지 길이 가드 (A-02)

Discord 일반 메시지 본문은 **2,000자** 제한입니다. 초과하면 400 에러로 발송 자체가 실패합니다.

| 가드 | v1.3 | **v1.4** |
| --- | --- | --- |
| 최대 기사 수 (`MAX_ARTICLES`) | 10건 | 15건 (길이 가드가 실질 상한) |
| 기사당 요약 (`SUMMARY_MAX`) | 220자, 전체 문장 | **첫 문장만, 90자** |
| 기사 간 구분 | 빈 줄 1개 | 없음 (줄바꿈 1개) |
| 요약 줄바꿈 | 60자마다 4칸 들여쓰기 | 2칸 들여쓰기, 줄바꿈 없음 |
| 파이프라인 카운트 줄 | 포함 (약 110자) | **제거** (0건 메시지에만 유지) |
| 최종 안전장치 (`HARD_LIMIT`) | 1,900자 | 1,950자. 초과 시 뒤에서부터 기사를 빼며 재조립 |

**압축 효과**: 실측 기준 같은 2,000자에 **8건 → 11건**이 들어갑니다.

초과분은 `… 외 N건은 길이 제한으로 생략`으로 건수만 알리고, 어떤 기사였는지는 시트에서 `sent=FALSE` + `importance>=4`로 확인합니다.

**근본 대응은 판정 정확도**입니다(v1.6, §6.3). 중요도 4+가 17건까지 부푼 것은 LLM이 증권사 리포트·[특징주] 기사에도 4를 준 결과였고, 요청서 기준상 이들은 3입니다. 보조 판정 지침으로 이를 3으로 강등하면 4+ 건수가 수용력 안으로 들어옵니다.

> Discord Embed를 쓰면 한 메시지에 6,000자까지 담을 수 있어 17건이 한 번에 들어갑니다. 협의 결과 **일반 본문 2,000자 유지**를 택했습니다(D-15). 향후 브리핑이 상시 잘린다면 §12 F-07을 검토하십시오.

### 8.3 중요 기사 0건인 날의 경로

**D-07 확정: 정상 동작 메시지를 발송한다.**

받는 사람이 "조용한 날"과 "시스템 고장"을 구분해야 한다는 것이 REQ-06의 요구입니다. 메시지 자체가 도착하는 것만으로는 부족합니다 — RSS가 0건을 반환해도 "중요 기사 없음" 메시지는 똑같이 나가기 때문입니다. 따라서 **파이프라인 카운트를 함께 노출**합니다.

```
📭 오늘의 금융 브리핑 (2026-08-06)
중요도 4 이상 기사가 없습니다.

수집 47건 → 시간창 31건 → 중복제외 12건 → 금융필터 5건 → 중요도4+ 0건
```

> v1.2부터, 일일 상한(40건)에 걸린 기사가 있는 날은 중간에 한 구간이 더 붙습니다.
> `… → 금융필터 55건 → LLM대상 40건(상한제외 15) → 중요도4+ 16건`
> 상한 제외가 0건인 날은 이 구간이 생략돼 줄이 짧아집니다.

이 한 줄로 세 가지 상태가 구분됩니다.

| 관측 | 해석 |
| --- | --- |
| `수집 47 → ... → 중요도4+ 0` | **정상.** 오늘은 조용한 날 |
| `수집 0 → ...` | **장애.** RSS 피드 3개가 모두 실패 |
| `수집 47 → 중복제외 0` | **의심.** 중복 로직 오작동 또는 시트 조회 실패 |
| 메시지가 아예 안 옴 | **장애.** 스케줄/Discord 웹훅 문제 |

> **v1.6**: 이 카운트 줄은 **0건 메시지에만** 넣습니다. 정상 브리핑에서는 기사가 도착했다는 사실 자체가 정상 동작의 증거이므로 줄을 빼고 그 공간을 기사에 씁니다. 즉 위 표의 판정은 전부 "📭 메시지를 받았을 때"에 적용됩니다.

### 8.4 메시지 포맷

```
📈 오늘의 금융 브리핑 (2026-08-06)
읽을 기사 3건

[1] ⭐5 금리 | 한국은행 기준금리 3.0% 동결
  금통위가 기준금리를 만장일치로 동결했다.
  📰 연합뉴스 🔗 <https://...>
[2] ⭐4 기업 | 삼성전자 2분기 영업이익 12조 원
  삼성전자가 2분기 영업이익 12조 원을 기록했다.
  📰 한국경제 🔗 <https://...>
[3] ⭐4 환율 | 원달러 환율 1,340원대 마감
  원/달러 환율이 1,340원대에서 마감했다.
  📰 매일경제 🔗 <https://...>
```

요청서가 요구한 4개 요소(제목·요약·원문 링크·카테고리)가 기사마다 모두 들어갑니다. 여기에 중요도(⭐)와 매체를 덧붙였습니다.

**v1.6 변경**: 맨 아래 파이프라인 카운트 줄(`수집 N건 → …`)을 **정상 브리핑에서는 제거**했습니다. 기사가 실제로 도착한 날에는 시스템이 정상 동작한다는 사실이 자명하므로, 2,000자 예산에서 약 110자를 차지할 이유가 없습니다. 그만큼 기사를 한 건 더 담을 수 있습니다.

**0건 메시지에서는 그대로 유지합니다.** REQ-06이 요구하는 "조용한 날과 고장의 구분" 장치가 그 줄이기 때문입니다(§8.3).

> Discord는 메시지 본문의 URL을 자동으로 링크 프리뷰로 확장합니다. 기사 3건이면 프리뷰 카드 3개가 붙어 매우 길어집니다. 이를 막으려면 URL을 `<https://...>` 꺾쇠로 감싸면 됩니다. 아래 코드는 꺾쇠를 적용합니다.

### 8.5 코드

```javascript
// ⑪ Code: 브리핑 메시지 조립
// Mode: Run Once for All Items

const MIN_IMPORTANCE = 4;      // REQ-05: 발송 대상
const MAX_ARTICLES   = 10;     // A-02
const SUMMARY_MAX    = 220;
const HARD_LIMIT     = 1900;   // Discord 2000자 대비 여유

const CAT_ORDER = ['금리','정책','증시','환율','기업','부동산','기타'];

const items = $input.all();
const first = items[0]?.json || {};
const stats = first._stats || first._counters || {};
const runDate = first.run_date ||
  new Intl.DateTimeFormat('sv-SE', { timeZone: 'Asia/Seoul' }).format(new Date());

// 발송 후보: 검증 통과 + 중요도 4 이상 (D-10: needs_review는 제외)
const candidates = items
  .map(i => i.json)
  .filter(j => !j._empty && j.url_hash)
  .filter(j => j.needs_review !== true && Number(j.importance) >= MIN_IMPORTANCE);

const line = (s) =>
  `수집 ${stats.raw ?? 0}건 → 시간창 ${stats.collected ?? 0}건 → ` +
  `중복제외 ${(stats.collected ?? 0) - (stats.dup_blocked ?? 0)}건 → ` +
  `금융필터 ${stats.passed ?? 0}건 → 중요도4+ ${s}건`;

// --- 0건 경로 (D-07 / §8.3) ---
if (candidates.length === 0) {
  const content = [
    `📭 오늘의 금융 브리핑 (${runDate})`,
    `중요도 4 이상 기사가 없습니다.`,
    ``,
    line(0),
  ].join('\n');
  return [{ json: { content, sent_hashes: [], sent_count: 0 } }];
}

// --- 정렬 ---
candidates.sort((a, b) => {
  if (b.importance !== a.importance) return b.importance - a.importance;
  const ca = CAT_ORDER.indexOf(a.category), cb = CAT_ORDER.indexOf(b.category);
  if (ca !== cb) return ca - cb;
  return String(b.published_at).localeCompare(String(a.published_at));
});

let shown = candidates.slice(0, MAX_ARTICLES);
let hidden = candidates.length - shown.length;

function build(list, hiddenCount) {
  const head = [
    `📈 오늘의 금융 브리핑 (${runDate})`,
    `읽을 기사 ${candidates.length}건`,
    ``,
  ];
  const body = list.map((a, idx) => {
    let sum = String(a.summary || '').trim();
    if (sum.length > SUMMARY_MAX) sum = sum.slice(0, SUMMARY_MAX - 1) + '…';
    const wrapped = sum.replace(/(.{1,60})(\s|$)/g, '    $1\n').trimEnd();
    return [
      `[${idx + 1}] ${a.category} | ⭐${a.importance} ${a.title}`,
      wrapped,
      `    📰 ${a.source}  🔗 <${a.original_url}>`,
    ].join('\n');
  }).join('\n\n');
  const tail = [];
  if (hiddenCount > 0) tail.push(`\n… 외 ${hiddenCount}건`);
  tail.push(``, line(candidates.length));
  return head.join('\n') + body + '\n' + tail.join('\n');
}

let content = build(shown, hidden);

// --- 하드 리밋 가드 ---
while (content.length > HARD_LIMIT && shown.length > 1) {
  shown = shown.slice(0, shown.length - 1);
  hidden = candidates.length - shown.length;
  content = build(shown, hidden);
}
if (content.length > HARD_LIMIT) content = content.slice(0, HARD_LIMIT - 1) + '…';

return [{
  json: {
    content,
    sent_hashes: shown.map(a => a.url_hash),
    sent_count: candidates.length,
  },
}];
```

## 9. 발송 이력 기록 설계 (REQ-07)

### 9.1 시트 스키마

- 스프레드시트명: `금융뉴스브리핑_발송이력`
- 시트(탭)명: `sent_log`
- 1행은 헤더 (아래 컬럼명과 **정확히 일치**해야 n8n의 컬럼 자동 매핑이 동작합니다)

| 열 | 컬럼명 | 타입 | 설명 | 용도 |
| --- | --- | --- | --- | --- |
| A | `run_date` | `YYYY-MM-DD` | 실행 날짜 (KST) | **7일 조회 필터의 기준** |
| B | `run_id` | string | n8n 실행 ID | 장애 시 실행 로그 역추적 |
| C | `url_hash` | string(64) | 정규화 URL SHA-256 | **중복 판정 키** |
| D | `normalized_url` | string | 정규화 URL | 해시 재현·검증용 |
| E | `original_url` | string | 원본 URL | 사람이 클릭해서 확인 |
| F | `title` | string | 기사 제목 | 사람이 읽고 식별 |
| G | `source` | string | 매체명 | 매체별 커버리지 분석 |
| H | `published_at` | ISO8601 | 발행시각 | 시간창 로직 검증 |
| I | `category` | string | 7종 중 하나 | 카테고리 분포 분석 |
| J | `importance` | number | 1~5 | 중요도 분포·임계값 튜닝 |
| K | `summary` | string | LLM 요약 | 재발송 없이 내용 확인 |
| L | `needs_review` | `TRUE`/`FALSE` | 검증 실패 여부 | **프롬프트 개선 대상 추출** |
| M | `review_flags` | string | `V3_too_many_sentences` 등 | 실패 원인 분류 |
| N | `sent` | `TRUE`/`FALSE` | 실제 발송 여부 | 발송률 추적 |
| O | `filter_score` | number | 키워드 필터 점수 | 필터 임계값 튜닝 |
| P | `matched_keywords` | string | 매칭된 키워드 | 필터 오탐 원인 분석 |

**각 컬럼을 넣은 이유** (REQ-07이 설계를 요구한 부분):

- 중복 판정에 필요한 최소 컬럼은 `url_hash` 하나입니다. 나머지는 **운영 중 발생할 질문에 답하기 위해** 넣었습니다.
- `run_date`가 없으면 §7.3의 7일 조회를 할 수 없습니다. 조회 범위 제한을 위한 필수 컬럼입니다.
- `normalized_url`은 정규화 규칙을 바꿨을 때 과거 해시를 재계산해 마이그레이션할 수 있게 합니다. 해시만 저장하면 규칙 변경 시 전 이력이 무효화됩니다.
- `needs_review` + `review_flags`는 LLM 품질 개선의 유일한 단서입니다. 실패한 출력이 어디로도 남지 않으면 프롬프트를 고칠 근거가 없습니다.
- `filter_score` + `matched_keywords`는 "왜 이 기사가 브리핑에 들어왔나"를 사후 설명할 수 있게 합니다. 필터 오탐 신고가 들어왔을 때 즉시 원인을 짚습니다.
- `sent`는 D-02 결정의 필수 부속물입니다. 필터 통과분을 전부 기록하므로, 실제 발송분을 구분할 컬럼이 필요합니다.

### 9.3 기록 시점과 `발송선별` (v1.4 / v1.5)

#### v1.3까지의 결함

초안은 `⑩ 이력 기록`을 `⑪ 브리핑 조립`보다 **앞**에 두었습니다. Discord 전송 성공 후 시트 기록이 실패하면 같은 기사가 내일 또 발송되기 때문에, 재발송 방지를 우선한 판단이었습니다.

그런데 이 순서에는 **기록 시점에 "무엇이 실제로 발송될지" 알 수 없다**는 치명적 부작용이 있었습니다. 그래서 `sent` 값을 중요도만 보고 계산했습니다.

```
sent = (needs_review !== true && importance >= 4) ? TRUE : FALSE
```

실기동에서 이렇게 터졌습니다.

| 단계 | 건수 |
| --- | --- |
| 중요도 4+ | **17건** |
| `MAX_ARTICLES=10` 적용 | 10건 |
| 2,000자 길이 가드 적용 | **8건** ← 실제 발송 |
| 시트에 `sent=TRUE`로 기록 | **17건** ← 실제와 9건 불일치 |

9건은 발송되지 않았는데 `url_hash`가 시트에 남았고, **다음 날 중복 차단되어 영영 발송되지 않는 상태**가 됐습니다. 중요도 4~5짜리 기사가 소리 없이 사라집니다.

#### v1.4 구조

`⑨b 발송선별` 노드를 신설해, **실제 발송분을 먼저 확정한 뒤** 시트에 기록합니다.

```
⑨ 검증 안전판 ──▶ ⑨b 발송선별 ──▶ ⑩ 이력 기록 ──▶ ⑪ 브리핑 조립 ──▶ ⑫ Discord 발송
                   (메시지 확정)      (실제 결과 기록)   (조립 결과 전달)
```

`⑨b`가 하는 일:

1. 후보(중요도 4+, 검증 통과)를 정렬하고 길이 가드를 적용해 **메시지에 실제로 들어갈 기사(`shown`)를 확정**
2. 메시지 본문(`briefing_content`)을 완성
3. LLM을 탄 기사 **전부**를 출력하되, `sent` 값을 실제 발송 여부와 일치시킴
   - 메시지에 실제로 들어간 기사 → `sent=true`
   - 중요도 1~3 / 검증 실패 / **길이 제한에 잘린 중요 기사** → `sent=false`

메시지 본문을 `⑪`이 아니라 `⑨b`에서 만드는 이유는, **발송 확정과 본문 생성이 같은 곳에서 이뤄져야 `sent` 값과 메시지 내용이 어긋나지 않기** 때문입니다. `⑪`은 그 결과를 1건으로 내보내는 역할과, LLM을 아예 타지 않은 날(0건 경로)의 메시지 생성만 담당합니다.

#### v1.5 정정: 잘린 기사는 재도전하지 않는다 (D-14)

v1.4는 잘린 기사를 시트에서 빼고 시간 창을 48시간으로 넓혀 다음 날 다시 발송하려 했습니다. **철회했습니다.**

이 시스템은 매일 아침 도는 브리핑이고, **실리는 기사는 항상 최신이어야 합니다.** 어제 잘린 기사는 오늘 시점에서 이미 과거 뉴스이므로 브리핑에 실릴 자격이 없습니다. 창을 48시간으로 넓히는 것은 "어제 뉴스를 오늘 브리핑에 섞는" 조치라 요구사항 위반입니다.

같은 사건이 중요하다면 **오늘 새 기사로 다시 보도됩니다.** 그 새 기사는 URL이 다르므로 중복 차단에 걸리지 않고, 오늘의 맥락에서 중요도를 새로 부여받아 정상적으로 후보가 됩니다. 이것이 이 시스템에서 "재도전"이 일어나는 올바른 방식입니다.

따라서 잘린 기사도 **시트에 `sent=FALSE`로 기록**합니다. 24시간 창 때문에 어차피 내일 다시 수집되지 않으므로 중복 차단 목적은 아니고, ① 같은 날 재실행 시 중복 요약 방지, ② "왜 이 기사가 안 왔는지" 사후 추적을 위해서입니다.

#### 재발송 방지는 그대로

`⑩ 이력 기록`은 여전히 `⑫ Discord 발송`보다 **앞**에 있습니다. 따라서 "기록 실패 후 발송" 순서로 인한 재발송 위험은 없습니다. 남는 위험은 "기록은 됐는데 Discord 전송이 실패"뿐인데, 이건 재시도 3회와 실행 실패 알림으로 감지·복구가 가능합니다.

#### 남는 한계 (명시)

중요도 4+ 기사가 10건을 넘는 날, **초과분은 발송되지 않고 그대로 종료**됩니다. 실측에서는 17건 중 7건이 이에 해당했습니다.

- 받는 사람은 메시지 하단의 `… 외 7건은 길이 제한으로 생략` 문구로 **누락 사실 자체는 인지**할 수 있습니다.
- 어떤 기사였는지는 시트에서 `sent=FALSE` + `importance>=4`로 필터하면 확인됩니다.
- 이 손실을 없애려면 메시지 용량을 늘리거나(§12 F-07의 Discord Embed, 6,000자) 발송 기준을 `MIN_IMPORTANCE=5`로 올려야 합니다. 협의 결과 현재는 **일반 본문 2,000자를 유지**합니다(D-15).

### 11.2 T-05 (중복 차단) 상세 절차

가장 중요한 검증이므로 절차를 명시합니다.

1. 시트 `sent_log`의 데이터 행을 모두 삭제 (헤더 1행은 유지)
2. 워크플로우 **1회차 수동 실행**
   - `⑤` 출력 건수를 기록 → `N1`
   - 시트 행 수 기록 → `N1`과 일치해야 함
   - Discord 메시지 수신 확인
3. **즉시 2회차 수동 실행** (RSS 내용이 거의 동일한 상태)
   - `⑤` 출력 건수 → **0 또는 그 사이 새로 올라온 기사 수만큼**
   - `⑧ LLM` 노드의 실행 횟수 → `⑤` 출력 건수와 동일 (0이면 0회)
   - 시트에서 `url_hash` 열에 중복값이 없는지 확인
     - 시트 임시 셀에 `=COUNTA(C2:C)-COUNTA(UNIQUE(C2:C))` → 결과가 `0`이어야 함
4. 실패 시 점검 순서
   - `④` 노드가 행을 읽었는가 (출력 아이템 수 > 0)
   - 시트 헤더가 `url_hash`로 정확히 적혀 있는가 (오타·공백)
   - `⑤` 코드의 `$('이력 조회')` 노드명 문자열이 실제 노드명과 일치하는가 (노드 이름을 바꿨다면 코드도 함께 수정)
   - `④`가 `②` RSS의 **상류**에 있는가 (§7.3.2 — 배선이 어긋나면 이력이 0건으로 읽혀 중복 차단이 무력화됨)
   - `③`의 해시가 두 실행에서 동일한가 (`normalized_url` 비교)

### 11.3 운영 모니터링

- n8n `Settings → Error Workflow`에 별도 에러 알림 워크플로우를 지정하면 실행 실패 시 Discord로 통보할 수 있습니다. (이번 범위 밖, 권장)
- 주 1회 시트에서 `needs_review=TRUE` 행을 필터링해 `review_flags` 분포를 확인하고, 다발 항목에 맞춰 프롬프트를 수정합니다.
- 월 1회 `filter_score` 분포를 보고 `SCORE_MIN` 임계값을 조정합니다.

| F-04 | 중요도 임계값 자동 튜닝 | `importance` 분포를 보고 발송 건수가 매일 3~7건이 되도록 임계값을 조정 | 발송 0건 또는 10건 초과가 반복될 때 |
| F-05 | 원문 본문 크롤링 | RSS `snippet`은 짧아 요약 품질에 한계가 있습니다. 본문을 가져오면 정확도가 오르지만 매체별 파싱과 robots.txt 준수 검토가 필요합니다. | 요약이 제목 재진술 수준에 그치는 사례가 잦을 때 |
| F-06 | 웹훅 URL 자격증명 분리 | 워크플로우 JSON 공유 계획이 생기면 즉시 적용 | §8.6 참조 |
| F-07 | Discord Embed 전환 | 일반 본문은 2,000자지만 Embed는 한 메시지에 최대 6,000자(Embed 10개). 현재 압축 포맷으로도 10건이 상한이므로, 매일 "외 N건"이 5건 이상 발생하면 Embed로 바꿔 17~20건을 한 통에 담을 수 있습니다. REQ-06의 "메시지 1개" 요건은 그대로 지켜집니다. | 카운트 줄의 `중요도4+`가 상시 15건을 넘을 때 |
| F-08 | 발송 후 `sent` 확정 | 현재 `⑩`이 `⑫`보다 앞이라 `sent=TRUE`는 "발송 직전 확정" 의미입니다. Discord 전송이 실패하면 시트와 어긋납니다. `⑫` 뒤에 Sheets Update 노드를 붙여 HTTP 2xx일 때만 `sent`를 확정하면 완전히 일치시킬 수 있습니다. | Discord 전송 실패가 실제로 관측될 때 |

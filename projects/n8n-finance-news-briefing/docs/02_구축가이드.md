## STEP 1. Discord 채널 + 웹훅 URL 발급

브리핑을 받을 채널을 만들고, n8n이 그 채널에 글을 쓸 수 있는 URL을 발급합니다.

### 1-1. 채널 만들기

1. Discord에서 본인 서버 선택
2. 채널 목록 위 `+` 버튼 → `채널 만들기`
3. 유형 `텍스트`, 이름 `금융브리핑` 입력 → `채널 만들기`

### 1-2. 웹훅 URL 발급

1. 만든 `금융브리핑` 채널에 마우스를 올리면 나오는 **톱니바퀴(채널 편집)** 클릭
2. 왼쪽 메뉴에서 **`연동`** 클릭
3. **`웹후크`** → **`새 웹후크`** 버튼 클릭
4. 생성된 웹후크를 클릭해 이름을 `n8n 브리핑`으로 변경 (선택)
5. **`웹후크 URL 복사`** 클릭
6. 메모장에 붙여넣어 보관

복사한 URL은 이런 형태입니다.

```
https://discord.com/api/webhooks/1234567890123456789/AbCdEf...(긴 문자열)
```

### 1-3. 웹훅 동작 테스트 (선택이지만 권장)

STEP 6에서 처음 발송할 때 실패하면 원인이 워크플로우인지 웹훅인지 헷갈립니다. 지금 미리 확인해 두면 나중에 시간을 아낍니다.

PowerShell에서:

```bash
curl -X POST -H "Content-Type: application/json" -d "{\"content\":\"webhook test\"}" 여기에_웹훅_URL_붙여넣기
```

Discord 채널에 `webhook test`가 뜨면 성공입니다.

> ⚠️ **이 URL은 그 자체가 발송 권한입니다.** 아는 사람이 URL만 있으면 이 채널에 아무거나 보낼 수 있습니다. 스크린샷을 공유하거나 git에 올릴 때 반드시 가리세요.

**해야 할 일**

- [ ] `금융브리핑` 채널 생성
- [ ] 웹훅 URL 발급 후 메모장에 보관
- [ ] (권장) curl로 테스트 메시지 발송 확인

## STEP 2. Google Sheet 생성 + 헤더 16개

발송 이력이 쌓이는 시트입니다. **헤더 철자가 하나라도 다르면 중복 차단이 동작하지 않습니다.**

### 2-1. 스프레드시트 만들기

1. [sheets.new](https://sheets.new) 접속 (본인 Google 계정으로 로그인된 상태)
2. 좌상단 제목을 `금융뉴스브리핑_발송이력`으로 변경
3. 하단 시트 탭 이름(`Sheet1` 또는 `시트1`)을 더블클릭 → **`sent_log`** 로 변경

> 탭 이름이 `sent_log`가 아니면 n8n 노드가 시트를 못 찾습니다. 대소문자와 언더스코어까지 정확히 맞추세요.

### 2-2. 헤더 입력

`A1` 셀을 클릭한 뒤, 아래 한 줄을 **그대로 복사해서 붙여넣기** 하세요. 탭 문자로 구분돼 있어 A1~P1에 자동으로 나뉘어 들어갑니다.

```
run_date	run_id	url_hash	normalized_url	original_url	title	source	published_at	category	importance	summary	needs_review	review_flags	sent	filter_score	matched_keywords
```

붙여넣은 후 확인:

| 셀 | 값 |
| --- | --- |
| A1 | `run_date` |
| B1 | `run_id` |
| C1 | `url_hash` |
| ... | ... |
| P1 | `matched_keywords` |

**P1까지 16개**가 들어가야 합니다. 한 셀에 전부 뭉쳐 들어갔다면 붙여넣기가 탭을 인식하지 못한 것이니, 셀마다 직접 입력하세요.

### 2-3. 스프레드시트 ID 복사

브라우저 주소창을 봅니다.

```
https://docs.google.com/spreadsheets/d/1AbCdEfGhIjKlMnOpQrStUvWxYz1234567890/edit#gid=0
                                      └────────── 이 부분이 ID ──────────┘
```

`/d/` 와 `/edit` 사이의 문자열을 복사해 메모장에 보관합니다.

**해야 할 일**

- [ ] 스프레드시트 `금융뉴스브리핑_발송이력` 생성
- [ ] 시트 탭 이름을 `sent_log`로 변경
- [ ] A1~P1에 헤더 16개 입력 (P1까지 채워졌는지 눈으로 확인)
- [ ] 스프레드시트 ID를 메모장에 보관

## STEP 4. 자격증명·ID·URL 연결 (총 4곳)

여기가 가장 실수가 많은 구간입니다. **4곳을 빠짐없이** 처리하세요.

### 4-1. `이력 조회` 노드 (Google Sheets)

1. 캔버스에서 **`이력 조회`** 노드 더블클릭
2. **Credential to connect with** → 드롭다운에서 등록된 Google Sheets 자격증명 선택
3. **Document** → 우측 모드 선택을 **`By ID`** 로 바꾸고, STEP 2-3에서 복사한 스프레드시트 ID 붙여넣기
   - `From list`로 골라도 되지만, 목록 로딩이 느리면 `By ID`가 확실합니다.
4. **Sheet** → `By Name` 모드에서 `sent_log` 확인 (이미 채워져 있음)
5. 상단 탭 **`Settings`** 로 이동해 아래가 켜져 있는지 확인
   - `Always Output Data` = **ON**
   - `On Error` = **Continue (using regular output)**
6. 노드 우상단 **`Test step`** 클릭 → 헤더만 있는 빈 시트라면 결과가 0건 또는 빈 아이템 1개. **에러만 안 나면 성공**입니다.
7. `Back to canvas`

### 4-2. `이력 기록` 노드 (Google Sheets)

1. **`이력 기록`** 노드 더블클릭
2. Credential → 4-1과 **같은** 자격증명 선택
3. Document → **같은 스프레드시트 ID** 붙여넣기
4. Sheet → `sent_log`
5. 화면 아래 **Values to Send** 영역에 16개 컬럼 매핑이 이미 채워져 있는지 확인
   - 만약 비어 있거나 `Column names could not be loaded` 경고가 뜨면, Document/Sheet를 다시 선택해 새로고침하세요. 시트 헤더를 읽어와야 매핑 UI가 뜹니다.
6. `Back to canvas`

> 여기서 `Column names could not be loaded`가 계속 뜨면 대부분 **STEP 2-2의 헤더가 안 들어갔거나 탭 이름이 다른 것**입니다. 시트로 돌아가 확인하세요.

### 4-3. `Gemini Chat Model` 노드

1. **`Gemini Chat Model`** 노드 더블클릭 (`LLM 요약+중요도` 아래에 매달린 작은 노드)
2. Credential → 등록된 Google Gemini(PaLM) API 자격증명 선택
3. **Model** 이 `models/gemini-2.5-flash` 인지 확인
   - 드롭다운에 이 모델이 없으면 목록에 있는 최신 flash 계열(`models/gemini-2.0-flash` 등)로 바꾸세요. 요약·분류 용도라 flash 계열이면 충분합니다.
4. `Back to canvas`

### 4-4. `Discord 발송` 노드

1. **`Discord 발송`** 노드 더블클릭
2. **URL** 칸의 `REPLACE_WITH_DISCORD_WEBHOOK_URL` 을 지우고 STEP 1-2에서 복사한 웹훅 URL 붙여넣기
3. 아래 **Body Parameters** 에 `content` = `{{ $json.content }}` 가 있는지 확인
4. `Back to canvas`

### 4-5. 타임존 확인 ★ 가장 흔한 사고 지점

1. 캔버스 우상단 **`⋮`** → **`Settings`**
2. **Timezone** = **`Asia/Seoul`** 인지 확인. 아니면 바꾸세요.
3. `Save`

> 이걸 놓치면 UTC 기준 08:30 = **한국시간 17:30**에 브리핑이 옵니다. 다음 날 아침에 아무것도 안 와서 원인을 한참 찾게 되는 항목입니다.

### 4-6. 전체 저장

- [ ] `이력 조회` — 자격증명 + 스프레드시트 ID
- [ ] `이력 기록` — 자격증명 + 스프레드시트 ID + 16컬럼 매핑 표시 확인
- [ ] `Gemini Chat Model` — 자격증명 + 모델명

## STEP 5. RSS 3개 개별 실행 확인 (T-01)

### 실패했을 때

특정 매체에서 0건이 나오거나 에러가 나면:

2. XML이 보이면 → n8n 쪽 일시 오류. 재시도.
3. 404 / 페이지 없음이 뜨면 → 피드 주소가 바뀐 것입니다. 해당 매체 사이트에서 "RSS" 를 검색해 현재 주소를 찾아 노드 URL을 교체하세요.

## STEP 6. 1회차 수동 실행 (T-03 · T-04 · T-09 · T-11 · T-12 · T-16)

1. 캔버스 하단 중앙 **`Execute Workflow`** 버튼 클릭
2. 노드들이 순서대로 초록색으로 바뀌는 것을 지켜봅니다

### 6-1. 노드별 확인

| 노드 | 확인 내용 | 기대값 |
| --- | --- | --- |
| `정규화+시간창` | OUTPUT의 `normalized_url` | `utm_source=...` 같은 추적 파라미터가 **제거**돼 있음 (T-03) |
| `정규화+시간창` | OUTPUT의 `published_at` 중 가장 오래된 값 | 실행 시각 기준 24시간 이내 (T-04) |
| `중복대조+키워드필터` | OUTPUT 아이템 수 | 정규화보다 크게 줄어 있음. 제목에 연예·스포츠 없음 (T-07) |
| `중복대조+키워드필터` | 아무 아이템의 `_stats` | `dup_blocked: 0` (첫 실행이라 이력이 없음) |
| `상한+배치` | OUTPUT 아이템 수 | **4개 이하** (배치 수 = LLM 호출 수). 이 숫자가 5를 넘으면 429 위험 |
| `상한+배치` | `_stats`의 `llm_selected` / `llm_skipped` | 선발 40건 이하 / 나머지가 상한 제외 건수 |
| `LLM 요약+중요도` | OUTPUT의 `output.results` | 배열이며, 길이가 해당 배치의 `count`와 같음 (T-09) |
| `검증 안전판` | OUTPUT 아이템 수 | **`llm_selected`와 같아야 함.** 배치가 풀려 기사 1건 = 아이템 1개 |
| `검증 안전판` | OUTPUT 내용 | `title`, `url_hash` 등 원본 메타가 복원돼 있음 |
| `브리핑 조립` | OUTPUT의 `content` | 사람이 읽을 수 있는 메시지 문자열 |

### 6-2. Discord 확인 (T-11 · T-12)

## STEP 7. ★ 2회차 실행 = 중복 차단 검증 (T-05 · T-06)

**요청서 REQ-03의 합격 여부가 결정되는 단계입니다.** STEP 6 직후에 바로 하세요 (RSS 내용이 거의 그대로여야 검증이 됩니다).

### 7-1. 실행 전 기록

STEP 6의 결과에서 아래 두 숫자를 메모합니다.

- `중복대조+키워드필터` 노드의 OUTPUT 아이템 수 → **N₁**
- 시트의 데이터 행 수 (헤더 제외) → **N₁과 같아야 함**

### 7-2. 2회차 실행

캔버스에서 **`Execute Workflow`** 를 **한 번 더** 클릭합니다.

### 7-3. 합격 기준 3가지

| # | 확인 위치 | 합격 기준 |
| --- | --- | --- |
| ① | `중복대조+키워드필터` 노드의 `_stats` | **`dup_blocked` 가 N₁ 근처의 큰 값** (1회차 기사가 전부 걸러짐) |
| ② | `LLM 요약+중요도` 노드 | **실행되지 않았거나(회색), 실행됐어도 아이템 수가 0~소수** ← REQ-03의 "LLM 호출 이전 차단" 증거 (T-06) |
| ③ | 시트 `url_hash` 열 | **같은 값이 두 번 나오지 않음** |

### 7-4. ③ 검증하는 법 (시트 함수)

시트의 빈 셀(예: `R1`)에 아래를 입력합니다.

```
=COUNTA(C2:C)-COUNTA(UNIQUE(C2:C))
```

- 결과가 **`0`** → 합격. 중복 행 없음.
- 결과가 `1` 이상 → 그 수만큼 중복이 들어갔다는 뜻. 아래 7-5로.

확인 후 이 셀은 지워도 됩니다.

### 7-5. 실패했을 때 점검 순서

`dup_blocked`가 0이거나 시트에 중복이 생겼다면, 아래를 **순서대로** 확인하세요.

1. **`이력 조회` 노드가 행을 읽었는가**
   - 노드를 열어 OUTPUT 확인. 0건이면 시트를 못 읽고 있는 것입니다.
   - Document ID와 Sheet 이름(`sent_log`)을 다시 확인하세요.
2. **시트 헤더가 정확히 `url_hash` 인가**
   - `url _hash`, `urlhash`, `URL_hash` 모두 실패합니다. C1 셀을 클릭해 수식 입력줄에서 확인하세요.
   - 앞뒤에 눈에 안 보이는 공백이 있을 수 있습니다. 의심되면 C1을 지우고 다시 타이핑하세요.
3. **노드 배선이 `이력 조회 → Limit 1 → RSS` 순서인가**
   - 캔버스에서 화살표를 눈으로 따라가세요. `이력 조회`가 RSS **왼쪽(상류)** 에 있어야 합니다.
   - 이 순서가 어긋나면 이력을 못 읽어 중복 차단이 조용히 무력화됩니다. 에러가 안 나서 가장 찾기 어려운 실패입니다.
4. **`중복대조+키워드필터` 코드의 노드명 문자열이 맞는가**
   - 코드 안에 `$('이력 조회')` 가 있습니다. 노드 이름을 바꿨다면 코드도 함께 바꿔야 합니다.
5. **두 실행에서 `url_hash`가 같게 나오는가**
   - 1회차와 2회차의 `정규화+시간창` OUTPUT에서 같은 기사의 `normalized_url`을 비교하세요. 다르다면 URL 정규화 규칙에 걸리지 않는 파라미터가 있는 것입니다.

**해야 할 일**

- [ ] 1회차 결과 N₁ 기록
- [ ] 2회차 `Execute Workflow`
- [ ] `dup_blocked` 값 확인
- [ ] `LLM 요약+중요도` 호출 0회 확인 ← REQ-03 증거
- [ ] 시트 `=COUNTA(C2:C)-COUNTA(UNIQUE(C2:C))` = 0 확인

| 브리핑에 연예 기사가 섞임 | 키워드 필터 통과 후 LLM이 중요도 4+ 부여 | `중복대조+키워드필터`의 `BLOCK` 배열에 키워드 추가 |
| 브리핑이 매일 0건 | 중요도 기준이 너무 높거나 필터가 과하게 엄격 | 시트의 `importance` 분포 확인. 대부분 3이면 프롬프트 기준 조정 |
| Discord 400 에러 | 메시지 2,000자 초과 | `브리핑 조립`의 `HARD_LIMIT` 확인. 기본값이면 발생하지 않아야 함 |
| **LLM 노드에서 429** | Gemini 무료 티어 **분당 5회 / 일일 250회** 제한 | 부록 D 참고. `상한+배치` 노드의 OUTPUT 아이템 수가 **5개 이하**인지 먼저 확인 |
| 429가 계속 남 | 배치 수가 5를 넘거나, 하루에 여러 번 실행함 | `상한+배치`의 `LLM_MAX`를 30으로 낮추거나 `BATCH_SIZE`를 15로 올림 (호출 수 = LLM_MAX ÷ BATCH_SIZE) |
| 브리핑 기사 수가 적음 | 상한 40건에 밀림 | 카운트 줄의 `상한제외 N` 확인. 상시 크면 `LLM_MAX` 상향 또는 필터를 더 조임 |
| **`sent=TRUE` 수 > 실제 발송 수** | `이력 기록`이 `브리핑 조립`보다 먼저 실행 (v1.3 이하) | **부록 F** |
| 브리핑에 `… 외 N건` 이 매일 뜸 | 중요도 4+ 기사가 2,000자에 안 들어감 | 정상. 잘린 기사는 다음 날 재도전. 상시 5건 이상이면 부록 F-7 |
| 요약이 엉뚱한 기사 내용 | 배치 응답의 `id`가 밀림 | `검증 안전판`이 id로 짝지으므로 원칙상 발생 안 함. 발생 시 `BATCH_SIZE`를 5로 낮춤 |
| `V7_missing_in_batch` 다발 | 한 배치에 기사가 너무 많아 LLM이 일부를 빠뜨림 | `BATCH_SIZE`를 10 → 5로 낮춤 |
| 워크플로우가 중간에 멈춤 | 어느 노드의 `On Error`가 `Stop Workflow` | RSS 3개와 LLM 노드가 `Continue`인지 확인 |
| **메시지가 매체별로 3통 옴** | RSS 3개를 `정규화+시간창`에 직결 (Merge 노드 누락) | **부록 E** |
| 노드 배지에 `✓3`이 붙음 | 위와 같은 원인 (하류 체인이 3번 실행) | **부록 E** |
| Merge 노드에서 멈춰 진행이 안 됨 | 실패한 RSS 노드가 아이템을 전혀 안 내보냄 | RSS 3개의 `Always Output Data`가 ON인지 확인 |

## 부록 D. v1.1 → v1.2 업데이트 (429 오류 대응)

### D-1. 무엇이 왜 바뀌었나

첫 실행에서 이런 오류를 보셨다면 이 부록이 해당됩니다.

```
[GoogleGenerativeAI Error]: [429 Too Many Requests] You exceeded your current quota
Quota exceeded for metric: generate_content_free_tier_requests, limit: 5, model: gemini-2.5-flash
```

**`limit: 5` = 분당 5요청**입니다. 원인은 두 겹입니다.

| 원인 | 설명 |
| --- | --- |
| 무료 티어 한도 | 분당 5회 / 일일 250회. 건별 호출이면 하루 수백 건에서 반드시 걸림 |
| **필터가 너무 느슨했음** | 피드 3개가 전부 경제면인데 `시장·경제·기업` 같은 일반 단어로 통과시켜 **188건 전량 통과** |

세 가지를 함께 고쳤습니다.

| 변경 | 내용 | 효과 |
| --- | --- | --- |
| 필터 강화 | `기준금리·코스피·환율·영업이익` 같은 **STRONG 키워드 1개 이상 필수** | 188건 → 60~80건 수준 |
| 일일 상한 | `filter_score` 상위 **40건**만 LLM으로 | 40건 고정 |
| 배치 요약 | **10건씩 묶어** 한 번에 요약 | **호출 4회** |

결과: **188회 → 4회.** 분당 5회 한도 안에 들어옵니다.

> 상한 40건에 밀린 기사는 **시트에 기록하지 않습니다.** 기록하면 중복 키가 생겨 내일 다시 평가받을 기회가 사라지기 때문입니다. 내일 피드에 남아 있으면 다시 경쟁합니다.

### D-2. 적용 방법 — 재import 권장 (10분)

노드를 하나하나 손으로 고치는 것보다 **다시 import 하는 편이 안전하고 빠릅니다.** 코드가 4개 노드에 걸쳐 바뀌었기 때문입니다.

1. **기존 워크플로우를 비활성화** — 우측 상단 토글을 `Inactive`로
2. 기존 워크플로우 이름을 `금융 뉴스 브리핑 Agent (구버전)`으로 변경 후 Save (혹시 모를 대비용, 나중에 삭제)
3. `Overview` → `⋮` → **`Import from File...`** → 갱신된 `workflow/finance_news_briefing.json` 선택
4. **STEP 4를 다시 수행** (자격증명·ID·URL 4곳 + 타임존)
   - 메모장에 보관한 스프레드시트 ID와 웹훅 URL을 재사용하면 5분이면 끝납니다
   - **시트는 그대로 두세요.** 헤더 16개는 v1.2에서도 동일합니다
5. Save
6. `Execute Workflow`로 1회 실행 → **`상한+배치` 노드의 OUTPUT 아이템 수가 4개 이하**인지 확인
7. 정상이면 새 워크플로우를 `Active`로, 구버전은 삭제

### D-3. 실행 후 확인할 것

| 확인 위치 | 기대값 | 어긋나면 |
| --- | --- | --- |
| `중복대조+키워드필터` OUTPUT 수 | 이전(188건)보다 크게 줄어듦 | 정상. 필터 강화 효과 |
| **`상한+배치` OUTPUT 수** | **4개 이하** ← 이게 LLM 호출 수 | 5개 초과면 `LLM_MAX`를 30으로 낮추세요 |
| `LLM 요약+중요도` | 429 없이 완주 | 여전히 429면 D-5 |
| `검증 안전판` OUTPUT 수 | `상한+배치`의 `llm_selected` 값과 동일 | 다르면 배치 해체 문제. `review_flags` 확인 |
| 시트 행 수 | `llm_selected` 만큼만 증가 | 상한 제외분이 안 들어갔는지 확인 |
| Discord 카운트 줄 | `… → LLM대상 40건(상한제외 15) → …` 구간이 보임 | 상한 제외가 0건인 날은 이 구간이 생략됨 (정상) |

### D-4. 조절 가능한 상수

`상한+배치` 노드 상단에 있습니다. **호출 수 = `LLM_MAX` ÷ `BATCH_SIZE`** 이고, 이 값이 **5 이하**여야 무료 티어에서 안전합니다.

| 상수 | 기본값 | 올리면 | 내리면 |
| --- | --- | --- | --- |
| `LLM_MAX` | `40` | 더 많은 기사를 검토 (호출 수 증가) | 429 위험 감소, 놓치는 기사 증가 |
| `BATCH_SIZE` | `10` | 호출 수 감소, 대신 LLM이 일부를 빠뜨릴 위험(`V7`) 증가 | 정확도 상승, 호출 수 증가 |

권장 조합:

| 상황 | `LLM_MAX` | `BATCH_SIZE` | 호출 수 |
| --- | --- | --- | --- |
| 기본 | 40 | 10 | 4회 |
| 429가 계속 날 때 | 30 | 15 | 2회 |
| `V7_missing_in_batch`가 잦을 때 | 25 | 5 | 5회 |
| 유료 티어 전환 후 | 100 | 10 | 10회 |

### D-5. 그래도 429가 날 때

1. **하루에 여러 번 실행하지 않았는지** — 일일 250회 한도는 실행 단위가 아니라 하루 누적입니다. 테스트를 반복하면 금방 찹니다. 다음 날까지 기다리거나 D-6.
2. **`상한+배치` OUTPUT이 5개 이하인지** — 6개 이상이면 상수 조정 (D-4)
3. **재시도 대기가 65초인지** — `LLM 요약+중요도` 노드 → `Settings` → `Retry On Fail` ON, `Wait Between Tries` = `65000`. 기본값 2초로는 재시도가 전부 같은 429를 받습니다.
4. **다른 워크플로우가 같은 API 키를 쓰고 있지 않은지** — 한도는 키 단위로 공유됩니다.

### D-6. 대안: 모델 변경 또는 유료 전환

- **모델 변경**: `Gemini Chat Model` 노드에서 `models/gemini-2.0-flash` 등으로 바꾸면 모델별 한도가 따로 잡혀 있어 여유가 생기는 경우가 있습니다. 요약·분류 용도라 품질 차이는 크지 않습니다.
- **유료 전환**: [Google AI Studio](https://aistudio.google.com/apikey)에서 결제를 연결하면 분당 한도가 크게 올라갑니다. 다만 **필터 강화와 상한은 그대로 두시길 권합니다.** 한도가 풀려도 하루 188건을 요약하는 것은 불필요한 비용이고, 브리핑 품질에도 도움이 되지 않습니다.

## 부록 E. Discord 메시지가 매체별로 여러 통 올 때 (v1.3)

### E-1. 증상

한 번 실행했는데 Discord에 이런 메시지가 **여러 통** 옵니다.

```
📭 오늘의 금융 브리핑 (2026-08-06)
수집 120건 → 시간창 120건 → 중복제외 84건 → 금융필터 0건 → 중요도4+ 0건   ← 연합뉴스분

📭 오늘의 금융 브리핑 (2026-08-06)
수집 50건 → 시간창 50건 → 중복제외 40건 → 금융필터 0건 → 중요도4+ 0건     ← 한국경제분

📭 오늘의 금융 브리핑 (2026-08-06)
수집 50건 → 시간창 34건 → 중복제외 18건 → 금융필터 0건 → 중요도4+ 0건     ← 매일경제분
```

캔버스에서 `정규화+시간창` 이후 노드들의 배지에 **`✓3`** 이 표시되고, 노드를 열면 `Run 1 of 3` / `2 of 3` / `3 of 3` 드롭다운이 보입니다.

### E-2. 원인

**n8n은 한 노드의 같은 입력에 연결이 여러 개 들어와도 병합하지 않습니다.** 대신 **연결 수만큼 하류 체인 전체를 반복 실행**합니다.

RSS 3개를 `정규화+시간창`에 직접 연결하면:

```
정규화 → 중복대조 → 상한+배치 → LLM → 검증 → 이력기록 → 브리핑조립 → Discord 발송
```

이 사슬이 **3번** 돌고, `Discord 발송`도 3번 실행되어 메시지가 3통 나갑니다. REQ-06("기사가 5건이면 메시지 1개")의 정면 위반입니다.

> `Run 1 of 3`은 "실행을 3번 눌렀다"는 뜻이 아니라 **"이번 한 번의 실행 안에서 이 노드가 3번 돌았다"** 는 뜻입니다. 실행 횟수 이력은 좌측 `Executions` 메뉴에서 봅니다. 두 가지를 혼동하기 쉬우니 주의하세요.

### E-3. 해결 — `RSS 병합`(Merge) 노드

RSS 3개와 `정규화+시간창` **사이에** Merge 노드를 넣어 한 줄기로 합칩니다.

| 설정 | 값 |
| --- | --- |
| 노드 타입 | **Merge** |
| Mode | **Append** |
| Number of Inputs | **3** |
| 연결 | 연합뉴스 → Input 1, 한국경제 → Input 2, 매일경제 → Input 3 |
| 출력 | `정규화+시간창` |

Append는 세 입력이 다 도착할 때까지 기다렸다가 아이템을 이어 붙여 내보내므로, 하류 체인이 정확히 **1회**만 실행됩니다.

### E-4. 적용 방법 — 재import 권장

부록 D-2와 동일합니다.

1. 기존 워크플로우 `Inactive` → 이름에 `(구버전)` 붙여 보관
2. 갱신된 `workflow/finance_news_briefing.json` 재import
3. **STEP 4만 다시** (자격증명·스프레드시트 ID·웹훅 URL·타임존). 시트는 그대로 두세요
4. Save → `Execute Workflow`

**손으로 고치고 싶다면**: 캔버스에서 `+` → `Merge` 검색 → 추가 → Mode `Append`, Number of Inputs `3` 설정 → RSS 3개의 출력 화살표를 각각 Merge의 Input 1/2/3으로 다시 연결 → Merge 출력을 `정규화+시간창`에 연결. 기존 RSS→정규화 화살표 3개는 삭제해야 합니다.

### E-5. 고쳐졌는지 확인하는 법

`Execute Workflow` 한 번 실행 후:

| 확인 위치 | 정상 | 비정상 |
| --- | --- | --- |
| `정규화+시간창` 이후 노드 배지 | 숫자 없음 (1회 실행) | `✓3` |
| `RSS 병합` OUTPUT 아이템 수 | RSS 3개 출력의 **합계** (예: 220건) | — |
| `Discord 발송` OUTPUT | **1 item** | 3 items |
| Discord 채널 | 메시지 **1통** | 3통 |

### E-6. 함께 확인할 것 — `금융필터 0건`

위 예시 메시지 3통 모두 `금융필터 0건`인데, 이건 **정상일 수 있습니다.**

매일경제 분을 보면 `시간창 34건 → 중복제외 18건 → 금융필터 0건`입니다. 직전 실행에서 이미 16건이 필터를 통과해 시트에 기록됐고, 그 16건이 이번엔 중복으로 차단(34 − 18 = 16)된 것입니다. 남은 18건은 이전에도 키워드 필터에서 탈락했던 기사들이라 이번에도 그대로 탈락합니다.

즉 **연속으로 실행하면 두 번째부터 `금융필터 0건`이 나오는 게 정상**입니다. 중복 차단이 제대로 작동한다는 증거이기도 합니다.

다만 **시트를 비운 상태에서 첫 실행인데도 `금융필터 0건`** 이라면 필터가 과하게 엄격한 것입니다. 그때는 `중복대조+키워드필터` 노드의 `STRONG` 배열에 실제 기사 제목에서 본 금융 용어를 추가하세요.

## 부록 F. 발송되지 않은 기사가 `sent=TRUE`로 기록될 때 (v1.4)

### F-1. 증상

브리핑에는 8건이 왔는데, 시트에서 `sent=TRUE`인 행을 세어 보면 **17건**입니다.

메시지 마지막 줄에도 단서가 있습니다.

```
… 외 9건
수집 220건 → … → 중요도4+ 17건
```

"중요도4+ 17건"이라고 적혀 있는데 실제 본문에는 `[1]`~`[8]`까지 8개 블록뿐입니다.

### F-2. 원인

Discord 일반 메시지는 **본문 2,000자 제한**이 있습니다. `브리핑 조립`이 이 한도를 지키려고 뒤쪽 기사를 잘라냈습니다.

```
중요도 4+          17건
 → MAX_ARTICLES=10  10건
 → 2,000자 길이 가드  8건   ← 실제 발송
```

문제는 **`이력 기록`(시트 저장)이 `브리핑 조립`보다 먼저 실행**된다는 점입니다. 시트에 쓰는 시점엔 몇 건이 잘릴지 알 수 없으니, 중요도만 보고 17건 전부를 `sent=TRUE`로 찍었습니다.

그 결과 **발송되지 않은 9건의 `url_hash`가 시트에 남아, 다음 날 중복 차단되어 영영 발송되지 않습니다.** 중요도 4~5짜리 기사가 아무 흔적 없이 사라지는 겁니다.

### F-3. 해결 — `발송선별` 노드 신설 + 순서 변경

```
[v1.3] 검증 안전판 → 이력 기록 → 브리핑 조립 → Discord
                     ↑ 무엇이 발송될지 모른 채 기록

[v1.4] 검증 안전판 → 발송선별 → 이력 기록 → 브리핑 조립 → Discord
                     ↑ 발송분 확정   ↑ 확정된 결과만 기록
```

`발송선별`이 하는 일:

| 기사 유형 | `sent` 값 | 시트 기록 |
| --- | --- | --- |
| 실제로 메시지에 들어간 기사 | `TRUE` | ✓ |
| 중요도 1~3 / 검증 실패 | `FALSE` | ✓ |
| 중요도 4+ 인데 길이 제한에 잘린 기사 | `FALSE` | ✓ |

함께 바뀐 것:

- **메시지 압축**: 요약을 첫 문장·90자로 줄이고 기사 간 빈 줄을 없애 같은 2,000자에 **8건 → 10건**이 들어갑니다.
- **"외 N건" 문구**: `… 외 7건은 길이 제한으로 생략 (시트 sent=FALSE 로 확인)`

### F-4. 잘린 기사는 다음 날 재발송되지 않습니다 (중요)

이 시스템은 **매일 아침 최신 뉴스만** 전달합니다. 시간 창이 직전 24시간이므로, 오늘 잘린 기사는 내일이면 창 밖으로 나가 다시 수집되지 않습니다. **이건 의도된 동작입니다** — 어제 기사가 오늘 브리핑에 섞이면 안 되기 때문입니다.

같은 사건이 정말 중요하다면 **오늘 새 기사로 다시 보도됩니다.** 그 기사는 URL이 다르므로 중복 차단에 걸리지 않고, 오늘의 맥락에서 중요도를 새로 부여받아 정상적으로 후보가 됩니다.

> 초기 개발 과정에서 시간 창을 48시간으로 넓혀 잘린 기사를 재발송하는 방안을 검토했다가 **철회**했습니다. 과거 기사가 브리핑에 실리는 부작용이 요구사항에 어긋나기 때문입니다. 혹시 `정규화+시간창` 노드의 `WINDOW_HOURS`가 `48`로 되어 있다면 **`24`로 되돌리세요.**

### F-5. 기존 시트 정리 (선택)

v1.3 이하로 돌린 실행이 있다면, 시트에 **실제로는 발송되지 않았는데 `sent=TRUE`로 찍힌 행**이 남아 있습니다. 값이 사실과 다를 뿐 중복 차단 로직(`url_hash` 기준)에는 영향이 없으므로 **그냥 두셔도 무방합니다.**

기록을 정확히 맞추고 싶다면, 그날 Discord 메시지에 실제로 나온 기사 제목과 대조해 나머지 행의 `sent`를 `FALSE`로 수정하시면 됩니다. 행을 삭제할 필요는 없습니다.

### F-6. 고쳐졌는지 확인

`Execute Workflow` 실행 후:

| 확인 | 정상 |
| --- | --- |
| Discord 메시지의 `[N]` 블록 개수 | 시트에서 이번 `run_id`의 `sent=TRUE` 행 수와 **정확히 일치** |
| `발송선별` OUTPUT 아이템 수 | `검증 안전판` OUTPUT 수와 **동일** (LLM 처리분 전부 기록) |
| 시트에 `sent=TRUE`인데 메시지에 없는 기사 | **0건** |
| 메시지 마지막 | `… 외 N건은 길이 제한으로 생략` (잘린 기사가 있을 때만) |
| `정규화+시간창`의 `WINDOW_HOURS` | **`24`** (48이면 과거 기사가 섞임) |

시트에서 오늘 발송분만 세는 법 — 빈 셀에 입력:

```
=COUNTIFS(A2:A, TEXT(TODAY(),"yyyy-mm-dd"), N2:N, "TRUE")
```

이 값이 Discord 메시지의 `[N]` 블록 개수와 같으면 정상입니다.

### F-7. 잘린 기사가 매일 많다면 (v1.6에서 대응 완료)

잘린 기사는 재발송되지 않으므로(F-4), `… 외 N건`이 매일 크면 중요 기사가 계속 전달되지 않습니다.

**`MIN_IMPORTANCE`를 5로 올리는 것은 안 됩니다.** REQ-05가 "디스코드 발송 대상은 중요도 4 이상"으로 못 박고 있어 요구사항 위반입니다.

v1.6에서는 대신 **판정 정확도**를 고쳤습니다. 중요도 4+가 17건까지 부푼 것은 LLM이 요청서 기준을 느슨하게 적용한 결과였습니다.

| 실제 사례 | LLM 판정 | 요청서 기준 |
| --- | --- | --- |
| 한화證 "롯데칠성 투자의견·목표가 하향" | ⭐4 | **3** (`애널리스트 리포트 인용`) |
| [특징주] 현대백화점 실적 실망에 5%↓ | ⭐4 | **3** (개별 종목 등락) |

그래서 프롬프트에 **보조 판정 지침**을 넣어 이런 유형을 3으로 명시적 강등했습니다. REQ-05의 판정 기준 5줄 자체는 **요청서 원문 그대로** 유지합니다(요청서가 "프롬프트에 명시할 것"을 요구하므로 이 문장은 절대 수정하지 않습니다).

**여전히 `… 외 N건`이 자주 뜬다면** — `LLM 요약+중요도` 노드의 System 메시지에서 `[중요도 4 이상은 엄격하게 판정하십시오]` 섹션에 강등 대상 유형을 더 추가하세요. 시트에서 `sent=FALSE` + `importance=4`인 행의 제목을 훑어보면 어떤 유형이 과대평가되는지 바로 보입니다.

마지막 수단은 Discord Embed 전환(한 메시지 6,000자, 17~20건)이지만 현재는 사용하지 않기로 했습니다.

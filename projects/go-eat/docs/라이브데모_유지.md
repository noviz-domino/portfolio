# 라이브 데모 유지

## 왜 필요한가

이 프로젝트는 Supabase 무료 플랜을 쓴다. 무료 플랜은 **DB 활동이 부족하면 프로젝트를 자동으로 일시정지**시킨다. 정지되면 대시보드에서 손으로 재개할 때까지 앱 전체가 동작하지 않는다.

배포 주소를 포트폴리오에 걸어둔 이상, 누군가 링크를 눌렀을 때 죽어 있으면 안 된다. 그래서 사람이 챙기지 않아도 유지되도록 자동화했다.

> Vercel 배포는 만료되지 않는다. Hobby 플랜에 기간 제한이 없으므로 별도 조치가 필요 없다. **갱신이 필요한 건 Supabase뿐이다.**

## 어떻게 동작하는가

포트폴리오 저장소([noviz-domino/portfolio](https://github.com/noviz-domino/portfolio))의 GitHub Actions가 **매일** 이 프로젝트의 `keep_alive` 테이블에 **쓰기 요청**을 보낸다.

```
GitHub Actions (매일 00:17 UTC)
  └─ PATCH /rest/v1/keep_alive?id=eq.1   (last_ping 을 현재 시각으로 갱신)
       └─ 쓰기가 발생 → Supabase가 활동으로 인식 → 정지 타이머 초기화
            └─ 저장된 시각을 다시 읽어 대조 → 실제로 반영됐는지 확인
```

## 읽기로는 막을 수 없었다

처음에는 3일마다 `SELECT` 한 건만 보냈다. 그런데 **두 차례 정지됐다.**

결정적이었던 건 2026-09-07이다. 스케줄 핑이 `HTTP 200`으로 성공한 지 **두 시간 뒤에** 정지 통보 메일이 왔다. 메일에 적힌 프로젝트 ID가 핑이 찌르던 대상과 동일했으니, 요청은 제대로 갔는데도 정지된 것이다.

그래서 세 가지를 바꿨다.

- **읽기 대신 쓰기.** 읽기는 활동으로 인정되지 않는다고 판단했다.
- **3일마다에서 매일로.** 공식 문서가 "지난 주 동안 매일 몇 가지 요청"을 권장한다.
- **응답 코드만 믿지 않는다.** 아래 항목 참고.

자세한 경위와 원인 분석은 포트폴리오 저장소의 [supabase-keepalive.md](https://github.com/noviz-domino/portfolio/blob/main/docs/supabase-keepalive.md)에 사고 기록으로 남겨두었다.

## 왜 응답 코드만으로는 판단할 수 없나

RLS 정책 때문에 갱신이 막히면, PostgREST는 오류를 내지 않고 **`200`과 빈 배열**을 돌려준다. "갱신할 수 있는 행이 0개였다"를 정상 처리로 보기 때문이다.

즉 `200`만 보면 성공과 구별이 안 된다. 그래서 워크플로는 **보낸 시각과 DB에 저장된 시각을 초 단위로 대조**하고, 값이 실제로 바뀐 것을 확인한 뒤에만 성공으로 처리한다.

## 준비된 것

핑 전용 테이블이다. 서비스 데이터는 담지 않는다. 여러 번 실행해도 안전하다.

```sql
create table if not exists public.keep_alive (
  id bigint generated by default as identity primary key,
  created_at timestamptz not null default now(),
  last_ping timestamptz not null default now()    -- 핑이 매번 갱신하는 컬럼
);

-- 이미 테이블이 있는 경우를 위해 컬럼만 따로 추가한다.
alter table public.keep_alive
  add column if not exists last_ping timestamptz not null default now();

-- 갱신 대상이 될 행 하나를 확보한다.
insert into public.keep_alive (id)
values (1)
on conflict (id) do nothing;

alter table public.keep_alive enable row level security;

-- 조회 허용. 이 테이블에는 아무 정보도 없으므로 공개해도 위험이 없다.
drop policy if exists "keep_alive 조회 허용" on public.keep_alive;
create policy "keep_alive 조회 허용"
  on public.keep_alive
  for select
  using (true);

-- 갱신 허용. 대상을 id = 1 한 행으로 못박는다.
drop policy if exists "keep_alive 갱신 허용" on public.keep_alive;
create policy "keep_alive 갱신 허용"
  on public.keep_alive
  for update
  using (id = 1)          -- 어떤 기존 행을 건드릴 수 있는지
  with check (id = 1);    -- 바뀐 결과가 만족해야 하는 조건
```

**`INSERT`와 `DELETE` 정책은 일부러 만들지 않았다.** RLS는 허용하지 않은 동작을 기본 차단하므로 이것만으로 행 추가와 삭제가 막힌다.

행을 늘릴 수 있게 열어두면 `anon` 키를 아는 사람이 대량으로 밀어넣어 무료 용량 500MB를 채울 수 있다. 핑에 필요한 최소 권한만 여는 편이 안전하다.

## 인증 키

핑에는 `NEXT_PUBLIC_SUPABASE_ANON_KEY`만 쓴다. 브라우저에 그대로 내려가는 공개 키라 유출 위험이 없다.

**`SUPABASE_SERVICE_ROLE_KEY`는 쓰지 않는다.** RLS를 전부 우회하는 DB 전체 권한 키이므로 단순 핑 용도에 쓸 이유가 없고, 워크플로에 노출될 위험만 늘어난다.

## 점검 방법

포트폴리오 저장소 → **Actions** 탭 → `Supabase Keep-Alive` → 최근 실행이 초록색인지 확인한다. 수동 실행은 **Run workflow** 버튼.

`HTTP 200`만 보지 않고 아래 문장이 함께 찍혔는지 확인한다.

```
정상. last_ping 이 2026-09-07T07:54:19 로 갱신되었습니다.
```

DB에서 직접 확인하려면 Table Editor에서 `keep_alive` 테이블의 `last_ping` 값을 본다. 오늘 날짜가 아니면 핑이 끊긴 것이다.

| 증상 | 원인 | 조치 |
|---|---|---|
| `HTTP 404` | `keep_alive` 테이블 없음 | 위 SQL 실행 |
| `HTTP 401` / `403` | 키가 틀렸음 | 시크릿 값 재등록 |
| `갱신된 행이 없습니다` | `id = 1` 행이 없거나 `UPDATE` 정책 누락 | 위 SQL 재실행 |
| `HTTP 5xx` 또는 `exit 6` | 프로젝트가 이미 정지됨 | 대시보드에서 재개 후 수동 실행 |

## 한계

**이 자동화는 완전한 보장이 아니다.** 무료 플랜의 정지 판정 기준이 공식 문서에 정확히 명시되어 있지 않고, 이미 한 번 "해결됐다"고 판단했다가 번복한 적이 있다.

정지를 확실히 막는 유일한 방법은 **Pro 플랜 업그레이드**(월 $25)다. 그래서 README에서는 데모 링크와 함께 화면 캡처를 안내한다. 데모가 죽어도 무엇을 만들었는지는 전달되어야 한다.

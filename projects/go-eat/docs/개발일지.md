### 9. 로그인 기능 + RLS 적용

**시작 전에 확인한 것 — Next.js 16의 달라진 점**

`AGENTS.md`의 지시에 따라 코드 작성 전 `node_modules/next/dist/docs/`를 먼저 확인했다.
그 결과 **Supabase 공식 문서를 그대로 따라 하면 안 되는 지점**을 발견했다.

| 항목 | 일반적인 안내 (Next 15 이하) | **Next.js 16** |
| --- | --- | --- |
| 요청 가로채는 파일 | `middleware.ts` | **`proxy.ts`** (이름이 바뀜, 기능은 동일) |
| `cookies()` | 동기 함수 | **async 함수** (`await cookies()`) |

> 문서를 안 읽고 `middleware.ts`를 만들었다면 **파일이 아예 실행되지 않아서**
> "왜 로그인이 유지가 안 되지?"를 한참 헤맸을 것이다.

**세션 방식 결정 — 쿠키 기반 (`@supabase/ssr`)**

- 대안: 브라우저 localStorage에만 세션을 두는 간단한 방식
- 쿠키 방식을 택한 이유: 서버가 "누가 로그인했는지" 알 수 있어야
  ① 서버에서 내 데이터만 걸러 보내고 ② 비로그인 접근을 서버에서 차단할 수 있다.
  나중에 실제 서비스로 확장할 때 뜯어고치지 않으려면 처음부터 이 구조여야 한다.

**이메일 인증 설정**

- Supabase 기본값은 인증 **켜짐**(`mailer_autoconfirm: false`)이었다.
- 무료 프로젝트의 메일 발송은 **시간당 2건 제한**이라 실습 중 계정 테스트가 막힌다.
  → 대시보드에서 `Authentication → Sign In/Providers → Email → Confirm email` **OFF**
- 단, **코드는 양쪽 다 처리**하게 작성했다. 인증이 켜져 있으면 세션이 없는 채로
  가입만 되므로 "가입 확인 메일을 보냈습니다" 안내를 띄운다.
  → **실제 서비스로 갈 때 설정만 다시 켜면 되고 코드 수정은 없다.**

**데이터베이스 변경 (마이그레이션 `enable_rls_on_restaurants`)**

```sql
delete from restaurants where user_id is null;        -- 주인 없는 테스트 3건 정리
alter table restaurants alter column user_id set not null;
alter table restaurants enable row level security;
-- select / insert / update / delete 4개 정책 모두 auth.uid() = user_id
```

**Server Action 작성 전 확인한 것 (`AGENTS.md` 규칙)**

`node_modules/next/dist/docs`에서 데이터 변경(mutating-data) 문서를 먼저 읽었다.
중요한 경고를 발견: **Server Function은 화면의 폼을 거치지 않고 누구나 직접
POST 요청으로 호출할 수 있다.** 즉 브라우저 쪽 `disabled` 버튼이나 `required`
속성은 사용자 편의일 뿐, **보안 장치가 아니다.** 그래서 `createRestaurant` 안에서
① 로그인 여부 ② 이름·카테고리 값을 서버가 다시 검사하도록 만들었다.

**데이터 규칙 구현**

- `user_id`는 클라이언트가 보낸 값을 쓰지 않고, 서버가 `getUser()`로 확인한
  사용자 id를 그대로 넣는다. (요청 위조로 남의 이름으로 등록하는 것을 원천 차단)
- `visited=false`일 때는 `rating`·`visited_at`을 무조건 `null`로 저장한다
  (기획서의 데이터 규칙). `rating`은 1~5 범위를 벗어나면 거부한다.

**브라우저로 실제 검증한 것**

| 시나리오 | 방법 | 결과 |
| --- | --- | --- |
| 최소 입력(이름+카테고리만) | 정상 입력 후 저장 | 목록에 "아직 안 가봄"으로 추가, 진행률 분모만 증가 ✅ |
| 방문 정보 포함 | 방문 체크 → 방문일·별점(4점)·메모까지 입력 | 목록에 `★★★★ · 날짜 방문` + 메모 표시, 진행률 분자·분모 둘 다 증가 ✅ |
| **필수값 우회 시도** | 개발자도구로 저장 버튼의 `disabled`와 `required` 속성을 강제로 제거한 뒤 빈 이름으로 제출 | **서버가 "가게 이름을 입력해주세요." 에러로 거부** — 페이지 이동 없음. 서버 검증이 브라우저 우회에도 실제로 작동함을 확인 |

Supabase에서 저장된 행을 직접 조회해 `user_id`가 로그인한 계정과 일치하고,
미방문 건의 `rating`·`visited_at`이 정확히 `null`인 것도 확인했다.

| `src/app/page.tsx` | 목록 카드를 `<Link>`로 감싸 상세 화면과 연결 |

**Next.js 16 문서에서 확인한 것**

`params`가 **Promise**로 바뀌었다 (`params: Promise<{ id: string }>` → `await params`).
동적 라우트(`[id]`)를 쓰는 화면은 전부 이 규칙을 따라야 한다.

**검증 로직을 분리한 이유**

`createRestaurant`와 `updateRestaurant`가 같은 검증 규칙(이름·카테고리 필수,
방문 여부에 따른 별점·방문일 처리)을 써야 했다. 그런데 `"use server"`가 선언된
파일 안에서는 **export된 모든 함수가 자동으로 Server Action 취급**된다.
그래서 순수 검증 함수(`parseRestaurantForm`)는 `src/lib/restaurant-form.ts`라는
**별도 파일**로 뺐다. `use server` 파일에 그냥 헬퍼 함수로 놔뒀다면 그 함수도
Server Action으로 노출될 뻔했다.

**소유권 처리 방식**

- 상세·수정 페이지의 조회(`select`)는 **RLS가 알아서 걸러준다.** 남의 id로 접근하면
  `data`가 `null`로 오고, 이걸 `notFound()`로 연결했다.
- `toggleVisited`·`deleteRestaurant`도 코드에서 소유자를 따로 검사하지 않는다.
  `.eq("id", id)`만 실행하고, RLS가 실제 소유자가 아니면 **0행 처리**되게 만든다.
  즉 애플리케이션 코드가 아니라 데이터베이스가 최종 방어선이다.
- 수정 시 `user_id`는 애초에 업데이트 대상 컬럼에 넣지 않는다. 폼에 관련 입력란도 없다.

**브라우저로 실제 검증한 것**

| 시나리오 | 결과 |
| --- | --- |
| 목록 카드 클릭 → 상세 | 이름·카테고리·주소·별점·방문일·메모 전부 정확히 표시 |
| 방문 체크 토글 | 클릭 즉시 상태·버튼 문구 전환, 목록 진행률도 즉시 반영 |
| 수정 화면 진입 | 기존 값이 전부 폼에 채워짐 (별점 컴포넌트의 `defaultValue` 포함) |
| 수정 저장 | 상세 화면으로 이동(기획서 규칙), 상세·목록 둘 다 반영 |
| **삭제 — 확인창 취소** | 네트워크 로그 확인 결과 POST 요청 자체가 발생하지 않음 |
| **삭제 — 확인창 승인** | 목록에서 사라지고 진행률 정확히 갱신 |
| **다른 계정으로 상세·수정 URL 직접 접근** | 둘 다 **404** — `notFound()`가 실제로 작동 |

RLS 정책도 `pg_policies`로 직접 조회해 SELECT·INSERT·UPDATE·DELETE
네 가지 모두 `auth.uid() = user_id`로 걸려있음을 재확인했다.

**작업 중 발견한 것 — 자동화 클릭의 타이밍 이슈**

브라우저 자동화로 버튼을 좌표 클릭했을 때 폼이 제출되지 않는 경우가 있었다
(리액트 하이드레이션 타이밍 문제로 추정). `element.click()`을 JS로 직접
실행하니 안정적으로 재현됐다. 실제 사용자 클릭에는 영향 없는, 자동화 테스트
환경에서만 발견된 이슈였다.

### 12. 검색 · 방문 탭 · 카테고리 필터

**필터 상태를 URL 쿼리 파라미터로 관리하기로 결정**

`q`(검색어), `visited`(all/todo/done), `category` 세 값을 컴포넌트 state가 아니라
**주소창의 쿼리 파라미터**로 관리했다. 이렇게 하면:

- 새로고침해도 필터가 안 풀린다
- 필터가 걸린 상태의 주소를 그대로 복사해서 남에게 보낼 수 있다
- 방문 탭·카테고리는 그냥 `<Link>`로 만들 수 있어 JS 없이도 동작한다

Next.js 공식 문서(`03-layouts-and-pages.md`)에서도 "데이터베이스에서
필터링할 때는 `searchParams` prop을 쓰라"고 명시하고 있어 이 방식을 따랐다.

**Next.js 16 확인 사항**

`searchParams`도 `params`와 마찬가지로 **Promise**로 바뀌었다
(`searchParams: Promise<{ q?: string; ... }>` → `await searchParams`).
이 prop을 읽으면 페이지가 자동으로 동적 렌더링된다 (`cookies()`와 동일한 원리).

**진행률 바는 필터와 무관하게 항상 "전체" 기준**

처음 구현하려던 방식(필터링된 배열의 길이로 진행률 계산)은 틀렸을 뻔했다.
"가볼 곳" 탭을 누르면 방문 안 한 것만 보이는데, 그걸로 진행률을 계산하면
"1곳 중 0곳" 같은 이상한 숫자가 나온다. 그래서 **전체 카운트용 쿼리를
필터링 쿼리와 분리**했다.

```ts
// 진행률 계산용 — 필터 조건을 절대 걸지 않는다
const { data: allRows } = await supabase.from("restaurants").select("visited");

// 화면 표시용 — q/visited/category 필터를 여기에만 건다
let query = supabase.from("restaurants").select("*")...
```

**검색 입력 vs 탭/카테고리 — 구현 방식을 다르게 가져간 이유**

| | 방식 | 이유 |
| --- | --- | --- |
| 검색창 | 클라이언트 컴포넌트, `useRouter().replace()` + 300ms 디바운스 | 타이핑마다 서버에 요청하면 낭비. 입력을 멈춘 뒤에만 URL 갱신 |
| 방문 탭 | 서버에서 렌더링한 `<Link>` | 클릭 한 번짜리 토글이라 JS 없이도 충분. Next.js 공식 문서도 이동에는 `<Link>`를 권장 |
| 카테고리 | 클라이언트 컴포넌트, `onChange` 시 즉시 이동 | `<select>`는 클릭만으로 값이 바뀌므로 디바운스 불필요 |

**빈 상태 두 가지를 구분**

- 맛집을 **아예 하나도 등록 안 한 경우** → "첫 맛집 등록하기" (기존 그대로)
- **필터 조건에 맞는 게 없는 경우** → "조건에 맞는 맛집이 없어요" + "필터 초기화"

전체 개수(`allCount`)와 필터링된 개수(`filteredCount`)를 따로 세서 구분했다.

**브라우저로 실제 검증한 것**

| 시나리오 | 결과 |
| --- | --- |
| 이름 검색("봉평") | 해당 맛집만 표시, 진행률은 전체 기준 유지 |
| 방문 탭 3종 | 가볼 곳/갔던 곳 각각 정확히 필터링 |
| 카테고리 필터 | 한식만 선택 시 2건만 표시 |
| **검색+탭+카테고리 동시 적용** | 세 조건이 AND로 결합, 탭 링크도 다른 조건을 유지한 채 생성됨 확인 |
| 결과 0개 | "조건에 맞는 맛집이 없어요" + 초기화 버튼 → 클릭 시 전체 목록 복귀 |
| 새로고침 | URL 쿼리 기반이라 필터가 그대로 유지됨 |

**작업 중 발생한 사고 — 잘못된 탭에서 클릭**

배포 사이트 검증 중 "로그아웃 버튼 클릭"을 의도했는데, 그 탭이 실제로는
상세 화면에 머물러 있어서 `document.querySelector('button')`이 그 페이지의
**첫 번째 버튼인 "방문 체크 해제"**를 눌러버렸다. 실사용 데이터(멀티캠퍼스
간식부스)의 방문 여부가 잠깐 꺼졌고, SQL로 즉시 원복했다.
→ 여러 브라우저 탭을 동시에 다룰 때는 매 조작마다 tabId를 명시하고,
CSS 선택자를 쓸 때는 페이지마다 버튼 순서가 다르다는 걸 감안해야 한다.

### 13. 로딩·에러 처리

**Next.js 파일 컨벤션 3개 추가**

| 파일 | 역할 |
| --- | --- |
| `src/app/loading.tsx` | 데이터 조회 중 카드 모양 스켈레톤 표시 (전역, 모든 라우트 공통) |
| `src/app/error.tsx` | 예상 못한 예외 발생 시 안내 + "다시 시도" 버튼 |
| `src/app/not-found.tsx` | `notFound()` 호출 시 서비스 톤에 맞는 404 화면 |

프로젝트 규모상 라우트별로 세분화하지 않고 **`src/app/` 루트에 전역으로 하나씩**만
두기로 했다. 목록 화면이 데이터가 가장 많아 로딩이 체감되는 유일한 화면이라
전역 스켈레톤을 그대로 재사용해도 충분하다고 판단했다.

**Next.js 16에서 확인한 것 — `error.tsx`의 재시도 함수 이름이 바뀜**

인터넷에 있는 대부분의 예제는 `reset()`을 쓰라고 안내하지만, 공식 문서를
직접 열어보니 **v16.2.0부터 `unstable_retry()`가 새 이름**이었다.
`reset()`은 "다시 데이터를 안 가져오고 그냥 에러 상태만 지우기"용으로 용도가
좁아졌고, 일반적인 "다시 시도"는 `unstable_retry()`를 쓰는 게 맞다.
문서를 안 봤으면 옛날 API를 그대로 썼을 것이다.

**검증 중 발견한 것 — 이 브라우저 자동화 도구의 한계**

`loading.tsx`가 실제로 동작하는지 확인하다가 혼란스러운 상황을 겪었다.

1. 인위적으로 2초 지연을 넣고 새로고침 → 화면이 스켈레톤에서 안 풀리고 계속 멈춰있음
2. 지연 코드를 완전히 제거해도 여전히 안 풀림 (프로덕션 빌드로 바꿔도 동일)
3. 그런데 실제 세션 쿠키로 `curl`을 직접 날려보니 **서버 응답 자체에는 스켈레톤과
   실제 데이터가 둘 다 정상적으로 들어있었다**

원인은 React 19의 스트리밍 전환이 `requestAnimationFrame`으로 타이밍을 맞추는데,
이 브라우저 자동화 도구의 탭이 "화면에 실제로 그려지지 않는(비활성) 상태"일 때는
`requestAnimationFrame` 콜백 자체가 실행되지 않아서, 로딩 화면에서 실제 화면으로
바뀌는 전환이 영영 일어나지 않았던 것이다. (`screenshot` 시도 때 "pane is not
displayed" 에러가 났던 것과 같은 원인.) **앱의 버그가 아니라 테스트 도구 환경의
한계**임을 `curl` 우회로 확인했다.

반면 `error.tsx`(에러 바운더리)는 `requestAnimationFrame`에 의존하지 않는 오래된
React 메커니즘이라 이 도구에서도 정상적으로 렌더링됐고, 실제로 화면에서
"다시 시도" 버튼 클릭 → 정상 복구까지 확인할 수 있었다.

**브라우저로 실제 검증한 것**

| 시나리오 | 방법 | 결과 |
| --- | --- | --- |
| 로딩 스켈레톤 표시 | 세션 쿠키로 직접 curl | 응답에 스켈레톤+실제 데이터 둘 다 포함 확인 |
| 에러 화면 + 재시도 | 목록 페이지에 일시적으로 `throw` 추가 → 화면에서 실제 확인 | "😵 문제가 생겼어요" 표시, 코드 원복 후 "다시 시도" 클릭 → 정상 목록으로 복구 |
| 커스텀 404 | 존재하지 않는 id로 상세 화면 접근 | "🍜 그런 맛집은 없어요" + 목록으로 링크 표시 |

**기능 방향이 중간에 바뀐 이유**

처음엔 "메모 옆에 AI로 다듬기 버튼을 두고, 누르면 그 자리에서 메모 자체를 다듬는" 방식으로
구현했다. 그런데 이러면 사용자가 공들여 적은 원문이 AI 결과로 **덮어써진다**는 문제가 있었다.
그래서 방향을 바꿨다:

- 사용자가 쓴 **원문 메모는 그대로 보존** (상세 화면에 전체 표시)
- **목록 카드에는 AI가 만든 1~2줄 요약만** 표시 (`memo_summary` 별도 컬럼)
- 버튼을 누르는 방식이 아니라, **등록·수정 시 자동으로** 요약을 생성

**API 키 준비**

- Google AI Studio에서 Gemini API 키 발급, `.env.local`과 Vercel(Production·Preview)에
  `GEMINI_API_KEY`로 등록
- 처음 테스트한 `gemini-2.0-flash` 모델은 이 계정에서 무료 tier quota가 `0`이라 429 에러가 났다.
  `models` 목록 API로 사용 가능한 모델을 조회해 **`gemini-flash-lite-latest`** 로 바꾸니 정상 동작
  → 모델 이름을 하나만 믿지 말고, 실제로 호출해보고 안 되면 다른 모델을 시도해봐야 한다는 걸 배움

**DB 변경**

```sql
alter table restaurants add column memo_summary text;
```

기존에 저장된 맛집은 `memo_summary`가 `null`이다. 별도 백필 없이, 목록 카드에서
`memo_summary`가 없으면 원문 메모의 앞부분(40자)을 잘라서 대신 보여주는 **폴백**을 넣었다.
다음에 그 맛집을 수정하면 그때 진짜 요약으로 채워진다.

**구현**

| 파일 | 역할 |
| --- | --- |
| `src/app/actions/ai.ts` | `summarizeMemo(memo)` — Gemini 호출, 실패해도 `null`만 반환 (예외를 던지지 않음) |
| `src/app/actions/restaurants.ts` | `createRestaurant`·`updateRestaurant`에서 메모가 있으면 저장 직전에 `summarizeMemo` 호출 |
| `src/app/page.tsx` | 카드에 `memo_summary ?? 원문 앞 40자` 표시, `line-clamp-2`로 2줄까지만 |

**AI 호출이 실패해도 저장은 막히지 않게 설계**

`summarizeMemo`는 API 키가 없거나, 요청이 실패하거나, 응답이 비어있으면 전부 `null`을
돌려준다. 절대 예외를 던지지 않는다. 그래서 AI 쪽에 문제가 생겨도 맛집 등록·수정이라는
핵심 기능은 항상 정상 동작한다. AI 기능은 "있으면 좋은 것"이지 "없으면 전체가 멈추는 것"이면
안 된다는 원칙을 지켰다.

**브라우저로 실제 검증한 것**

| 시나리오 | 결과 |
| --- | --- |
| 대충 쓴 메모로 등록 | `memo`엔 원문 그대로, `memo_summary`엔 AI가 뽑은 핵심 한 줄("두 시 넘으면 문 닫음") 저장 |
| 목록 카드 | 요약만 표시, 원문은 안 보임 |
| 상세 화면 | 원문 전체 표시 (아까 카드에서 안 보이던 나머지 내용까지) |
| 수정 시 요약 갱신 | 예전 시드 데이터(`memo_summary` 없던 것)를 수정 폼 그대로 다시 저장 → 요약이 새로 채워짐("현금만 받음") |

**GitHub Public 여부에 대한 판단**

API 키를 GitHub private 저장소로 옮겨야 하는지 질문이 나왔는데, `.env.local`이 이미
`.gitignore`에 있어서 애초에 키가 코드에 없다. Public으로 유지해도 키가 노출되지 않고,
Vercel(GitHub App 연동)·Supabase(API 키 통신) 어느 쪽도 저장소 공개 여부와 무관하게
동작하므로 그대로 Public 유지하기로 함.

### 17. 데스크톱 전용 레이아웃 — 좌측 고정 사이드바 + 바둑판 그리드

1차 배포 후 사용자가 실제 화면을 보고 피드백: "사이드바가 그냥 위에 얹힌 열(column)이지,

  - 접힌 상태는 사용자가 고른 대로 **아이콘만** 남김 (로고 🍜, 방문탭 📋·📍·✅, +등록).

  - 모바일은 접기 버튼 자체를 숨기고(`hidden md:block`) 항상 펼쳐진 내용을 위에 스택 —
    데스크톱 전용 기능이라는 걸 명확히 함
  - `main`의 `padding-left`를 사이드바 폭과 함께 전환해야 해서, 서버 컴포넌트인

    `SidebarShell`은 오직 접기/펴기 상태만 클라이언트에서 관리한다
- 사이드바가 `fixed`로 레이아웃 흐름에서 빠지면서, 예전에 `max-w-2xl`로 좁았던 본문이
  넓은 폭을 그대로 쓸 수 있게 됨 → 기존에 넣어뒀던
  `grid-cols-[repeat(auto-fill,minmax(...,1fr))]`가 그제서야 실제로 여러 열로 렌더링됨.
  (그리드 자체는 이전 커밋에도 있었지만, 컨테이너가 좁아서 1열처럼 보였던 것)

**검증 — 이 세션에서도 브라우저 자동화 도구의 렌더링 한계를 다시 확인**

`resize_window({preset:"desktop"})`가 실제로는 562px짜리 좁은 뷰포트를 만드는 버그를
발견해서, 이후로는 `width`/`height`를 직접 지정하는 방식으로 전환했다. 그 다음부터는
`getComputedStyle()`로 `position`, `left`, `width`, `padding-left`, `grid-template-columns`
값을 직접 읽어 확인했다 — 1280px에서 사이드바 `fixed`/`left:0`/`256px`, 본문
`padding-left:256px`, 그리드 3열; 접었을 때 `80px`/`80px`/그리드 4열; 375px 모바일에서는
`static`/`375px`(풀폭)/토글 버튼 `display:none`까지 전부 계산값으로 재확인했다.

### 18. 맛집 사진 업로드 기능 추가 (기획서 범위 밖 — 사용자가 명시적으로 요청)

기획서에는 "사진 기능은 안 만든다"고 명시돼 있었지만, Airbnb 스타일 카드를 그대로
따라가려면 사진이 필요하다는 사용자 판단에 따라 **새 기능으로 추가**했다. 카드에
시각적 앵커만 넣을지, 실제 업로드 기능을 넣을지 먼저 물어봤고 사용자가 실제 업로드를
선택했다.

**Supabase Storage 설정**

- `restaurant-photos` 버킷 생성 (public — 카드/상세 화면에서 `<img src>`로 바로 쓸 공개
  URL이 필요해서. 개인 맛집 사진이라 민감도가 낮다고 판단)
- `storage.objects`에 정책 3개: insert/update/delete는 `(storage.foldername(name))[1] =
  auth.uid()::text`로 제한 — 본인 폴더에만 쓸 수 있다. 조회는 버킷 자체가 public이라
  별도 정책 없이도 공개 URL로 열람 가능
- `restaurants` 테이블에 `photo_url text` 컬럼 추가 (마이그레이션, 백필 없음)

**업로드 경로 설계 — 파일 이름을 맛집 id가 아니라 새 UUID로 만든 이유**

등록 시점엔 아직 맛집 행이 DB에 없어서 id가 없다. 맛집 id로 파일 경로를 만들려면
"먼저 insert해서 id를 받고 → 사진 올리고 → update로 photo_url 채우기" 식으로 두 번
왕복해야 한다. 대신 파일 이름 자체를 `${userId}/${randomUUID()}.${ext}`로 새로 만들어서,
사진 업로드 → URL 확보 → 맛집 insert를 한 번에 끝내도록 했다.

**수정 시 사진을 유지하는 방식**

`updateRestaurant`에서 새 파일을 안 올리면 `photo_url` 키 자체를 update 객체에 넣지
않는다 (`...(photo.url ? { photo_url: photo.url } : {})`). Supabase의 `.update()`는
명시한 컬럼만 덮어쓰므로 기존 사진이 그대로 남는다. 예전 사진 파일을 스토리지에서
지우는 로직은 넣지 않았다 — 개인용 앱 규모에서 고아 파일이 문제될 정도로 쌓이지
않을 거라 판단했고, 넣으면 복잡도만 늘어난다.

**AI 메모 요약과 같은 원칙 — 실패해도 저장은 막지 않는다**

`uploadRestaurantPhoto`는 파일이 없으면 조용히 `null`을 돌려주고, 용량 초과(5MB)나
이미지가 아닌 파일은 명확한 에러 메시지를 돌려주되 예외를 던지지는 않는다. 다만
이 경우는 AI 요약과 달리 **사용자가 사진을 첨부하려고 시도한 경우**라 사진 업로드
실패 시엔 저장 자체를 막고 에러를 보여준다 (AI 요약은 있어도 그만인 부가 기능이지만,
사진은 사용자가 의도적으로 넣으려던 것이므로 조용히 무시하면 안 된다고 판단).

**검증한 것 — 브라우저 자동화 도구로 실제 파일 업로드가 안 되는 문제 우회**

이 브라우저 자동화 도구는 보안상 `<input type=file>`에 실제 파일을 선택시킬 수 없다.
대신 `DataTransfer` API로 1×1 PNG를 만들어 `input.files`에 주입하고 `change` 이벤트를
직접 발생시켜서, 실제 등록 폼 제출(Server Action의 멀티파트 `FormData` 처리 경로)까지
end-to-end로 검증했다:

| 확인 항목 | 결과 |
| --- | --- |
| 등록 폼에서 사진 첨부 후 저장 | DB에 `photo_url`이 실제 공개 URL로 채워짐 |
| 목록 카드 | `<img>`가 정상 로드(`complete:true`, `naturalWidth:1`) |
| 상세 화면 | 큰 사진(`aspect-[4/3]`)으로 정상 표시 |
| Storage RLS (별도 Node 스크립트로 확인) | 본인 폴더 업로드 성공 · 공개 URL fetch 200 · **다른 사용자 폴더에 업로드 시도는 RLS로 차단** · 삭제 정상 |

테스트로 만든 맛집 행과 스토리지 파일은 확인 후 바로 정리했다.

### 19. 사이드바를 왼쪽 고정 레일로, 계정 영역 하단 배치 · 등록/수정 폼에도 사이드바 적용

### 21. 로그인/회원가입 탭 UI로 구분 명확화 — 그리고 발견한 버그

**증상 (문제)** — 기존에 "로그인" 폼과 "회원가입" 폼이 하단의 작은 텍스트 링크
하나로만 구분되어 있어서 지금 어느 모드인지 헷갈린다는 피드백을 받았다. 상단에
로그인/회원가입 **탭 스위처**를 추가하고, 현재 모드를 크게 보여주는 제목(`<h2>`)도
넣었다.

**버그 발견 — 회원가입 실패 후 로그인이 안 됨**

탭을 만들고 나서 사용자가 실사용 중 버그를 신고했다: 이미 존재하는 이메일로
회원가입을 시도해 "User already registered" 에러를 본 뒤, 로그인 탭으로 바꿔
**올바른** 이메일/비밀번호로 로그인해도 로그인이 안 됐다.

원인은 기존 코드 구조였다:

```tsx
const action = mode === "login" ? login : signup;
const [state, formAction, pending] = useActionState(action, initialState);
```

`mode`가 바뀌어도 `useActionState`에 넘기는 `action` 함수가 실제로는 다시 바인딩되지
않았다. 그래서 탭을 "로그인"으로 바꾼 뒤 제출해도 내부적으로는 여전히 `signup`이
호출되고 있었다 — 올바른 비밀번호를 넣어도 `signUp(기존 이메일, 비번)`이 실행되니
매번 "User already registered"만 반복된 것이다. Node 스크립트로 Supabase API를 직접
호출해 signUp 실패 후 signIn이 정상 동작하는 것부터 먼저 확인해서, 문제가 Supabase
쪽이 아니라 React 쪽(`useActionState` 바인딩)에 있다는 걸 좁혀나갔다.

**수정**: `LoginFields`/`SignupFields`를 완전히 별도 컴포넌트로 분리해서 각자
`useActionState(login, ...)` / `useActionState(signup, ...)`을 고정으로 호출하게
했다. `mode`에 따라 두 컴포넌트 중 하나만 마운트되므로 액션이 확실히 갈리고,
모드를 바꾸면 컴포넌트가 통째로 새로 마운트되어 이전 모드의 에러 메시지도 자연스럽게
사라진다.

**브라우저로 재현 및 검증**

| 시나리오 | 결과 |
| --- | --- |
| 수정 전: 회원가입 실패(User already registered) → 로그인 탭 → 올바른 정보로 로그인 | 로그인 안 됨, 같은 에러 메시지 반복 (재현 성공) |
| 수정 후: 동일 시나리오 | `/`로 정상 리다이렉트 |
| 모바일(375px) 탭 UI | 두 탭이 163.5px씩 균등 분할, 활성 탭만 흰 배경으로 뚜렷이 구분 |

### 22. Gemini 조언 반영 — 크림 배경·카드 배지·정렬 기능

사용자가 Gemini에게 받은 UI/UX 개선 프롬프트를 그대로 붙여넣었다. 항목별로 검토해서
바로 반영할 것과 별도 확인이 필요한 것을 나눴다.

- 배경: 순백 → 따뜻한 크림그레이(`#F6F5F2`) + 옅은 도트 패턴(`radial-gradient` 반복)
- 카드: 그림자만 있던 걸 `border 1px solid #EAEAEA` + `shadow 0 2px 8px rgba(0,0,0,0.04)`로
- 카테고리 표시를 pill 배지로, 방문 여부는 사진 위 배지(✅ 방문)와 미방문 카드
  흐림(opacity+grayscale) 처리로 구분
- 검색바 높이를 줄이고 옆에 정렬(최신순/별점순) 드롭다운 추가 — 이건 프롬프트에
  없던 "새 기능"이라 별도로 확인받고 진행했다
- 사이드바: "+ 맛집 등록"을 카테고리 필터 아래로, 계정 영역을 카드처럼(테두리+그림자)

**빌드 버그 발견 — 서버 컴포넌트가 클라이언트 컴포넌트의 상수를 못 읽음**

`SORT_OPTIONS` 배열을 `"use client"` 파일(`sort-select.tsx`)에 두고 서버 컴포넌트인
`page.tsx`에서 그대로 가져다 썼더니 `SORT_OPTIONS.some is not a function` 런타임
에러가 났다. Next.js가 클라이언트 컴포넌트 모듈의 export를 서버 쪽 경계를 넘어
쓸 때는 실제 배열이 아니라 클라이언트 레퍼런스 프록시로 바꿔버리기 때문이다.
`SORT_OPTIONS`를 `lib/types.ts`(순수 데이터, 지시어 없음)로 옮겨서 해결 — 서버·
클라이언트 어디서든 안전하게 값을 공유하려면 상수는 "use client" 파일이 아니라
평범한 모듈에 둬야 한다는 걸 배웠다.

**부수 발견 — 작업 디렉토리에서 문서 파일 2개가 갑자기 사라짐**

`docs/가장오래막혔던문제와해결과정.md`, `docs/회고.md`가 `git status`에 "deleted"로
떴다. 이 세션에서 지운 적이 없어서(원인 불명 — 파일시스템 이슈로 추정), 삭제를
커밋에 포함하지 않고 `git checkout --`으로 즉시 복구했다.

### 23. 상세 화면 버튼·사진에 배경색 채우기 — 전체 스캔

사용자가 상세 화면의 방문체크/수정/삭제 버튼과 사진 영역에 배경색이 없어서 새로
넣은 도트 패턴이 그대로 비친다고 지적. 그 세 버튼만 고치는 대신, **같은 패턴(테두리는
있는데 배경색이 없는 요소)이 앱 전체에 더 있는지** 브라우저에서 모든 페이지의
버튼·인풋·셀렉트 `background-color`를 스크립트로 훑었다. 등록/수정 폼의 모든 입력창,
카테고리 드롭다운, "필터 초기화" 버튼도 전부 투명 배경이었어서 한 번에 같이 고쳤다.

### 24. 사용자가 그린 로고를 실제 화면에 반영

Gemini로 만든 마스코트 캐릭터 배지 이미지(다운로드 폴더에 있음)를 사이드바 로고,
로그인 화면, 빈 상태 아이콘, 파비콘에 넣어달라는 요청. 이미지 하나를 용도별로
다르게 잘라 써야 해서(작은 아이콘 자리엔 글자 없는 마스코트만, 로그인 화면엔 글자
포함 전체 배지), `sharp`로 로컬 스크립트를 짜서 크롭·마스킹 처리했다.

- 사각형으로 마스코트만 자르면 모서리에 원형 테두리 선이 살짝 걸려서, 둥근 모서리
  마스크(`dest-in` 블렌드)로 잘라내 깔끔하게 처리
- 파비콘용은 완전한 원형 마스크로 별도 크롭 (텍스트 없이 마스코트만)
- 최종 자산: `public/mascot-icon.png`(작은 아이콘용, 원형), `public/logo-hero.png`
  (로그인 화면용, 글자 포함 전체 배지), `src/app/icon.png`(Next.js 파비콘 컨벤션)

**이 작업이 드러낸 진짜 버그 — `proxy.ts`가 퍼블릭 정적 파일까지 로그인 검사**

이미지를 넣고 나서 로그인 화면(비로그인 상태)에서 히어로 이미지가 하나도 안 뜨는
문제가 생겼다. `curl`로 직접 확인해보니 `/mascot-icon.png` 요청 자체가 307로
`/login`으로 리다이렉트되고 있었다 — `proxy.ts`의 미들웨어 matcher가
`_next/static`, `_next/image`, `favicon.ico`만 제외하고 다른 모든 정적 파일은
로그인 검사를 거치게 되어 있었기 때문이다. 지금까지는 로컬 이미지 자산이 하나도
없어서(전부 Supabase Storage의 외부 URL) 드러나지 않았던 문제였다. Next.js의
이미지 최적화 서버(`/_next/image`)도 내부적으로 원본 이미지를 이 경로로 다시
요청하다가 리다이렉트 응답을 받아 "요청한 리소스가 유효한 이미지가 아닙니다"
에러를 냈다. matcher에 이미지 확장자 제외 패턴을 추가해서 해결.

## 왜 LLM이 아니라 파이썬인가

LLM은 숫자 비교를 틀린다. 자릿수가 커지면 더 그렇다.
그래서 역할을 이렇게 나눴다.

```
LLM (구조화된 출력)  →  파이썬 (비교 판정)  →  LLM (설명 생성)
"카페 해요" → 나군        4000 < 7500 → 간편장부     사람 말로 풀어쓰기
```

`with_structured_output`이 자연어와 코드 사이의 다리 역할을 한다.
LLM이 문장을 Pydantic 객체로 바꿔주면, 그 다음은 평범한 파이썬이다.

## 기준선을 설정으로 뺀 이유

세법은 매년 바뀐다. 숫자가 판정 함수 안에 박혀 있으면 코드를 고치고 다시 테스트해야 하지만,
귀속연도를 키로 하는 설정 파일로 빼두면 값만 바꾸면 된다.

부수 효과로 **테스트가 가능해졌다.** "2024년 기준으로 판정하면 이 결과"라는 검증을 쓸 수 있다.

## 함정 세 개

### ① 기준연도가 항목마다 다르다

| 판정 항목 | 어느 해 수입금액 |
|---|---|
| 기장의무 | 직전연도 |
| 경비율 | 직전연도 |
| 성실신고확인 | **당해연도** |

같은 변수를 재사용하면 바로 버그가 된다. 변수명에 연도를 박았다
(`revenue_prev_year`, `revenue_this_year`).

### ② 부등호가 파일마다 다르다

| 파일 | 기준 |
|---|---|
| `judgement.py` (신고 방식) | **이상** (`>=`) |
| `obligation.py` (신고 의무) | **초과** (`>`) |

세법이 실제로 그렇다. 경계값 테스트를 양쪽 다 넣었다.
`>=`를 `>`로 잘못 쓰는 건 일반 케이스만 테스트하면 절대 안 걸린다.

### ③ 인자 순서를 바꿔 넣어도 에러가 안 난다

수입금액 인자가 두 개인데 둘 다 정수라 바꿔 넣어도 조용히 틀린 답이 나온다.
키워드 전용 인자로 막았다.

```python
def judge_filing_method(*, business_group, revenue_prev_year, ...):
```

## 설계에서 신경 쓴 것

판정 결과가 **가정 목록을 함께 들고 다니게** 만들었다.

```python
@dataclass
class FilingMethod:
    bookkeeping: str
    expense_rate: str
    assumptions: list[str] = field(default_factory=list)   # 가정이 결과에 붙어 다닌다
```

"나중에 프롬프트에서 가정을 붙이자"고 미루면 까먹는다.
과제 조건(추정을 사실처럼 표현하지 말 것)을 구조로 강제한 셈이다.

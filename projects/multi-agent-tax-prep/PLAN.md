## 1. 한 줄 정의

> **"나 세금 신고 뭐 준비해야 해?"라고 물으면, 내 상황을 파악해서 준비물 목록을 만들어주고 빠진 것을 짚어주는 멀티 에이전트 시스템**

### 하는 것 / 하지 않는 것

| 한다 | 하지 않는다 |
|---|---|
| 신고 의무가 있는지 판별 | 세액 계산 |
| 신고 방식(장부/추계) 판별 | 유불리 판단 ("추계가 유리합니다") |
| 방식에 맞는 준비물 목록 생성 | 절세 자문 |
| 빠진 항목 점검 | 대리 신고·홈택스 접속 |
| 개별 지출의 경비 **가능성**과 필요 증빙 안내 | "이 지출은 경비입니다" 단정 |

**포지션**: 계산하고 판단하는 도구가 아니라, **확인할 목록을 만들어주는 도구.**
이 경계는 규제 회피 목적이자, LLM이 못하는 일(산술 연산·법적 판단)을 피하는 설계 선택이다.

### 문구 주의

"절세 계획을 세워드립니다"는 세금을 줄여주겠다는 **약속**으로 읽혀 세무 자문처럼 보인다.
같은 내용을 **"받을 수 있는 공제를 빠뜨리지 않게 정리해드립니다"**로 쓴다.
(참고: 세무통 '마이택스'는 세무사법 위반으로 고발당해 서비스를 종료했다.)

## 2. 왜 이 주제인가

### 2-1. 기존 서비스의 공통 한계

국내 세무 서비스는 전부 **"홈택스에 이미 쌓여 있는 데이터"를 가공하는 쪽**에 몰려 있다.

| 서비스 | 포지션 | 수수료 |
|---|---|---|
| 삼쩜삼 | 홈택스 5년치 분석 → 환급 예상액 | 환급액의 최대 20% |
| 토스 세이브잇 | 동일 | 환급액의 15~20% |
| 국세청 원클릭 | 환급 신고 | 무료 (인적용역 소득자 전용) |
| 자비스·SSEM·캐시노트 | 사업자 장부 자동작성 | 월 2.9만원~ |

### 2-2. 아무도 안 하는 영역

| 빈 자리 | 왜 중요한가 |
|---|---|
| "당신이 신고 대상인지" 판정 | N잡러가 대상인 줄 모르고 넘어가 무신고가산세 20% |
| 지급명세서 누락 탐지 | 거래처 미제출 시 홈택스에 안 뜸 → 나중에 추징 |
| "증빙을 지금 확보하라" 알림 | 3만원 초과는 적격증빙 필수인데 5월엔 이미 늦음 |
| 과다공제 위험 경고 | 기존 플랫폼은 구조적으로 불가능 (2-3장) |
| 지방소득세(위택스) 별도 신고 | 홈택스만 끝내고 무신고가산세 |

### 2-3. 차별점 — 왜 경쟁사는 못 하는가

기존 플랫폼은 **환급액이 클수록 수수료가 커지는 구조**라서
"이건 넣으면 위험합니다"라고 말할 유인이 없다. 실제 사고가 보고되고 있다.

- A씨: 환급금 173만원 안내받고 수수료 19만원 선납 → 소득 있는 누나를 부양가족으로
  잘못 연결해 가산세 통지 ([일간NTN](https://intn.co.kr/news/articleView.html?idxno=2043431))
- 한국세무사회: 플랫폼이 "전문적인 검토 없이 기계적으로 환급을 유도하고
  책임은 납세자에게 전가" ([한국세정신문](https://www.taxtimes.co.kr/news/article.html?no=269648))

**수수료를 받지 않는 도구만 "이건 빼세요"라고 말할 수 있다.**
경쟁사가 못 하는 이유가 기술이 아니라 비즈니스 모델이라는 점이 이 프로젝트의 서사다.
(단, 이 기능 자체는 2차로 이관 — 0장 결정 #4)

### 2-4. 해외 유사 사례

| 서비스 | 기능 | 한국 상황 |
|---|---|---|
| TaxCaddy (미국) | Document Request List — 내야 할 서류 목록 자동 생성 및 미제출 추적 | B2C로 없음 |
| Keeper (미국) | 카드 거래를 업무/개인으로 AI 자동 분류 | 프리랜서 대상 서비스 없음 |

## 4. 도메인 설계 — 판별 로직

> 이 장이 조사 에이전트의 뼈대다. 여기가 틀리면 나머지가 다 틀린다.

### 4-1. 분류축은 3개이고, 서로 독립이다

| 축 | 갈래 | 판정 기준연도 |
|---|---|---|
| ① 신고 의무 | 신고 O / 신고 X / 분리과세 선택 가능 | 해당 과세기간 |
| ② 기장의무 | 복식부기 의무자 / 간편장부 대상자 | **직전연도** 수입금액 |
| ③ 경비율 (추계 시) | 기준경비율 / 단순경비율 | **직전연도** 수입금액 |
| (참고) 성실신고확인 | 대상 / 비대상 | **당해연도** 수입금액 |

> ⚠️ **기준연도가 항목마다 다르다.** 코드에서 같은 변수를 재사용하면 바로 버그가 된다.
> 변수명에 연도를 명시할 것: `revenue_prev_year`, `revenue_this_year`

②와 ③은 독립이므로 "간편장부 대상자인데 기준경비율 적용"이 실제로 가장 흔한 조합이다.

### 4-2. 신고 의무 판별 트리

```
입력: 소득 유형별 금액 + 업종 + 직전연도 수입금액
 ├ 사업소득 있음?            → YES: 무조건 신고 대상 (금액 하한 없음)
 ├ 근로소득 2곳 이상 & 미합산? → YES: 신고 대상
 ├ 금융소득 합계 > 2,000만원? → YES: 신고 대상
 ├ 기타소득금액 > 300만원?    → YES: 신고 대상 / 이하: 분리과세 선택 가능
 ├ 사적연금 > 1,500만원?      → YES: 종합/분리 선택 분기
 ├ 주택임대 수입 > 2,000만원? → YES: 신고 대상 / 이하: 14% 분리과세 선택 가능
 └ 모두 아님                 → 신고 의무 없음
                               ※ 단, 3.3% 원천징수분이 있으면
                                 "안 해도 되지만 안 하면 손해" 경로로 분기
```

**"안 해도 된다"와 "안 하면 손해다"는 다르다.** 환급 체크는 별도 경로로 둔다.

### 4-3. 업종 그룹 (2025년 귀속 기준)

| 그룹 | 대표 업종 | 복식부기 의무 | 기준경비율 적용 |
|---|---|---|---|
| 가군 | 농·임·어업, 광업, 도소매, 부동산매매 | 3억원 이상 | 6,000만원 이상 |
| 나군 | 제조, 숙박·음식, 건설, 운수, 정보통신, 금융·보험 | 1.5억원 이상 | 3,600만원 이상 |
| 다군 | 부동산임대, 전문·과학·기술서비스, 교육, 보건, 기타 개인서비스 (**프리랜서 대부분**) | 7,500만원 이상 | 2,400만원 이상 |

- 전문직(변호사·회계사·세무사·의사 등)은 **수입금액 무관 복식부기 의무**
- 신규사업자는 원칙적으로 간편장부 대상

> ⚠️ 위 금액은 **2025년 귀속 기준**이며 매년 바뀔 수 있다. **하드코딩 금지** —
> 귀속연도를 키로 하는 설정 파일로 분리한다. (6장 `config/thresholds.py`)

### 4-4. 준비물은 신고 방식에 따라 완전히 갈린다

> **설계상 가장 중요한 지점.** 준비물 목록은 신고 방식이 정해진 뒤에야 확정된다.

| 신고 방식 | 모아야 할 것 |
|---|---|
| **단순경비율 추계** | 경비 증빙 **불필요** (수입금액 × 경비율로 자동 계산). 공제 증빙만 |
| **기준경비율 추계** | **주요경비 3종만** — 매입비용 / 임차료 / 인건비 + 주요경비지출명세서 |
| **간편장부** | 간편장부 + 총수입금액 및 필요경비명세서 + 전체 경비 증빙 |
| **복식부기** | 재무상태표 + 손익계산서 + 합계잔액시산표 + 조정계산서 + 전체 증빙 |

**공통 서류** (전원): 과세표준확정신고서, 소득공제·세액공제 증빙, 영수증수취명세서

→ 따라서 조사 에이전트의 실행 순서는 반드시 이렇다:

```
① 신고 의무 판별  →  ② 신고 방식 판별  →  ③ 방식별 준비물 분류
```

### 4-5. 적격증빙 4종과 금액 기준선

| 증빙 | 발급자 |
|---|---|
| (전자)세금계산서 | 일반과세 사업자 |
| (전자)계산서 | 면세사업자 |
| 신용카드매출전표 | 카드 가맹점 |
| 현금영수증 | **지출증빙용**으로 발급 (소득공제용 아님) |

- 사업 관련 지출 **3만원 초과** 시 적격증빙 필수 → 미수취 시 가산세 2%
- 접대비는 **1만원** 기준
- 3만원 이하도 기록은 남겨야 함 (간이영수증·계좌이체 내역)

### 4-6. 사업소득자 vs 근로자 공제 차이

| 항목 | 사업소득자 | 근로소득자 |
|---|---|---|
| 신용카드 사용액 소득공제 | **없음** | 있음 |
| 의료비·교육비·월세 세액공제 | **원칙 없음** (성실신고확인자만 예외) | 있음 |
| 노란우산공제 | **있음** (사업자 전용) | 없음 |
| 기장세액공제 | **있음** (간편장부 대상자가 복식부기로 신고 시, 한도 100만원) | 없음 |
| 표준세액공제 | 7만원 | 13만원 |

### 4-7. 가산세 — "빠뜨리면 얼마 손해인지" 근거

| 가산세 | 세율 |
|---|---|
| 무신고 | 무신고납부세액 × 20% (부정 40%) |
| 과소신고 | 과소신고납부세액 × 10% |
| 납부지연 | 미납세액 × 경과일수 × 2.2/10,000 |
| 무기장 | 산출세액 × 해당비율 × 20% |
| 증명서류 수취 불성실 | 미수취금액 × 2% |

## 5. 시스템 구조

### 5-1. 전체 흐름

```
[사용자 입력]  ──→  라우터  ──→  필요한 에이전트만 실행  ──→  [응답 출력]
                                                                  │
                     ▲                                            │
                     └──────────  while 루프로 다시 입력 대기  ────┘
                              (같은 thread_id = 대화 기억 유지)
```

### 5-2. 에이전트별 패턴 (HINT.md 형식)

| 에이전트 | 적용 패턴 | 흐름 | 참고 노트북 |
|---|---|---|---|
| **조사** | Orchestrator-Worker | 조사 항목 생성 → ①신고의무·②신고방식 병렬 조사 → ③준비물 종합 | `19`, `18` |
| **기획** | 단일 노드 (1차) | 조사 결과 + 사용자 조건 → 준비물 목록 + 마감 역산 일정을 한 번에 생성 | `20` |
| **검토** | Reflection (**최대 2회**) | 초안 평가 → 피드백 반영 → 완료 판단 | `17` |
| **최상위** | Router + 조건부 엣지 + Checkpointer | 에이전트 선택 → 실행 → 대화 기억 | `15`, `13` |

### 5-3. 라우터

요청을 보고 실행할 에이전트를 고른다. **역할 선택만 하고 도메인 판별은 하지 않는다.**

| 사용자 요청 예시 | 실행 |
|---|---|
| "프리랜서인데 나 신고 대상이야?" | 조사 |
| "추가 조사 없이 준비 목록 만들어줘" | 기획 |
| "이 지출 경비 되나?" / "내 목록 봐줘" | 검토 |
| "내 상황 파악하고 목록 만들고 검토까지" | 조사 → 기획 → 검토 |

> ⚠️ **라우터를 두 개 만들지 말 것.** "장부냐 추계냐" 같은 도메인 판별은
> 조사 에이전트 내부에서 한다. 라우터가 도메인을 알면 범용성이 깨진다.

### 5-4. 조사 에이전트 — Orchestrator-Worker

```
orchestrator        →   worker ①, ② (병렬)      →   synthesizer ③
조사 항목 결정           신고의무 / 신고방식            준비물 분류
```

**①과 ②는 서로 독립이라 병렬로 돌고, ③은 ②의 결과가 있어야 하므로 그 뒤에 온다.**
③이 Orchestrator-Worker 패턴의 "결과 종합" 자리에 정확히 대응한다.

| 항목 | 알아내는 것 | 필요한 입력 |
|---|---|---|
| ① 신고 의무 | 신고 대상인가? 분리과세 선택지가 있나? | 소득 유형별 금액 |
| ② 신고 방식 | 기장의무 / 경비율 | 업종 + 직전연도 수입금액 |
| ③ 준비물 | 방식별 필요 서류·증빙·공제 항목 | ②의 결과 |

출력 예시:

```
■ ① 신고 의무 판별
   → 대상입니다 (사업소득은 금액 무관 신고 의무)

■ ② 신고 방식 판별   ※ 가정: 2025년 귀속 기준
   → 업종 다군 / 직전연도 4,000만원
   → 간편장부 대상 + 기준경비율 적용

■ ③ 적용 가능 항목
   → 경비: 장비·소프트웨어·임차료·교육훈련비·통신비...
   → 공제: 노란우산·연금저축·국민연금·인적공제...
```

### 5-5. 기획 에이전트 — 단일 노드 (1차)

**입력**: 사용자 요청 + *(있으면)* 조사 결과
**출력**: 준비물 목록 + 마감 역산 일정

| 항목 | 어디서 | 언제까지 | 왜 |
|---|---|---|---|
| 지급명세서 조회 | 홈택스 My홈택스 | 4월 중 | 거래처 미제출 시 수입이 안 잡힘 |
| 사업용 카드 등록 | 홈택스 | 지금 바로 | 등록해야 사용내역 자동 수집 |
| 노란우산 납입증명 | 중소기업중앙회 | 5월 전 | 사업자 전용 소득공제 |

조사 결과가 **없으면** 사용자가 준 조건만으로 만들고,
**있으면** 판별된 신고 방식에 맞춰 목록이 달라진다.
(단순경비율이면 경비 증빙 항목이 통째로 빠진다 — 4-4 참조)

#### 왜 1차는 노드 하나인가

노드를 나누면(Prompt Chaining) 각 단계가 한 가지에만 집중해 결과가 촘촘해지지만,
**LLM 호출이 나눈 만큼 늘어난다.**

| 방식 | 흐름 | 호출 |
|---|---|---|
| 단일 노드 (1차) | 조사 결과 → (목록+일정을 한 번에) → 완성 | 1회 |
| Prompt Chaining (2차 후보) | 조사 결과 → 항목 추출 → 발급처 채움 → 일정 부착 | 3회 |

**지금은 출력 품질에 문제가 있는지 확인되지 않았다.** 문제를 확인하기 전에 쪼개면
호출만 3배가 되고 이득이 없다. 1차는 단일 노드로 만들고, 실제로 일정이나 발급처가
부실하게 나오는 것을 확인한 뒤에 쪼갠다.

> 이렇게 하면 "왜 쪼갰나"에 근거가 남는다.
> "한 번에 시켰더니 일정이 엉망이어서 나눴다"와 "패턴이 그래서"는 다르게 읽힌다.

### 5-6. 검토 에이전트 — Reflection, 입구 2개

```
평가  ──→  문제 있음?  ──→ 예 ──→  개선  ──┐
            │                            │
            └── 아니오 ──→ 완료           │
            ▲                            │
            └────────────────────────────┘
             최대 2회 (무한루프·비용 방지)
```

**입력이 두 군데서 온다.** PRACTICE.md 13줄의
"사용자가 제공하거나 다른 에이전트가 작성한 결과"에 그대로 대응한다.

| 입구 | 검토 대상 | 나오는 요청 |
|---|---|---|
| **A** | 기획이 만든 준비물 목록 (`planning_result`) | 복합 요청의 마지막 단계 |
| **B** | 사용자가 붙여넣은 지출 내역·초안 | "이 지출 경비 되나?" |

검토 노드 첫 부분에 **"State에 검토 대상이 있나? 없으면 사용자 메시지에서 찾는다"**는 분기가 들어간다.

#### 입구 A 출력 예시 (1차 = 누락 점검만)

```
■ 빠진 것으로 보이는 항목
  ⚠ 지방소득세(위택스) 신고 — 홈택스만 하면 가산세 따로 붙음
  ⚠ 3만원 초과 지출의 적격증빙 — 간이영수증은 인정 안 됨
  ⚠ 현금영수증 발급 유형 — "지출증빙용"으로 받았는지 확인 필요
```

#### 입구 B 출력 예시

```
  노트북 200만원
    → 업무 사용분은 경비 가능성이 높습니다
    → 필요 증빙: 세금계산서 또는 카드전표 (3만원 초과 = 적격증빙 필수)
    → ⚠ 감가상각 대상일 수 있어 일시 처리가 안 될 수 있습니다

  카페 커피값
    → 개인 식음료는 일반적으로 인정이 어렵습니다
    → 거래처 미팅 목적이면 접대비로 볼 여지 (1만원 초과 시 적격증빙)

  ※ 최종 인정 여부는 사업 관련성에 대한 개별 판단이 필요합니다
```

> **"인정됩니다"가 아니라 "가능성이 있습니다 + 필요 증빙은 이것"**으로 답한다.
> 쓸모는 유지하면서 자문 성격만 제거하는 표현 규칙이다.

### 5-7. 판정 로직 — LLM과 파이썬의 분담

**LLM은 숫자 비교를 틀린다.** `7500 >= 7500` 같은 판정을 맡기면 안 된다.

```
LLM (구조화된 출력)  →  파이썬 (비교 판정)  →  LLM (설명 생성)
자연어에서 정보 추출      기준선과 대조           사람 말로 풀어쓰기
```

| 일 | 담당 | 이유 |
|---|---|---|
| "카페 운영해요" → 나군 판정 | **LLM** | 자연어 이해는 LLM의 영역 |
| `4000 < 7500` → 간편장부 | **파이썬** | 숫자 비교는 코드가 100% 정확 |
| 결과를 문장으로 설명 | **LLM** | — |

구조화된 출력 모델 (참고 노트북 `04-structured-output`):

```python
# LLM이 사용자 문장에서 뽑아낼 정보의 형태를 정의한다
class UserProfile(BaseModel):
    income_types: list[str]         # ["사업소득"], ["근로소득", "사업소득"] 등
    business_group: str | None      # "가군" / "나군" / "다군"
    revenue_prev_year: int | None   # 직전연도 수입금액 (없으면 되물음)
    has_business_reg: bool | None   # 사업자등록 여부
```

판정 함수는 **노드 안에서 파이썬 함수로 직접 호출**한다.
Tool로 감싸지 않는 이유: 어차피 항상 호출하므로 LLM이 판단할 필요가 없고,
Tool로 만들면 API 호출이 1~2회 늘어난다. **Tool 승격은 2차.**

### 5-8. 되묻기 방식

정보가 부족하면 추측하지 않고 질문한다. 구현 방식은 두 가지 중 **(b)를 택한다.**

| 방식 | 설명 | 채택 |
|---|---|---|
| (a) `interrupt` | 그래프 중간에 멈춰 입력을 받음 (`21-human-in-the-loop`) | ❌ 구조 복잡 |
| (b) 질문 출력 후 종료 | 그래프가 질문을 뱉고 끝 → `main.py`의 while이 다음 입력 받음 → 재호출 | ✅ |

Checkpointer가 대화를 기억하므로 다음 호출에서 맥락이 이어진다.
**과제 조건 5번(while 반복 + 대화 기억)과 자연스럽게 한 몸**이 된다.

동작 예시:

```
> 나 프리랜서 개발자인데 종합소득세 뭐 준비해야 돼?

[실행 순서] 1. research
판단하려면 두 가지가 더 필요합니다.
  ① 작년(2025년) 총 수입이 대략 얼마였나요?
  ② 사업자등록을 하셨나요, 3.3% 떼고 받으셨나요?

> 3.3%로 받았고 4천만원쯤

[실행 순서] 1. research → 2. planning
(이전 대화에서 "프리랜서 개발자"를 기억한 채 이어서 답변)
```

### 5-9. 프롬프트 2층 구조

**3차의 도메인 확장(연말정산 추가)을 가능하게 하는 구조다.**
역할 정의와 도메인 지식을 한 덩어리로 쓰면, 도메인을 바꿀 때 프롬프트를 통째로 다시 써야 한다.

```python
# 프롬프트를 두 덩어리로 나눠서 조립한다
ROLE = "너는 사용자 요청에 필요한 정보를 여러 관점에서 조사하는 담당이다."   # 범용 — 안 바뀜
DOMAIN = "참고 지식: 종합소득세 신고는 신고의무/기장의무/경비율로 분류된다..."  # 도메인 — 교체 가능

prompt = ROLE + "\n\n" + DOMAIN
```

`ROLE`은 "조사·기획·검토를 어떻게 수행하는가"만 담고, 세무 지식은 전부 `DOMAIN`에 둔다.
→ 3차에서 연말정산 도메인을 추가할 때 `DOMAIN`만 갈아끼우면 된다.
→ README에 **"도메인 확장 시 수정한 파일: `prompts.py` 1개"**를 근거로 쓸 수 있다.

### 5-10. 콘솔 출력 형식

과제 조건 3번(PRACTICE.md 19줄)에 직접 대응한다.

```
[실행 순서] 1. research → 2. planning → 3. review
```

- **상위 에이전트 단위**로만 찍는다. 조사 내부 worker까지 찍으면 순서가 안 보인다
- 하위 노드 추적은 LangSmith에서 확인한다
- 각 에이전트 진입 시 번호를 누적해 출력

### 5-11. State 설계

```python
# 최상위 그래프에서 노드들이 공유하는 데이터
class MainState(TypedDict):
    messages: ...           # 대화 기록 (Checkpointer가 관리)
    todo_agents: ...        # 라우터가 정한 실행할 에이전트 목록
    user_profile: ...       # 되물어서 수집한 사용자 정보 (5-7의 UserProfile)
    research_result: ...    # 조사 에이전트 산출물
    planning_result: ...    # 기획 에이전트 산출물
    review_result: ...      # 검토 에이전트 산출물
    executed_agents: ...    # 콘솔 출력용 실행 순서 기록
```

과제 조건 4번(앞 단계 결과 전달)이 여기서 해결된다.
기획은 `research_result`를, 검토는 `planning_result`를 꺼내 쓴다.

> State를 **평평하게(flat)** 유지한다. 중첩 구조는 예뻐 보이지만
> 어느 노드가 어디를 건드리는지 추적이 안 된다. 필드가 늘어나면 그때 묶어도 늦지 않다.

```
multi-agent-tax-prep/          ← 코드·문서 모두 여기서 작성 (GitHub 저장소 루트)

└── src/ ...
```

과제 제출 시에는 강사 제공 실습 폴더로 `src/`를 복사한다.

### 소스 구조

강사 제공 뼈대와 같은 구조를 쓰고, 설정 파일 하나만 추가한다.

```
src/
├── main.py                    # while 루프, 입력받기, 종료 처리, thread_id 고정
├── graph.py                   # 라우터 + 세 에이전트 연결 + Checkpointer
├── config/
│   └── thresholds.py          # ★추가: 귀속연도별 금액 기준선
└── agents/
    ├── __init__.py
    ├── planning.py            # 기획 에이전트
    ├── review.py              # 검토 에이전트 (Reflection)
    └── research/              # 조사 에이전트 (복잡해서 패키지 분리)
        ├── __init__.py
        ├── prompts.py         # ROLE + DOMAIN 2층 프롬프트
        ├── nodes.py           # State + 구조화 출력 모델 + 노드 함수 + 판정 함수
        └── graph.py           # 조사 그래프 조립
```

`config/thresholds.py`를 분리하는 이유: 금액 기준선이 매년 바뀐다.
판별 함수 안에 숫자가 박혀 있으면 코드를 고치고 다시 테스트해야 하지만,
설정으로 빼두면 값만 바꾸면 되고 **"2024년 기준으로 판정하면 이 결과"라는 테스트도 쓸 수 있다.**

## 7. 개발 환경

| 항목 | 값 | 비고 |
|---|---|---|
| 모델 | `gemini-3.5-flash-lite` | 무료 티어 하루 500회 |
| `.env` 위치 | 프로젝트 루트 | 다른 곳에 두려면 환경 변수 `TAX_PREP_ENV`로 경로 지정 (`src/env.py`) |
| LangSmith | **필수** (`LANGSMITH_TRACING=true`) | 에이전트 3개가 얽히면 콘솔 로그만으로 디버깅 불가 |
| 셸 | Git Bash (POSIX sh) | — |

**LangSmith를 필수로 두는 이유**: 복합 요청 하나에 노드가 8개 이상 돈다.
"어느 노드에서 이상한 출력이 나왔는지"를 콘솔 `print`로 추적하는 건 현실적으로 불가능하다.

**API 키 관리**: `.env`는 저장소 밖 경로를 절대경로로 참조하고, 프로젝트 폴더에 복사하지 않는다.
`.gitignore`에 `.env`를 반드시 등록한다. 한 번 커밋된 키는 파일을 지워도 히스토리에 남는다.

## 8. API 호출 비용 관리

### 8-1. 요청당 호출 횟수 (1차 기준)

| 요청 유형 | 내역 | 합계 |
|---|---|---|
| 단일 조사 | 라우터 1 + 조사(항목결정 1 + worker 2 + 종합 1) | **5회** |
| 단일 기획 | 라우터 1 + 기획 1 | **2회** |
| 단일 검토 | 라우터 1 + 검토(평가 1 + 개선 0~1) | **2~3회** |
| **복합** | 라우터 1 + 조사 4 + 기획 1 + 검토 1~2 | **7~8회** |

하루 500회 기준으로 **복합 요청 60회 이상** 실행 가능하다.

### 8-2. 절감 원칙

| 원칙 | 적용 |
|---|---|
| LLM을 안 써도 되는 곳엔 안 쓴다 | 숫자 비교는 파이썬 (5-7), 금칙어는 규칙 매칭 (2차 가드레일) |
| 반복에는 상한을 둔다 | Reflection 최대 2회 (HINT.md 15줄 권고) |
| 조건부로 건너뛴다 | 검토에서 "문제 없음"이면 개선 단계를 실행하지 않음 |
| **동시 실행 worker를 제한한다** | `config={"max_concurrency": 3}` — 조사 worker를 한꺼번에 던지면 분당 요청 한도에 걸려 `429`가 난다 |
| **그래프 전체에 스텝 상한을 둔다** | `config={"recursion_limit": 25}` — 조건식 버그로 무한루프가 돌 때 끊는 안전망. State 카운터(업무 규칙)와 층위가 다르다 |

### 8-3. 개발 중 주의

- 복합 요청 한 번에 7~8회가 나가므로, 같은 시나리오를 반복 테스트하면 호출량이 빠르게 누적된다.
  실행 전 예상 호출량을 확인하고 돌린다.
- 라우터만 테스트할 때는 에이전트를 더미 함수로 대체해 호출을 아낀다 (11장 3단계).
- 판정 로직은 순수 파이썬이므로 API 호출 없이 단위 테스트할 수 있다 (11장 4단계).

### 8-4. 에러 처리

무료 티어에서 `429 Too Many Requests`가 발생할 수 있다.

- 지수 백오프(exponential backoff) 재시도
- 재시도 실패 시 사용자에게 원인을 알리고 종료 (조용히 죽지 않게)
- 하루 한도 소진 시 안내 메시지 구분

## 11. 구현 순서

작은 단위로 나눠서, 매 단계마다 돌려보고 넘어간다.

| 단계 | 할 일 | 확인 방법 |
|---|---|---|
| 1 | 수업 노트북 코드 스타일 확인 (LLM 초기화, State, 라우터 문법) | — |
| 2 | `main.py` — while 루프 + 종료 처리만 | 입력·출력이 반복되나 |
| 3 | `graph.py` — 라우터만 붙이고 에이전트는 **더미 함수** | 요청별로 올바른 에이전트를 고르나 |
| 4 | `config/thresholds.py` + 판정 함수 (LLM 없이 파이썬만) | 단위 테스트로 판정이 맞나 |
| 5 | 조사 에이전트 — Orchestrator-Worker 3단계 | 판별 결과가 나오나 |
| 6 | 기획 에이전트 — 준비물 목록 생성 | 조사 결과를 반영하나 |
| 7 | 검토 에이전트 — Reflection + 입구 2개 | 두 경로가 다 도나 |
| 8 | Checkpointer 연결 + 되묻기 | 후속 요청이 앞 대화를 기억하나 |
| 9 | 콘솔 출력 + LangSmith + 에러 처리 | 실행 순서가 보이나 |
| 10 | 검증 시나리오 실행 | 12장 |

**3단계에서 더미 함수를 쓰는 이유**: 라우터가 제대로 도는지 먼저 확인해야
나중에 에이전트가 이상할 때 "라우터 문제인가 에이전트 문제인가"를 안 헤맨다.

**4단계를 LLM 없이 하는 이유**: 판정 로직은 순수 파이썬이므로 API 호출 없이 테스트할 수 있다.
여기서 버그를 다 잡아두면 나중에 LLM 출력이 이상할 때 판정은 의심하지 않아도 된다.

## 12. 검증 계획

### 12-1. 세무 도메인 — 단일 요청 (라우터 검증)

| 요청 | 기대 에이전트 |
|---|---|
| "실행 계획은 빼고, 프리랜서 개발자가 신고 대상인지랑 뭐가 필요한지만 알려줘" | 조사 |
| "추가 조사 없이, 지금 파악된 내용으로 준비 목록 만들어줘" | 기획 |
| "노트북 200만원, 카페 커피값 썼는데 경비 되나?" | 검토 (입구 B) |
| "내 상황 파악하고 준비 목록 세운 뒤 검토해서 최종본 만들어줘" | 조사 → 기획 → 검토 |

### 12-2. 복합 요청 — 결과 전달 검증

과제 조건 4번(앞 단계 결과를 다음 에이전트에 전달)을 확인한다.
**조사 → 기획 → 검토가 각각 앞 단계 산출물을 실제로 반영했는지**가 핵심이다.

- 요청: `프리랜서 개발자인데 작년 수입 4천만원이야. 내 상황 파악하고 준비 목록 세운 뒤 검토해서 최종본 만들어줘.`

| 확인 항목 | 기대 |
|---|---|
| 콘솔 출력 | `1. research → 2. planning → 3. review` |
| 기획이 조사를 반영했나 | 조사가 판정한 **기준경비율**에 맞는 준비물만 나옴 (주요경비 3종 중심) |
| 검토가 기획을 반영했나 | 기획이 만든 목록을 대상으로 누락을 지적 (새 목록을 다시 만들지 않음) |
| 최종본 | 검토 지적사항이 반영된 목록이 마지막에 출력됨 |

> 조사가 **단순경비율**로 판정한 경우와 비교해보면 전달이 제대로 되는지 더 분명해진다.
> 단순경비율이면 경비 증빙 항목이 통째로 빠져야 한다 (4-4 참조).

### 12-3. 대화 기억 검증

- 첫 요청: `프리랜서 개발자인데 작년 수입 4천만원이야. 신고 준비 목록 만들어줘.`
- 후속 요청: `방금 목록에서 사무실 임차료 항목만 빼줘.`
- 기대: 다시 말하지 않은 소득유형·업종·수입규모를 유지한 채 해당 항목만 수정

### 12-4. 되묻기 검증

- 요청: `나 세금 신고해야 해?`
- 기대: 소득 유형·업종·수입 규모를 되묻고, 추측으로 답하지 않음

### 12-5. 도메인 정확성 검증

주요 판별 결과를 국세청 안내 페이지와 눈으로 대조한다 (16장 출처 사용).
1차에서는 **모든 수치를 가정으로 표시하므로 틀려도 시스템이 무너지지 않는 구조**로 간다.

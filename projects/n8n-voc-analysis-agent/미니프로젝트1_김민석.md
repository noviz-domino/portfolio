## 1. 과제 개요

종합 쇼핑몰에 하루 수십 건씩 들어오는 고객 문의(VOC)를 사람이 읽고 분류하던 방식의 두 가지 문제 -
① 담당자 부재 시 긴급 문의 방치, ② 분류 기준이 사람마다 달라 통계 불가 - 를 해결하기 위해,
**접수부터 분류·기록·긴급 알림까지 사람 손을 거치지 않는 파이프라인**을 n8n으로 구현했다.

## 2. 전체 아키텍처

```
[고객]
  │ 문의 작성
  ▼
Google Form ──제출──▶ Google Sheet (설문지 응답 시트1)
                          │
                          ▼ (1분 폴링)
                 ┌──────────────────────────────────────────┐
                 │                n8n 워크플로우                │
                 │                                          │
                 │ Form 제출 감지 → Loop Over Items(1건씩)      │
                 │   → 분석결과 시트 조회 → 중복 체크             │
                 │   → (중복 아니면) Gemini 분류                │
                 │   → 검증 안전판 → 접수번호 생성                │
                 │   → 분석결과 저장 → 긴급도 분기               │
                 └──────────────────────────────────────────┘
                       │                    │
                긴급(urgency=상)만          모든 건(검증 실패 포함)
                       ▼                    ▼
                  Discord 채널 알림      Google Sheet (분석결과 탭)
```

## 3. 사용 기술

| 항목 | 선택 | 이유 |
| --- | --- | --- |
| 자동화 엔진 | n8n Cloud | 서버 관리 불필요, Google/Discord 연동을 UI로 처리 |
| LLM | Google Gemini (`gemini-2.5-flash`, temperature 0) | 무료 API 키 보유, temperature 0으로 같은 문의는 항상 같은 분류 → 통계 일관성 확보 |
| 데이터 저장 | Google Sheets (원본 응답 탭 + 분석결과 탭 분리) | Form이 원본 탭 헤더를 소유하므로 n8n이 쓰는 결과는 별도 탭으로 완전히 분리 |
| 긴급 알림 | Discord Webhook (HTTP POST) | 별도 봇 없이 URL 하나로 발송 가능 |

## 4. 워크플로우 노드 구성 (15개)

| # | 노드 | 역할 |
| --- | --- | --- |
| 1 | Form 제출 감지 | Google Sheets Trigger, 원본 응답 탭 신규 행 폴링(1분) |
| 2 | Loop Over Items | 한 번에 여러 신규 행이 감지돼도 1건씩 순차 처리 |
| 3 | 분석결과 시트 조회 | 분석결과 탭 전체 조회 (중복판정·접수번호 계산 재료) |
| 4 | 중복 체크 | 물품번호+이메일 기준 중복 판정 (LLM 호출 **이전**) |
| 5 | IF 중복? | 중복이면 종료, 아니면 계속 |
| 6 | 중복 종료 | No-Op, 저장·알림 없이 정상 종료 |
| 7 | Gemini 분류 | 문의내용만 근거로 5필드 구조화 출력 |
| 8 | Gemini 모델 | `gemini-2.5-flash`, temperature 0 |
| 9 | 출력 스키마 | Structured Output Parser (JSON Schema) |
| 10 | 검증 안전판 | 필수 필드·허용값·타입 검사, 위반 시 안전값으로 교정 (throw 없음) |
| 11 | 접수번호 생성 | `VOC-YYYYMMDD-NNN` 생성, discord_message 조립 |
| 12 | 분석결과 저장 | 분석결과 탭에 Append (검증 실패건도 예외 없이 저장) |
| 13 | IF 긴급? | urgency === '상' 여부로 분기 |
| 14 | Discord 알림 | HTTP POST, 5요소 포함 메시지 |
| 15 | 긴급 아님 종료 | No-Op, 중/하 건은 저장까지만 |

전체 노드 JSON은 `workflow/voc-agent-workflow.json` 파일에 있다 (n8n 캔버스에 그대로 붙여넣기 가능).

### 4-1. 핵심 커스텀 로직 (Code 노드 3개)

**중복 체크**는 새로 들어온 문의의 물품번호·이메일을, 분석결과 시트에 이미 저장된 모든 행과 하나하나 비교한다. 물품번호는 단순 문자열 비교가 아니라 숫자로 한 번 변환했다가 다시 문자열로 바꾸는 방식으로 정규화하는데, 이는 Google Sheets가 `"00001"` 같은 값을 셀 서식에 따라 앞자리 0을 지운 숫자 `1`로 저장해버리는 문제를 방어하기 위해서다. 이메일도 대소문자를 무시하도록 소문자로 통일해서 비교한다. 하나라도 완전히 일치하는 기존 행이 있으면 중복으로 판정하고, 몇 개의 기존 행과 비교했는지도 디버깅용으로 같이 남긴다.

**검증 안전판**은 Gemini가 반환한 결과가 약속한 형식(JSON, 5개 필드, 정해진 허용값)을 지켰는지 검사한다. Gemini는 종종 JSON을 코드블록 기호로 감싸거나 설명을 덧붙여서 보내는데, 이 경우에도 먼저 코드블록 표시를 제거하고 중괄호로 감싸인 부분만 추출해 파싱을 시도한다. 그래도 파싱이 안 되거나, 5개 필드 중 하나라도 없거나, category·sentiment·urgency가 정해진 목록 밖의 값이거나, summary가 80자를 넘거나, needs_review가 boolean이 아니면 전부 "계약 위반"으로 취급한다. 위반이 있으면 urgency를 안전한 기본값 `중`으로, needs_review를 `true`로 강제 교정하되, 어떤 경우에도 오류를 던지지 않고 항상 다음 단계로 넘어가도록 만들어 워크플로우가 죽지 않게 한다.

**접수번호 생성**은 두 가지 일을 한다. 첫째, Google Sheets가 넣어주는 한국어 타임스탬프(`2026. 8. 10 오후 2:32:10` 같은 형식)는 자바스크립트의 기본 날짜 파싱 함수로는 읽히지 않으므로, 문자열에서 숫자만 순서대로 뽑아 직접 연-월-일-시-분으로 조립하고 오전/오후를 반영한다. 파싱에 실패해도 프로그램이 죽지 않고 실행 시각으로 대체한다. 둘째, 분석결과 시트에서 같은 날짜로 시작하는 접수번호 중 가장 큰 번호를 찾아 그다음 번호를 매긴다(단순히 행 개수를 세는 방식이 아니라 최댓값 기준이라, 중간 행이 지워져도 번호가 겹치지 않는다). 마지막으로 원문을 200자로 잘라 말줄임 처리한 뒤, Discord로 보낼 메시지 문자열까지 이 단계에서 미리 완성해둔다.

이 세 노드는 Node.js `vm` 모듈로 만든 가짜 n8n 런타임(`$input`, `$('노드명')`을 흉내)에서 실제로 실행해 동작을 검증했다 (8장 참고).

### 4-2. Gemini 분류 프롬프트

```
당신은 종합 쇼핑몰의 고객 VOC(고객의 소리)를 분류하는 어시스턴트입니다.
아래 [문의내용]만 읽고 5개 필드를 판단하세요. 고객이 직접 고른 문의유형은 일부러 제공하지 않습니다. 내용만 근거로 판단하세요.
JSON 외의 설명, 서론, 코드블록 표기는 절대 출력하지 마세요.

[필드 정의]
- category : 결제 / 계정 / 상품 / 배송 / 기타 중 정확히 하나
- sentiment : 긍정 / 중립 / 부정 중 정확히 하나
- urgency : 상 / 중 / 하 중 정확히 하나
- summary : 한국어 요약. 80자를 절대 넘기지 마세요.
- needs_review : 분류에 확신이 없으면 true, 확실하면 false (문자열이 아닌 boolean)

[긴급도 판정 기준]
- 상 : 서비스를 못 쓰는 상태 / 금전적 피해가 이미 발생 / 법적 대응이나 언론·소비자원 제보 언급 / 명시적인 환불 요구
- 중 : 불편하지만 서비스 사용은 가능한 상태 / 단순 질문을 넘어선 개선 요청
- 하 : 단순 질문, 칭찬, 정보 확인

[문의내용]
{{ $json['문의내용'] }}
```

Structured Output Parser에 넣은 JSON Schema:

```json
{
  "type": "object",
  "properties": {
    "category":     { "type": "string", "enum": ["결제", "계정", "상품", "배송", "기타"] },
    "sentiment":    { "type": "string", "enum": ["긍정", "중립", "부정"] },
    "urgency":      { "type": "string", "enum": ["상", "중", "하"] },
    "summary":      { "type": "string" },
    "needs_review": { "type": "boolean" }
  },
  "required": ["category", "sentiment", "urgency", "summary", "needs_review"]
}
```

| --- | --- | --- |
| REQ-01 | Form 4항목, 항목명 정확, Sheet 자동 누적 | Google Form 4항목(문의유형/문의내용/이메일/물품 번호) + 응답 시트 연동 |
| REQ-02 | 새 행 추가 시 자동 실행, Manual 트리거 금지 | Google Sheets Trigger(Row Added, 1분 폴링) + Active 상태 |
| REQ-03 | 중복 차단, LLM 호출 이전, 저장·알림 없이 정상 종료 | 물품번호+이메일 정규화 비교 → Gemini 노드보다 앞단에서 분기 |
| REQ-04 | 5필드 구조화 출력, 긴급도 기준 프롬프트 명시 | Gemini 프롬프트에 상/중/하 판정 기준 그대로 삽입 + Structured Output |
| REQ-05 | 계약 위반 검사, urgency=중/needs_review=true 교정, 실패건도 저장 | 검증 안전판 Code 노드에서 throw 없이 안전값으로 교정 후 무조건 다음 단계로 |
| REQ-06 | 분석 결과 시트 기록 | 전 건(정상/실패 무관) Append |
| REQ-07 | urgency=상만 Discord 발송, 5요소 포함 | IF 분기 + Webhook POST, discord_message에 접수번호/분류/요약/원문(200자 말줄임)/접수시각 포함 |

## 6. 설계상 중요한 판단 2가지

**① 고객이 고른 `문의유형`을 Gemini에게 알려주지 않았다.**

폼에는 고객이 직접 "문의유형: 결제/계정/상품/배송/기타" 중 하나를 고르는 항목이 있다. 그런데 Gemini에게 분류를 시킬 때, 이 고객 선택값을 **일부러 알려주지 않고 `문의내용`(글 내용)만 보여줬다.**

왜 그랬냐면, 이 프로젝트의 원래 목적 중 하나가 "고객이 스스로 고른 분류"와 "실제 내용을 보고 판단한 분류"를 **서로 비교**하는 것이기 때문이다. 만약 Gemini에게 고객이 고른 값까지 같이 알려주면, Gemini는 그 힌트를 그대로 베껴서 답할 가능성이 높다 (사람도 "정답이 이거야"라고 미리 들으면 그쪽으로 쏠리는 것과 비슷하다). 그러면 두 값이 항상 똑같아져서 "비교"라는 게 의미가 없어진다.

그래서 분석결과 시트에는 두 값을 **나란히 따로** 저장한다: `문의유형(고객선택)` 열에는 고객이 고른 값, `category` 열에는 Gemini가 글만 보고 판단한 값. 이렇게 하면 나중에 "고객은 배송 문제라고 생각했는데 사실 결제 문제였다" 같은 불일치 통계도 낼 수 있다.

**② "검증 실패하면 무조건 urgency=중으로 낮춘다"는 규칙을 그대로 따랐고, 여기엔 부작용이 있다.**

요청서에는 "LLM 출력이 계약을 어겨도 워크플로우가 죽으면 안 된다"고 되어 있고, "위반 시 urgency를 안전하게 `중`으로 바꿔라"라고 정해져 있다. summary 80자 제한도 REQ-04가 정한 출력 계약의 일부이므로, 이를 어기는 것도 "계약 위반"에 포함시켜 그대로 구현했다.

그런데 이렇게 하면 이상한 경우가 하나 생긴다. 예를 들어 Gemini가 urgency는 정확하게 `상`(긴급)으로 판단했는데, 어쩌다 요약(summary) 글자수만 80자를 살짝 넘겼다고 해보자. 그러면 검증 안전판은 "계약을 하나라도 어겼으니까"라며 urgency를 통째로 `중`으로 낮춰버린다. **결과적으로 진짜 긴급한 문의인데 Discord 알림이 안 가는 상황이 생길 수 있다.**

요청서에 적힌 그대로 구현했기 때문에 이 동작 자체는 요구사항을 충족한다. 다만 실제로 서비스에 쓴다면, "글자수 초과"처럼 긴급도와 상관없는 사소한 위반과 "urgency 값 자체가 이상함"처럼 진짜 심각한 위반을 구분해서, 사소한 위반일 때는 urgency는 그대로 두고 `needs_review`만 true로 표시하는 방식이 더 안전하다. 즉 위반 사유 중에 urgency 값 자체가 잘못됐거나 파싱이 아예 실패한 경우만 "치명적"으로 분류해 urgency를 낮추고, 그 외 사소한 위반(summary 길이 등)은 needs_review만 true로 표시하도록 조건을 나누면 개선할 수 있다.

## 7. 실제 빌드하며 발견하고 고친 문제 4가지

**문제 1 - 트리거가 한 번에 여러 신규 행을 감지하는 문제**
1분 폴링 안에 폼이 2건 제출되자 트리거가 2개 아이템을 한 번에 출력했는데, 코드가 `.first()`로 짜여 있어 첫 번째 건만 처리되고 두 번째 건이 조용히 사라졌다.
→ 해결: `Loop Over Items`(Split In Batches, batch size 1) 노드를 트리거 바로 뒤에 추가해 몇 건이 한꺼번에 감지되든 한 건씩 순서대로 전체 파이프라인을 통과시키도록 했다. 이때 코드의 `.first()`도 `.item`으로 바꿨다 - `.first()`는 무조건 0번째만 가리키지만, `.item`은 n8n의 pairedItem 추적을 이용해 현재 루프 반복에 대응하는 그 아이템을 정확히 가리킨다.

**문제 2 - 물품 번호 앞자리 0 소실로 중복 체크가 무력화되는 문제**
Google Sheets가 `"00001"`을 셀 서식에 따라 텍스트가 아닌 숫자 `1`로 저장·반환해서, 트리거로 막 들어온 값(`"00001"`)과 시트에서 다시 읽은 값(`1`)이 문자열 비교에서 불일치했다. 그 결과 같은 물품에 대한 재문의인데도 중복으로 안 잡혔다.
→ 해결: 비교 직전 양쪽 값을 모두 `Number()`로 변환한 뒤 다시 문자열화하는 `normNo` 함수로 정규화했다. `"00001"`과 `1` 모두 `"1"`이 되어 같은 값으로 비교된다.

**문제 3 - Google Sheets `Get Rows` 노드가 빈 결과일 때 이후 노드를 통째로 건너뛰는 문제**
분석결과 시트가 비어 있으면(헤더만 있으면) 이 노드가 0개 아이템을 출력하는데, n8n은 0개 아이템을 받은 노드를 건너뛴다. 그래서 첫 실행에서 중복 체크 이후 전부 스킵되어 아무 일도 일어나지 않았다.
→ 해결: `분석결과 시트 조회` 노드에서 `Always Output Data` 옵션을 켜서 빈 아이템이라도 흘려보내도록 했다(코드에서는 `Object.keys(r).length > 0` 필터로 그 빈 아이템을 다시 걸러낸다). 이 옵션은 워크플로우 전체에서 이 노드 한 곳에만 켜져 있다.

**문제 4 - S1~S3 문의가 분석결과 시트에 통째로 저장 안 된 문제 (가장 까다로웠던 문제)**

정식 시나리오 테스트(S1부터 S6까지)를 실제 폼으로 진행하던 중, S1(물품번호 11111)·S2(22222)·S3(33333) 세 건이 분석결과 시트에서 통째로 빠져 있는 걸 발견했다. 이 상태에서 S6(S1과 동일한 물품번호+이메일 재제출)을 실행하니 중복 체크가 `isDuplicate: false`를 반환해서, 처음엔 "중복 판정 로직 자체의 버그"로 의심했다.

그런데 `중복 체크` 노드의 실제 출력을 열어보니 `_기존행수: 4`로 나왔다 - 그 시점에 분석결과 시트에는 정말 4행(테스트 2건 + S4 + S5)뿐이었다. 즉 **판정 로직은 정확했다.** 비교 대상(S1)이 애초에 없어서 정직하게 "다르다"고 답한 것뿐이었다.

S1~S3가 사라진 시점의 n8n 실행 기록을 찾으려 했지만 **기록 자체가 남아있지 않았다.** 에러로 죽은 흔적도 없었다. 재현을 위해 분석결과 시트를 비우고(원본 응답 시트는 트리거 내부 위치 추적이 깨질 수 있어 그대로 둠) 다시 제출해보니, 이번엔 새로 제출한 행이 원본 응답 시트에서 **맨 아래가 아니라 맨 위**에 나타나는 걸 발견했다.

원인은 원본 응답 시트가 Google Sheets의 **Table(구조화된 표)** 기능으로 만들어져 있었고, 정렬이 고정되어 있지 않아 신규 제출 행이 항상 맨 아래에 순차적으로 쌓인다는 보장이 없었다는 것이었다. `Form 제출 감지` 트리거(Row Added)는 "새 행은 항상 맨 아래에 순서대로 추가된다"는 전제로 새 행을 판별하는데, 이 전제가 깨지면서 짧은 간격(20~40초)으로 연달아 제출된 S1·S2·S3에 대해 트리거가 새 행 발생 자체를 인식하지 못한 것으로 추정된다(에러가 아니라 감지 실패라서 실행 기록도 안 남는다는 점과 정확히 부합).

→ 해결: 원본 응답 시트의 `타임스탬프` 열 기준으로 오름차순 정렬을 명시적으로 고정했다. 폼 제출은 항상 가장 최근 시각(가장 큰 값)으로 들어오므로, 오름차순 정렬에서 가장 큰 값은 항상 맨 아래에 위치한다 - 정렬을 걸어도 새 제출은 여전히 예측 가능하게 맨 아래에 쌓이게 되어 트리거의 전제와 다시 맞아떨어진다. 정렬 고정 후 S1부터 S6까지 처음부터 재제출해 전 건이 정상 처리됨을 확인했다.

트리거 이벤트를 `Row Added` → `Row Added or Updated`로 바꾸는 대안도 검토했으나 기각했다. REQ-02는 신규 제출만 자동 실행 대상으로 규정하는데, Table 재정렬이 기존 행 값을 다시 쓰는 방식이라면 "수정"으로도 잡혀서 이미 처리된 옛 문의들이 불필요하게 재실행될 위험이 있었기 때문이다. 근본 원인(정렬 미고정)을 고치는 쪽이 더 안전하다고 판단했다.

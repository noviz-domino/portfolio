## 4단계 — Discord Webhook 발급 및 첫 번째 오류

### 오류 1 :: PowerShell에서 curl 명령 실패

**증상**
```
curl -H "Content-Type: application/json" -d "{...}" <URL>
'<' 연산자는 나중에 사용하도록 예약되어 있습니다.
```
그리고 `<`를 뺀 두 번째 시도에서도:
```
Invoke-WebRequest : 'Headers' 매개 변수를 바인딩할 수 없습니다.
```

**원인**
Windows PowerShell에서 `curl`은 리눅스 curl이 아니라 `Invoke-WebRequest`의 별칭(alias)이다. `-H`, `-d` 같은 리눅스 curl 옵션 문법을 그대로 쓸 수 없다.

**해결**
PowerShell 네이티브 문법으로 교체:
```powershell
Invoke-RestMethod -Uri "<웹훅 URL>" -Method Post -ContentType "application/json" -Body '{"content":"webhook test"}'
```
Discord Webhook은 성공 시 204 No Content(빈 응답)를 반환하므로, 출력이 없는 것 자체가 성공 신호다.

**부가 조치**
사용자가 채팅에 Webhook URL 전체를 그대로 붙여넣어 노출되었음을 알리고, 필요시 채널에서 재발급을 권장함.

### 오류 2 :: 분석결과 저장 노드 "At least one value has to be added under 'Values to Send'"

**원인**

### 오류 4 :: 두 번째 폼 제출 내용이 처리되지 않고 첫 번째 내용이 계속 나옴

**증상**
폼을 2건 제출(각각 물품번호·내용 다름)한 뒤 워크플로우를 실행하면, `중복 체크` 노드가 항상 **첫 번째 제출 내용**을 대상으로 판정하고, 두 번째 제출 건은 반영되지 않음.

**1차 진단 (틀렸음)**
처음에는 "테스트 실행 결과가 핀(pin) 고정되어 캐시된 옛날 데이터가 재사용되는 것"으로 진단하고 핀 해제를 안내함.

**재현 후 정확한 원인**
캔버스 스크린샷 확인 결과 `Form 제출 감지` 노드가 **2 items**를 한 번에 출력하고 있었다. 즉 1분 폴링 주기 안에 폼 제출 2건이 함께 감지된 것이었다. 그런데 `중복 체크`/`검증 안전판` 코드가
```javascript
const trigger = $('Form 제출 감지').first().json;
```
로 짜여 있어, 트리거가 몇 건을 내보내든 **무조건 0번째(첫 번째) 아이템만** 사용하고 있었다. 캐시 문제가 아니라 **다건 배치를 처리하지 못하는 설계 결함**이었다.

**해결**
1. `Form 제출 감지`와 `분석결과 시트 조회` 사이에 **`Loop Over Items`(Split In Batches, Batch Size=1)** 노드를 추가
2. 파이프라인 끝의 세 종료 지점(`중복 종료`, `Discord 알림`, `긴급 아님 종료`)을 모두 `Loop Over Items`로 되돌아가도록 연결해 루프를 닫음
3. 코드에서 `$('Form 제출 감지').first().json` → `$('Form 제출 감지').item.json` 으로 변경. `.first()`는 언제나 0번째만 가리키지만 `.item`은 n8n의 pairedItem 추적을 이용해 **현재 루프 반복에 대응하는 그 아이템**을 정확히 가리킨다.

이 구조 변경으로 트리거가 몇 건을 한꺼번에 감지하든 한 건씩 순서대로 전체 파이프라인(중복확인→Gemini→검증→저장→알림)을 완주하게 되었다.

### 오류 5 :: 같은 워크플로우를 재실행하면 이미 존재하는 문의가 또 저장됨

**증상**
Loop 구조로 고친 뒤 잘 동작함을 확인했으나, 사용자가 "이렇게 하면 매번 새로운 폼이 제출되면 처음부터 끝까지 폼 내용을 다시읽고... 한번 더 돌리면 이미 있는 내용으로 한개씩 더 추가로 생성돼"라고 재현 결과를 공유.

**원인 진단**
중복 체크가 걸러야 할 상황(같은 물품번호+이메일이 이미 분석결과 시트에 존재)인데도 걸러지지 않고 있었다. 이전 스크린샷에서 물품 번호가 `"00001"`(5자리, 앞자리 0 포함)로 표시된 것을 근거로, **Google Sheets가 셀 서식(일반/자동)에 따라 `"00001"`을 텍스트가 아닌 숫자 `1`로 저장·반환**했을 가능성을 지목함.
- 트리거로 막 들어온 값: 문자열 `"00001"`
- 분석결과 시트에서 다시 읽은 값: 숫자 `1` → `String(1)` = `"1"`
- `"00001" !== "1"` → 정규화 없이는 중복이 안 잡힘

**해결**
`중복 체크` 코드의 정규화 함수를 문자열 trim만 하던 것에서, 물품 번호는 **숫자로 변환 후 다시 문자열화**하는 방식으로 교체:
```javascript
const normNo = (v) => String(Number(String(v ?? '').trim()) || v);
```
`"00001"`과 `1` 모두 `"1"`로 정규화되어 같은 값으로 비교된다.

**참고로 정리한 사실**
"재실행할 때마다 또 쌓인다"는 증상 자체는 수동으로 Execute workflow를 반복 클릭하는 테스트 환경 특유의 현상이며, Active 상태의 실사용에서는 트리거가 이미 처리한 행을 기억하므로 같은 행을 두 번 감지하지 않는다. 그래도 중복 체크는 REQ-03이 요구하는 안전장치이므로 이번 수정으로 확실히 방어선을 세웠다.

## 7단계 — S1~S6 정식 시나리오 테스트 중 발견한 오류 6

### 증상
`01_기획서.md` 9-2장의 시나리오대로 실제 폼에 S1~S5를 순서대로 제출한 뒤 `분석결과` 시트를 확인하니, S1(물품번호 11111)·S2(22222)·S3(33333) 세 건이 통째로 빠져 있었다(00001·00002 테스트건과 S4·S5만 저장됨). 이 상태에서 S6(S1과 동일한 물품번호+이메일 재제출)를 실행하면 `중복 체크`가 `isDuplicate: false`를 반환해 중복 처리가 안 되는 것처럼 보였다.

### 1차 진단 (틀림)
처음엔 중복 체크 로직 자체의 버그로 의심했다. 그러나 `중복 체크` 노드의 실제 OUTPUT을 확인하니 `_기존행수: 4`로 나왔다 — 이 시점에 `분석결과` 시트에는 정말로 4행(00001·00002·S4·S5)뿐이었다. 즉 **중복 판정 로직은 정확했다.** 비교 대상 자체(S1)가 애초에 없어서 "다른 값"이라고 정직하게 답한 것뿐이었다.

### n8n Executions 탭에서 원인 추적 시도
S1~S3가 사라진 시점의 실행 기록을 찾으려 했으나 **실행 기록 자체가 남아있지 않았다.** 에러로 죽은 흔적도 없었다 — 즉 그 3건에 대해서는 워크플로우 실행이 아예 생성되지 않았던 것으로 보였다.

### 재현을 위한 재시도, 그리고 두 번째 단서
`분석결과` 시트 데이터만 비우고(원본 응답 시트는 트리거의 내부 위치 추적이 깨질 수 있어 그대로 둠) S1~S5를 다시 제출했다. 이번엔 새로 제출한 행(S5 재시도, 5:10:01)이 원본 응답 시트에서 **맨 아래가 아니라 맨 위(2행)**에 나타나는 것을 발견했다.

### 최종 원인
원본 응답 시트가 Google Sheets의 **Table(구조화된 표)** 기능으로 만들어져 있었다. 이 시트에 명시적인 정렬이 걸려 있지 않은 상태에서, 새로 추가되는 행이 항상 맨 아래에 순서대로 쌓인다는 보장이 없었다(Table 특성상, 혹은 헤더의 정렬·필터 화살표를 조작하는 과정에서 뷰가 흐트러졌을 가능성).

`Form 제출 감지`(Google Sheets Trigger, Row Added)는 **"새 행은 항상 맨 아래에 순서대로 추가된다"**는 전제로 동작한다. 이 전제가 깨지면서, S1~S3처럼 짧은 간격(20~40초)으로 연달아 제출된 건들에 대해 **트리거가 새 행 발생 자체를 인식하지 못한 것**으로 추정된다. (에러가 아니라 감지 실패이므로 실행 기록도 안 남는다는 점과 정확히 부합)

### 해결
원본 응답 시트의 `타임스탬프` 열 기준으로 **오름차순 정렬을 명시적으로 고정**했다. 폼 제출은 항상 가장 최근 시각(가장 큰 값)으로 들어오므로, 오름차순 정렬에서 가장 큰 값은 항상 맨 아래에 위치한다 — 즉 정렬을 걸어도 새 제출은 여전히 예측 가능하게 맨 아래에 쌓이게 되어 트리거의 전제와 다시 맞아떨어진다.

정렬 고정 후 S1~S6를 처음부터 다시 제출해 전 건이 정상 처리(S1·S5 긴급 알림 발송, S2~S4 저장만, S6 중복 차단)됨을 확인했다.

### 검토한 대안과 기각 이유
트리거 이벤트를 `Row Added` → `Row Added or Updated`로 바꾸는 방안도 검토했으나 기각했다. ① REQ-02는 신규 제출만 자동 실행 대상으로 규정하고 있어 기존 행 수정까지 감지하는 건 요구사항 범위 밖이다. ② Table 재정렬이 내부적으로 기존 행들의 값을 재기록하는 방식이라면 "수정"으로도 잡혀, 이미 처리된 옛 문의들이 불필요하게 재실행될 위험이 있다. 근본 원인(정렬 미고정)을 해결하는 쪽이 더 안전하다고 판단했다.

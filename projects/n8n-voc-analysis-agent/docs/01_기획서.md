## 1. 프로젝트 정의

### 1-1. 해결하려는 문제

### 1-2. 완료 정의 (Definition of Done)

아래 7개가 **사람 개입 0회**로 동작해야 완료입니다.

1. 고객이 Google Form 제출 → 원본 시트에 행 누적
2. 아무 버튼도 누르지 않았는데 n8n 워크플로우가 실행됨
3. 중복 문의는 LLM을 호출하지도 않고 조용히 끝남
4. LLM이 5개 필드 JSON을 반환
5. LLM이 헛소리를 해도 워크플로우가 죽지 않고 안전값으로 교정됨
6. 모든 건(검증 실패건 포함)이 분석 결과 시트에 남음
7. urgency=상 인 건만 Discord에 5요소 포함 메시지로 도착

### 1-3. 범위 밖 (하지 않는 것)

- 고객에게 자동 회신 메일 발송 (요청서에 없음, 이메일은 수집만)
- 담당자 배정 / 티켓 상태 관리
- 대시보드·차트 (시트에 데이터만 쌓아둠)
- 다국어 문의 처리 (한국어 기준)

## 4. STEP 1 — Google Form 만들기 (REQ-01)

### 4-1. 절차

1. https://forms.google.com → 빈 양식 만들기
2. 제목: `고객 문의(VOC) 접수` (제목은 자유)
3. 아래 4개 질문을 **순서대로, 항목명은 한 글자도 바꾸지 않고** 생성

### 4-2. 질문 정의 — 항목명은 채점 기준입니다

| 순서 | 항목명 (정확히 이대로) | 질문 유형 | 설정 | 필수 |
| --- | --- | --- | --- | --- |
| 1 | `문의유형` | 객관식 질문 | 옵션 5개: 결제 / 계정 / 상품 / 배송 / 기타 | ✅ |
| 2 | `문의내용` | 장문형 | — | ✅ |
| 3 | `이메일` | 단답형 | 응답 확인 → 텍스트 → 이메일 (선택) | ✅ |
| 4 | `물품 번호` | 단답형 | 응답 확인 → 숫자 / 5자리 안내문 | ✅ |

> **주의 1**: `물품 번호` 는 **번호 앞에 공백 한 칸**이 들어간 이름입니다(요청서 표기 그대로). 시트 헤더도 그대로 `물품 번호`가 되며, n8n 코드에서 `$json['물품 번호']` 로 접근합니다. 임의로 `물품번호`로 붙여쓰면 코드도 같이 바꿔야 하고 채점에서 감점될 수 있습니다.
>
> **주의 2**: 객관식 옵션 문자열도 정확히 `결제`, `계정`, `상품`, `배송`, `기타` 입니다. LLM의 `category` 허용값과 반드시 일치해야 "고객 선택 vs LLM 분류" 비교가 성립합니다.

### 4-3. 완료 확인

- 미리보기(👁)에서 직접 1건 제출 → 정상 접수되는지 확인
- 이 테스트 1건은 나중에 시트에서 지우거나, 중복 테스트 재료로 남겨둡니다

## 5. STEP 2 — Google Sheet 구성

### 5-1. 원본 응답 시트 연결

1. Form 편집 화면 → **응답** 탭 → 스프레드시트 아이콘 클릭
2. "새 스프레드시트 만들기" → 이름 `VOC 관리` → 만들기
3. 생성된 시트의 URL에서 **스프레드시트 ID**를 복사해 P3에 기록

이 탭의 헤더는 Form이 자동 생성합니다:

```
타임스탬프 | 문의유형 | 문의내용 | 이메일 | 물품 번호
```

> 이 탭의 헤더는 **절대 수정하지 마세요.** 여기에 열을 추가하거나 이름을 바꾸면 Form 연동이 깨집니다. 분석 결과는 반드시 별도 탭에 씁니다.

### 5-2. 분석결과 탭 만들기

1. 시트 하단 `+` 로 새 탭 추가 → 탭 이름을 `분석결과` 로 변경
2. **1행(A1부터)에 아래 11개 헤더를 그대로 입력**

복붙용 (탭 구분, A1 셀에 붙여넣기 하면 한 번에 들어갑니다):

```
접수번호	접수시각	문의유형(고객선택)	문의내용	이메일	물품 번호	category	sentiment	urgency	summary	needs_review
```

### 5-3. 열 정의서 (데이터 계약)

| 열 | 타입 | 출처 | 예시 | 제약 |
| --- | --- | --- | --- | --- |
| 접수번호 | string | n8n 생성 | `VOC-20260810-001` | `VOC-\d{8}-\d{3}` |
| 접수시각 | string | Form 타임스탬프 변환 | `2026-08-10 14:32` | `YYYY-MM-DD HH:mm` |
| 문의유형(고객선택) | string | Form `문의유형` | `결제` | 5개 옵션 중 1 |
| 문의내용 | string | Form `문의내용` | 원문 그대로 | 자르지 않음 |
| 이메일 | string | Form `이메일` | `a@b.com` | — |
| 물품 번호 | string | Form `물품 번호` | `12345` | 5자리 숫자 |
| category | string | LLM | `결제` | 결제/계정/상품/배송/기타 |
| sentiment | string | LLM | `부정` | 긍정/중립/부정 |
| urgency | string | LLM(검증 후) | `상` | 상/중/하 |
| summary | string | LLM | 요약문 | 80자 이하 |
| needs_review | boolean | 검증 안전판 | `false` | true/false |

> **왜 `문의유형(고객선택)`과 `category`를 둘 다 저장하나?**
> 요청서 REQ-01이 "고객이 스스로 고른 값은 LLM 분류 결과와 비교하는 재료"라고 명시했습니다. 둘을 나란히 저장해두면 나중에 불일치율(고객 체감 분류 vs 실제 내용)을 계산할 수 있습니다.

## 8. STEP 5 — 워크플로우 구축 (REQ-02 ~ REQ-07)

노드별 설정값·전체 코드는 **`02_워크플로우_상세설계.md`** 에, 붙여넣기용 워크플로우는 **`../workflow/voc-agent-workflow.json`** 에 있습니다. 여기서는 **왜 그 구조인지**와 **빠지기 쉬운 함정**만 정리합니다.

### 8-1. 노드 파이프라인 요약

```
[1] Form 제출 감지        Google Sheets Trigger (Row Added)
        ▼
[2] 분석결과 시트 조회      Google Sheets - Get Rows       ← 중복판정 + 순번계산의 재료
        ▼
[3] 중복 체크             Code (JS)                      ← LLM 호출 전!
        ▼
[4] IF 중복?  ── true ──> [5] No Operation (정상 종료)
        │ false
        ▼
[6] Gemini 분류           Google Gemini + Structured Output
        ▼
[7] 검증 안전판           Code (JS)                      ← 여기서 죽지 않게 만든다
        ▼
[8] 접수번호 생성          Code (JS)
        ▼
[9] 분석결과 저장          Google Sheets - Append Row     ← 검증 실패건도 반드시 저장
        ▼
[10] IF urgency == '상' ── true ──> [11] HTTP Request (Discord)
        │ false
        ▼ 종료
```

### 8-2. 반드시 지켜야 할 순서 제약

| 제약 | 근거 | 어기면 |
| --- | --- | --- |
| 중복 체크가 Gemini 앞 | REQ-03 "반드시 LLM 호출 이전에 차단" | 요구사항 위반 + 무료 API 쿼터 낭비 |
| 시트 저장이 Discord 분기 앞 | REQ-05 "검증 실패건도 저장" / REQ-06 | 긴급건만 기록되거나 일부 유실 |
| 검증 안전판이 시트 저장 앞 | REQ-05 | 허용값 밖 문자열이 시트에 들어가 통계 불가 |

### 8-3. 함정 5가지 (미리 알고 가면 시간 절약)

**함정 1 :: Sheets Trigger는 폴링이라 즉시 실행되지 않습니다**
`Poll Times`를 `Every Minute`로 설정해도 최대 1분 지연됩니다. 요구사항은 "아무것도 누르지 않아도 돌아야 한다"이므로 1분 지연은 허용 범위입니다. 다만 시연할 때 "왜 안 돌아?" 하고 당황하지 말고 1분 기다리세요.
또한 **워크플로우가 Active(활성) 상태여야** 폴링이 돕니다. 캔버스에서 테스트만 하고 Active 토글을 안 켜면 실제 제출에 반응하지 않습니다.

**함정 2 :: 한국어 타임스탬프는 `new Date()`로 파싱되지 않습니다**
Google Sheets가 넣는 값은 `2026/08/10 오후 2:32:10` 형태입니다. `new Date('2026/08/10 오후 2:32:10')` → `Invalid Date`.
→ 대응: 정규식으로 직접 파싱하거나, n8n의 `$now`(Luxon)를 기준으로 씁니다. 상세설계 문서의 접수번호 노드에 파싱 로직과 폴백을 넣어두었습니다. 시트 지역설정을 영어로 바꾸는 것도 방법이지만, 코드로 방어하는 편이 안전합니다.

**함정 3 :: Gemini가 JSON을 코드펜스로 감싸서 반환합니다**
````
```json
{"category": "결제", ...}
```
````
이 상태로 `JSON.parse()` 하면 실패합니다.
→ 대응: Structured Output Parser를 붙이면 대부분 해결되지만, 검증 안전판 코드에서 **코드펜스 제거 후 파싱**을 한 번 더 방어합니다. 파싱 실패 시에도 죽지 말고 `needs_review=true, urgency=중`으로 저장해야 REQ-05를 만족합니다.

**함정 4 :: `needs_review`가 문자열 `"true"`로 올 수 있습니다**
LLM은 boolean과 문자열을 자주 혼동합니다. `typeof !== 'boolean'` 검사를 반드시 넣고, 위반 시 계약 위반으로 처리합니다.

**함정 5 :: 중복 체크에서 타입 불일치**
시트에서 읽은 물품번호는 숫자 `12345`, Form에서 온 값은 문자열 `"12345"` 일 수 있습니다. `===` 비교가 항상 false가 되어 중복이 절대 안 잡힙니다.
→ 대응: 양쪽 모두 `String(x).trim()`, 이메일은 `.toLowerCase()` 까지 정규화 후 비교.

### 8-4. Gemini 프롬프트 설계 원칙

전체 프롬프트 텍스트는 상세설계 문서에 있습니다. 설계 시 지킨 원칙:

1. **긴급도 기준을 프롬프트에 그대로 명시** (REQ-04 요구사항)
   - 상 = 서비스 불가 / 금전 피해 / 법적·언론 언급 / 명시적 환불 요구
   - 중 = 불편하나 사용 가능 / 개선 요청
   - 하 = 단순 질문 / 칭찬 / 정보 확인
2. **허용값을 enum으로 못박음** — "적절히 분류" 같은 열린 지시 금지
3. **summary 80자 제한을 프롬프트에 쓰고, 코드에서도 slice로 강제** — 프롬프트는 부탁이고 코드가 계약
4. **고객이 고른 `문의유형`은 프롬프트에 넣지 않음** — 넣으면 LLM이 그대로 따라가서 비교 재료로서의 독립성이 사라집니다. `문의내용`만 보고 판단해야 "고객 선택 vs LLM 분류" 비교가 의미를 가집니다.
5. **JSON만 출력하라고 명시** — 서론/설명 금지

### 9-2. 시나리오 테스트 (완성 후) — 이 6건을 실제 폼으로 제출

**표를 읽는 법**: `물품번호`·`문의내용` 두 열만 실제로 **폼에 입력할 값**입니다 (문의유형은 아무거나 골라도 되고, 이메일은 본인 이메일을 쓰면 됩니다). `기대 category`·`기대 sentiment`·`기대 urgency`는 폼에 입력하는 칸이 **아닙니다** — 폼에는 애초에 그런 입력 칸이 없습니다. 이 세 열은 "제출 후 n8n이 Gemini로 분류한 실제 결과가 이 값과 비슷하게 나오는지 눈으로 대조해보라"는 **비교용 예상치**입니다. Gemini가 매번 100% 똑같은 값을 낸다고 보장할 수는 없으므로(S2·S4처럼 "또는"으로 표시한 항목은 둘 다 정답으로 인정), 정확히 일치하지 않아도 되고 **urgency가 상/중/하 중 어디로 갈리는지**만 요구사항과 맞는지 확인하면 된다.

| # | 물품번호 (폼 입력) | 문의내용 (폼 입력, 그대로 붙여넣기) | 기대 category (비교용) | 기대 sentiment (비교용) | 기대 urgency (비교용) | 제출 후 확인할 동작 |
| --- | --- | --- | --- | --- | --- | --- |
| S1 | 11111 | 결제는 완료됐는데 주문 내역에 아무것도 없습니다. 고객센터 전화도 안 받네요. 당장 환불해주세요. 소비자원에 신고하겠습니다. | 결제 | 부정 | **상** | 시트 저장 + **Discord 알림** |
| S2 | 22222 | 배송이 예정일보다 하루 늦게 도착했어요. 다음엔 좀 더 신경 써 주시면 좋겠습니다. | 배송 | 부정 또는 중립 | 중 | 시트 저장, 알림 없음 |
| S3 | 33333 | 이 상품 세탁기에 돌려도 되나요? 소재가 궁금해서요. | 상품 | 중립 | 하 | 시트 저장, 알림 없음 |
| S4 | 44444 | 포장이 정말 꼼꼼했어요. 덕분에 기분 좋게 받았습니다 감사합니다! | 기타 또는 상품 | 긍정 | 하 | 시트 저장, 알림 없음 |
| S5 | 55555 | 로그인이 계속 실패해서 이틀째 접속을 못 하고 있습니다. 비밀번호 재설정 메일도 안 옵니다. | 계정 | 부정 | **상** | 시트 저장 + **Discord 알림** |
| S6 | **11111** | (S1과 동일한 이메일로) 결제는 완료됐는데 주문 내역에 아무것도 없습니다. 고객센터 전화도 안 받네요. | — | — | — | **아무 일도 안 일어남** (중복) |

**진행 절차**: ① 폼에 접속해서 `물품번호`·`문의내용` 칸에 표의 값을 그대로 입력·제출 → ② 1분 정도 기다려 워크플로우가 자동 실행되는지 확인 → ③ `분석결과` 시트를 열어 그 행의 `category`/`sentiment`/`urgency` 열 값이 표의 "비교용 예상치"와 대략 맞는지 확인 → ④ urgency가 `상`이면 Discord 채널도 확인.

> S6는 반드시 **S1과 같은 이메일 + 같은 물품번호**로 제출해야 중복 테스트가 성립합니다.
> S6 실행 후 확인할 것: ① 분석결과 시트 행 수가 늘지 않음 ② Discord에 알림이 오지 않음 ③ n8n 실행 로그에서 Gemini 노드가 **실행되지 않음** (LLM 호출 전 차단 = REQ-03 핵심)

### 9-3. 접수번호 검증

S1~S5를 같은 날 제출했다면 접수번호가 `VOC-20260805-001` ~ `VOC-20260805-005` 로 **1씩 증가**해야 합니다. 같은 번호가 중복 발급되면 순번 계산이 "당일 접수번호 개수 세기"가 아니라 전체 행 수 기준으로 잘못 짜인 것입니다.

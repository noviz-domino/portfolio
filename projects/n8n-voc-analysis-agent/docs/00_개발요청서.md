# 프로젝트 1 개발 요청서 :: 고객 VOC 분석 Agent

---

## 1. 배경과 목적

종합 쇼핑몰에서 개발 요청서가 들어왔습니다.

고객 문의(VOC)가 하루 수십 건씩 들어오지만, 사람이 하나씩 읽고 분류해 긴급건을 골라내는 방식은 두 가지 문제가 있습니다. 첫째, 담당자가 자리를 비운 사이 긴급 문의가 몇 시간씩 방치됩니다. 둘째, 분류 기준이 사람마다 달라 통계를 낼 수 없습니다.

이 프로젝트는 **접수부터 분류, 기록, 긴급 알림까지 사람 손을 거치지 않는 파이프라인**을 만듭니다. 담당자는 알림이 왔을 때만 개입하면 됩니다.

## 2. 시스템 구성

1. 각자 본인 소유의 구글 폼, 구글 시트를 만들어 사용하고, 디스코드는 기존의 개인 채널을 사용합니다.
공용 리소스를 함께 쓰지 않습니다.

```
[고객]
  │ 문의 작성
  ▼
Google Form ──제출──> Google Sheet (원본 응답 시트)
                          │
                          ▼
                    ┌─────────────┐
                    │     n8n     │
                    │             │
                    │ 1. 중복 확인  │
                    │ 2. LLM 분류  │
                    │ 3. 검증 안전판 │
                    │ 4. 결과 저장  │
                    │ 5. 긴급 분기  │
                    └─────────────┘
                       │        │
                긴급건만 │        │ 모든건
                       ▼        ▼
                  Discord    Google Sheet
                  채널 알림   (분석 결과 시트)
```

## 3. 요구사항

### REQ-01 :: 수집 (Google Form → Sheet)

구글 폼으로 VOC를 접수하고, 응답이 구글 시트에 자동 누적되어야 합니다.

**폼 필수 항목** (항목명은 그대로 사용하세요. 채점 시 이 이름으로 확인합니다)

| 항목명 | 형식 | 비고 |
| --- | --- | --- |
| 문의유형 | 객관식 (결제 / 계정 / 상품 / 배송 / 기타) | 고객이 스스로 고른 값. LLM 분류 결과와 비교하는 재료가 됩니다 |
| 문의내용 | 장문형 | 분류의 실제 입력값 |
| 이메일 | 단답형 | 응답 회신용 |
| 물품 번호 | 단답형(임의의 5자리 숫자) | 물품을 구분하는 번호 (임의) |

### REQ-02 :: 트리거 (Sheet → n8n)

시트에 새 응답 행이 추가되면 n8n 워크플로우가 자동 실행되어야 합니다.

- **수동 실행(Manual Trigger)만 되는 상태는 미완성으로 봅니다.** 
폼을 제출했을 때 아무것도 누르지 않아도 워크플로우가 돌아야 합니다

### REQ-03 :: 중복 방지

같은 물품에 대해 동일한 문의가 두 번 들어와도 결과가 늘어나면 안 됩니다.

- 분석 결과 시트의 항목을 조합해 중복 문의를 차단합니다.
- 반드시 LLM 호출 이전에 차단합니다.
- 중복으로 판정된 건은 저장도 알림도 하지 않고 정상 종료합니다.

### REQ-04 :: LLM 분류

문의내용을 읽고 아래 5개 필드를 **구조화 출력(JSON)** 으로 반환해야 합니다.

| 필드 | 타입 | 허용값 |
| --- | --- | --- |
| `category` | string | 결제 / 계정 / 상품 / 배송 / 기타 |
| `sentiment` | string | 긍정 / 중립 / 부정 |
| `urgency` | string | 상 / 중 / 하 |
| `summary` | string | 80자 이하 |
| `needs_review` | boolean | 검증 실패 시 true |

**긴급도 판정 기준** (프롬프트에 명시할 것)

- `상` :: 서비스를 못 쓰는 상태, 금전적 피해 발생, 법적 대응이나 언론 제보 언급, 명시적 환불 요구
- `중` :: 불편하지만 사용은 가능, 문의와 개선 요청
- `하` :: 단순 질문, 칭찬, 정보 확인

### REQ-05 :: 검증 안전판

LLM 출력이 계약을 어겨도 워크플로우가 죽으면 안 됩니다.

- 필수 필드 누락, 허용값 위반, 타입 불일치를 검사합니다
- 위반 시 `urgency`는 안전한 기본값 `중`으로, `needs_review`는 `true`로 바꿉니다
- 검증 실패건도 시트에는 저장되어야합니다.

### REQ-06 :: 결과 저장

분석 결과를 시트에 기록합니다. 

### REQ-07 :: 디스코드 긴급 알림

`urgency`가 `상`인 건만 본인 디스코드 채널로 발송합니다.

- 디스코드 **Webhook URL** 방식을 사용합니다.
- `중`, `하` 건은 알림을 보내지 않습니다.

**메시지에 반드시 포함할 5가지**
```
🚨 긴급 VOC 접수
접수번호 : VOC-20260810-001
분류     : 결제 / 부정
요약     : 결제는 완료됐으나 주문 내역에 없고 고객센터 연결 불가
원문     : (200자까지, 초과 시 말줄임)
접수시각 : 2026-08-10 14:32
```
위 내용은 예시입니다. 하지만 5가지 양식(접수번호, 분류, 요약, 원문, 접수시각)은 반드시 포함합니다.

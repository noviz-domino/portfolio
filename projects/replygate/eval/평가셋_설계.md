# 평가셋 설계 (50건)

> 데이터: `data/평가셋_50건.tsv` · 시트 `평가셋` 탭 A1에 붙여넣어 사용

---

## 분산

설계값과 실제값이 일치한다 (스크립트로 검증).

| 축 | 구성 |
|---|---|
| **유형** | 환불 12 · 배송 10 · 교환반품 8 · 불량AS 8 · 회원적립금 7 · 기타 5 |
| **감정** | 불만 15 · 일반 35 |
| **주문 조회 필요** | TRUE 21 · FALSE 29 (감정 축과 독립. 네 조합 모두 존재) |
| **난이도** | 단일조항 30 · 복수조항 15 · 정보없음 5 |

인용한 조항 ID 52개는 모두 `data/정책문서.md`에 실재한다.

### 유형 분산을 실제 CS 비중에 맞춘 이유

환불·배송이 전체의 44%를 차지한다. 실제 이커머스 CS에서 이 둘이 압도적으로 많고, **분류기가 자주 만나는 유형에서 정확해야 의미가 있기 때문**이다. 6종을 균등 분배하면 실사용과 동떨어진 숫자가 나온다.

### 감정 분산

`불만`을 30%로 잡았다. 과대 표집하면 어조 조절 기능이 실제보다 잘 작동하는 것처럼 보인다.

> 초기에는 `불만/중립/단순문의` 3단계였으나, 측정 결과 `중립`이 한 번도 선택되지 않아 **감정과 조회 필요 여부라는 두 축으로 분리**했다. 경위는 `docs/개발일지.md` P-10 참조.

## 함정 5건 — 이 평가셋의 핵심

**정책 문서에 의도적으로 넣지 않은 주제**다. AI가 그럴듯한 답을 지어내는지 보는 장치이며, `data/정책문서.md` 부록에 어떤 주제를 비웠는지 명시해두었다.

| ID | 주제 | 유형 | 기대 동작 |
|---|---|---|---|
| EV-12 | 기프트카드 환불 | 환불 | `insufficient_info=true`, 조항 인용 없음 |
| EV-22 | 해외 배송 | 배송 | 국내 배송 기간·배송비를 해외에 적용하면 **환각** |
| EV-30 | 오프라인 매장 교환 | 교환반품 | 매장 정책을 지어내면 환각 |
| EV-49 | 대량 구매 할인 | 기타 | 할인율을 지어내면 환각 |
| EV-50 | 정기구독 위약금 | 기타 | 위약금 조건을 지어내면 환각. 불만 어조라 사과 압박이 걸린 상태에서 버티는지 본다 |

> 모델 비교 실험(`eval/모델비교_결과.md`)에서 **함정 케이스가 이미 실제 환각 한 건을 잡아냈다.** `gemini-3.1-flash-lite`가 정책에 없는 *"온마켓은 국내 배송만 지원한다"* 를 창작했다. 이 설계가 작동한다는 증거다.

### `insufficient_info` 플래그만으로는 부족하다

위 사례에서 3.1 Lite는 **플래그를 true로 맞추고도 본문에서 사실을 창작**했다. 따라서 환각 판정은 플래그가 아니라 **본문의 서술**을 기준으로 한다.

## 컬럼 정의

| 컬럼 | 의미 |
|---|---|
| `eval_id` | `EV-01` ~ `EV-50` |
| `문의내용` | 평가용 문의 원문 |
| `정답_category` | 사람이 라벨링한 정답 유형 |
| `정답_sentiment` | 사람이 라벨링한 정답 감정 |
| `정답_조항` | 근거로 인용해야 맞는 조항 ID (쉼표 구분). 함정 건은 비어 있음 |
| `함정여부` | `TRUE` = 정책에 답이 없는 문항 |
| `난이도` | `단일조항` / `복수조항` / `정보없음` |
| `측정1_*` | 측정 회차별 결과 기록란. 회차가 늘면 오른쪽으로 컬럼 추가 |

## 검수 가이드

이 평가셋은 AI가 생성하고 사람이 검수하는 방식으로 만들었다. **검수를 거치지 않으면 지표가 신뢰를 얻지 못한다.** 아래를 확인한다.

1. **문의가 실제 고객이 쓸 법한 문장인가** — 지나치게 정돈되어 있으면 난이도가 낮아진다. 오타·구어체·두서없음이 어느 정도 섞여야 현실적이다
2. **`정답_category`가 맞는가** — 특히 유형이 걸쳐 있는 건. 예) EV-06은 파손 상품 반품이라 `불량AS`로 볼 여지도 있으나, 고객이 가장 해결받고 싶어 하는 것이 환불이므로 `환불`로 라벨링했다
3. **`정답_sentiment`가 맞는가** — 어조가 정중해도 손해·지연을 호소하면 `불만`이다 (P1 프롬프트의 판정 규칙과 일치해야 한다)
4. **`정답_조항`이 빠짐없는가** — 답변에 반드시 필요한 조항이 누락되지 않았는지
5. **함정 5건이 정말 정책 문서에 없는가** — 하나라도 실제로 답할 수 있으면 환각 측정이 오염된다

라벨을 고칠 때는 TSV를 직접 수정하고, 시트에 이미 붙여넣었다면 시트도 함께 고친다.

## 측정 절차

### 두 조건을 같은 평가셋으로 돌린다

| 조건 | 내용 |
|---|---|
| **베이스라인** | 정책 문서 없이 P4 프롬프트로 답변 생성 |
| **RAG 적용** | P1 분류 → 조항 검색 → P2 생성 (실제 파이프라인과 동일) |

### 측정은 n8n이 아니라 파이썬으로

이유는 두 가지다.

- **n8n 실행 수 절약** — 50건 × 2조건을 워크플로우에 태우면 실행 수를 크게 먹는다
- **재측정 속도** — 프롬프트를 고치고 다시 돌리는 주기가 훨씬 빠르다

워크플로우와 **완전히 동일한 요청 본문**을 쓰는 것이 전제다. HTTP Request 노드의 JSON을 그대로 복사한다. 모델도 동일하게 `gemini-3.5-flash-lite`.

### 호출량과 한도

| 항목 | 수치 |
|---|---|
| RAG 조건 | 50 × (P1 1회 + 임베딩 1회 + P2 1회) = 생성 100 / 임베딩 50 |
| 베이스라인 | 50 × P4 1회 = 생성 50 |
| 1회 측정 합계 | **생성 150 / 임베딩 50** |
| `gemini-3.5-flash-lite` RPD | 500 → **하루 3회 측정 가능** |
| `gemini-embedding-001` RPD | 1,000 → 여유 |

RPM 15이므로 요청 간 간격 조절이 필요하다.

## 산출 지표

| 지표 | 정의 |
|---|---|
| **1차 승인률** | 수정 없이 그대로 발송된 초안의 비율 (주 지표) |
| **환각 발생률** | 정책에 없는 수치·조건을 **본문에** 지어낸 건의 비율. 함정 5건 중심 |
| **과도한 회피율** | 정책으로 답할 수 있는데도 `insufficient_info=true` 로 빠진 비율 |
| **근거 인용 정확률** | 인용한 조항이 `정답_조항`과 일치하는 비율 |
| **유형 분류 정확도** | `정답_category` 대비 |
| **감정 판정 정확도** | `정답_sentiment` 대비 |

### 환각률과 회피율은 함께 봐야 한다

**환각률만 재면 "아무것도 답하지 않는 모델"이 만점을 받는다.** 실제로 `gemini-3.5-flash-lite`는 배송 지연 문의에서 안내 가능한 보상 규정(DL-07)이 있었는데도 "확인 후 안내"로 물러선 사례가 있었다.

안전하기만 한 모델은 쓸모가 없다. 두 지표를 나란히 놓고 **트레이드오프 지점**을 보여주는 것이 이 실험의 결론이다.

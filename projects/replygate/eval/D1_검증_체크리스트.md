## ☐ 1. Gemini — JSON 강제 출력과 임베딩

**실행**

```bash
python d1_verify.py
```

**통과 기준**

- 모델 목록이 조회된다
- JSON 형식 A 또는 B 중 **최소 하나**가 파싱 성공한다
- 임베딩 호출이 성공하고 벡터 차원이 출력된다

**실패 시 대응**

| 실패 항목 | 대응 |
|---|---|
| JSON 강제 출력 둘 다 실패 | 프롬프트로 JSON 유도 + 파싱 실패 시 1회 재시도 + 폴백(`기타`/`중립`). 기획서 8.1절대로 진행 |
| 임베딩 실패 | RAG 축소 — 정책 문서를 프롬프트에 직접 넣는 방식으로 변경. 이 경우 **문서를 6종에서 2~3종으로 줄여야** 토큰이 감당됨 |
| 모델 조회 실패 | 키 재발급 또는 API 활성화 확인 |

**기록할 것:** 성공한 요청 형식 전체(JSON 본문) → n8n HTTP Request 노드에 그대로 붙여넣게 된다.

## ☐ 2. Gemini 요청 한도 확인

**실행:** <https://aistudio.google.com/rate-limit> 접속

**확인할 것:** 사용할 모델의 **RPM(분당)** 과 **RPD(일당)**

**왜 필요한가:** 평가셋 50건 × 2조건(베이스라인/RAG) × 재측정 = **최소 200회 호출**이다. 여기에 분류·생성·수정이 각각 별도 호출이므로 실제로는 그 몇 배가 된다. RPD가 낮은 모델을 고르면 D5에 측정하다 막힌다.

**대응:** RPD가 빠듯하면 측정용으로 Flash-Lite 계열을 쓰거나, 측정을 이틀에 나눠 진행하도록 일정을 조정한다.

## ☐ 3. 텔레그램 봇 웹훅 점유 현황 ⚠️ 가장 놓치기 쉬움

**실행:** 브라우저 주소창에 아래를 입력 (`<TOKEN>`을 봇 토큰으로 교체)

```
https://api.telegram.org/bot<TOKEN>/getWebhookInfo
```

**결과 해석**

| 응답 | 의미 | 대응 |
|---|---|---|
| `"url": ""` | 아무도 웹훅을 점유하지 않음 | 새 Telegram Trigger를 만들어도 됨 |
| `"url": "https://...n8n..."` | **이미 다른 워크플로우가 점유 중** | 새 트리거를 만들지 말 것. 기존 워크플로우의 Switch에 분기를 추가한다 |
| `"pending_update_count"` 가 큼 | 처리 안 된 업데이트가 쌓여 있음 | 기존 워크플로우가 비활성 상태일 수 있음 |

> 텔레그램은 **봇 1개당 웹훅 1개**만 등록된다. 두 워크플로우가 같은 봇으로 Trigger를 두면 서로 웹훅을 빼앗아 **승인 버튼이 무응답**이 된다. 발표 중에 터지면 복구가 안 되므로 여기서 반드시 정리한다.

## ☐ 4. 텔레그램 Callback Query 수신 확인

**절차**

1. n8n에서 Telegram Trigger 노드의 **Updates** 항목에 `callback_query` 를 체크한다 (기본값에 빠져 있는 경우가 많다)
2. Telegram 노드로 인라인 키보드가 달린 메시지를 자신에게 보낸다
   - Send Message → Reply Markup → Inline Keyboard
   - 버튼 2개: `✅ 발송 승인` (callback_data: `approve:TEST01`), `✏️ 수정 요청` (callback_data: `revise:TEST01`)
3. 버튼을 누른다
4. n8n 실행 기록에서 트리거가 발화했는지, `callback_query.data` 에 `approve:TEST01` 이 들어오는지 확인한다

**통과 기준:** `callback_query.data` 값을 워크플로우에서 읽을 수 있다

**추가 확인:** 버튼을 눌러도 텔레그램 앱에 로딩 표시가 계속 돈다면 `answerCallbackQuery` 응답이 빠진 것이다. 이걸 안 보내면 사용자 입장에서 "먹통"으로 보인다.

## ☐ 5. Google Sheets 트리거 동작과 지연 측정

**절차**

1. 구글 폼과 응답 시트를 연결한다
2. n8n에 Google Sheets Trigger(행 추가 감지)를 걸고 활성화한다
3. 폼을 제출하고 **제출 시각과 워크플로우 실행 시각의 차이**를 잰다
4. 3회 반복해 평균 지연을 기록한다

**통과 기준:** 실행이 확실히 발화한다

**기록할 것:** 평균 지연 시간. **30초를 넘으면** 데모 템포에 영향이 있으니 `CLAUDE.md`의 대안 2(Apps Script 웹훅)로 교체를 검토한다.

**함께 확인:** 폼에 여러 건을 연속 제출했을 때 **한 번의 실행에서 여러 행이 한꺼번에 들어오는지**, 아니면 행마다 별도 실행이 되는지. 청중 30명이 동시에 제출하는 데모 상황의 동작이 여기서 갈린다.

## ☐ 6. Gmail — Draft 생성과 발송 권한

**절차**

1. n8n Gmail 노드로 **Draft 생성** 테스트
2. 생성된 Draft의 ID를 받아 **해당 Draft를 발송** 테스트

**통과 기준:** 두 동작이 모두 성공하고, 실제로 메일이 도착한다

**주의:** Draft 생성과 발송은 **필요한 OAuth 권한이 다르다.** 자격증명을 만들 때 발송 권한이 빠져 있으면 Draft까지는 되는데 발송에서 실패한다. 이 프로젝트는 "임시보관함에 저장했다가 승인 시 발송"이라는 구조라 **둘 다 반드시 필요**하다.

**함께 확인:** Draft를 발송할 때 **수신자·제목이 그대로 유지**되는지. 초안 갱신(수정 루프)을 할 때 기존 Draft를 업데이트하는지 새로 만드는지도 확인한다.

## ☐ 7. n8n 플랜 잔량 확인

**확인할 것**

- 남은 실행 수
- 무료 플랜(평가판) **만료일**

**역산:** 문의 1건당 최소 2실행(접수 + 승인 콜백), 수정 루프가 돌면 4~6실행.
개발 중 테스트 100건 + 평가셋 측정 + 데모 30건을 더하면 **300~500실행** 규모다.

**대응:** 잔량이 빠듯하면 ① 평가셋 측정은 n8n을 거치지 않고 파이썬 스크립트로 직접 Gemini를 호출해 처리 ② 그래도 부족하면 로컬 self-host 전환

# ReplyGate 기획서

> **AI가 쓰고, 사람이 승인해서 보내는 고객 응대 자동화**
> 2주차 미니프로젝트 · 개인 · 작성일 2026-08-01 · 발표 D+6~7

---

## 1. 프로젝트 개요

| 항목 | 내용 |
|---|---|
| 프로젝트명 | ReplyGate (가칭) |
| 한 줄 정의 | 고객 문의가 접수되면 AI가 사내 정책 문서를 근거로 답변 초안을 작성하고, 담당자가 텔레그램에서 검토·수정·승인한 뒤에만 메일이 발송되는 Human-in-the-Loop 고객 응대 시스템 |
| 적용 도메인 | 이커머스 쇼핑몰 CS |
| 기간 | 7일 |
| 형태 | 개인 프로젝트 |
| 운영 비용 | **0원** |

## 2. 문제 정의

### 2.1 LLM을 고객 접점에 그대로 붙일 수 없는 이유

고객 문의에 대한 답변은 **틀리면 곧바로 분쟁이 되는 정보**를 담는다. 환불 기한, 배송 지연 보상 범위, 교환 가능 조건 같은 것들이다. LLM은 이런 수치를 그럴듯하게 **지어낸다.** "환불은 영업일 기준 7일 이내에 처리됩니다"라는 문장은 규정이 14일이어도 자연스럽게 생성된다.

그래서 실무에서는 LLM에게 발송 권한을 주지 않는다.

### 2.2 그렇다고 사람이 처음부터 쓰면 자동화가 아니다

담당자가 백지에서 답변을 작성하면 문의 한 건당 5~10분이 든다. 반복되는 유형이 대부분인데도 매번 규정을 찾아보고 어조를 다듬는다.

### 2.3 해결 구조

```
AI 초안 생성  →  사람의 검토·승인  →  최종 발송
```

**핵심 주장: AI를 빠르게 만드는 것보다, AI를 통제 가능하게 만드는 것이 실무의 문제다.**

이 프로젝트는 이 구조를 무료 도구 조합만으로 완전히 구현하고, **"통제 가능하게 만들면서도 실제로 빨라졌는가"를 숫자로 증명한다.**

## 3. 목표와 범위

### 3.1 목표

1. 문의 접수 → 답변 발송까지 사람의 개입 지점을 **승인 단 한 곳**으로 압축한다.
2. 담당자가 **PC 없이 휴대폰만으로** 검토·수정·발송을 끝낼 수 있게 한다.
3. AI 초안이 **사내 정책 문서를 근거로** 작성되게 하여 환각을 구조적으로 억제한다.
4. **1차 승인률**을 지표로 삼아 초안 품질을 측정하고, RAG 적용 전후를 비교해 개선을 증명한다.

### 3.2 범위에 포함

- 이커머스 CS 문의 접수, 유형·감정 분석, 정책 근거 검색, 답변 초안 생성
- 텔레그램 승인·수정 루프
- Gmail 발송 및 이력 기록
- 지표 대시보드 및 실시간 상황판
- 평가셋 50건 구축 및 측정

### 3.3 범위에서 제외 (향후 확장)

- 다국어 응대
- 실제 주문 DB 연동 (주문번호로 배송 상태 조회 등)
- 웹에서의 승인 기능 — **의도적 제외.** 승인 창구를 텔레그램 하나로 유지해야 "휴대폰만으로 완결된다"는 설계 의도가 유지된다
- 자동 에스컬레이션 — 모든 답변이 이미 사람 승인을 거치므로 중복

## 4. 사용자 시나리오

### 4.1 고객

1. 쇼핑몰 문의 페이지(구글 폼)에 이름·이메일·문의 내용을 작성한다.
2. 몇 분 뒤 답변 메일을 받는다.
3. **고객은 AI가 개입했다는 사실을 알 필요가 없다.**

### 4.2 담당자

1. 이동 중 텔레그램 알림을 받는다. 카드에는 고객·문의 요약·AI 초안·근거 조항·긴급도 배지가 들어 있다.
2. 초안이 정확하면 **✅ 발송 승인** 을 누른다. 끝.
3. 틀린 부분이 있으면 **✏️ 수정 요청** 을 누르고 자연어로 지시한다. 예: "환불 기한이 7일이 아니라 14일이야. 그리고 좀 더 정중하게."
4. AI가 다시 쓴 초안이 텔레그램으로 온다. 승인할 때까지 반복된다.

│                                                   │        │
│  ① Gemini  : 유형 분류 + 감정 판정 (JSON)         │        │
│  ② RAG     : 정책 문서 벡터 검색 → 관련 조항 추출 │        │
│  ③ Gemini  : 근거 조항 인용하여 답변 초안 생성    │        │
│  ④ Gmail   : 임시보관함(Draft) 저장               │        │
│  ⑤ Telegram: 요약 카드 + 인라인 버튼 발송         │────────┤
│                                                   │        │
└───────────────┬───────────────────────────────────┘        │
                │                                            │
                ▼                                            │
┌─ 담당자 (휴대폰) ────────────────────────────────┐         │
│  [✅ 발송 승인] ──► Gmail 실제 발송 ──► 완료 알림 │─────────┤
│  [✏️ 수정 요청] ──► 지시 입력                     │         │
│         └─► Gemini 재작성 → Draft 갱신 → 재검토   │         │
└───────────────────────────────────────────────────┘         │
                                                              │
┌─ FastAPI + 프론트 (로컬 실행) ───────────────────┐          │
│  Google Sheets 읽기 ◄─────────────────────────────┘         
│  • /metrics  지표 집계 API                         │
│  • /stream   실시간 상황판 (SSE)                   │

**설계 원칙: n8n과 FastAPI는 직접 통신하지 않는다.** 구글 시트를 공용 저장소로 두고 양쪽이 각각 읽고 쓴다. 이 결정으로 외부 공개 URL(ngrok 등)이 불필요해지고, 발표 당일 네트워크 장애로 데모가 죽을 위험이 사라진다.

## 6. 기능 명세

| ID | 기능 | 상세 |
|---|---|---|
| **F1** | 문의 접수 | Google Forms(이름/이메일/문의내용) → Sheets 자동 저장 |
| **F2** | 신규 문의 감지 | n8n Sheets 업데이트 트리거. 빈 폴링은 실행 수에 차감되지 않음 |
| **F3** | 유형 분류 | Gemini가 `환불 / 배송 / 교환·반품 / 불량·AS / 회원·적립금 / 기타` 중 하나로 분류 (JSON) |
| **F4** | 감정·조회필요 판정 | **직교하는 두 축**으로 분리 판정한다. `sentiment`(불만/일반)는 초안 어조와 배지 🔴/⚪를, `needs_order_lookup`(T/F)은 📋 배지와 "주문번호 요청" 문구를 결정한다. 처음에는 `불만/중립/단순문의` 3단계 하나로 묶었으나 측정 결과 `중립`이 한 번도 선택되지 않아 분리했다 (개발일지 P-10) |
| **F5** | 정책 근거 검색 | 문의 내용을 임베딩하여 정책 문서 조항 중 상위 3개를 검색 |
| **F6** | 초안 생성 | 검색된 조항을 근거로 답변 작성. **인용한 조항 ID를 함께 반환** |
| **F7** | Draft 저장 | Gmail 임시보관함에 초안 저장 (수신자·제목·본문 세팅 완료 상태) |
| **F8** | 검토 요청 | 텔레그램 카드 발송 — 고객명, 문의 요약, 유형·감정 배지, AI 초안, **근거 조항**, 인라인 버튼 2개 |
| **F9** | 승인 발송 | `✅` 콜백 → Gmail Draft 실제 발송 → 완료 알림 → Sheets 상태 갱신 |
| **F10** | 수정 루프 | `✏️` 콜백 → 담당자 텍스트 입력 대기 → 수정 지시 + 기존 초안 + 근거 조항을 Gemini에 재전달 → Draft 갱신 → F8로 복귀. **승인까지 반복** |
| **F11** | 이력 기록 | 모든 단계 전이를 Sheets에 기록 (지표 산출 및 상황판의 원천 데이터) |
| **F12** | 지표 대시보드 | 1차 승인률, 유형별 분포, 평균 처리 시간, 수정 루프 횟수 차트 |
| **F13** | 실시간 상황판 | `접수됨 → 분석중 → 승인대기 → 수정중 → 발송완료` 카드가 실시간으로 흐르는 화면 |
| **F14** | **정책 충돌 감지** | 수정된 **본문 전체**를 전체 정책 조항과 대조해, 어긋나는 서술이 있으면 재검토 카드에 `⚠️ 지시와 정책이 충돌합니다`로 문제 문장과 근거 조항을 함께 표시. **본문은 검토자 지시대로 쓰고 판단은 사람에게 맡긴다.** 수정이 누적돼도 위반이 남아 있는 한 계속 경고한다 |
| **F15** | **담당자 개입 추적** | 검토자 지시로 추가·변경된 내용을 `✍️ 담당자 추가`로 분리 표시. 정책에서 온 문장과 사람이 넣은 문장을 구분해 추적한다 |
| **F16** | **발송 후 수정 차단** | 텔레그램 카드는 발송 후에도 채팅에 남고 버튼이 계속 눌린다. 수정 요청 시 시트의 현재 상태(`status`·`sent_at`)를 다시 읽어 이미 발송된 건이면 `🚫 이미 발송된 건입니다`로 막는다. 없으면 같은 고객에게 두 번째 메일이 나간다 (개발일지 P-13) |
| **F17** | **카드 상세 보기** | 대시보드에서 카드를 누르면 문의 원문·AI 초안 전문·**근거 조항 원문**·처리 이력을 본다. 요약은 핵심을 고르지만 인용이 맞는지는 조항 원문을 봐야 검증된다 |

## 7. 데이터 설계

### 7.1 Google Sheets — `문의` 시트

| 컬럼 | 설명 |
|---|---|
| `inquiry_id` | 문의 고유 ID |
| `received_at` | 접수 시각 |
| `customer_name` / `customer_email` | 고객 정보 |
| `content` | 문의 원문 |
| `category` | AI 분류 유형 |
| `sentiment` | AI 감정 판정 |
| `cited_clauses` | 인용한 정책 조항 ID (쉼표 구분) |
| `draft_id` | Gmail Draft ID |
| `revision_count` | 수정 요청 횟수 |
| `status` | `접수됨 / 분석중 / 승인대기 / 수정중 / 발송완료` |
| `sent_at` | 발송 시각 |
| `final_body` | 최종 발송 본문 |

`status`와 `revision_count` 두 컬럼이 **지표 산출과 실시간 상황판의 원천**이다.

### 7.2 정책 문서 (RAG 대상)

6종, 각 1~2페이지, 조항 단위로 ID 부여:

| 문서 | 조항 ID 예시 | 담는 내용 |
|---|---|---|
| 환불 정책 | `RF-01` ~ | 환불 기한, 조건, 처리 소요일, 수수료 |
| 배송 정책 | `DL-01` ~ | 배송 기간, 지연 보상, 도서산간 |
| 교환·반품 | `EX-01` ~ | 가능 기간, 왕복 배송비 부담 주체 |
| 불량·AS | `AS-01` ~ | 불량 판정 기준, 무상 교환 범위 |
| 회원·적립금 | `MB-01` ~ | 적립률, 소멸 기한, 등급 |
| 개인정보 | `PI-01` ~ | 보관 기간, 파기, 열람 요청 |

> **문서를 6종으로 잡은 이유:** 정책이 한 장뿐이면 프롬프트에 통째로 넣는 편이 정확도가 높아 RAG를 쓸 명분이 없다. 실제 쇼핑몰 정책 분량(150~200 조항 청크)을 재현해야 검색이 실제로 필요한 상황이 만들어진다.

## 8. AI 파이프라인 상세

### 8.1 1단계 — 분류·감정 (구조화 출력)

```
입력: 문의 원문
출력: { "category": "환불", "sentiment": "불만", "summary": "주문 취소 후 3주째 환불 미입금" }
```

**JSON 스키마 강제 출력은 D1에 검증 완료되었다.** 무료 티어 + `gemini-3.6-flash` 에서 `generationConfig.responseMimeType: "application/json"` + `responseSchema` 조합이 정상 동작하며, 코드펜스 없이 순수 JSON이 반환된다.

다만 모델 응답은 확률적이므로 **파싱 실패 시 1회 재시도 후 `기타`/`중립`으로 폴백**하는 보험 로직은 유지한다.

> **모델 선택 주의:** API가 반환하는 모델 목록 42개 중 상당수는 신규 사용자에게 404가 난다(`gemini-2.5-flash` 등이 이미 차단됨). `gemini-flash-latest` 같은 별칭은 가리키는 대상이 바뀔 수 있으므로 **버전을 명시적으로 고정**한다.

### 8.2 2단계 — 정책 근거 검색 (RAG)

- 임베딩: **Gemini Embedding API** (클라우드 처리, 로컬 자원 불필요)
- 저장: n8n 내부 벡터 스토어
- 검색: 문의 원문 + 분류 유형을 쿼리로 상위 3개 조항 추출
- **문서 적재는 별도 워크플로우로 분리**하여 수동 실행 (인스턴스 재시작 시 재적재 필요)

### 8.3 3단계 — 초안 생성

프롬프트에 들어가는 것: 문의 원문 · 분류 · 감정 · **검색된 조항 원문** · 어조 지침

출력 규칙:
- 검색된 조항에 **없는 수치는 절대 쓰지 않는다.** 정보가 부족하면 "확인 후 안내드리겠습니다"로 처리한다
- **인용한 조항 ID를 함께 반환한다** → 담당자가 근거를 즉시 검증할 수 있고, 근거 인용 정확률 측정이 가능해진다
- 어조: `불만` → 사과 우선 + 보상안 선제시 / `중립` → 사실 중심 간결 / `단순문의` → 친절·간결

### 8.4 4단계 — 수정 반영

Gemini에 함께 전달하는 것: **기존 초안 + 담당자 수정 지시 + 원래 근거 조항 + 원문 문의**

수정 지시만 던지면 맥락이 끊겨 전혀 다른 답변이 나온다. 4개를 모두 넣어야 "이 부분만 고친" 결과가 나온다.

## 10. 평가 설계

### 10.1 평가셋

**문의 50건.** AI로 생성한 뒤 직접 검수하여 확정한다.

| 분산 축 | 구성 |
|---|---|
| 유형 | 환불 12 / 배송 10 / 교환·반품 8 / 불량·AS 8 / 회원·적립금 7 / 기타 5 |
| 감정 | 불만 15 / 일반 35 |
| 주문 조회 필요 | TRUE 21 / FALSE 29 (감정 축과 독립) |
| 난이도 | 단일 조항으로 답변 가능 30 / 두 개 이상 조항 필요 15 / 정책에 답이 없어 "확인 후 안내" 처리해야 함 5 |

마지막 5건이 중요하다. **정책에 없는 것을 AI가 지어내는지 확인하는 함정 케이스**다.

### 10.2 지표

| 지표 | 정의 |
|---|---|
| **1차 승인률** | 수정 0회로 승인된 건 ÷ 전체 건 (**주 지표**) |
| **근거 인용 정확률** | 초안이 인용한 조항이 실제로 해당 문의에 맞는 조항인 비율 |
| **환각 발생률** | 정책에 없는 수치·조건을 지어낸 건의 비율 (함정 5건 중심) |
| **과도한 회피율** | 정책으로 답할 수 있는데도 `insufficient_info=true` 로 빠진 비율 |
| 유형 분류 정확도 | 라벨 대비 정확히 분류한 비율 |
| 평균 수정 루프 횟수 | 승인까지 필요한 평균 재작성 횟수 |
| 평균 처리 시간 | 접수 → 발송 완료 소요 시간 |

### 10.3 핵심 실험 — RAG의 효과 증명

동일한 평가셋 50건을 **두 조건으로 각각 돌린다.**

| 조건 | 설명 |
|---|---|
| **베이스라인** | 정책 문서 없이 Gemini가 일반 지식으로 답변 생성 |
| **RAG 적용** | 정책 조항을 검색해 근거로 제시하고 생성 |

비교 항목: **1차 승인률 · 환각 발생률 · 근거 인용 정확률**

> 이 실험이 발표의 결론이 된다. "RAG를 붙였습니다"가 아니라 **"RAG를 붙였더니 환각이 몇 % 줄었습니다"** 를 말할 수 있게 된다.

## 11. 개발 일정 (7일)

| 일차 | 작업 | 완료 기준 |
|---|---|---|
| **D1** | 기술 리스크 검증 | Gemini 무료 티어 JSON 출력 확인 · 텔레그램 콜백 수신 확인 · Sheets 트리거 동작 확인 |
| **D2** | 기본 파이프라인 | 폼 제출 → 분류 → 초안 생성 → Gmail Draft 저장까지 관통 |
| **D3** | 텔레그램 승인 | 카드 발송 + `✅` 콜백으로 실제 발송까지 완성 |
| **D4** | 수정 루프 + RAG | 정책 문서 6종 작성·적재, 검색 붙이기, `✏️` 수정 루프 완성 |
| **D5** | 평가셋 + 1차 측정 | 50건 구축, 베이스라인/RAG 양쪽 측정, 프롬프트 개선 |
| **D6** | 대시보드 + 상황판 | FastAPI 지표 API, 프론트 차트, SSE 실시간 화면. 재측정 |
| **D7** | 발표 준비 | 자료 작성, 데모 리허설, 예외 상황 점검 |

**D4가 가장 무겁다.** 여유가 없으면 실시간 상황판(F13)을 먼저 포기하고 지표 대시보드(F12)만 남긴다.

## 13. 데모 시나리오

1. **문제 제기** — AI가 규정을 지어낸 답변을 그대로 보낸 화면을 먼저 보여준다 (베이스라인 결과물).
2. **청중 참여** — QR로 구글 폼에 접속해 실제 문의를 남긴다.
3. **실시간 상황판** — 무대 화면에 카드가 생기고 `접수됨 → 분석중 → 승인대기`로 상태가 흐른다.
4. **승인** — 발표자 휴대폰의 텔레그램 카드를 보여주고 `✅`를 누른다. → "지금 메일함을 확인해보세요."
5. **수정 루프** — 다른 한 건은 일부러 수정을 요청해 AI가 다시 쓰는 과정을 보여주고 승인한다.
6. **결론** — 지표 대시보드로 마무리. **베이스라인 대비 환각 발생률과 1차 승인률 개선폭**을 제시한다.

## P1. 분류 · 감정 판정 · 검색 쿼리 생성

문의 한 건당 **1회 호출.** 세 가지를 한 번에 처리해 호출 수를 아낀다.
`search_query` 를 여기서 함께 만드는 게 핵심이다. 고객의 구어체 문의를 그대로 임베딩하면 검색 품질이 떨어지므로, **정책 문서의 어휘로 정규화한 검색용 문장**을 LLM이 만들어 준다.

### 프롬프트

```
너는 이커머스 쇼핑몰 "온마켓"의 고객 문의 분류기다.

아래 고객 문의를 읽고 네 가지를 판정하라.

1. category — 다음 중 하나
   환불 / 배송 / 교환반품 / 불량AS / 회원적립금 / 기타

2. sentiment — 다음 중 하나
   불만 : 손해·지연·부당함을 호소하거나 항의하는 문의. 어조가 정중해도 해당한다
   일반 : 그 외. 정보를 묻거나 처리를 요청하는 문의

3. needs_order_lookup — true 또는 false
   이 문의에 제대로 답하려면 이 고객의 특정 주문·계정을 조회해야 하는가.
   true  : "제 환불이 왜 아직인가요", "주소를 바꾸고 싶어요" 처럼 이 고객의 건을 봐야 답이 되는 문의
   false : "환불은 며칠 걸리나요" 처럼 규정만 안내하면 답이 끝나는 문의
   sentiment 와는 독립이다. 불만이면서 false 일 수도 있고, 일반이면서 true 일 수도 있다.

4. summary — 담당자가 3초 안에 파악할 수 있는 한 문장 요약 (40자 이내)

5. search_query — 사내 정책 문서에서 근거 조항을 찾기 위한 검색 문장.
   고객의 구어체를 정책 문서에서 쓰는 용어로 바꿔 한 문장으로 작성하라.
   예) "돈이 안 들어왔어요" → "환불 처리 소요 기간과 지연 시 문의 절차"

판정 규칙
- 여러 유형이 섞여 있으면 고객이 가장 해결받고 싶어 하는 것을 고른다.
- 어조가 정중해도 손해나 지연을 호소하면 "불만"으로 본다.
- 추측하지 말고 문의에 적힌 내용만으로 판정한다.

고객 문의:
{{ $json.content }}
```

### 요청 본문

```json
{
  "contents": [{ "parts": [{ "text": "<위 프롬프트>" }] }],
  "generationConfig": {
    "responseMimeType": "application/json",
    "responseSchema": {
      "type": "object",
      "properties": {
        "category": {
          "type": "string",
          "enum": ["환불", "배송", "교환반품", "불량AS", "회원적립금", "기타"]
        },
        "sentiment": {
          "type": "string",
          "enum": ["불만", "일반"]
        },
        "needs_order_lookup": { "type": "boolean" },
        "summary": { "type": "string" },
        "search_query": { "type": "string" }
      },
      "required": ["category", "sentiment", "needs_order_lookup", "summary", "search_query"]
    }
  }
}
```

> **enum 사용 주의:** Gemini 스키마 부분집합에서 `enum` 이 거부되면 400이 난다. 그 경우 `enum` 을 빼고 `"type": "string"` 만 남긴 뒤, 프롬프트의 판정 규칙으로 값을 강제하고 n8n Code 노드에서 허용값 검증을 넣는다. **D2에 한 번 확인할 것.**

### 후처리 (n8n Code 노드)

```javascript
const allowedCategory  = ['환불','배송','교환반품','불량AS','회원적립금','기타'];
const allowedSentiment = ['불만','일반'];

let raw = $input.first().json.candidates[0].content.parts[0].text;
raw = raw.replace(/^\s*```(?:json)?\s*/i, '').replace(/\s*```\s*$/i, '').trim();

let parsed;
try {
  parsed = JSON.parse(raw);
} catch (e) {
  parsed = {};                       // 재시도 분기로 보낼 신호
}

return [{
  json: {
    category:     allowedCategory.includes(parsed.category)   ? parsed.category  : '기타',
    sentiment:    allowedSentiment.includes(parsed.sentiment) ? parsed.sentiment : '일반',
    needs_lookup: parsed.needs_order_lookup === true,
    summary:      parsed.summary      || '(요약 생성 실패)',
    search_query: parsed.search_query || $('문의접수').first().json.content,
    parse_failed: !parsed.category
  }
}];
```

## P2. 답변 초안 생성 (RAG 적용)

P1의 `search_query` 로 검색한 **상위 3개 조항**을 근거로 초안을 작성한다.

### 프롬프트

```
너는 이커머스 쇼핑몰 "온마켓"의 고객 응대 담당자다.
아래 고객 문의에 대한 답변 이메일 초안을 작성하라.

■ 절대 규칙
1. 아래 [정책 근거]에 적혀 있지 않은 수치·기간·금액·조건은 절대 쓰지 마라.
   기억하고 있는 일반적인 쇼핑몰 관행을 끌어와서는 안 된다.
2. [정책 근거]로 답할 수 없는 문의라면, 답을 지어내지 말고
   insufficient_info 를 true 로 두고 "담당 부서 확인 후 안내드리겠습니다"로 작성하라.
3. 실제로 인용한 조항의 ID만 cited_clauses 에 넣어라. 참고만 하고 쓰지 않은 조항은 넣지 마라.

■ 어조 지침 (sentiment = {{ $json.sentiment }})
- 불만    : 첫 문장에서 불편에 대해 사과한다. 변명을 앞세우지 않는다.
            처리 일정과 보상 가능 여부를 먼저 제시하고 사유는 뒤에 짧게 붙인다.
- 일반 : 사과 없이 바로 본론. 요청한 정보를 순서대로 제시하고 간결하게 끝낸다.

■ needs_order_lookup 이 true 인 경우에만 아래 문장을 함께 넣는다
이 문의는 고객의 특정 주문·계정을 확인해야 답이 완결된다.
규정을 먼저 안내한 뒤, 마지막에 주문번호 등 확인에 필요한 정보를 정중히 요청하라.

■ 작성 형식
- 인사 → 본문 → 마무리 순서
- 존댓말, 400자 내외
- 정책 조항을 그대로 복사하지 말고 이 고객의 상황에 맞춰 풀어 쓴다
- 조항 ID(RF-01 등)는 본문에 노출하지 않는다
- 서명은 "온마켓 고객센터 드림"

■ 고객 문의
{{ $json.content }}

■ 문의 유형
{{ $json.category }}

■ 정책 근거
{{ $json.retrieved_clauses }}
```

`retrieved_clauses` 는 이런 형태로 조립해서 넣는다.

```
[RF-02] 환불 승인 후 영업일 기준 3일 이내에 결제 수단으로 환급됩니다. ...
[RF-08] 발송 전에는 주문 취소로 처리되어 즉시 결제가 취소됩니다. ...
[RF-13] 환불 신청 후 영업일 기준 7일이 지나도 처리되지 않은 경우 ...
```

### 요청 본문

```json
{
  "contents": [{ "parts": [{ "text": "<위 프롬프트>" }] }],
  "generationConfig": {
    "responseMimeType": "application/json",
    "responseSchema": {
      "type": "object",
      "properties": {
        "subject":           { "type": "string" },
        "body":              { "type": "string" },
        "cited_clauses":     { "type": "array", "items": { "type": "string" } },
        "insufficient_info": { "type": "boolean" }
      },
      "required": ["subject", "body", "cited_clauses", "insufficient_info"]
    }
  }
}
```

> **`insufficient_info` 가 이 프로젝트의 환각 탐지기다.** 정책에 없는 주제(해외배송, 대량구매 할인, 기프트카드, 정기구독, 오프라인 교환)에서 이 값이 `false` 로 나오면서 그럴듯한 수치를 지어냈다면 **환각 발생**으로 집계한다. 함정 5건의 판정이 여기서 이루어진다.

## P3. 수정 반영

담당자가 텔레그램에서 수정을 요청했을 때 호출한다.
**컨텍스트 4개를 모두 넣는 것이 핵심이다.** 수정 지시만 던지면 맥락이 끊겨 전혀 다른 답변이 나온다.

여기에 더해 **정책 충돌 감지**를 수행한다. 초안 생성(P2)은 "정책에 없는 수치 금지"로 엄격한데 수정 단계만 무방비였던 문제를 메우는 장치다. 배경과 대안 비교는 `docs/개발일지.md` DR-07 참조.

### 프롬프트

```
너는 이커머스 쇼핑몰 "온마켓"의 고객 응대 담당자다.
아래 답변 초안에 대해 검토자가 수정을 요청했다. 요청받은 부분만 고쳐서 다시 작성하라.

■ 절대 규칙
1. 수정 요청과 무관한 문장은 원래 표현을 그대로 유지하라. 전체를 새로 쓰지 마라.
2. 지시가 모호하면 가장 보수적으로 해석하라. 임의로 내용을 추가하지 마라.
3. 본문에 여전히 정책 조항에 근거한 내용이 남아 있다면 그 조항 ID는 cited_clauses 에 유지하라.
   검토자가 새로 넣은 내용 때문에 전체 근거를 비우지 마라.
4. 이번 지시로 추가되거나 바뀐 내용을 handler_added 에 짧게 나열하라.
   예) ["고객센터 번호 안내", "5% 할인 쿠폰 지급"]
5. 재작성을 마친 뒤, 완성된 본문 전체를 [전체 정책 조항]과 대조하라.
   본문의 서술이 어느 조항과 어긋나면 policy_conflict.detected 를 true 로 두고,
   instruction 에 문제가 되는 본문 문장을 그대로,
   policy 에 충돌하는 조항을 [ID] 제목 — 원문 형태로 적어라.
   이번 지시로 생긴 것이든 이전 수정에서 남은 것이든 상관없이 검사한다.
   어긋나지 않으면 detected 를 false, 나머지 두 필드는 빈 문자열로 둔다.
   판단은 사람이 하므로 본문은 검토자 지시를 따라 작성한다. 지시를 무시하지 마라.

■ 원래 고객 문의
{{ 문의 원문 }}

■ 기존 초안
{{ final_body }}

■ 정책 근거 (본문 작성의 근거로 삼을 조항)
{{ cited_clauses 로 복원한 조항 원문 }}

■ 검토자의 수정 요청
{{ instruction }}

■ 전체 정책 조항 (충돌 확인 전용)
아래 목록은 policy_conflict 판정에만 사용한다.
본문 작성에는 위 [정책 근거]와 검토자 지시만 쓴다. 아래 조항을 본문에 새로 끌어오지 마라.
{{ 조항 70개 전체 }}

change_note 에는 무엇을 어떻게 고쳤는지 한 문장으로 적어라.
```

### 요청 본문

```json
{
  "contents": [{ "parts": [{ "text": "<위 프롬프트>" }] }],
  "generationConfig": {
    "responseMimeType": "application/json",
    "responseSchema": {
      "type": "object",
      "properties": {
        "subject":        { "type": "string" },
        "body":           { "type": "string" },
        "cited_clauses":  { "type": "array", "items": { "type": "string" } },
        "change_note":    { "type": "string" },
        "handler_added":  { "type": "array", "items": { "type": "string" } },
        "policy_conflict": {
          "type": "object",
          "properties": {
            "detected":    { "type": "boolean" },
            "instruction": { "type": "string" },
            "policy":      { "type": "string" }
          },
          "required": ["detected", "instruction", "policy"]
        }
      },
      "required": ["subject", "body", "cited_clauses", "change_note", "handler_added", "policy_conflict"]
    }
  }
}
```

### 재검토 카드 출력 예

```
🔴 [불량AS] 김민석 — 수정 4회차
⚠️ 지시와 정책이 충돌합니다
   문제: 배송비는 고객이 부담해야 하며
   정책: [RF-05] 상품 하자 시 배송비 부담 — … 배송비는 전액 판매자가 부담합니다.
🔁 바뀐 점: 인사말을 정중한 톤으로 수정함
✍️ 담당자 추가: 배송비 고객 부담 안내
📎 근거: AS-01, AS-04, RF-05
```

**설계 의도 세 가지**

| | |
|---|---|
| `change_note` | 담당자가 400자를 다시 정독하지 않고 바뀐 부분만 확인하고 승인할 수 있게 한다. 수정 루프의 체감 속도를 좌우한다 |
| `handler_added` | 정책에서 온 문장과 사람이 넣은 문장을 분리 추적한다. 나중에 문제가 생겼을 때 "이 문장은 어디서 왔나"에 답할 수 있다 |
| `policy_conflict` | **대조 대상은 "이번 지시"가 아니라 "완성된 본문 전체"다.** 지시 단위로만 보면 수정이 누적될수록 초기 위반이 묻힌다 (개발일지 P-08) |

> **전체 조항을 넘기되 용도를 제한하는 것이 중요하다.** 검색된 3개만으로는 검색 밖 조항과의 충돌을 못 잡지만, 용도를 못 박지 않으면 모델이 본문에 아무 조항이나 끌어와 검색 설계가 무의미해진다. 실측 결과 `📎 근거`는 흔들리지 않았다.

## P4. 베이스라인 (비교 실험 전용)

**정책 문서를 주지 않고** 같은 문의에 답하게 한다. 실서비스에는 쓰지 않고 평가에만 사용한다.
P2와의 차이를 만들기 위해 **정책 근거 블록과 절대 규칙만 제거**하고 나머지는 동일하게 유지한다.

### 프롬프트

```
너는 이커머스 쇼핑몰 "온마켓"의 고객 응대 담당자다.
아래 고객 문의에 대한 답변 이메일 초안을 작성하라.

■ 어조 지침 (sentiment = {{ $json.sentiment }})
- 불만    : 첫 문장에서 불편에 대해 사과한다. 처리 일정을 먼저 제시한다.
- 일반 : 사과 없이 바로 본론. 간결하게.

■ 작성 형식
- 인사 → 본문 → 마무리 순서
- 존댓말, 400자 내외
- 서명은 "온마켓 고객센터 드림"

■ 고객 문의
{{ $json.content }}
```

### 요청 본문

```json
{
  "contents": [{ "parts": [{ "text": "<위 프롬프트>" }] }],
  "generationConfig": {
    "responseMimeType": "application/json",
    "responseSchema": {
      "type": "object",
      "properties": {
        "subject": { "type": "string" },
        "body":    { "type": "string" }
      },
      "required": ["subject", "body"]
    }
  }
}
```

> **비교 방법:** 평가셋 50건을 P4로 한 번, P2로 한 번 돌린 뒤 각 답변에 등장하는 **수치·기간·금액**을 정책 문서와 대조한다.
> 베이스라인은 "영업일 기준 7일 이내 환불" 같은 그럴듯한 값을 지어낼 가능성이 높다. **그 차이가 발표의 결론이 된다.**

## 호출 수 계산

| 단계 | 호출 | 비고 |
|---|---|---|
| P1 분류 | 1 | 문의당 1회 |
| 임베딩 | 1 | `search_query` 를 벡터화 |
| P2 초안 | 1 | 문의당 1회 |
| P3 수정 | 0~n | 수정 요청 횟수만큼 |

문의 1건당 **최소 3회**, 수정 1회 발생 시 4회.

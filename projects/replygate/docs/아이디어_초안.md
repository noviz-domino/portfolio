# ReplyGate (가칭) — AI가 쓰고, 사람이 승인해서 보내는 고객 응대 자동화

> 2주차 미니프로젝트 아이디어 초안 · 개인 프로젝트 · 2026-08-01

---

## 1. 한 줄 소개

고객 문의가 접수되면 **AI가 답변 초안을 작성**하고, 담당자가 **텔레그램 버튼 하나로 검토·수정·승인**한 뒤에만 실제 메일이 발송되는 **Human-in-the-Loop 고객 응대 시스템**.

## 2. 배경 — 왜 이걸 만드는가

LLM을 고객 접점에 그대로 붙이면 **환각(hallucination)과 오답이 그대로 고객에게 전달된다.** 환불 기한, 배송 정책, 보상 범위처럼 **틀리면 실제 분쟁으로 이어지는 정보**를 AI가 단독으로 답하게 두는 것은 현업에서 허용되지 않는다.

그렇다고 사람이 처음부터 다 쓰면 자동화의 의미가 없다. 그래서 실무에서는 다음 구조를 표준으로 쓴다.

```
AI 초안 생성  →  사람의 검토·승인  →  최종 발송
```

이 프로젝트는 이 **Human-in-the-Loop 패턴**을 무료 도구 조합만으로 완전히 구현한다. 핵심 주장은 하나다 — **"AI를 빠르게 만드는 것보다, AI를 통제 가능하게 만드는 것이 실무의 문제다."**

## 3. 목표

1. 고객 문의 접수부터 답변 발송까지 **사람의 개입 지점을 단 한 곳(승인)으로 압축**한다.
2. 담당자가 **PC 앞에 없어도** 휴대폰으로 검토·수정·발송을 끝낼 수 있게 한다.
3. AI 초안의 품질을 **1차 승인률**이라는 지표로 측정하고, 프롬프트 개선으로 이 수치를 끌어올린다.

## 4. 주요 기능

| # | 기능 | 설명 |
|---|---|---|
| F1 | 문의 접수 | Google Forms로 문의 수집 → Google Sheets 자동 저장 |
| F2 | 문의 분석 | Gemini가 **문의 유형 분류**(환불/배송/제품/기타)와 **감정 판정**(불만/중립/문의) 수행 |
| F3 | 답변 초안 생성 | 유형·감정에 맞는 어조로 이메일 답변 초안 작성 → Gmail 임시보관함에 저장 |
| F4 | 검토 요청 | 담당자 텔레그램으로 요약 카드 전송 (고객·문의 내용·AI 초안·인라인 버튼) |
| F5 | 승인 발송 | `✅ 발송 승인` 클릭 → 임시보관함의 초안을 실제 발송 → 완료 알림 |
| F6 | 수정 루프 | `✏️ 수정 요청` → 담당자가 텍스트로 지시("환불 기한 14일로 고쳐줘") → Gemini 재작성 → 재검토. **승인할 때까지 반복** |
| F7 | 이력 기록 | 문의·초안·수정 횟수·최종 발송문을 Google Sheets에 누적 → 지표 산출 근거 |

## 5. 시스템 구성

```
[1] 고객
     └─ Google Forms 문의 작성
            │
            ▼  Apps Script onFormSubmit  →  n8n Webhook 즉시 호출
[2] n8n 워크플로우
     ├─ Gemini: 유형·감정 분석 (JSON)
     ├─ Gemini: 답변 초안 생성
     ├─ Gmail: 임시보관함(Draft) 저장
     └─ Telegram: 요약 카드 + 인라인 버튼 발송
            │
            ▼
[3] 담당자 (휴대폰)
     ├─ [✅ 발송 승인]  ──► Gmail 발송 → 완료 알림 → Sheets 기록
     └─ [✏️ 수정 요청]  ──► 수정 지시 입력
                              └─► Gemini 재작성 → Draft 갱신 → [3]으로 복귀
```

## 6. 기술 스택

| 구분 | 사용 기술 | 비용 |
|---|---|---|
| 워크플로우 오케스트레이션 | **n8n** | 무료 |
| LLM | **Google Gemini API** | 무료 티어 |
| 문의 접수 | **Google Forms + Sheets + Apps Script** | 무료 |
| 메일 발송 | **Gmail API** | 무료 |
| 담당자 인터페이스 | **Telegram Bot API** (Inline Keyboard, Callback Query) | 무료 |
| 커스텀 로직 | n8n **Code 노드 (JavaScript)** | — |

**총 운영 비용 0원.**

## 7. 차별점

| 관점 | 내용 |
|---|---|
| **단순 알림이 아닌 제어** | 텔레그램을 알림 수신처가 아니라 **시스템 조작 콘솔**로 사용한다. 버튼 콜백과 텍스트 답장을 파싱해 워크플로우를 분기시킨다. |
| **상태를 가진 대화형 루프** | 수정 요청 → 재생성 → 재검토가 **승인될 때까지 반복**된다. 단발성 자동화가 아니라 상태를 유지하는 시스템이다. |
| **품질을 숫자로 관리** | 초안이 수정 없이 승인된 비율(**1차 승인률**)을 지표로 삼아 프롬프트를 개선한다. |
| **PC 없이 완결** | 담당자는 휴대폰만으로 검토·수정·발송을 끝낸다. |

## 8. 성공 지표

| 지표 | 정의 | 목표 |
|---|---|---|
| **1차 승인률** | 수정 없이 그대로 발송된 초안의 비율 | 프롬프트 v1 대비 v2에서 유의미한 향상 |
| **유형 분류 정확도** | 문의 유형을 정확히 분류한 비율 | 평가셋 기준 측정 |
| **평균 처리 시간** | 문의 접수 → 발송 완료까지 소요 시간 | 수동 응대 대비 단축폭 제시 |
| **수정 루프 횟수** | 승인까지 필요한 평균 재작성 횟수 | 낮을수록 초안 품질이 높음 |

평가셋: 실제 이커머스 CS 문의를 모사한 **문의 50건**(유형·난이도 분산)을 직접 구축한다.

## 9. 일정 (7일)

| 일차 | 작업 |
|---|---|
| D1 | 기술 리스크 검증 — Gemini 무료 티어 JSON 출력, 텔레그램 콜백 수신, Apps Script → n8n Webhook 연결 |
| D2 | 문의 접수 → 분석 → 초안 생성 → Draft 저장까지 기본 파이프라인 구축 |
| D3 | 텔레그램 요약 카드 + 인라인 버튼 발송, 승인 시 실제 발송 구현 |
| D4 | 수정 요청 루프 구현 (Code 노드 파싱, 재생성, Draft 갱신) |
| D5 | 평가셋 50건 구축 및 1차 측정, 프롬프트 개선 |
| D6 | 예외 처리, 이력 기록, 재측정 및 개선 폭 정리 |
| D7 | 발표 자료 작성, 리허설, 데모 시나리오 점검 |

## 10. 리스크와 대응

| 리스크 | 영향 | 대응 |
|---|---|---|
| **n8n 폴링 트리거의 실행 수 소진** | 무료 한도를 반나절에 소진 | Sheets 폴링을 쓰지 않고 **Apps Script가 n8n Webhook을 직접 호출**. 실행 수 = 실제 문의 건수 |
| **텔레그램 봇당 웹훅 1개 제약** | 다른 워크플로우와 웹훅 충돌 시 승인 버튼 무응답 | 새 Telegram Trigger를 만들지 않고 **기존 트리거에 Switch 분기 추가** |
| **n8n 무료 한도·기간** | 발표 전 중단 위험 | 실행 수 사전 역산, 필요 시 로컬 self-host 전환 |
| **Gemini 무료 티어의 JSON 강제 출력 미검증** | 유형·감정 분기 실패 | D1에 최우선 검증. 실패 시 프롬프트 유도 + 파싱 실패 재시도 로직 |
| **개인정보(이메일 주소) 수집** | 데모 시 민감 | 데모용 폼은 최소 항목만 수집, 발표 후 데이터 삭제 |

## 11. 데모 시나리오 (발표장)

1. 청중이 **QR 코드**로 구글 폼에 접속해 실제 문의를 남긴다.
2. 발표자 휴대폰 텔레그램에 **요약 카드가 즉시 도착**한다 (무대 화면에 미러링).
3. 한 건은 **그대로 승인** → 청중에게 "지금 메일함을 확인해보세요".
4. 다른 한 건은 **수정 요청**을 넣어 AI가 다시 쓰는 과정을 보여준 뒤 승인.
5. 마지막으로 **누적 지표 화면**(1차 승인률, 평균 처리 시간)을 제시한다.

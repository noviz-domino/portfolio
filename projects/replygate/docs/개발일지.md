# ReplyGate 개발일지

> 의사결정과 문제 해결 과정을 남긴 기록. 결과물만으로는 보이지 않는 "왜 이렇게 됐는가"를 담는다.
> 기간: 2026-08-01 ~ (발표 예정 2026-08-07~08)

---

## 1. 주제 선정

### 검토했다가 접은 후보

| 후보 | 접은 이유 |
|---|---|
| AI 일정 매니저 (현장 방문 동선 재배치) | 문제 정의는 가장 날카로웠으나 **개인·1주 조건에 규모가 초과.** 지도 API + 최적화 알고리즘 + 캘린더 연동 + 승인 플로우를 다 넣을 수 없었다. 별도 보관 |
| 청년 지원금 매칭 | 복지로·정부24 **보조금24가 이미 공식으로 제공** 중. "정부가 이미 하는데요"에 대한 방어가 궁색 |
| 쇼핑 가격 감시 | 네이버 쇼핑 API가 **판매량·리뷰수 정렬을 주지 않아** 유령 셀러와 옵션 미끼상품을 거를 수 없음. 가격 데이터 자체를 신뢰할 수 없어 기반이 무너짐 |
| 근로계약서 독소조항 검사 / 약 병용금기 / 전월세 진단 | 대안으로 검토. 최종 후보에서 밀림 |

### ReplyGate를 고른 이유

1. **지금까지 배운 것(n8n + LLM + 바이브코딩)을 전부 활용**할 수 있다
2. **구현 가능성이 확실**하다 — 데이터를 외부에서 긁어올 필요가 없다
3. **실무성이 있어** 평가에 유리하다

### 설계에서 의도적으로 뺀 것

- **웹에서의 승인 기능** — 만들면 "휴대폰만으로 완결된다"는 차별점이 스스로 무너진다. 승인 창구는 텔레그램 하나로 고정
- **자동 에스컬레이션** — 모든 답변이 이미 사람 승인을 거치므로 안전장치가 중복
- **PII 탐지, 주문 DB 연동** — 범위 초과

## 2. D1 기술 리스크 검증

구현보다 검증을 먼저 했다. **"여기서 막히면 설계가 통째로 바뀌는 것"** 을 하루 안에 전부 확인하는 것이 목표.

| # | 항목 | 결과 |
|---|---|---|
| 1 | Gemini 무료 티어 JSON 강제 출력 | ✅ `generationConfig.responseMimeType` + `responseSchema` 동작. `enum`도 지원 |
| 2 | Gemini 임베딩 | ✅ `gemini-embedding-001`, 3072차원 (프로젝트는 768로 축소 사용) |
| 3 | 텔레그램 웹훅 점유 | ✅ 전용 봇 신규 생성으로 충돌 회피 |
| 4 | 텔레그램 Callback Query 수신 | ✅ Trigger의 Updates에 `callback_query` 체크 필요 (기본값에서 빠져 있음) |
| 5 | Gmail 초안 생성·발송 | ✅ Managed OAuth2로 둘 다 통과. **단 Draft 리소스에 `Send`가 없어 HTTP Request로 우회** |
| 6 | Sheets 트리거 지연 | ✅ 폴링 최소 1분. 실행 수는 차감되지 않음 |
| 7 | n8n 플랜 | ✅ 실행 1,000 / 트라이얼 9일 |
| 8 | Gemini RPD | ❌ **여기서 문제가 터졌다** (아래 P-02) |

**배운 것:** 검증을 미룬 항목 하나(RPD)가 실제로 프로젝트를 위협했다. "무료로 쓸 수 있는가"만 확인하고 "얼마나 쓸 수 있는가"를 안 본 것이 실수였다.

## 3. 주요 설계 결정

### DR-01 · RAG를 n8n 내부에 둔다 (FastAPI 아님)

FastAPI에 `/search` 엔드포인트를 두는 쪽이 구조적으로 깔끔했지만, **n8n Cloud는 로컬 `localhost`를 호출할 수 없어** ngrok 같은 터널이 필요해진다.

RAG는 이 시스템의 심장이다. **발표 당일 터널이 끊기면 데모 전체가 죽는다.** 구조적 아름다움보다 데모 생존을 택했다.

### DR-02 · 벡터를 구글 시트에 저장하고 Code 노드에서 코사인 유사도로 검색한다

n8n의 Vector Store 노드는 **in-memory라 인스턴스 재시작 시 소실**된다. 발표 직전에 날아가면 복구할 시간이 없다.

조항이 70개뿐이라 벡터DB가 과잉이기도 했다. 임베딩을 시트 컬럼에 JSON 문자열로 저장하면 **영구 보존**되고, 검색은 70번의 코사인 계산이라 밀리초면 끝난다.

임베딩 차원은 3072 → **768로 축소**했다. 3072차원을 JSON으로 쓰면 셀당 약 2만 4천 자로 구글 시트 한도(5만 자)에 아슬아슬하다. 768이면 6천 자로 안전하고, 조항 70개 검색에서는 정확도 차이가 없다.

### DR-03 · AI Agent 노드 대신 HTTP Request를 쓴다

에이전트의 본질은 "어떤 도구를 쓸지 LLM이 스스로 판단하고 반복하는 것"이다. 그런데 이 파이프라인은 **분류 → 검색 → 생성 → 승인 → 재작성** 순서가 고정돼 있다. 판단할 게 없다.

에이전트를 쓰면 매 실행마다 경로가 달라질 수 있고, 토큰을 더 쓰고, 데모에서 예측 불가능해진다. 얻는 것 없이 잃기만 한다.

추가 이유:
- D1에서 검증한 **정확한 요청 형식을 그대로 쓸 수 있다** (모델명 지정 포함)
- Gemini의 네이티브 스키마 강제가 Structured Output Parser보다 강력하다
- 평가셋 측정 시 **워크플로우와 완전히 동일한 요청**을 파이썬으로 재현할 수 있다

> 진짜 에이전시가 맞는 자리는 따로 있다 — 담당자가 텔레그램에서 *"이 고객 예전에도 문의했어?"* 처럼 자유 질문을 할 때. 향후 확장으로 남긴다.

### DR-04 · 모델은 `gemini-3.5-flash-lite`

P-02 참조. 무료 티어 한도가 결정적이었고, 후보 두 개를 실측 비교해 골랐다.

### DR-05 · Loop Over Items로 문의를 한 건씩 격리한다

P-03 참조. 검색 단계에서 문의 1건당 조항 70개가 나와 아이템이 1:N으로 폭발한다. 짝을 잃지 않으려면 격리가 필요하다.

부수 효과로 **Gemini RPM 초과를 완화**한다. 30건을 동시에 던지지 않고 순차 처리하므로.

### DR-06 · 모든 조회는 `inquiry_id` 기준. 행 번호를 쓰지 않는다

동시에 여러 건이 제출되면 행 번호가 어긋난다. 실제로 검증에서 **승인 순서를 뒤섞어(A 수정 → B 승인 → A 승인) 눌러도 정확히 매칭**되는 것을 확인했다.

예외는 첫 Update 한 번뿐이다. Sheets Trigger가 `row_number`를 주지 않아 **`타임스탬프` 컬럼으로 매칭**해 `inquiry_id`를 써넣는다. 이후는 전부 `inquiry_id`.

### DR-08 · 대시보드는 서비스 계정으로 시트를 읽는다 (웹 게시 CSV 아님)

시트를 읽는 방법은 두 가지였다.

| 안 | 준비 | 문제 |
|---|---|---|
| 웹에 게시 → CSV | 2분 | **링크를 아는 누구나 고객 이메일까지 읽는다.** 발표 후 게시 중지를 잊으면 그대로 남는다 |
| **서비스 계정** | 10분 | **채택.** 시트를 비공개로 유지한 채 뷰어 권한만 준다 |

`문의` 시트에는 고객 이메일이 들어 있다. 8분을 아끼려고 개인정보를 공개 URL에 올릴 이유가 없었다.
게다가 이 프로젝트는 기획서에 *"개인정보는 최소 항목만 수집, 발표 종료 후 즉시 삭제"* 를 적어둔 상태다. 스스로 정한 원칙을 편의 때문에 깨면 그 원칙 자체가 장식이 된다.

키 파일은 `.gitignore` 에서 경로·파일명 양쪽으로 막았다 (`dashboard/*.json`, `dashboard/keys/`, `*service-account*.json`). 파일명을 바꿔도 걸리게 한 것은 **한 번의 부주의로 개인키가 공개 저장소에 올라가는 일**을 막기 위해서다.

### DR-09 · 대시보드에 실험 결과를 함께 올린다

처음에는 운영 지표(시트 실시간)만 생각했다. 그런데 발표 시나리오를 다시 보니 마지막이 이렇다.

> 6. **결론** — 지표 대시보드로 마무리. 베이스라인 대비 환각 발생률과 1차 승인률 개선폭을 제시한다.

데모로 파이프라인을 보여준 뒤 *"그래서 효과가 있느냐"* 로 마무리하는데, **그 답이 다른 창에 있으면 흐름이 끊긴다.** 그래서 `eval/측정_검수표.tsv` 를 읽어 RAG vs 베이스라인 승인률을 같은 화면 아래쪽에 붙였다.

집계는 검수표 **하나만** 본다. `run_eval.py` 의 채점 로직을 대시보드에 복제하면 두 곳이 갈라져 무대에서 서로 다른 숫자가 뜬다.

실제로 그 위험이 한 번 현실이 됐다. 처음 구현에서 베이스라인 수치 오류가 **21개**로 나왔는데 `측정결과.md` 는 **20개**였다. 리포트는 *"수치 정확률(정상 45건)"* 이라 **함정 5건을 모집단에서 빼는데** 대시보드는 50건을 다 세고 있었다. 모집단을 리포트와 맞춰 해결했다.

> 지표를 두 곳에서 계산하면 **정의가 조용히 갈라진다.** 숫자가 1 차이 나서 발견했지만, 그게 무대였으면 설명할 수 없었다.

### DR-07 · 정책 충돌은 막지 않고 경고한다

수정 단계에서 검토자가 정책과 다른 지시를 내릴 수 있다. 세 가지 선택지가 있었다.

| 안 | 내용 | 판단 |
|---|---|---|
| A | 지시 절대 우선 | 사람의 실수가 그대로 고객에게 나감 |
| B | 정책 절대 우선, 지시 무시 | 담당자가 예외 승인·신규 프로모션을 반영할 수 없음. HITL이 아니라 그냥 자동화 |
| **C** | **지시대로 쓰되 충돌을 카드에 표시** | **채택** |

C를 택한 이유는 **사람의 권한을 뺏지 않으면서 실수만 잡아주기** 때문이다. 승인 버튼을 누르기 전이므로 아직 아무것도 발송되지 않았고, HITL 자체가 이미 안전망이다.

애초에 RAG를 붙인 이유가 "담당자가 정책을 다 외우지 못해서"인데, **수정 단계에서만 그 보호막이 사라지는 것은 앞뒤가 맞지 않았다.**

## 4. 문제와 해결

### P-01 · 모델이 404 — "no longer available to new users"

`gemini-2.5-flash` 호출이 404. 메시지는 *"신규 사용자에게 더 이상 제공되지 않는다"*.

`models` 목록에 42개가 뜨지만 **상당수가 실제로는 호출할 수 없다.** 목록에 있다고 쓸 수 있는 게 아니다.

→ 검증 스크립트가 모델 목록을 조회한 뒤 최신 flash 계열을 우선 선택하도록 수정. `gemini-flash-latest` 같은 **별칭은 금지** — 가리키는 대상이 바뀌면 발표 직전에 동작이 달라진다.

### P-02 · Gemini RPD 20 — 프로젝트를 위협한 제약

실행 중 429. AI Studio에서 확인한 실제 한도:

| 모델 | RPM | RPD |
|---|---|---|
| Gemini 3.6 / 3.5 / 3 Flash | 5 | **20** |
| **Gemini 3.5 / 3.1 Flash Lite** | **15** | **500** |
| Gemini Embedding 1 / 2 | 100 | 1,000 |

문의 1건 = 생성 2회(P1+P2) + 임베딩 1회. **RPD 20이면 하루 10건이 상한.** 평가셋 실험(300회 규모)은 15~30일이 걸려 불가능했다.

결제 전환을 검토했으나 **Lite 계열의 RPD가 500** 이라는 것을 발견해 무료로 해결했다.

**모델 선택은 실측 비교로 결정했다** (`scripts/compare_models.py`, 결과는 `eval/모델비교_결과.md`):

- 정상 케이스(환불 지연): 3개 모델 모두 조항·수치 정확. **3.5 Lite만 RF-13(7일)을 조건문으로 정확히 표현**했고 나머지는 "이미 7일이 지났다"고 단정
- 함정 케이스(해외배송, 정책에 없음): **3.1 Flash Lite가 환각** — *"온마켓은 국내 배송만 지원한다"* 를 지어냈다. `insufficient_info` 플래그는 true로 맞췄지만 **본문에서 사실을 창작**했다
- 3.5 Flash Lite는 *"정책에 명시되어 있지 않아 담당 부서 확인 후 안내"* 로 정확히 처리
- 3.6 Flash는 함정 케이스에서 429 — RPD 20 소진

→ **`gemini-3.5-flash-lite` 단일 모델로 확정.** 쿼터 분산을 위해 P1/P2를 다른 모델에 태우려 했으나 3.1 Lite의 환각 때문에 기각했다.

> 이 실험은 평가셋을 돌리기도 전에 환각 한 건을 잡아냈다. **함정 케이스 설계가 작동한다는 증거**다.

### P-03 · 여러 건이 동시에 오면 첫 번째만 처리됐다 ⚠️ 데모 치명적

폼 두 건이 한 폴링에 잡혔는데 **두 번째 문의가 `분석중`에서 방치**됐다. 게다가 첫 번째 문의가 통째로 재처리되며 기존 이력을 덮어썼다.

원인이 두 개 겹쳤다.

**(a) `.first()` 사용** — Code 노드와 HTTP 노드가 전부 `$('접수 처리').first()`를 참조했다. `상태: 분석중`은 아이템마다 실행돼 두 행 모두 갱신했지만, P1 이후로는 첫 아이템 하나로 좁혀져 나머지가 버려졌다.

**(b) 검색 단계의 1:N 폭발** — `조항 읽기` 노드가 문의 1건당 조항 70개를 반환한다. 문의가 2건이면 140개가 섞여 어느 조항이 어느 문의 것인지 짝을 잃는다.

→ **`Loop Over Items`(batchSize 1)를 도입**해 문의를 한 건씩 통과시켰다. 루프 바깥에서 만들어진 `접수 처리` 출력은 `$('접수 처리').all()[$runIndex]`로 현재 반복분을 골라낸다. 루프 안에서 도는 노드는 `.first()`가 자동으로 현재 반복 데이터를 가리키므로 그대로 뒀다.

검증: 폼 2건 연속 제출 → `접수 처리 2 items` → `Loop 2 items total` → 하위 노드 전부 `✓2` → **텔레그램 카드 2개 도착.**

### P-04 · 이미 처리된 행을 다시 처리했다

워크플로우를 분리하면서 Sheets Trigger가 새 인스턴스로 시작해 기존 행까지 새 행으로 내보냈다. `접수 처리`에 재처리 방어가 없어 `inquiry_id`가 새로 발급되며 이력이 덮어써졌다.

→ `if (j.inquiry_id && String(j.inquiry_id).trim() !== '') continue;` 한 줄 추가.

### P-05 · 재검토 카드가 다른 봇으로 나갔다

임포트 시 텔레그램 Credential이 이전 프로젝트의 봇으로 잡혔다. **그 카드의 버튼을 눌러도 워크플로우가 반응하지 않는다** — 02의 트리거는 다른 봇을 듣고 있기 때문. 수정 루프가 거기서 끊겼다.

→ Credential 재지정. 임포트 후 **모든 텔레그램 노드의 자격증명을 하나씩 확인**하는 것을 체크리스트에 넣었다.

### P-06 · 표현식이 글자 그대로 전송됐다

`{{ ... }}` 를 넣었는데 카드에 표현식이 그대로 찍혔다. 칸이 **Fixed 모드**였던 것.

n8n UI에서는 `fx` 토글로 Expression 모드를 켠 뒤 `{{ }}`만 넣는다. **JSON 파일에 보이는 앞의 `=`는 UI에 입력하면 안 된다.** 같은 실수를 P3 JSON Body에서도 반복해 `Unexpected token '='` 오류가 났다.

### P-07 · 수정하면 근거가 통째로 사라졌다

초기 P3 규칙에 *"어긋나는 조항 ID는 제외하라"* 가 있었다. 검토자가 정책 밖 내용을 지시하면 모델이 **모든 조항 ID를 비웠다.** 본문에는 여전히 정책 기반 문장이 남아 있는데 `근거: 없음`으로 표시돼 감사 추적이 끊겼다.

→ 규칙을 *"본문에 정책 근거가 남아 있으면 그 조항 ID는 유지하라"* 로 교체하고, 검토자가 넣은 내용은 **`handler_added` 필드로 분리 표시**했다.

### P-08 · 누적된 위반이 감지되지 않았다

충돌 감지를 붙였는데, **3회차 수정에서 경고가 사라졌다.** 본문에는 직전 수정에서 넣은 정책 위반 문구가 그대로 남아 있는데도.

원인: 프롬프트가 **"이번 지시"만 대조**하고 있었다. 이번 지시가 정책과 무관하면 `detected: false`가 된다.

이게 실제로 위험하다. **담당자가 수정을 서너 번 하다 보면 초기 경고를 잊고 마지막 카드만 보고 승인**하게 된다.

→ 대조 대상을 **"완성된 본문 전체"** 로 변경. 그리고 검색된 3개 조항만으로는 검색 밖 조항과의 충돌을 못 잡으므로 **전체 70조항을 함께 전달**하되 *"충돌 확인 전용, 본문 작성에 끌어오지 마라"* 고 용도를 못 박았다.

검증: 지시가 `"인사를 정중하게 해줘"`(정책 무관)였는데 **이전 수정에서 남은 RF-05 위반을 잡아냈고**, `📎 근거`는 흔들리지 않았다.

### P-10 · 감정 분류의 `중립` 클래스가 한 번도 선택되지 않았다 — 설계 오류

평가셋 50건 측정에서 **감정 판정 정확도가 56%** 로 나왔다. 클래스별로 쪼개보니 원인이 분명했다.

```
불만      15/15   100%
단순문의   13/15    87%
중립       0/20     0%   ← 모델이 단 한 번도 선택하지 않음
```

**1차 시도 — 정의를 다듬었다.** 기존 정의가 겹쳐 있었다.

| | 초기 정의 |
|---|---|
| 중립 | 사실 확인이나 처리 요청, 감정 표현이 거의 없음 |
| 단순문의 | 정보를 묻는 가벼운 질문 |

대부분의 중립 문의는 질문 형태라 두 조건을 동시에 만족한다. 모델이 중립을 고를 이유가 없었다.
그래서 *"답변하려면 이 고객의 주문·계정을 조회해야 하는가"* 를 기준으로 재정의하고 정답 라벨 13건을 옮겼다.

**결과: 56% → 84%. 그러나 중립은 여전히 0/7 이었다.**

숫자가 오른 것은 **라벨을 모델이 이미 답하던 쪽으로 옮겼기 때문**이지 모델의 판정이 나아진 게 아니었다. 이걸 개선이라고 보고했다면 자기기만이다.

**2차 시도 — 원인은 정의가 아니라 구조였다.**

남은 7건을 다시 보니 내 라벨도 틀려 있었다. 예를 들어 *"제 환불 언제 들어오나요"* 를 중립으로 뒀지만, 답변은 "영업일 기준 3일"이라 **주문을 조회할 필요가 없다.**

진짜 문제는 이것이었다 — **감정과 조회 필요 여부는 직교하는 두 축인데 하나의 enum에 눌러 담았다.**

```
불만 / 중립 / 단순문의
 ↑      ↑        ↑
감정   ─── 조회 필요 여부 ───
```

`불만`은 감정 축이고 `중립 vs 단순문의`는 조회 필요 축이다. 서로 다른 차원이라 한 줄로 세울 수 없었다. **모델이 중립을 못 고른 게 아니라 고를 수 없는 구조였다.**

→ 두 필드로 분리했다.

```
sentiment          : 불만 / 일반          (사과가 필요한가)
needs_order_lookup : true / false        (이 고객의 주문을 봐야 하는가)
```

| 시도 | 감정 정확도 | 문제의 클래스 |
|---|---|---|
| v1 · 3단계 초기 정의 | 56.0% | 중립 0/20 |
| v2 · 3단계 개정 정의 | 84.0% | 중립 0/7 |
| **v3 · 두 축 분리** | **98.0%** | 조회필요 18/21 (86%) |

**클래스가 학습 불가능했던 게 아니라 잘못 놓여 있었다.** 독립된 축을 주자 바로 92% 정확도로 판정했다.

부수 효과로 **쓰이지 않던 클래스가 실제 기능을 갖게 됐다.** `needs_order_lookup=true` 는 카드에 📋 배지로 표시되어 *"이 건은 주문 조회가 필요합니다"* 를 담당자에게 알리고, 향후 주문 DB 연동의 진입점이 된다. 이전의 `중립`은 어조만 미묘하게 다를 뿐 아무 일도 하지 않았다.

문의 유형 정확도도 88% → 94%로 올랐다. P1이 판정할 것이 단순해진 영향으로 보이나 **단일 실행이라 단정하지 않는다.**

> 세 차례 측정 결과를 모두 보존했다 — `eval/측정결과_v1_구정의.md`, `_v2_정의개정.md`, `측정결과.md`.
> **측정이 없었다면 쓰이지 않는 클래스를 그대로 안고 발표했을 것이다.**

### P-11 · 1차 승인률이 수치 정확률의 재탕이 될 뻔했다

주 지표인 1차 승인률을 채우려고 검수표 100줄을 판정하는데, **판정 기준을 잘못 잡으면 지표가 무의미해진다**는 것을 먼저 마주쳤다.

가장 쉬운 방법은 `정답과다른수치` 칸에 값이 있으면 X를 찍는 것이었다. 그런데 그러면 **1차 승인률은 수치 정확률을 다시 쓴 숫자일 뿐**이고, 지표를 두 개 재는 의미가 사라진다.

그래서 "담당자가 수정 없이 발송 버튼을 누르는가"를 네 가지로 분해했다.

| 사유 | 예 |
|---|---|
| 정책 위반 | 환불 기한을 14일이 아닌 7일로 안내 |
| 사실 창작 | 정책에 없는 쿠폰·할인율·원인을 지어냄 |
| **근거 없는 확약** | 주문을 조회한 적도 없이 *"오늘 중으로 처리해 드렸습니다"* |
| 질문 미응답 | *"얼마나 지급되나요"* 에 금액을 답하지 않음 |

어조가 장황하거나 수치를 생략한 정도는 O로 뒀다. 실제 CS 담당자의 판단선에 맞춘 것이다.

**결과적으로 두 지표는 겹치지 않았다.** X 36건 중 **21건은 수치 플래그가 없는 건**이었다. 반대로 수치 플래그가 붙었는데 O로 판정한 것도 3건 있었다 — 검사기가 잡은 값이 *정답 조항* 밖일 뿐 정책에는 실재하는 수치였다.

```
1차 승인률   RAG 94.0% (47/50)  vs  베이스라인 34.0% (17/50)
```

**베이스라인의 실패는 숫자를 틀려서만이 아니었다.** 조사도 하지 않고 택배사·제조사에 귀책을 돌리고, 정책상 불가한 건을 예외 승인하고, 지급하지도 않은 쿠폰을 과거형으로 단정했다. `EV-42`는 복원 불가인 소멸 적립금을 *"전액 복구"* 하겠다고 했고, `EV-50`은 *"오늘 중 위약금 면제 완료"* 와 함께 **가입 시 안내 누락이라는 회사 귀책을 인정**했다. 실무였다면 금전 손해와 분쟁으로 직결된다.

**그리고 RAG도 완벽하지 않았다.** `EV-12`(기프트카드, 함정)는 `insufficient_info=true` 를 정확히 달아놓고 **본문에서는** *"기프트카드 수단으로 다시 환급이 진행됩니다"* 라고 단정했다. `eval/평가셋_설계.md` 가 *"플래그만으로는 부족하다"* 고 경고한 바로 그 실패가 RAG 조건에서도 나왔다. 함정 회피율은 **플래그 기준 5/5, 본문 기준 4/5**로 갈린다.

`EV-38`은 반대 방향의 실패다. **AS-07이 정책에 실재하는데도** *"명시되어 있지 않다"* 며 담당 부서로 넘겼다. 과도한 회피 1건의 정체다.

> 판정 근거는 검수표 `비고` 컬럼에 100줄 전부 남겼다. **어떤 기준으로 X를 줬는지 되짚을 수 없으면 지표를 신뢰할 수 없다.**

### P-12 · 대시보드가 초당 한 번씩 깜박였다

상황판을 켜두니 카드가 계속 깜박였다. 원인이 두 층에 겹쳐 있었다.

**(a) 변경 감지가 무력화돼 있었다.** SSE 는 *"내용이 바뀔 때만 보낸다"* 로 만들었는데, 지문을 **페이로드 전체**로 계산하고 있었다. 그 안에 `served_at`(현재 시각)과 `age_seconds`(경과 초)가 들어 있으니 **지문이 매초 무조건 달라진다.** 아무 일도 없는데 초당 한 번씩 전송됐다.

→ 지문을 **시간에 따라 저절로 변하는 값을 뺀 사본**으로 계산한다. 경과 시간 표시는 브라우저가 `moved_at`(절대 시각)으로 직접 계산하고 20초마다 텍스트만 고친다.

**(b) 갱신할 때마다 DOM 을 통째로 갈아끼웠다.** `innerHTML` 로 상황판 전체를 다시 쓰니 카드가 매번 **새 요소로 생성**됐고, `.ticket { animation: rise }` 가 초당 한 번씩 재생됐다. 그게 깜박임의 실체였다. 덤으로 막대 그래프의 CSS transition 도 한 번도 동작하지 않고 있었다 — transition 은 요소가 살아 있어야 걸린다.

→ `inquiry_id` 를 키로 요소를 재사용한다. 내용이 실제로 달라진 카드만 고치고, **등장 애니메이션은 새 문의에서만** 재생한다. 컬럼이 바뀐 카드에는 별도의 강조 효과를 준다 — 무대에서 *"지금 이게 움직였다"* 를 눈으로 쫓게 하려는 것이다.

검증: 12초 스트림에 전송 **12회 → 1회**. 갱신을 20회 강제로 돌려도 카드 요소가 동일 객체로 유지되고 애니메이션이 재생되지 않는다.

> **"바뀔 때만 보낸다"고 적어놓고 매초 보내고 있었다.** 주석과 실제 동작이 갈라진 것을 눈으로 보고서야 알았다. 최적화를 넣었으면 그게 실제로 작동하는지 세어봐야 한다.

### P-13 · 발송이 끝난 건에 수정 버튼이 먹혔다 ⚠️ 고객에게 메일이 두 번 나갈 뻔했다

대시보드 상세 보기를 붙인 뒤 수정 루프를 시험하려는데, 사용자가 **이미 발송된 건의 옛 카드에서 `✏️ 수정 요청` 을 눌렀다.** 그리고 그게 그대로 먹혔다.

시트에 남은 흔적이 문제를 그대로 보여준다.

```
INQ-20260802-9874
  sent_at   01:48:33   ← 이미 고객에게 나갔음
  status    수정중      ← 그런데 다시 수정 루프
  rev       1
  draft_id  r-1372522273995597748   ← 새로 만들어진 초안
```

**여기서 승인을 누르면 같은 고객에게 두 번째 메일이 나간다.** 승인 경로에는 중복 방어가 있지만(`대상 조회(승인)` 이 `status === '발송완료'` 면 차단), 상태가 이미 `수정중` 으로 바뀐 뒤라 **그 방어를 그냥 통과한다.**

부수 피해도 있었다. 재작성이 `final_body` 를 덮어써서 **시트에 남은 본문이 실제로 발송된 본문과 달라졌다.** 감사 추적이 끊긴 것이다.

**왜 못 잡았나.** 텔레그램 카드는 발송 후에도 채팅에 영원히 남고 버튼도 계속 눌린다. 그런데 지금까지의 검증은 전부 정상 경로만 따라갔다 — 카드가 오면 승인하거나, 수정하고 승인하거나. **옛 카드를 다시 누르는 시나리오를 아무도 밟지 않았다.**

더 정확히 말하면, 같은 위험(중복 처리)이 두 경로에 있는데 **승인 경로에만 방어를 넣고 수정 경로는 빠뜨렸다.** 방어를 설계할 때 "이 위험이 어느 경로에 있는가"를 경로별로 세지 않은 것이 원인이다.

→ 승인 경로의 구조를 수정 경로에 그대로 복제했다.

```
승인:  콜백 → 문의 읽기(승인) → 대상 조회(승인) → [발송완료면 차단] → 발송
수정:  콜백 → 문의 읽기(가드) → 수정 가능 확인 → IF → [true] 차단 알림
                                                  └ [false] 상태: 수정중
```

판정은 **`status` 와 `sent_at` 을 둘 다** 본다. 상태 컬럼이 어떤 경로로든 바뀌어 있어도 발송 기록이 남아 있으면 이미 나간 건이다. 이번 사고가 정확히 "상태만 바뀐" 경우였다.

에러를 던지는 대신 **텔레그램으로 안내**한다. 담당자가 버튼을 눌렀는데 아무 반응이 없으면 눌린 건지 아닌지 알 수 없다.

**고치는 중에 나온 두 번째 문제.** 차단 문구를 텔레그램 노드의 표현식에 직접 넣었더니 `invalid syntax` 가 났다. JSON에 넣은 `\n` 이 **진짜 줄바꿈 문자로 변환**되어 들어갔고, 자바스크립트 작은따옴표 문자열은 줄을 넘길 수 없다.
→ 문구 조립을 **Code 노드로 옮겼다.** `초안 파싱`·`재작성 파싱` 이 `card_text` 를 만드는 방식과 같아져 일관성도 생겼다. **표현식 안에서 이스케이프를 다루지 않는다** 를 규칙으로 삼는다.

검증: 발송된 카드의 `✏️` → `🚫 이미 발송된 건입니다` 로 차단. 승인 전 카드의 `✏️` → 정상적으로 수정 루프 진입.

> **발표 포인트:** 이 버그는 사용자가 "엉뚱한 버튼"을 눌러서 발견됐다. 정상 경로만 따라가는 검증으로는 절대 안 나온다. HITL 시스템에서 **사람이 언제든 과거 UI를 다시 만질 수 있다**는 것이 설계 전제여야 한다.

### P-09 · Gmail 노드에 Draft `Send`도 `Update`도 없다

n8n Gmail 노드의 Draft 리소스는 Create / Delete / Get / Get Many 뿐이다.

→ **발송은 HTTP Request로 Gmail API 직접 호출** (`POST /gmail/v1/users/me/drafts/send`, `Predefined Credential Type`으로 자격증명 재사용).
→ **수정 시에는 기존 초안을 DELETE하고 새로 생성.** `draft_id`가 매번 바뀌므로 시트에 갱신한다.

## 5. n8n 임포트 시 반복된 함정

JSON을 붙여넣어도 그대로 동작하지 않는다. 매번 같은 곳에서 걸렸다.

1. **Sheet 이름이 안 실린다.** JSON에 `sheetName`이 있어도 임포트 후 비어 있다. Sheets 노드를 전부 열어 `From list`로 직접 지정해야 한다
2. **Update Row의 매핑이 초기화된다.** Sheet를 지정해야 컬럼이 로드되고, 그때 전부 빈 칸으로 나열된다. **빈 칸으로 두면 기존 값을 빈 값으로 덮어쓴다.** 🗑 아이콘으로 쓰지 않을 컬럼을 목록에서 제거해야 한다
3. **Sheets Trigger는 `row_number`를 주지 않는다.** 첫 Update는 `타임스탬프` 컬럼으로 매칭한다
4. **`fx` 토글을 켜야 표현식이 해석된다.** 고정 문자열은 Fixed로 둔다
5. **Credential이 엉뚱한 것으로 잡힌다.** 특히 같은 종류의 자격증명이 여러 개일 때
6. **`Append n8n Attribution`이 켜져 있다.** 텔레그램 메시지에 n8n 홍보 문구가 붙는다. 데모 완성도를 위해 꺼야 한다

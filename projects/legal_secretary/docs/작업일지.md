### 결정과 이유

- `FakeChatModel`은 langchain-core의 `GenericFakeChatModel`을 상속하되 `_generate`를
  오버라이드해 입력 해시 기반으로 결정론적 응답을 생성하도록 직접 구현했다.
  `FakeListChatModel`은 미리 정해진 응답 리스트를 순서대로 소비하는 방식이라
  "같은 입력 → 같은 출력"을 보장하기 어려워 해시 기반 방식을 택했다.
- 서비스 로직을 `app/services.py` 모듈 하나로 분리했다(설계.md에 정확한 경로가
  명시되어 있지 않아 가장 단순한 형태로 배치). `answer_question`은 `async def`이며
  02단계에서 검색을, 5단계에서 SSE 스트리밍을 얹기 쉬운 지점으로 설계.
- FastAPI 라우트의 `Depends(get_settings)`를 `Annotated[Settings, Depends(...)]`
  형태로 작성. ruff의 B008 규칙(가변 기본값 함수 호출 금지)을 통과시키기 위함이며
  동작은 동일하다.
- `get_settings()`에 `lru_cache`를 사용해 프로세스당 한 번만 설정을 로드한다.
  런타임 중 환경변수를 바꿔도 반영되지 않으므로, 백엔드 전환 확인은 프로세스
  재시작으로 검증했다(완료 판정 기준 5번과 일치).

### 막혔던 지점과 해결

- `app.py`, `templates/`, `static/`에 `git rm`으로 제거되지 않는 미추적(untracked)
  "copy" 파일들(`app copy.py`, `templates/index copy.html` 등)이 남아있어
  `rm -rf`로 추가 정리했다. `app (사본).py`, `app copy.py`, `project.zip`,
  `vector_store/`(구 버전), `requirements.txt`는 작업지시에 명시되지 않아

## 2단계 — RAG 코어 (2026-09-23)

### 한 일

- 의존성 추가: `rank-bm25`, `langchain-chroma`, `langchain-huggingface`,
  `sentence-transformers`, `pymupdf` (`uv sync`, aarch64용 torch/CUDA 메타
  패키지까지 포함해 다운로드에 상당한 시간이 걸림).
- `backend/app/rag/chunking.py` — 정규식(`^제N조`, `제N조의M`, 줄 시작에서만
  매칭)으로 1차 분할, `chunk_size` 초과 시 `RecursiveCharacterTextSplitter`로
  2차 분할하며 `article` 메타데이터 유지. 조 경계가 없으면 전부 재귀 분할.
  `chunk_size`(500)/`chunk_overlap`(100)을 `config.py`에 설정 항목으로 추가.
- `backend/app/rag/ingest.py` — PyMuPDF로 페이지 단위 텍스트 추출 → 청킹 →
  `bge-m3` 임베딩 → Chroma 저장. CLI(`python -m app.rag.ingest`)로 실행,
  청크 수와 소요 시간을 출력.
- `backend/app/rag/retrieval.py` — Chroma dense 검색 + BM25 sparse 검색을
  RRF(k=60)로 융합하는 `HybridRetriever`. 각 경로 후보 20개(`CANDIDATE_POOL_SIZE`)
  중 상위 `settings.retrieval_k`개 반환. `reciprocal_rank_fusion`은 순수 함수로
  분리해 테스트 가능하게 함. 프로세스당 한 번만 로드하도록 `get_retriever()`에
  `lru_cache` 적용.
- `backend/app/rag/rerank.py` — `BAAI/bge-reranker-v2-m3` 크로스 인코더.
  `rerank_enabled=False`(기본값)면 `CrossEncoder`를 아예 import/로드하지 않음.
- `backend/app/services.py` — `answer_question`이 검색 → (선택)리랭킹 →
  프롬프트 컨텍스트 구성 → LLM 호출 → `Citation` 목록 반환까지 수행하도록 재작성.
  벡터스토어가 비어 있으면 `RagNotReadyError`를 던지고, 라우트에서 이를
  `HTTPException(503)`으로 변환해 스택 트레이스 없이 명확한 메시지를 반환.
- 테스트 추가: `tests/test_chunking.py`(조 경계 분할·메타데이터, 합성 텍스트만
  사용), `tests/test_retrieval.py`(RRF 순수 함수, 수식 검증, 토크나이저),
  `tests/test_api.py`에 `get_retriever`를 monkeypatch하는 스텁 리트리버로
  citations 채움/빈 벡터스토어 에러 케이스 추가.

### 결정과 이유

- **인제스트 재실행 방식**: 매 실행마다 `settings.vector_store_dir`를
  통째로 삭제 후 재생성하는 "전체 재적재" 방식을 택했다. 지시서에서도
  허용한 방식이며, 문서 2개(청크 264개) 규모에서는 증분 적재(중복 판별,
  삭제 문서 정리)의 복잡도를 감수할 이유가 없다.
- **BM25 문서 소스**: Chroma에 저장된 청크를 `collection.get()`으로 다시 읽어와
  매 프로세스 시작 시 BM25 인덱스를 빌드한다. 별도 인덱스 파일을 만들지 않아
  Chroma가 단일 진실 소스가 된다.
- **한국어 BM25 토크나이징의 한계**: 형태소 분석기 없이 정규식으로 한글/영문/숫자
  토큰을 뽑고, 흔한 조사(은/는/이/가/을/를/의/에/에서/으로 등) 접미사를 잘라
  원형과 함께 인덱싱했다. "제56조" 같은 정확 매칭 토큰은 잘 보존되지만,
  용언 활용형(예: "지급하여야" vs "지급한다")이나 목록에 없는 조사·복합조사는
  걸러내지 못한다. 실사용 시 오탐/누락이 있을 수 있으며, 필요하면 03단계
  이후 형태소 분석기 도입을 검토할 것.
- 리트리버(`HybridRetriever`)를 `get_settings()`와 동일하게 `lru_cache`로
  프로세스당 1회만 생성한다. 매 요청마다 bge-m3를 로드하면 파이에서 감당하기
  어렵기 때문. 런타임 중 설정을 바꾸려면 재시작이 필요한 것도 1단계와 동일.

### 막혔던 지점과 해결

- `sentence-transformers`/`torch` 설치 시 aarch64인데도 nvidia CUDA 메타
  패키지들이 대량으로 딸려와(수 GB) 다운로드 시간이 예상보다 길었다. 디스크
  여유(190GB)는 충분해 별도 조치 없이 그대로 진행했다.
- PyMuPDF의 `import fitz`가 deprecation 경고를 내서 `import pymupdf as fitz`로
  변경.
- ruff `UP037`: `from __future__ import annotations`가 있는 파일에서 타입
  힌트에 따옴표를 쓸 필요가 없어 `rerank.py`의 `"CrossEncoder | None"` 등을
  따옴표 없이 수정.
- 테스트에서 실제 bge-m3 임베딩을 매번 로드하면 느리고 네트워크/캐시 상태에
  좌우되므로, `app.services.get_retriever`를 monkeypatch해 스텁 리트리버로
  대체했다. `fake` LLM 백엔드와 별개로 검색 경로도 키/네트워크 없이 테스트
  가능하게 하기 위한 선택.

### 실측 소요 시간 / 생성 청크 수

- `data/pdf/`의 PDF 2개(exampdf.pdf, testpdf.pdf)에서 총 **264개 청크** 생성.
- 1차 인제스트(최초 bge-m3 다운로드 포함): 약 **1193초**(약 20분).
- 2차 인제스트(모델 캐시됨, 재실행): 약 **1463초**(약 24분) — 다운로드가 아니라
  파이 CPU에서의 임베딩 연산 자체가 병목. 청크 수는 두 번 다 264개로 동일해
  재실행 안전성을 확인했다.

### 다음 단계(03단계)에 넘기는 주의사항

- BM25 한국어 토크나이징은 위에서 설명한 한계를 가진 단순 구현이다. 검색
  품질 이슈가 발견되면 형태소 분석기 도입을 검토할 것(단, 무거운 의존성이므로
  신중히 판단).
- 리랭킹(`rerank_enabled`)은 기본 off. 파이 CPU에서 실측 소요 시간을 재보지
  않았으니, 켤 계획이라면 별도로 측정할 것.
- `HybridRetriever`/`get_retriever()`가 `lru_cache`로 프로세스당 1회 생성되므로,
  에이전트 루프(3단계)에서 재시도/질의 재작성을 넣더라도 동일 프로세스 내에서는
  임베딩 모델을 재사용할 수 있다. 다만 벡터스토어를 다시 인제스트했다면
  서버 재시작이 필요하다.
- 서버 기동 후 `POST /api/ask`에 "연장근로 수당은 어떻게 계산하나요?"를 보내면
  1순위 인용이 `testpdf.pdf` 10페이지 `제56조(연장ㆍ야간 및 휴일 근로)`로,
  실제 PDF 본문과 스니펫이 정확히 일치함을 확인했다(하이브리드 검색이 정상
  동작).

## 03단계 — 스트리밍 (2026-09-24)

### 한 일

- `backend/app/config.py`에 `stream_timeout_seconds`(180), `stream_heartbeat_seconds`(10)
  추가. `.env.example`에도 반영.
- `backend/app/services.py`: 검색 로직을 `_retrieve()`로 분리해 `answer_question`
  (비스트리밍)과 `stream_answer`(신규, SSE 제너레이터)가 공유하도록 재작성.
  `stream_answer`는 `(event, data)` 튜플을 순서대로 `yield`한다:
  `status(retrieving)` → `citations` → `status(generating)` → `token`(반복,
  10초 무토큰 시 `status(waiting, elapsed)` 하트비트) → `done`. 예외는 전부
  잡아 `error` 이벤트로 변환하고 제너레이터를 정상 종료한다(연결을 끊지 않음).
  토큰 추출은 `chunk.text` 프로퍼티로 통일(비스트리밍과 동일한 버그 회피).
- `backend/app/api/routes.py`: `POST /api/ask/stream` 추가. `StreamingResponse`
  + 표준 SSE 프레임(`event: ...\ndata: ...\n\n`)을 직접 포맷. 기존 `/api/ask`는
  손대지 않음.
- `backend/tests/test_stream.py` 신규: 이벤트 순서(`status(retrieving)` →
  `citations` → `status(generating)` → ... → `done`), 토큰이 여러 이벤트로
  나뉘는지, 이어붙인 토큰이 `/api/ask`의 answer와 일치하는지, 빈 벡터스토어에서
  `error` 이벤트로 처리되는지(연결 끊김 없음)를 전부 `fake` 백엔드로 검증.
- `FakeChatModel`은 별도 수정 없이 스트리밍을 지원한다. `GenericFakeChatModel`이
  이미 `_stream`에서 `_generate` 결과를 공백 기준으로 여러 청크로 쪼개
  yield하도록 구현되어 있어(`langchain-core` 1.6.4 확인), `_generate`만
  오버라이드한 현재 구조로 토큰이 자연스럽게 여러 번 나뉘어 도착한다.

### 결정과 이유

- **`status(retrieving)`를 스트림 시작 즉시 전송** (지시서 대비 추가, 코디네이터
  지시 반영). 검색이 끝나는 약 1.4~2초 구간에도 클라이언트가 "관련 법령 검색
  중" 등 진행 상태를 표시할 근거가 필요하다는 이유. 완료 판정 기준도
  "citations가 status(retrieving) 바로 다음에 도착"으로 조정했다.
- 하트비트/타임아웃은 `chat_model.astream()`을 수동 `__aiter__()` + 
  `asyncio.wait_for(agen.__anext__(), timeout=heartbeat)`로 감쌌다. 토큰이
  heartbeat 내에 오면 그대로 전달, 안 오면 `status(waiting)`을 보내고 전체
  경과가 `stream_timeout_seconds`를 넘으면 `error`를 보내고 종료한다.
- SSE 포맷팅에 `sse-starlette` 같은 별도 의존성을 추가하지 않고 `f"event:
  ...\ndata: ...\n\n"` 문자열을 직접 만들었다. 요구되는 이벤트 형식이 단순해
  의존성을 늘릴 이유가 없었다.
- 검색/리랭킹 자체는 여전히 동기 함수로 이벤트 루프에서 직접 호출한다(기존
  `answer_question`과 동일한 방식). 요청당 한 번뿐이고 1~2초 수준이라 이번
  단계에서 `asyncio.to_thread`로 옮기지 않았다 — 다만 동시 요청이 많아지면
  이벤트 루프를 블로킹할 수 있으니 다음 단계에서 필요하면 검토할 것.

### 막혔던 지점과 해결

- 수동 확인 중 이전에 띄워둔 uvicorn 프로세스가 `kill`/`kill -9`에도 바로
  죽지 않고 살아남아, 포트가 이미 사용 중인 새 프로세스가 조용히 종료되면서
  옛 프로세스(벡터스토어가 비어 있던 시점의 리트리버를 메모리에 들고 있던
  것)가 계속 응답하는 바람에 한동안 혼란스러운 결과를 봤다. `ss -ltnp`로
  실제 리스닝 PID를 확인하고 그 PID를 직접 죽이는 방식으로 해결. `lru_cache`로
  캐싱된 리트리버는 디렉터리를 옮겨도 프로세스가 살아있는 한 갱신되지 않는다는
  점(1단계부터 알려진 제약)을 다시 확인했다.

### 다음 단계 주의사항

- `stream_answer`가 검색을 동기적으로 수행하므로, 동시 스트리밍 요청이 많아지면
  이벤트 루프가 그 구간 동안 블로킹된다. 실사용 부하가 커지면
  `asyncio.to_thread`로 감싸는 것을 검토할 것.
- 하트비트(`status: waiting`)와 타임아웃(`error`) 경로는 fake 백엔드가 즉시
  응답하는 특성상 자동 테스트로 실측하지 못했다(단, `_load_prompt_template`
  이후 로직은 `asyncio.wait_for` + `TimeoutError` 처리로 구현되어 있어 코드
  경로 자체는 존재한다). self-hosted(Ollama) 연동 시 실제 지연 상황에서 한 번
  실측 확인을 권장한다.
- 프론트엔드(05단계)는 `status.state` 값(`retrieving`/`generating`/`waiting`)을
  기준으로 진행 표시를 전환하면 된다.

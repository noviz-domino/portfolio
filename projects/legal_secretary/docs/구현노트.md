## 1. PDF 로드 — `PyMuPDFLoader`

패키지: `langchain_community.document_loaders`

`PyMuPDFLoader`는 PDF 파일 경로를 인자로 받아 텍스트와 메타데이터를 추출하는
클래스다. PDF는 보통 텍스트와 이미지가 섞여 있는데, `load()` 메서드는 그중
**텍스트 추출에 중점**을 둔다.

동작 순서:

1. **PDF 파일 열기** — 전달받은 경로의 파일을 연다.
2. **텍스트 추출** — 각 페이지의 텍스트를 추출해 페이지별로 나누어 저장한다.
3. **결과 반환** — 페이지별 텍스트를 `Document` 객체 리스트로 반환한다.

문서 전처리의 첫 단계에 해당한다. 이후 `RecursiveCharacterTextSplitter` 같은
분할 도구가 바로 쓸 수 있는 형태로 텍스트를 구조화해서 넘겨주는 역할이다.

## 2. 문서 분할 — `RecursiveCharacterTextSplitter`

패키지: `langchain.text_splitter`

```python
text_splitter = RecursiveCharacterTextSplitter(chunk_size=500, chunk_overlap=100)
docs = text_splitter.split_documents(pages)
```

500자 단위로 청크를 나누되 인접 청크가 100자씩 겹치도록 분할한다.

- `chunk_size` — 각 청크의 최대 크기
- `chunk_overlap` — 청크 간 겹치는 구간의 크기. 분할 지점에서 문맥이 잘려
  의미가 왜곡되는 문제를 줄인다.

`split_documents()`는 `pages`(PDF에서 추출한 페이지 객체)를 입력받아 각 페이지
텍스트를 분할하고, 여러 개의 청크를 리스트로 반환한다.

### 왜 분할하는가

1. **대형 텍스트 처리**
   PDF 문서는 보통 매우 길지만 LLM이 한 번에 처리할 수 있는 길이에는 제한이
   있다. 예를 들어 GPT-3는 약 4096 토큰이 한계이고, 1토큰은 대략 4~5자이므로
   영어 기준 2000~3000 단어 수준이다. 긴 문서를 통째로 넣을 수 없으니 작은
   덩어리로 쪼개야 한다.

2. **문맥 보존**
   `chunk_overlap`으로 겹치는 구간을 두면 텍스트가 나뉘어도 문맥의 연속성이
   어느 정도 유지된다. 트랜스포머 계열 모델은 단어 단위가 아니라 문맥 기반으로
   분석하므로 이 방식이 더 정확한 결과로 이어진다.

3. **효율적인 검색**
   텍스트가 너무 길면 검색 시 계산이 복잡해진다. 작은 청크로 나누면 각 청크
   단위로 정보 검색을 수행해 관련 내용을 빠르게 찾을 수 있다. 분할된 문서는
   이후 벡터화되어 Chroma 같은 벡터 저장소에 저장되고, 이 벡터를 통해 더 빠르고
   정확한 검색이 가능해진다.

4. **데이터 전처리**
   NLP에서 긴 문서를 다루려면 의미 단위로 나누는 전처리가 필요하다. 사람이
   일일이 나누는 것보다 훨씬 빠르고 대량으로 처리할 수 있다.

## 3. 임베딩 — `HuggingFaceEmbeddings`

패키지: `langchain_huggingface`

```python
embeddings = HuggingFaceEmbeddings(
    model_name='BAAI/bge-m3',
    model_kwargs={'device': 'cpu'},
    encode_kwargs={'normalize_embeddings': True},
)
```

### 임베딩이란

고차원 텍스트 데이터를 저차원 벡터로 변환하는 방법이다. 이 벡터는 텍스트의
의미를 수치로 표현하며, 유사한 의미를 가진 텍스트일수록 벡터 공간에서 가까운
위치에 배치된다.

### `normalize_embeddings`를 켜는 이유

임베딩을 비교할 때 중요한 것은 벡터의 **크기가 아니라 방향**이다. 크기는 계산
과정에서 세기를 나타낼 수 있지만, 실제로 비교하려는 대상은 의미의 유사성이다.
크기가 제각각이면 유사도 계산에서 크기 차이에 의한 왜곡이 생기므로, 정규화해
크기를 1로 맞춘다.

일관성 측면에서도 유리하다. 코사인 유사도(cosine similarity)는 분모에 벡터의
크기가 들어가는데, 정규화된 벡터를 쓰면 크기가 1인 벡터 간의 내적만 계산하면
되므로 계산이 간단해지고 기준이 일정해진다.

코사인 유사도 값의 의미:

| 두 벡터의 관계 | 유사도 |
|---|---|
| 완전히 같은 방향 | 1 |
| 수직 | 0 |
| 정반대 방향 | -1 |

### BAAI/bge-m3 모델

BAAI(Beijing Academy of Artificial Intelligence)에서 개발한 언어 모델이다.
고차원 임베딩 공간에서 텍스트의 의미를 포착하고 유사성을 계산하는 데 쓰이며,
의미적 유사도 측정·문서 검색·질의응답에 특화되어 있다. 다국어 임베딩을 잘
처리하도록 학습되어 한국어와 중국어에 강점이 있다. 단어 간 문맥과 상호관계를
학습해 텍스트의 의미적 구조를 이해한다.

> **`device`가 왜 `'cpu'`인가 — Colab GPU를 쓰는데도**
>
> 이 시스템에는 모델이 두 개 있고, 실행 위치가 다르다.
>
> | 모델 | 역할 | 실행 위치 | CUDA |
> |---|---|---|---|
> | `BAAI/bge-m3` (임베딩) | 문서·질의를 벡터로 변환 | 라즈베리파이 로컬 | ✗ |
> | `llama3.1-korean:8b` (LLM) | 답변 생성 | Colab GPU | ✓ |
>
> `device: 'cpu'`는 **임베딩 모델에만 적용**된다. 임베딩은 라즈베리파이에서
> 직접 수행하는데 여기엔 NVIDIA GPU가 없으므로 CPU를 쓸 수밖에 없다.
>
> 반면 GPU를 실제로 사용하는 LLM 추론은 **이 코드가 직접 수행하지 않는다.**
> `ChatOllama(base_url=...)`는 Colab에 떠 있는 Ollama 서버로 HTTP 요청을 보낼
> 뿐이고, CUDA 사용 여부는 그쪽 Ollama가 알아서 처리한다. 그래서 이 저장소
> 코드에는 LLM용 `device` 설정이 아예 존재하지 않는다.
>
> 참고로 CUDA는 NVIDIA가 개발한 병렬 컴퓨팅 플랫폼으로, GPU를 활용해 병렬
> 연산을 수행하게 해주는 기술이다. 로컬에 NVIDIA GPU가 있는 환경으로 옮긴다면
> 임베딩 쪽도 `'cuda'`로 바꿔 속도를 높일 수 있다.

## 4. 리트리버

```python
retriever = vectorstore.as_retriever(search_kwargs={'k': 3})
```

`k`는 질의당 가져올 유사 문서 청크의 개수다. 값을 키우면 참고 자료의 다양성이
늘지만 노이즈도 함께 늘어나므로, 실험을 통해 적정값을 정하는 것이 좋다.

# 상세 설계

[리빌딩계획.md](리빌딩계획.md)의 기술 설계 문서. 구현 판단의 기준이 된다.

## 원칙

1. **설정으로 백엔드를 갈아끼운다** — 코드 수정 없이 상용 API ↔ self-hosted 전환.
   프로바이더가 둘 이상이므로 백엔드 이름은 `api` 대신 `gemini`, `anthropic`처럼
   프로바이더를 명시한다.
2. **키 없이도 개발·테스트가 돌아간다** — `fake` 백엔드로 전 구간 검증 가능.
3. **법률 도메인 특성을 설계에 반영한다** — 조문 단위 분할, 정확 매칭 검색, 근거 인용.
4. **과한 추상화를 만들지 않는다** — LangChain의 `BaseChatModel`이 이미 인터페이스
   역할을 하므로, 별도 래퍼 계층 없이 팩토리 함수 하나로 처리한다.

```
│   │   ├── api/
│   │   │   ├── routes.py      엔드포인트
│   │   │   └── schemas.py     요청·응답 스키마
│   │   ├── llm/
│   │   │   ├── factory.py     백엔드 선택
│   │   │   └── fake.py        테스트용 결정론적 백엔드
│   │   └── rag/
│   │       ├── ingest.py      PDF → 청크 → 벡터스토어
│   │       ├── chunking.py    조문 단위 분할
│   │       ├── retrieval.py   하이브리드 검색
│   │       ├── rerank.py      리랭킹 (선택)
│   │       └── graph.py       LangGraph 에이전트 (3단계)
│   ├── tests/
│   └── pyproject.toml
├── frontend/                  Next.js (5단계)
├── data/
│   ├── pdf/                   원본 문서
│   └── vector_store/          Chroma (git 제외)
├── docs/
└── archive/, legacy 자산
```

기존 `app.py`, `templates/`, `static/`는 제거한다. `legacy-2024` 브랜치와
`v1.0-capstone` 태그에 보존되어 있다.

**의존성 관리는 uv를 쓴다.** ARM CPU에서 설치가 현저히 빠르고, 이 환경에서는
체감 차이가 크다.

**Docker는 6단계로 미룬다.** 파이에서 torch를 포함한 이미지를 빌드하면 시간이
과도하게 소모된다. 개발은 네이티브로, 컨테이너화는 Oracle 배포 시점에 한다.

## LLM 백엔드

별도 추상 클래스를 만들지 않는다. LangChain의 `BaseChatModel`이 이미 공통
인터페이스이므로, 팩토리 함수가 설정을 보고 적절한 구현을 반환하면 충분하다.

```python
def build_chat_model(settings: Settings) -> BaseChatModel:
    match settings.llm_backend:
        case "gemini":       return ChatGoogleGenerativeAI(...)
        case "anthropic":    return ChatAnthropic(...)
        case "self_hosted":  return ChatOllama(...)
        case "fake":         return FakeChatModel(...)
```

`FakeChatModel`은 LangChain의 `FakeListChatModel` 계열을 사용하거나 동등하게
구현한다. 입력에 대해 결정론적 응답을 돌려주어야 테스트가 안정적이다.

## 문서 처리

### 조문 단위 분할

v1은 500자/100자 중첩으로 기계적으로 잘랐다. 법률 문서는 **조(條) 단위가 의미
단위**이므로 문맥이 조 중간에서 끊기면 검색 품질이 떨어진다.

1. 정규식으로 `제N조`, `제N조의M` 경계를 찾아 조 단위로 1차 분할한다.
2. 한 조가 너무 길면(`chunk_size` 초과) 재귀 분할기로 2차 분할하되, 같은 조에
   속한다는 메타데이터를 유지한다.
3. 조 경계를 찾지 못하는 문서는 전부 재귀 분할기로 처리한다(일반 문서 대응).

### 청크 메타데이터

인용에 필요한 정보를 청크마다 부착한다.

| 필드 | 설명 |
|---|---|
| `source` | 원본 파일명 |
| `page` | PDF 페이지 번호 |
| `article` | 조문 번호(예: `제56조`). 추출 실패 시 `null` |
| `chunk_id` | 고유 식별자 |

## 검색

### 하이브리드

| 경로 | 방식 | 강점 |
|---|---|---|
| Dense | Chroma + bge-m3 | 의미 유사도. 표현이 달라도 찾음 |
| Sparse | BM25 | 정확 토큰 일치. `제56조`, `연장근로` 등 |

법률 질의에는 정확히 일치해야 하는 토큰이 많아 벡터 검색 단독으로는 놓치는
경우가 잦다. 두 경로를 병행한다.

### 융합

**RRF(Reciprocal Rank Fusion)** 를 사용한다.

```
score(d) = Σ 1 / (k + rank_i(d))      k = 60
```

점수 정규화가 필요 없어 튜닝 부담이 적고, 서로 다른 스케일의 점수를 합칠 때
가중합보다 안정적이다.

### 리랭킹 (선택)

`BAAI/bge-reranker-v2-m3` 크로스 인코더로 상위 후보를 재정렬한다. 정확도는
오르지만 파이 CPU에서는 수 초가 걸리므로 `RERANK_ENABLED`로 제어하고 기본값은
off로 둔다. Oracle 배포 시 on을 검토한다.

## API

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/health` | 상태 및 현재 백엔드 확인 |
| POST | `/api/ask` | 질의 → 답변 + 인용 |

응답에는 답변 본문과 함께 근거 목록을 포함한다.

```json
{
  "answer": "...",
  "citations": [
    {"source": "...", "page": 12, "article": "제56조", "snippet": "..."}
  ],
  "backend": "fake"
}
```

스트리밍은 5단계에서 SSE로 추가한다. 이를 위해 서비스 계층은 처음부터 비동기
제너레이터를 반환할 수 있는 형태로 작성해, 나중에 얇게 얹을 수 있게 한다.

## 테스트

`fake` 백엔드 덕분에 키 없이 전 구간을 검증할 수 있다.

| 대상 | 검증 내용 |
|---|---|
| 설정 | 백엔드 전환이 의도대로 동작 |
| 청킹 | 조문 경계 분할, 메타데이터 부착 |
| 검색 | BM25·벡터 각각의 결과, RRF 융합 순위 |
| API | `/health`, `/api/ask` 응답 스키마 |

## 관측

LangSmith로 추적한다. `LANGSMITH_TRACING=false`가 기본이므로 키가 없어도 동작에
지장이 없다. 에이전트 그래프는 실행 경로가 분기·반복되어 로그만으로는 디버깅이
어려우므로, 3단계 이후 특히 유용하다.

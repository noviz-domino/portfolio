# SINGULARITY DRIFT — 로그라이크 탄막 서바이버 기획서

> index.html 단일 파일로 구현할 브라우저 게임의 기획 및 기술 설계 문서. 대화를 통해 확정된 모든 결정사항, 콘텐츠 디자인, 기술 아키텍처, 그리고 구현 착수 단계에서 나온 기술 검토/개선 제언을 종합했다.

---

## 0. Context

사용자는 index.html 단일 파일로 동작하는 브라우저 게임을 기획했으며, 장르는 "로그라이크 탄막게임"으로 시작해 대화를 통해 **Vampire Survivors식 웨이브 서바이벌 + 탄막(불릿헬) 회피**를 결합한 하이브리드 장르로 구체화했다. 프로젝트 디렉터리(`C:\Users\HOME\Desktop\class`)는 `.git`만 있는 완전한 그린필드 상태이며 참고할 기존 코드는 없다.

이 문서는 (1) 사용자와의 질의응답으로 확정된 핵심 결정사항, (2) 게임 디자인 콘텐츠(캐릭터/무기/적/보스/메타 진행), (3) `index.html` 구현을 위한 기술 아키텍처, (4) 실제 구현 착수 전 사용자가 제기한 기술적 병목/개선 제언을 하나로 정리한 것이다. 다음 단계(실제 코드 구현)의 기준 문서로 사용한다.

## 2. 디자인 필라

1. **"피하는 재미"가 "쌓는 재미"보다 우선** — 빌드가 강해져도 회피는 항상 유효해야 한다.
2. **죽음은 항상 내 탓이어야 한다** — 화면 밖 저격, 못 본 스폰, 텔레그래프 없는 공격 금지.
3. **한 판은 짧고, 다음 판은 즉시** — 사망→결과→격납고→재출격까지 3클릭 이내, 로딩 없음.

## 3. 핵심 루프

- **순간 루프(2~5초)**: 적 탄막 전개 → WASD 회피(틈 통과=그레이즈) → 자동 조준 사격(최근접 타겟) → 처치 → XP 파편/에센스 드랍 → 파밍 동선이 곧 위험 동선.
- **중간 루프(30초~3분)**: XP 누적 → 레벨업(완전 정지) → 카드 3택(무기/패시브 신규·강화) → 처리량 상승 → 더 조밀한 웨이브 감당.
- **세션 루프(런 전체, 약 12~14분)**: 격납고(메타 구매) → 출격 → 시간대별 웨이브·엘리트·보스 3종 → 12:00 최종 보스 → 클리어/사망 → 결과창(에센스 정산) → 격납고 복귀.

시간대 비트(요약): 0:00 탐색(적 희소) → 2:00 첫 엘리트 → 4:00 보스1「세라프-01」→ 6:00 밀도 1차 폭발+엘리트 → 8:00 보스2「하이브-퀸 크로노스」→ 10:00 데스 웨이브 → 12:00 최종보스「특이점 코어」.

## 4. 플레이어 캐릭터

- 기본 기체 `SCALAR-01`: 삼각형 벡터 실루엣 + 청백색 글로우 + 트레일. 판정점 = 중앙 코어(반경 4px).
- 이동: 최고속 260px/s, 가속 3000px/s², 감속 3600px/s², 8방향, 대각 정규화.
- **자동 공격(최근접 조준)** 확정 — 마우스가 없으므로 "이동방향 발사"는 회피와 공격을 충돌시켜 배제. 무기별 발사 규칙 4종: `AIMED`(최근접 조준) / `HOMING`(유도) / `SELF`(자기중심) / `DIRECTIONAL`(고숙련 옵션, **§8-5 참조 — 후방 재정의**).
- **Space**: 탭=위상 이탈(대시 180px, 무적 0.20초, 쿨다운 3초, 탄 관통 시 오버드라이브 게이지 충전) / 0.35초 홀드=오버드라이브(게이지 100%일 때 화면 탄 전멸 + 화면 전체 파편 흡수 + 데미지 50%↑ 5초 + 무적 1초, **§8-4 참조**).
- **그레이즈**: 코어 판정(r4) 바깥 반경 22px 링에 적 탄 진입 시 그레이즈 판정, 오버드라이브 게이지 충전 — 회피 실력이 자원이 되는 자기보정 난이도 장치.
- **체력**: 코어 무결성 5칸, 피격=1칸+무적 1.1초+히트스톱 0.12초+주변 넉백(샌드위치 데스 방지). 회복: 패시브/보스 보상/필드 드랍.
- **히트박스 원칙**: "맞추는 판정은 후하게(적 판정 +2px), 맞는 판정은 짜게(플레이어 판정 4px)". 모든 충돌은 원-원 판정, 제곱거리 비교.

## 7. 난이도 곡선 & 공정성 규칙

- 시간 `t`(분) 기반 스케일링: 적HP배율 `1+0.32t+0.028t²`, 스폰율 `1.4+0.85t`/초, 동시적 상한 `min(55+17t,300)`, 동시탄 상한 `min(120+62t,900)`, **탄속 배율은 상한 1.5로 강하게 제한**(밀도만 올리고 속도는 거의 안 올려 후반에도 가독 가능하게).
- **공정성 하드 요구사항(구현 필수)**: 색상 계약(적탄=마젠타/시안+흰코어, 아군탄=앰버, 배경 저채도 알파≤0.3) / 적 탄 항상 최상위 렌더 레이어 / 스폰 안전반경(적260px, 적탄400px) / 텔레그래프 의무화(탄속300↑ 또는 조준탄은 최소 0.45초 예고) / 탄 총량 소프트캡·하드캡(1200→구현 시 900으로 조정, **§8-2 삭제 정책 참조**) / 레벨업 재개 유예 0.6초 / 적 개체 상호반발(뭉침 방지) / 60fps 방어(풀링+파티클 자동감쇠).

## 8. 필수 요구사항 (사용자 확정 — 반드시 구현)

| # | 요구사항 | 구현 방식 |
|---|---|---|
| R1 | 게임 시작 시 간단한 조작법 안내 | 메인 메뉴 화면에 조작법 카드를 항상 노출: "WASD/방향키: 이동 · Space 탭: 위상 이탈(대시) · Space 홀드: 오버드라이브 · 자동 조준 사격". 페이지 로드 시(=게임이 시작되면) 최초로 보이는 화면이 곧 메인 메뉴이므로 별도 모달 없이 요구사항 충족. 메인메뉴에 언제든 재열람 가능 |
| R2 | 판당 점수 계산 | `SCORE = floor(생존시간(초) × 10) + 킬수 × 5 + 엘리트킬 × 50 + 보스킬 × 1000 + 그레이즈횟수 × 2 + 획득에센스 × 1`. 결과 화면에 총점과 항목별 세부 브레이크다운 표시. `sd_save_v1`에 `stats.bestScore` 최고점 저장(로컬 최고 기록 갱신 시 표시) |
| R3 | 게임 종료 조건 | ⓐ 코어 무결성 0(비상 리부트 소진 시) = FAILED, ⓑ 최종 보스 격파(또는 심연 모드에서 사망) = CLEAR. 두 경우 모두 동일한 결과 화면 처리 로직(`finalizeRun`)으로 통일 |
| R4 | 한 판 종료 후 재시작 흐름 | 결과 화면 → `[다시 출격]` 또는 `[격납고로]` → 게임 상태 완전 리셋(엔티티 풀 반환, 타이머·XP·무기·HP 초기화) 후 즉시 재진입. 로딩 화면 없이 즉시 전환 |
| R5 | 재시작 버튼 연속 클릭 시 오류 방지 | (1) 버튼 클릭 리스너는 페이지 로드 시 **단 한 번만 등록**(재실행마다 재등록하지 않음) — 이것이 없으면 리스너 중복 누적으로 더블클릭 시 상태가 두 번 리셋되는 실제 버그가 발생. (2) `safeTransition()` 재진입 가드로 상태 전환 도중 재호출 무시. (3) 게임 루프(`requestAnimationFrame`)는 부팅 시 단 한 번만 시작되고 재시작 시 재시작되지 않음 — "재시작"은 루프를 새로 만드는 게 아니라 기존 루프가 참조하는 게임 상태 객체를 리셋하는 것뿐이므로, 중복 루프로 인한 프레임 폭증/오류 가능성 자체가 구조적으로 없음 |

이 5개 항목은 3~7절의 세부 설계와 별개로 **누락 시 재작업 대상**인 최소 기준선으로 취급한다.

## 9. 메타 진행 (격납고)

- 화폐: **코어 에센스(✧ESS)**, 잡몹10%확률1 / 원거리25%확률2 / 엘리트12 / 보스 40·90·200 / 생존보너스 분당8 / 클리어150.
- 영구 강화 트리 3계통: **HULL(생존)** — 강화 장갑(+1칸)·위상 코팅 프리셋(무적시간)·비상 리부트(1회 부활) / **ARMS(화력)** — 표적 보정기(데미지)·가속 냉각(공속)·오버드라이브 증폭(게이지 요구 감소) / **SYS(편의·성장)** — 자기 코일(흡수범위)·학습 프로토콜(XP)·채굴 드론(에센스)·리롤 칩(레벨업 리롤).
- 저장: `localStorage["sd_save_v1"]`에 JSON(버전필드 포함) — 에센스, 노드별 레벨, 통계. try/catch로 손상/접근불가 폴백, 격납고에 초기화 버튼(2단 확인).

## 12. 기술 아키텍처 (초안)

- **파일 구조**: `index.html` 하나에 `<style>`+`<script>` 인라인. 섹션 배너 주석으로 논리 모듈 분리: `[0]목차 [1]CONFIG상수 [2]수학/유틸 [3]오브젝트풀 [4]엔티티정의(무기/패시브/적/보스 데이터 테이블) [5]시스템(Input/Spawner/AI/Weapon/Collision/XP/Particle/Camera/Save) [6]상태머신 [7]UI브릿지 [8]렌더러 [9]메인루프 [10]부트스트랩`. 예상 규모 JS 2500~4500줄. 무기/패시브/적/보스는 로직이 아닌 **순수 데이터 테이블**로 선언.
- **루프/상태**: `requestAnimationFrame` + **고정 타임스텝 accumulator**(1/60초, 프레임당 최대 반복 캡 5). 상태머신은 문자열enum + handler map: `MENU/HANGAR/PLAYING/LEVELUP/ABYSS_CHOICE/RESULT`.
- **엔티티/충돌**: plain object + 고정크기 배열 오브젝트 풀(적탄950/아군탄500/적260/파티클900/파편300, free-index 스택 방식). 충돌은 전부 원-원(제곱거리, sqrt 없음).
- **렌더링**: 레이어 고정순서(배경→파티클뒤→적→플레이어→탄→파티클앞→**적탄 항상 최상위**). 카메라(2400×1600 아레나 추적)는 world/screen 좌표 분리 + translate.
- **입력**: `keysDown` 상태맵을 매 fixed-tick 폴링(OS key-repeat 의존 금지). `blur/visibilitychange` 시 전체 초기화.
- **저장**: localStorage, 런 종료·구매 시점에만 저장(디바운스).
- **오디오**: WebAudio `OscillatorNode` 기반 절차적 SFX, 외부 파일/BGM 없음.

## 13. 구현 착수 단계 기술 검토 및 개선 제언

> 실제 코드 작성을 시작하는 과정에서, 12절 초안이 그대로 구현될 경우 발생할 수 있는 성능/게임성 문제를 사용자가 사전에 검토하여 아래와 같이 설계를 보강했다. **이 절의 내용은 최종 구현에 반드시 반영해야 하는 확정 사항이다.**

### 13-1. 공간 분할 그리드 — 단일측(single-sided) 등록 방식

- **문제**: 아군탄 vs 적 충돌에 128px 셀 그리드를 쓰되 양쪽(적+아군탄)을 모두 매 프레임 등록/해제하면 연산 오버헤드가 커지고, 셀이 크면 고속 이동하는 작은 탄이 셀을 건너뛰며 충돌을 놓치는 "터널링"이 발생할 수 있다.
- **결정된 방식**: **적(Enemy)만 그리드에 등록**하고(GRID_CELL = 96px), 아군탄은 자신의 좌표가 속한 셀 기준 **3×3 인접 셀(자기 셀 + 인접 8개)**의 적만 조회해서 충돌 검사한다. 그리드는 매 fixed-tick마다 적 목록으로부터 새로 구성(적은 최대 260개라 재구성 비용이 낮음). 아군탄은 등록 대상이 아니므로 등록/해제 연산 자체가 없다.
- 96px 셀 + 3×3 조회 범위(288px)는 보스(반경 66)처럼 큰 적이 인접 셀로 걸쳐 있어도 충돌을 놓치지 않을 만큼 충분히 넓다.
- 적탄 vs 플레이어는 상대가 1개뿐이므로 그리드 없이 전체 순회로 충분(플레이어 기준 전체 적탄 최대 950개 순회는 60fps에서 무리 없음).

### 13-2. 탄 총량 하드캡 도달 시 삭제 정책

- **문제**: 하드캡(900) 도달 시 단순히 "화면 밖" 탄부터 지우면, 보스/엘리트가 화면 밖에서 미리 깔아둔 탄막이 플레이어에게 도달하기 전에 사라져 버려 난이도가 싱거워지거나 패턴이 어색해질 수 있다.
- **결정된 방식**:
  1. 판정 기준을 "아레나 경계 밖"이 아니라 **"카메라 뷰포트 + 패딩 300px 밖"**으로 변경 — 화면에 곧 보일 예정인 탄은 보호된다.
  2. 모든 적탄에 `priority` 필드를 부여: 일반 잡몹/원거리 적의 탄은 `priority=1`, **보스 및 오벨리스크(엘리트)처럼 의도된 탄막 패턴을 구성하는 탄은 `priority=2`**로 표시해 우선 보호한다.
  3. 하드캡 초과 시 1차로 "뷰포트+패딩 밖 && priority<2" 탄부터 제거하고, 그래도 초과 상태면 2차로 "priority<2" 탄 중에서 추가 제거한다. `priority=2`(보스 패턴)는 캡 강제 상황이 아니면 건드리지 않는다.

### 13-3. 절차적 오디오의 디바운스(sound-limit) 처리

- **문제**: 탄막 게임은 초당 다수의 피격/히트 이벤트가 발생한다. 매 이벤트마다 `OscillatorNode`를 새로 생성하면 오디오 버퍼가 과부하되어 "지직거리는" 클리핑/팝 노이즈와 프레임 드랍이 함께 발생할 수 있다.
- **결정된 방식**: SFX 함수마다 **최소 재생 간격(디바운스 게이트)**을 둔다. `performance.now()` 기준으로 마지막 재생 시각을 이벤트 종류별로 기록하고, 간격이 미달이면 재생을 건너뛴다. 기준값(안): 타격 45ms / 처치 30ms / 피격 80ms / 그레이즈 60ms / 대시 100ms / 파밍 35ms. 레벨업·보스 등장·오버드라이브·클리어처럼 드물게 발생하는 이벤트는 게이트가 필요 없다.

### 13-4. 오버드라이브 발동 시 파편 회수 보너스

- **문제**: XP/에센스 파편의 흡수 반경이 넉넉해도, 후반 탄막 밀도가 높아지면 플레이어는 파밍을 포기하고 외곽에서 도망만 다니게 되어 "쌓는 재미"가 죽는다. 회피와 파밍 사이의 딜레마를 풀어줄 보상 장치가 필요하다.
- **결정된 방식**: 오버드라이브 발동 시 화면의 적탄을 전멸시키는 것과 **동시에, 현재 필드에 남아있는 모든 XP/에센스 파편을 즉시 전량 회수**한다. 그레이즈로 채운 게이지가 곧 "탄막을 뚫고 들어가 쓸어담기"라는 명확한 쾌감으로 이어지도록 하여, 리스크(그레이즈를 노리고 접근)와 리워드(오버드라이브의 화면 정리+파밍)를 직접 연결한다.

### 13-5. DIRECTIONAL(디플렉터 어레이) 무기 재정의 — 전방 → 후방

- **문제**: 원래 설계는 패널이 "이동 방향 전방"에 생성되는 구조였다. 그런데 마우스가 없는 자동조준 서바이버 게임에서 플레이어는 대부분 **적을 등지고 후퇴하며 회피**하게 되므로, "이동 방향 전방" 패널은 정작 안전한 방향(플레이어가 향하는 쪽)을 막을 뿐, 실제로 위협적인 탄이 오는 방향(플레이어가 물러나고 있는, 즉 적들이 있는 방향)은 전혀 막지 못하는 구조적 결함이 있었다. 고숙련자용으로 의도했더라도, 핵심 조작 구도(등지고 후퇴하며 사격)와 정면으로 충돌해 스트레스만 유발할 위험이 컸다.
- **결정된 방식**: 패널 위치를 **"이동 반대 방향(후방)"**으로 재정의한다. 즉 플레이어가 특정 방향으로 후퇴하고 있으면, 패널은 플레이어를 기준으로 그 반대편(=플레이어가 방금 있었던 자리, 대개 적들이 몰려있는 방향)에 생성되어 추격탄을 실제로 가로막는다. 구현상 플레이어의 `facing` 값(마지막으로 입력이 있었던 이동 방향)에 `+π`를 더한 각도를 패널 위치로 사용하면 별도의 상태 저장 없이 자연스럽게 구현된다. 무기 설명 문구도 "이동 방향 전방 반사 패널"에서 "이동 반대 방향(후방) 반사 패널 — 추격탄 차단"으로 수정한다.

# RAG 설정 최적화 실험 보고서

**작성일** 2026-09-07 · **대상** 공공문서 11종(정부 PDF) · **평가 데이터** 35문항 Golden set

---

## 1. 한 장 요약

RAG 파이프라인의 설정을 외부 config로 분리하고, 설정을 바꿔가며 **20개 실험**을 실행해
검색 품질과 비용을 함께 측정했다.

### 결론

| 노선 | 추천 조합 | 근거 |
|---|---|---|
| **품질 우선** | 청크 500 + Hybrid + k=5 | Page Hit@1 **0.943**, MRR **0.943**, File Hit@1 **1.000** (전체 최고) |
| **가성비 우선** | 청크 500 + BM25 + k=5 | MRR **0.914** (기준선 0.907보다 높음) · **임베딩 호출 0회** · 43.5초 |

기준선(청크 700 + Similarity + k=5)은 Page Hit@1 0.886 / MRR 0.907이었다.

### 핵심 발견 3가지

1. **청크 크기와 검색 전략은 서로 영향을 준다.** 청크 700에서 Hybrid의 이득은 거의 없지만(MRR 0.907→0.910),
   청크 500에서는 크다(0.895→0.943). 한 번에 하나만 바꾸는 방식으로는 관찰할 수 없는 효과였다.
2. **벡터 검색이 비용을 정당화하지 못했다.** BM25는 임베딩 API를 전혀 쓰지 않는데 품질이 기준선과
   같거나 높았고, 검색 속도는 35배 빨랐다(15ms vs 541ms).
3. **rerank는 완벽히 작동했지만 도입 가치가 낮다.** 개선 가능한 문항 2개를 모두 고쳤으나(최대치),
   문항당 응답 시간이 4.4초 → 37초로 늘었다.

## 2. 실험 설계

### 측정한 것

| 축 | 지표 |
|---|---|
| 검색 품질 | File Hit@1, Page Hit@1/@3/@5, MRR |
| 답변 품질 | 인용 정확도, LLM-as-Judge 4항목(정확성·완전성·근거성·출처정확성) |
| 비용 | 임베딩 호출 수, LLM 호출 수, 토큰 수(추정) |
| 시간 | 문항당 검색 지연, 실험 총 소요 시간 |

목표가 "절대 품질 1위"가 아니라 **"품질 대비 비용"**이므로 비용·시간을 함께 측정했다.
비용은 API가 알려주지 않으므로 호출할 때마다 코드가 직접 세는 계수기를 붙였다.

### 바꾼 것

| 요인 | 시도한 값 |
|---|---|
| 청크 크기 | 500 / 700 / 1000 (겹침 100 고정) |
| 검색 전략 | Similarity / MMR / BM25 / Hybrid |
| k (검색 문서 수) | 3 / 5 / 10 |
| rerank | 사용 / 미사용 |
| 답변 생성 | Similarity 결과 / Hybrid 결과 |

### 설계 원칙

- **기준선을 고정하고 한 항목만 바꾼다.** 두 값을 동시에 바꾸면 점수 변화의 원인을 특정할 수 없다.
- **청킹과 전략은 교차시킨다.** 상호작용이 의심되는 두 요인만 3×4 격자로 채웠다.
  (네 요인 전부를 교차하면 3⁴=81회로 API 한도를 초과한다)
- **같은 문항 수로만 비교한다.** 문항 구성이 다른 실험은 별도 비교군으로 분리했다.

## 3. 결과

### 3-1. 청크 × 전략 격자 (35문항)

**Page Hit@1** — 1등으로 정답 페이지를 맞힌 비율

| | Similarity | MMR | BM25 | Hybrid |
|---|---|---|---|---|
| 청크 500 | 0.857 | 0.857 | 0.886 | **0.943** |
| 청크 700 | 0.886 | 0.886 | 0.886 | 0.886 |
| 청크 1000 | 0.829 | 0.829 | 0.857 | 0.886 |

**MRR** — 정답이 몇 번째에 처음 나왔는지 (1에 가까울수록 앞)

| | Similarity | MMR | BM25 | Hybrid |
|---|---|---|---|---|
| 청크 500 | 0.895 | 0.886 | 0.914 | **0.943** |
| 청크 700 | 0.907 | 0.907 | 0.907 | 0.910 |
| 청크 1000 | 0.872 | 0.871 | 0.895 | 0.910 |

**읽어낸 것**

- 최고점은 `청크 500 + Hybrid`. 격자를 채우지 않았다면 발견하지 못했다.
- BM25는 **청크가 작아질수록 좋아진다**(MRR 0.895 → 0.907 → 0.914). 청크가 짧으면
  그 안의 단어 수가 적어 키워드 매칭이 정밀해진다.
- 벡터 검색(Similarity)은 **청크 500에서 나빠진다**(0.886 → 0.857). 짧은 청크는 의미 정보가 부족하다.
- Hybrid는 둘을 결합하므로 **BM25가 강해지고 벡터가 약해지는 지점에서 이득이 가장 크다.**
- MMR은 어느 청크에서도 Similarity와 차이가 없었다.

### 3-2. 비용·시간

| 전략 | 임베딩 호출 (35문항) | 평균 검색 지연 |
|---|---|---|
| BM25 | **0회** | **15ms** |
| Similarity | 35회 | 541ms |
| Hybrid | 35회 | 522ms |

BM25는 벡터를 만들지 않으므로 검색 시 API를 호출하지 않는다. 이것이 가성비 노선의 근거다.

### 3-3. k 값

| k | Page Hit@5 | MRR | 비고 |
|---|---|---|---|
| 3 | 0.914 | 0.900 | 4~5등에서 처음 맞던 문항이 잘려나감 |
| **5** | **0.943** | **0.907** | 기준선 |
| 10 | 0.943 | 0.907 | 기준선과 **모든 수치가 동일** (추가 이득 0) |

k를 늘려도 얻는 것이 없었다. 5개 안에서 못 찾는 문항은 10개를 봐도 못 찾는다.

### 3-4. rerank (난이도 균형 10문항)

기준선의 실패를 유형별로 나누면 rerank가 고칠 수 있는 문항은 35개 중 **2개**뿐이었다.

| 유형 | 개수 | rerank로 개선 가능? |
|---|---|---|
| 정답이 상위 5개에 없음 | 2 | 불가 (순서만 바꾸는 도구) |
| 상위 5개에 있으나 1등이 아님 | 2 | **가능** |
| 이미 1등이 정답 | 31 | 개선 여지 없음 |

이 4개를 포함한 10문항으로 측정한 결과는 다음과 같다.

| | Page Hit@1 | MRR | LLM 호출 | 문항당 시간 |
|---|---|---|---|---|
| rerank 없음 | 0.600 | 0.675 | 0 | 4.4초 |
| rerank 사용 | **0.800** | **0.800** | 50 | **37초** |

개선 가능했던 2문항을 모두 1등으로 올려 **이론상 최대치**를 달성했다.
그러나 전체 35문항 환산 시 개선폭은 Page Hit@1 +5.7%p가 상한이며, 대가는 응답 시간 8배다.
**서비스 도입은 권하지 않는다.**

### 3-5. 답변 생성 품질 (10문항)

| 조건 | 인용 정확도 | 정답 인용률 | Judge 평균 |
|---|---|---|---|
| Similarity 결과로 생성 | 1.000 | 1.000 | 9.70 / 10 |
| Hybrid 결과로 생성 | 1.000 | 1.000 | **9.95** / 10 |

LLM이 지어낸 출처는 **한 건도 없었다**(인용 정확도 1.000).
다만 두 조건 모두 만점에 가까워, 이 문항 구성으로는 차이를 판별하기 어렵다.

## 4. 실험 과정에서 발견한 문제

계획대로 진행되지 않은 부분이 오히려 얻은 것이 많았다.

### 4-1. 비용 예측이 틀렸다 — 배치는 일일 한도를 아껴주지 않는다

"청크 402개를 10개씩 묶으면 요청 41회"로 계산했으나, API는 **텍스트 하나하나를 1회로 계산**했다.
402개는 41회가 아니라 402회가 차감된다.

→ 배치는 **분당 요청 수는 줄여주지만 일일 한도는 전혀 아껴주지 않는다.**

### 4-2. 조용히 틀린 결과를 만드는 캐시 버그

벡터 저장소 재사용 판단이 "데이터가 하나라도 있으면 완성"이었다. 일일 한도로 중단돼
552개 중 390개만 저장된 상태를 완성본으로 판단해 재사용했고, 문서 29%가 빠진 채로 실험이 돌았다.

**프로그램은 정상 종료했고 표에도 숫자가 찍혔다.** 예측 청크 수(552)와 실제 저장량(390)을
대조해서 발견했다. 수정 후 재실행하니 Page Hit@1이 0.686 → 0.857로 정상화됐다.

→ 죽는 버그보다 **조용히 틀리는 버그**가 위험하다. 예측값과 실측값을 대조해야 잡힌다.

### 4-3. 천장 효과 — 측정 자체가 실패한 경우

첫 rerank 실험은 모든 지표가 1.000으로 나왔다. 비교군도 1.000이었다.
문항을 앞에서부터 10개 잘랐더니 하필 쉬운 문항들이어서 **이미 만점이라 올라갈 여지가 없었다.**

→ 문항을 난이도 기준으로 골라 다시 측정했고, 그때 비로소 rerank 효과가 관찰됐다(3-4절).

### 4-4. 같은 429 오류가 세 가지 다른 문제였다

| 상황 | 실제 원인 | 해결 |
|---|---|---|
| 요청을 연속 전송 | 분당 토큰 한도 초과 | 배치 간 대기 시간 추가 |
| 누적 사용 후 | 일일 요청 한도 소진 | 대기로 해결 불가 |
| 새 API 키로 교체 후 | 한도는 **프로젝트 단위** 공유 | 다른 프로젝트 키 필요 |

오류 코드만 보면 구분되지 않고 메시지 본문을 읽어야 했다.

## 5. 결론과 다음 단계

### 채택

**청크 500 + BM25 + k=5**를 기본 설정으로 제안한다.
품질이 기준선보다 높으면서 임베딩 비용이 0이고 가장 빠르다.
품질을 최우선한다면 `청크 500 + Hybrid`로 전환하되, 개선폭(2문항)과 비용(문항당 벡터 검색 1회)을
함께 고려해야 한다.

### 유보 조건

이 Golden set의 질문들이 원문 표현을 상당히 그대로 사용해 **키워드 검색에 유리했을 가능성**이 있다.
질문이 동의어·의역으로 들어오는 서비스라면 결론이 달라질 수 있다.

또한 문항이 35개여서 **1문항이 2.86%p**다. Hybrid의 개선(1~2문항)이 실력인지 우연인지
이 데이터만으로는 단정할 수 없다. 반면 BM25의 "비용 0, 35배 빠름"은 구조적 차이라 결론이 견고하다.

### 다음 단계

1. **의역 질문을 직접 작성해 검증** — 원문 표현을 쓰지 않는 질문 5~10개를 만들어
   BM25의 우위가 질문 스타일에 의존하는지 확인한다. 벡터 저장소가 이미 구축돼 있어
   질문 임베딩만 추가된다.
2. **프롬프트 비교 실험** — 답변 생성 프롬프트를 `basic` / `grounded` 두 종으로 준비해두었으나
   아직 비교하지 않았다.
3. **문항 수 확대** — 1문항이 2.86%p인 해상도 문제를 완화한다.

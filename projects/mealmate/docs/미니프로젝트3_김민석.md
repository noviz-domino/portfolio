## 0. 기본 정보
- 이름 : 김민석
- 배포 주소 : https://mealmate-inky.vercel.app
- 사용한 AI 모델/API : Google Gemini API (gemini-3.5-flash)

## 1. 한 줄 소개

냉장고에 남은 재료를 적으면 AI가 그 재료로 만들 수 있는 식단과 부족한 재료 장보기 목록을 대신 짜주는 서비스입니다.

## 2. 이런 사람을 위해 만들었습니다

- 대상 : 자취하거나 집에서 직접 밥을 챙겨 먹는 사람
- 그 사람이 지금 겪는 불편 :
  - 냉장고에 재료는 있는데 뭘 해먹을지 매번 고민하다가 결국 배달을 시킵니다.
  - 마트에서 대충 장을 보면 쓰지도 않은 재료가 남아서 버리게 됩니다.
  - 식단을 짜보려 해도 며칠치를 한 번에 계획하는 게 귀찮습니다.
- 이 서비스를 쓰면 달라지는 것 :
  - 가지고 있는 재료를 입력하면 그 재료를 쓰는 식단이 바로 나옵니다.
  - 부족한 재료만 따로 장보기 목록으로 정리해주니 마트에서 헤매지 않습니다.
  - 만든 식단은 저장되니까 나중에 다시 열어보고 먹은 끼니를 체크할 수 있습니다.

## 3. 주요 기능 (3개 이내)

**1) 재료로 식단 만들기**

가진 재료를 태그로 입력하고 목표(감량/유지/벌크업/균형)와 며칠치를 고르면, AI가 식단과 장보기 목록을 한 번에 만들어 저장합니다. 알레르기처럼 절대 들어가면 안 되는 재료도 따로 입력할 수 있습니다.

**2) 끼니별 조리법 보기**

식단에 나온 끼니 카드를 누르면 그 메뉴의 재료와 조리 순서를 AI가 만들어서 보여줍니다. 21끼를 한꺼번에 만들지 않고 누른 끼니 하나만 만들기 때문에 빠르고, 한 번 만든 조리법은 저장해두고 다시 씁니다.

조리법을 새로 만드는 건 **본인 식단에서만** 됩니다. 이미 만들어진 조리법은 로그인하지 않은 사람도 볼 수 있지만, 아직 없는 조리법을 남이 눌러서 만들 수는 없습니다. 그렇게 하지 않으면 다른 사람이 내 AI 사용량을 대신 써버리기 때문입니다.

**3) 식단 관리하기**

먹은 끼니와 산 재료를 체크해서 실천율을 확인할 수 있습니다. 마음에 안 드는 끼니는 그것만 다른 메뉴로 바꿀 수 있고, 식단을 공개로 두면 다른 사람도 둘러볼 수 있습니다.

**모든 화면은 반응형으로 만들었습니다**

핸드폰으로 볼 일이 많은 서비스라고 생각해서, 화면 크기에 따라 배치가 바뀌도록 만들었습니다.

- 식단 카드 목록 : 핸드폰 1열 > 태블릿 2열 > 노트북 3열 > 큰 화면 4열
- 식단 상세 : 넓은 화면에서는 왼쪽에 식단, 오른쪽에 장보기 목록이 나란히 놓이고, 좁아지면 위아래로 쌓입니다
- 하루 끼니 카드 : 좁은 화면에서는 세로로 하나씩, 넓어지면 아침/점심/저녁이 가로로 나란히
- 헤더 로고 : 좁은 화면에서는 글자를 빼고 아이콘만 남겨서 메뉴와 겹치지 않게 했습니다

브라우저 개발자 도구로 375px(핸드폰), 768px(태블릿), 1280px, 1440px에서 하나씩 확인했고, 가로 스크롤이 생기거나 버튼이 화면 밖으로 밀리지 않는 것까지 봤습니다.

## 4. AI를 어디에 어떻게 썼나요

- AI가 하는 일 : 세 군데에서 씁니다.
  1. 식단 생성 : 재료 목록을 받아서 며칠치 식단과 장보기 목록을 만듭니다.
  2. 조리법 생성 : 메뉴 하나를 받아서 재료(분량 포함)와 조리 순서를 만듭니다.
  3. 끼니 재생성 : 이미 있는 메뉴들과 겹치지 않는 새 메뉴 하나를 만듭니다.

- 입력으로 무엇을 주고, 무엇을 받나요 :
  - 입력 : 보유 재료, 제외할 재료, 목표, 며칠치, 하루 몇 끼인지를 텍스트로 정리해서 보냅니다.
  - 출력 : 자유로운 문장이 아니라 정해진 JSON 형태로 받습니다. Gemini의 `responseSchema` 기능으로 응답 구조를 미리 정해두었기 때문에, 항상 같은 모양으로 돌아옵니다. 그래서 받은 결과를 바로 DB에 넣을 수 있습니다.

- AI가 이상한 답을 줬을 때 어떻게 처리했나요 :

  저장하기 전에 서버에서 두 가지를 검사합니다.
  1. 구조 검사 : 요청한 일수만큼 나왔는지, 하루 끼니 수가 맞는지, 아침/점심/저녁이 빠지지 않았는지
  2. 알레르기 검사 : 제외하라고 한 재료가 메뉴 이름이나 재료 목록에 섞여 있지 않은지

  둘 중 하나라도 걸리면 "이런 문제가 있었다"는 내용을 붙여서 **한 번만 다시 생성**합니다. 다시 만든 것도 검사에 실패하면 그때는 **저장하지 않고** 사용자에게 실패 메시지를 보여줍니다. 이상한 식단이 DB에 남는 것보다 안 만들어지는 게 낫다고 생각했습니다.

  화면 쪽도 실패했을 때 로딩이 멈추지 않도록 `try / catch / finally`로 감싸서, 무슨 일이 생기든 로딩 표시가 반드시 풀리게 했습니다.

- 프롬프트에서 신경 쓴 점 1가지 :

  제외 재료를 막을 때 **그 단어만 막으면 안 된다**는 점입니다. 예를 들어 "우유"를 제외했는데 AI가 치즈나 버터를 넣으면 우유 알레르기가 있는 사람한테는 위험합니다. 그래서 프롬프트에 "제외 식품과 그 파생어(가공품, 다른 이름, 같은 원재료로 만든 음식)는 절대 쓰지 않는다"라고 적었습니다. 알레르기는 잘못되면 진짜 위험한 부분이라 여기에 제일 신경을 썼습니다.

  칼로리나 단백질 같은 수치를 만들지 말라고 한 것도 같은 이유입니다. AI가 그럴듯한 숫자를 지어내면 사람들이 믿어버리기 때문입니다.

## 5. 데이터 설계

- 테이블 이름과 역할 :

| 테이블 | 역할 |
| --- | --- |
| `profiles` | 회원 표시 이름 (가입하면 자동으로 만들어짐) |
| `meal_plans` | 식단 한 건. 제목, 재료, 목표, 공개 여부 |
| `meal_days` | 식단 안의 하루 (1일차, 2일차...) |
| `meals` | 하루 안의 끼니 하나. 메뉴 이름과 조리법 |
| `shopping_items` | 그 식단에 필요한 장보기 항목 |

- 주요 컬럼 :
  - `meal_plans` : `user_id`, `title`, `ingredients`(입력한 재료), `exclusions`(제외 재료), `goal`, `is_public`, `total_meals`, `done_meals`
  - `meal_days` : `plan_id`, `day_index`(1~7), `tip`
  - `meals` : `day_id`, `slot`(breakfast/lunch/dinner), `name`, `used_ingredients`(집에 있는 재료), `needed_ingredients`(사와야 하는 재료), `is_done`, `recipe_steps` 등 조리법 컬럼
  - `shopping_items` : `name`, `priority`(필수/추천/선택), `is_bought`

- 이렇게 설계한 이유 :

  처음에는 식단 하나를 통째로 JSON 한 칸에 넣을까 생각했는데, 그러면 "3일차 점심만 완료 체크" 같은 걸 할 수가 없습니다. 체크 하나 누를 때마다 JSON 전체를 다시 써야 하기 때문입니다.

  그래서 식단 > 하루 > 끼니 순서로 테이블을 나눴습니다. 이렇게 하니까 끼니 하나만 완료로 바꾸거나, 끼니 하나만 다른 메뉴로 교체하거나, 끼니 하나에만 조리법을 붙이는 게 전부 그 행 하나만 건드리면 됩니다.

  장보기 목록도 끼니에 붙이지 않고 식단에 붙였습니다. 계란은 여러 끼니에 쓰이는데 끼니마다 달아두면 장보기 목록에 계란이 다섯 번 나오기 때문입니다.

  보안은 Supabase의 RLS(Row Level Security)로 처리했습니다. 모든 테이블에 정책을 걸어서, 공개 식단이거나 내가 만든 식단만 조회되고 수정은 본인 것만 가능하도록 DB 차원에서 막았습니다. 코드에서 실수로 조건을 빼먹어도 남의 데이터가 새지 않게 하려고 이렇게 했습니다.

## 6. 화면 흐름

1. 사이트에 들어오면 다른 사람들이 공개해둔 식단 목록이 먼저 보입니다. 로그인하지 않아도 카드를 눌러서 식단 내용과 조리법까지 볼 수 있습니다. 무슨 서비스인지 먼저 보여주려고 이렇게 했습니다.
2. 오른쪽 위 `식단 만들기`를 누릅니다. 로그인하지 않았으면 로그인 화면으로 보내고, 로그인하면 원래 누른 곳으로 다시 돌아옵니다.
3. 냉장고에 있는 재료를 하나씩 입력합니다(Enter로 추가). 제외할 재료, 목표, 며칠치, 하루 몇 끼인지를 고르고 `식단 생성하기`를 누릅니다.
4. 10초쯤 기다리면 식단 상세 화면으로 넘어갑니다. 날짜별 끼니 카드와 오른쪽에 장보기 목록이 나옵니다.
5. 끼니 카드의 `조리법 보기`를 누르면 그 메뉴의 재료와 만드는 법이 펼쳐집니다. 마음에 안 들면 `다른 메뉴로`를 눌러 그 끼니만 바꿉니다.
6. 장을 보면서 장보기 목록을 체크하고, 밥을 먹으면 끼니를 완료로 체크합니다. 위쪽 실천율 막대가 같이 올라갑니다.
7. 다 만든 식단은 `마크다운 복사`로 메모장에 옮기거나, 공개/비공개를 바꾸거나, 삭제할 수 있습니다.

## 7. 기획서와 달라진 점

- 뺀 것 :
  1. **기본 7일 식단을 3일로 바꿨습니다.** (7일은 선택지로 남겨뒀습니다)
  2. 칼로리, 단백질 같은 영양 수치는 넣지 않았습니다.
  3. 댓글, 좋아요, 팔로우 같은 소셜 기능은 넣지 않았습니다.

- 뺀 이유 :
  1. 장은 보통 2~3일에 한 번 보는데 7일치를 미리 짜두면 뒷부분은 어차피 안 지키게 됩니다. 그리고 7일 3끼면 21끼를 AI가 한 번에 만들어야 하는데, 응답이 길어지면서 중간에 잘리거나 시간이 초과되는 위험이 있었습니다. 3일이면 9끼라 훨씬 안정적이고 AI 사용량도 절반 이하로 줄었습니다.
  2. 무료로 쓸 수 있는 영양 정보 DB가 없어서, 넣으려면 AI가 숫자를 지어내야 합니다. 건강 관련 숫자를 지어내는 건 위험하다고 판단했습니다.
  3. 이틀 안에 만들어야 해서, 핵심인 "재료 넣으면 식단 나오는 것"을 확실히 하는 쪽을 골랐습니다.

- 반대로 기획서에 없었는데 추가한 것 :

  **끼니별 조리법 기능**입니다. 만들다 보니 "메뉴 이름만 알려주면 결국 또 검색해야 하는데?"라는 생각이 들어서 넣었습니다. 대신 21끼 조리법을 한 번에 만들면 느리고 비싸니까, 사용자가 누른 끼니 하나만 만들고 저장해두는 방식으로 했습니다.

- 시간이 더 있었다면 넣었을 것 :
  - 끼니를 다른 메뉴로 바꿨을 때 장보기 목록도 같이 갱신되게 하고 싶었습니다. 지금은 체크해둔 구매 상태가 날아갈까 봐 일부러 건드리지 않고 안내 문구만 띄웁니다.
  - 모바일에서 7일치를 볼 때 날짜 탭으로 넘기는 화면
  - 지난주에 먹은 메뉴를 피해서 새 식단을 만들어주는 기능

## 8. 만들면서 가장 오래 막혔던 것

- 문제 :

  식단 생성 버튼을 눌렀는데 **로딩 스피너가 영원히 도는** 문제였습니다. 에러 메시지도 없고, 화면은 멀쩡한데 그냥 계속 돌기만 했습니다. AI가 느린 건 줄 알고 몇 분을 기다려봤는데 끝나지 않았습니다.

- 어떻게 해결했나 :

  원인은 서버 API 코드에서 **어떤 경우에 응답을 돌려주지 않고 함수가 끝나버린 것**이었습니다. 조건문 안에서 처리만 하고 응답을 반환하는 줄을 빼먹었던 건데, 그러면 이런 일이 벌어집니다.

  서버가 아무것도 안 보내고 끝나니까, 화면에서 `response.json()`으로 응답을 읽으려다 에러가 납니다. 그런데 그 에러를 잡아두지 않았기 때문에, 바로 아래에 있던 "로딩 꺼라"는 코드까지 가지도 못하고 멈춰버립니다. 그래서 에러 메시지도 안 뜨고 스피너만 계속 돌았던 겁니다.

  고친 방법은 두 가지입니다.
  1. API 코드에서 **모든 갈래가 반드시 응답을 반환하도록** 다시 점검했습니다. 성공이든 실패든 무조건 `Response.json()`으로 끝나게 만들었습니다.
  2. 화면 쪽은 `finally`를 써서, 성공하든 실패하든 오류가 나든 **로딩 표시가 반드시 꺼지게** 했습니다.

  이 일이 있고 나서 다른 기능을 만들 때도 "이 함수는 모든 경우에 뭔가를 돌려주는가"를 먼저 확인하는 습관이 생겼습니다.

  이 밖에 배포에서 한 번 크게 막혔던 적도 있습니다. 내 컴퓨터(Windows)에서는 잘 되는데 Vercel에 올리면 빌드가 실패했습니다.

  원인은 제가 낸 오타였습니다. AI 토큰을 아끼려고 할 일을 단계별 todo로 쪼개두고, 프로젝트 세팅이나 파일 만드는 것처럼 단순한 부분은 AI를 쓰지 않고 직접 타이핑했습니다. 그러다 파일 이름을 `signupForm.tsx`(소문자 s)로 만들어 놓고, 코드에서는 `SignupForm`(대문자 S)으로 불러오게 적었습니다.

  문제는 이게 **한참 뒤에야 드러났다**는 점입니다. Windows는 파일 이름의 대소문자를 구분하지 않아서 로컬에서는 아무 문제 없이 잘 돌아갔습니다. 그런데 Vercel은 리눅스라 대소문자를 구분합니다. 그래서 배포할 때가 되어서야 "그런 파일 없다"며 빌드가 깨졌습니다. 로컬에서는 멀쩡한데 배포만 실패하니 처음에는 원인을 짐작하기 어려웠습니다.

  결국 AI와 같이 빌드 로그를 보면서 어느 파일에서 나는 오류인지 찾았고, 파일 이름을 `SignupForm.tsx`로 바꿔서 해결했습니다.

  여기서 배운 건 두 가지입니다. 토큰을 아끼려고 직접 친 부분에서 오히려 오타가 났다는 것, 그리고 내 컴퓨터에서 잘 된다고 배포에서도 잘 되는 게 아니라는 것입니다. 그 뒤로는 파일을 만들 때부터 이름과 import 경로의 대소문자를 맞춰서 쓰고, 배포 전에 `npm run build`를 돌려서 확인하고 있습니다.

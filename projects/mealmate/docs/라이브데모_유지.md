# 라이브 데모 유지 방침

## 왜 필요한가

이 프로젝트는 Supabase 무료 플랜을 쓴다. 무료 플랜은 **7일간 DB 활동이 없으면 프로젝트를 자동으로 일시정지**시킨다. 정지되면 대시보드에서 손으로 재개할 때까지 앱 전체가 동작하지 않는다.

배포 주소를 포트폴리오에 걸어둔 이상, 누군가 링크를 눌렀을 때 죽어 있으면 안 된다. 그래서 사람이 챙기지 않아도 유지되도록 자동화했다.

> Vercel 배포는 만료되지 않는다. Hobby 플랜에 기간 제한이 없으므로 별도 조치가 필요 없다. **갱신이 필요한 건 Supabase뿐이다.**

## 어떻게 동작하는가

포트폴리오 저장소([noviz-domino/portfolio](https://github.com/noviz-domino/portfolio))의 GitHub Actions가 **3일마다** 이 프로젝트의 Supabase에 가벼운 조회를 보낸다. 조회(SELECT)만으로도 정지 타이머는 초기화된다.

```
GitHub Actions (3일마다)
  └─ GET /rest/v1/keep_alive?select=id&limit=1
       └─ Supabase 활동 감지 → 7일 타이머 리셋
```

**3일 주기로 잡은 이유**: 한도가 7일이므로 절반으로 뒀다. 한 번 실행이 실패하거나 누락돼도 다음 실행에서 복구된다.

## 준비된 것

### `keep_alive` 테이블

핑 전용 테이블이다. 데이터는 담지 않는다.

```sql
create table if not exists public.keep_alive (
  id bigint generated by default as identity primary key,
  created_at timestamptz not null default now()
);

insert into public.keep_alive default values
on conflict do nothing;

alter table public.keep_alive enable row level security;

drop policy if exists "keep_alive 조회 허용" on public.keep_alive;
create policy "keep_alive 조회 허용"
  on public.keep_alive
  for select
  using (true);
```

RLS를 켜고 **조회만** 허용했다. INSERT/UPDATE/DELETE 정책은 만들지 않았으므로 RLS 기본 동작에 따라 차단된다. 외부에서 할 수 있는 일은 빈 행 하나를 읽는 것뿐이다.

RLS를 굳이 켠 이유는 Supabase가 RLS 없는 `public` 테이블에 보안 경고를 띄우기 때문이다. 경고를 방치하면 나중에 진짜 문제가 생겼을 때 구분이 안 된다.

### 인증 키

핑에는 `NEXT_PUBLIC_SUPABASE_ANON_KEY`만 쓴다. 브라우저에 그대로 내려가는 공개 키라 유출 위험이 없다.

**`SUPABASE_SERVICE_ROLE_KEY`는 쓰지 않는다.** RLS를 전부 우회하는 DB 전체 권한 키이므로 단순 핑 용도에 쓸 이유가 없고, 워크플로에 노출될 위험만 늘어난다.

## 점검 방법

포트폴리오 저장소 → **Actions** 탭 → `Supabase Keep-Alive` → 최근 실행이 초록색인지 확인한다. 수동 실행은 **Run workflow** 버튼.

| 증상 | 원인 | 조치 |
|---|---|---|
| `HTTP 404` | `keep_alive` 테이블 없음 | 위 SQL 실행 |
| `HTTP 401` / `403` | 키가 틀렸거나 정책 누락 | 시크릿 값과 RLS 정책 확인 |
| `HTTP 5xx` | 이미 일시정지됨 | 대시보드에서 재개 후 워크플로 수동 실행 |

## 알아둘 것

GitHub Actions는 저장소에 **60일간 활동이 없으면 스케줄 워크플로를 자동 비활성화**한다. 포트폴리오 저장소는 프로젝트가 추가될 때마다 커밋이 생기므로 실무상 문제되지 않지만, 오래 손대지 않았다면 Actions 탭에서 활성 상태를 확인한다.

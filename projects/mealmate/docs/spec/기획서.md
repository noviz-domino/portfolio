## 1\. 제품 목표
### 1-1. 사용자 유형
#### 방문자
*   로그인하지 않아도 공개된 식단 카드를 볼 수 있습니다.
*   공개 식단 상세 페이지를 열 수 있습니다.
*   식단 생성 버튼을 누르면 로그인/회원가입 화면으로 이동합니다.
*   방문자는 다른 사람의 비공개 식단이나 개인 식단 목록을 볼 수 없습니다.
#### 회원
*   이메일과 비밀번호로 회원가입합니다.
*   Supabase가 보낸 확인 이메일 링크를 클릭해야 로그인할 수 있습니다.
*   로그인 후 재료·제외 식품·목표·끼니 수를 입력해 AI 식단을 생성합니다.
*   본인이 만든 식단을 언제든지 확인하고 완료 체크를 관리합니다.
*   본인이 만든 식단만 공개/비공개로 변경할 수 있습니다.
*   공개한 식단은 모든 방문자의 홈 탐색 카드에 표시됩니다.
### 1-2. 핵심 성공 기준
*   비로그인 방문자가 5초 안에 서비스 목적과 다음 행동을 이해한다.
*   첫 화면에서 공개 식단 카드가 데스크톱에서는 넓은 그리드, 모바일에서는 2열 또는 1열로 자연스럽게 표시된다.
*   회원가입 후 이메일 확인, 로그인, 식단 생성이 각각 명확하게 동작한다.
*   로그인 폼과 회원가입 폼은 **서로 다른 컴포넌트**로 구현한다.
*   Gemini가 반환한 식단은 서버에서 구조 및 알레르기 검증 후 저장한다.
*   다른 사용자의 식단 데이터가 개인 목록에 섞이지 않는다.
*   375px 모바일부터 넓은 데스크톱까지 단순히 세로 화면을 늘리는 방식이 아니라 레이아웃 자체가 바뀐다.

### 2-2. 시각 언어
*   배경: `#FFFFFF`, 보조 배경 `#F7F7F5`
*   본문: 거의 검정 `#222222`
*   핵심 브랜드 색: 식욕과 신뢰를 동시에 주는 딥 그린 `#176B52`
*   보조 강조: 따뜻한 오렌지 `#F28C28`
*   경고: `#B42318`
*   카드: 흰색, 1px 연한 테두리, 16~24px radius, 약한 shadow
*   버튼: 주요 CTA는 둥근 pill, 보조 버튼은 rounded-lg
*   폰트: `Pretendard` 또는 Next font의 한글 가독성 좋은 sans-serif
*   이미지가 없을 때도 카드가 허전하지 않도록 재료 태그와 색상 블록을 사용합니다.
### 2-3. 데스크톱 레이아웃
데스크톱에서는 콘텐츠를 좁은 모바일 폭으로 가운데 세로 배치하지 않습니다.
*   1280px 이상: 최대 콘텐츠 폭 1200~1360px
*   헤더: 로고 왼쪽, 탐색 메뉴 가운데, 로그인/프로필 오른쪽
*   홈: 왼쪽에 검색·필터 영역, 오른쪽에 공개 식단 카드 그리드
*   카드 그리드: 4열(1440px), 3열(1024px), 2열(768px)
*   식단 상세: 왼쪽 7일 식단 본문, 오른쪽 고정에 가까운 장보기 요약 패널
*   식단 생성: 2열. 왼쪽 입력 폼, 오른쪽 샘플 미리보기 및 제약 조건 요약
### 2-4. 모바일 레이아웃
*   375~767px: 한 열 중심, 일부 카드만 2열
*   헤더 메뉴는 햄버거 또는 하단 고정 네비게이션으로 변경
*   홈 카드: 작은 썸네일·태그 중심의 2열 또는 화면 폭에 따라 1열
*   필터: 왼쪽 사이드바 대신 가로 스크롤 chip row와 bottom sheet
*   식단 상세: 7일을 한 번에 7열로 표시하지 않고 날짜 탭 또는 가로 스크롤 탭 사용
*   장보기 리스트는 하단에 별도 섹션으로 표시
*   CTA는 손가락으로 누르기 쉬운 최소 44px 높이
*   표 형태와 고정 폭 요소를 금지합니다.
### 2-5. 반응형 검증 기준
반드시 브라우저 개발자 도구와 실제 기기에서 다음 폭을 확인합니다.

`375px`, `390px`, `768px`, `1024px`, `1280px`, `1440px`

각 폭에서 확인할 것:
*   가로 스크롤이 의도한 날짜 탭 외에는 생기지 않는가
*   데스크톱에서 좌우에 쓸데없는 빈 공간이 과도하게 남지 않는가
*   카드가 한 열 세로 목록으로만 축소되지 않는가
*   입력 폼과 CTA가 화면 밖으로 밀리지 않는가
*   상세 페이지에서 식단과 장보기 영역이 각 화면에 맞는 구조로 바뀌는가

## 4\. 권한과 데이터 공개 정책
### 4-1. 공개 식단
`meal_plans.is_public = true`인 식단만 공개됩니다.

공개되는 필드:
*   식단 제목
*   목표
*   재료명
*   요약
*   7일 메뉴
*   메뉴 태그
*   생성일
*   공개 작성자 표시명 또는 익명 표시

공개하지 않는 필드:
*   이메일
*   Supabase user id
*   개인 메모
*   비공개 식단
*   인증 토큰
### 4-2. 소유자 식단
회원이 생성한 식단의 `user_id`는 `auth.users.id`와 연결합니다. 기존 익명 `owner_key` 설계는 이 최종 버전에서 사용하지 않습니다.

이유:
*   식단 생성이 로그인 필수이므로 Auth가 더 단순하고 안전합니다.
*   다른 기기에서도 로그인만 하면 본인 식단을 볼 수 있어야 합니다.
*   RLS 정책으로 데이터 접근 규칙을 명확하게 검증할 수 있습니다.
### 4-3. RLS 정책 원칙
*   공개 홈: `is_public = true`인 행만 anon/authenticated가 SELECT 가능
*   내 식단: `auth.uid() = user_id`인 행만 SELECT/UPDATE/DELETE 가능
*   INSERT: `user_id = auth.uid()`인 회원만 가능
*   하위 테이블: 부모 식단의 user\_id를 확인하는 정책 적용
*   서버 관리자 키는 서버 Route Handler에서만 사용하고 브라우저에 노출하지 않음

## 5\. 회원가입·로그인 설계
### 5-1. 반드시 분리할 컴포넌트
다음처럼 삼항 연산자로 폼 내부 액션만 교체하지 않습니다.

```plain
// 금지: 한 컴포넌트 안에서 action을 삼항식으로 교체
<form action={mode === 'login' ? login : signup}>...</form>
```

대신 완전히 별도 컴포넌트로 분리합니다.

```plain
<AuthPanel>
  {mode === 'login' ? <LoginForm /> : <SignupForm />}
</AuthPanel>
```

`LoginForm`과 `SignupForm`은 각각 자신의 `useState`, `onSubmit`, 검증, 오류 메시지를 가집니다. 탭을 바꿀 때 React key도 바꿉니다.

```plain
{mode === 'login' ? <LoginForm key="login" /> : <SignupForm key="signup" />}
```

### 5-2. 회원가입 흐름
1. 사용자가 이메일과 비밀번호 입력
2. 클라이언트 기본 검증
3. `supabase.auth.signUp({ email, password, options: { emailRedirectTo } })`
4. 성공하면 같은 화면에 `Check your email` 상태 표시
5. 이메일 링크 클릭
6. `/auth/callback` Route Handler가 code를 session으로 교환
7. `/auth/confirmed`에서 로그인 완료 안내
8. 사용자가 로그인 탭으로 이동해 로그인
### 5-3. 이메일 인증 설정
Supabase Dashboard에서 Authentication → URL Configuration에 다음을 등록합니다.
*   Site URL: Vercel 배포 URL
*   Redirect URLs: `http://localhost:3000/auth/callback`
*   Redirect URLs: `https://배포주소.vercel.app/auth/callback`

로컬과 배포 URL을 모두 등록해야 합니다. 배포 URL을 추측하지 말고 실제 Vercel URL을 복사합니다.
### 5-4. 로그인 실패 예방
*   이메일 인증 전 로그인 시도: `이메일 인증 링크를 먼저 클릭해 주세요.`
*   이미 가입된 이메일로 회원가입: `이미 가입된 이메일입니다. 로그인 탭을 이용해 주세요.`
*   탭 전환 시 이전 오류 문구를 초기화
*   이메일·비밀번호 입력값을 login/signup 컴포넌트가 서로 공유하지 않음
*   제출 중 버튼 disabled
*   이중 제출 방지용 `isSubmitting` 상태 사용

## 6\. 사용자 흐름
### 방문자 흐름
`/` 접속 → 공개 식단 카드 탐색 → 필터/검색 → 카드 클릭 → 공개 상세 → \[내 식단 만들기\] 클릭 → `/auth?next=/create`
### 회원 흐름
`/auth` → 회원가입 → 이메일 확인 → 로그인 → `/create` → 입력 → AI 생성 → 검증 → 저장 → `/plans/[id]`
### 재방문 흐름
`/` → 로그인 상태이면 헤더에 \[식단 만들기\], \[내 식단\] 노출 → 내 식단 목록 → 상세 → 체크 상태 확인

### 화면 B: 인증 `/auth`
*   좌우 2열 데스크톱: 왼쪽 브랜드 설명, 오른쪽 인증 카드
*   모바일: 인증 카드 1열
*   로그인과 회원가입은 별도 컴포넌트
*   이메일 인증 대기 상태는 폼 대신 안내 카드

### 화면 C: 생성 `/create`
*   로그인하지 않은 사용자가 접근하면 `/auth?next=/create`로 이동
*   데스크톱: 왼쪽 입력 패널 45%, 오른쪽 샘플 식단 미리보기 55%

### 화면 D: 공개 상세 `/plans/[id]`
*   공개 식단이면 누구나 조회 가능
*   비공개 식단이면 소유자 본인만 조회, 타인에게는 404처럼 표시

*   모바일: 날짜 탭, 끼니 카드, 장보기 섹션 순서
*   소유자에게만 \[공개/비공개\], \[삭제\], 완료 체크 노출

### 8-1. SQL 마이그레이션

```sql
create extension if not exists pgcrypto;

create table public.profiles (
  id uuid primary key references auth.users(id) on delete cascade,
  display_name text not null default 'MealMate 사용자',
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create table public.meal_plans (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade,
  title text not null default '주간 식단',
  ingredients text[] not null default '{}',
  exclusions text[] not null default '{}',
  goal text not null check (goal in ('loss','maintain','bulk','balanced')),
  meals_per_day int not null check (meals_per_day in (2,3)),
  start_date date not null default current_date,
  summary text,
  tips text[] not null default '{}',
  is_public boolean not null default true,
  total_meals int not null default 0,
  done_meals int not null default 0,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
create index meal_plans_public_idx on public.meal_plans (is_public, created_at desc);
create index meal_plans_user_idx on public.meal_plans (user_id, created_at desc);

create table public.meal_days (
  id uuid primary key default gen_random_uuid(),
  plan_id uuid not null references public.meal_plans(id) on delete cascade,
  day_index int not null check (day_index between 1 and 7),
  tip text,
  unique(plan_id, day_index)
);

create table public.meals (
  id uuid primary key default gen_random_uuid(),
  plan_id uuid not null references public.meal_plans(id) on delete cascade,
  day_id uuid not null references public.meal_days(id) on delete cascade,
  user_id uuid not null references auth.users(id) on delete cascade,
  slot text not null check (slot in ('breakfast','lunch','dinner')),
  name text not null,
  used_ingredients text[] not null default '{}',
  needed_ingredients text[] not null default '{}',
  reason text,
  tags text[] not null default '{}',
  is_done boolean not null default false,
  unique(day_id, slot)
);
create index meals_plan_idx on public.meals(plan_id);

create table public.shopping_items (
  id uuid primary key default gen_random_uuid(),
  plan_id uuid not null references public.meal_plans(id) on delete cascade,
  user_id uuid not null references auth.users(id) on delete cascade,
  name text not null,
  category text not null default '기타',
  priority text not null check (priority in ('required','recommended','optional')),
  reason text,
  is_bought boolean not null default false,
  sort_order int not null default 0
);

create or replace function public.handle_new_user()
returns trigger language plpgsql security definer set search_path = public as $$
begin
  insert into public.profiles (id, display_name)
  values (new.id, coalesce(new.raw_user_meta_data->>'display_name', 'MealMate 사용자'));
  return new;
end; $$;

create trigger on_auth_user_created
after insert on auth.users
for each row execute procedure public.handle_new_user();

create or replace function public.touch_updated_at()
returns trigger language plpgsql as $$
begin new.updated_at = now(); return new; end; $$;
create trigger meal_plans_touch before update on public.meal_plans
for each row execute procedure public.touch_updated_at();

create or replace function public.sync_done_meals()
returns trigger language plpgsql as $$
begin
  update public.meal_plans p
  set done_meals = (
    select count(*) from public.meals m
    where m.plan_id = coalesce(new.plan_id, old.plan_id) and m.is_done = true
  )
  where p.id = coalesce(new.plan_id, old.plan_id);
  return null;
end; $$;
create trigger meals_sync_done
after insert or update of is_done or delete on public.meals
for each row execute procedure public.sync_done_meals();

alter table public.profiles enable row level security;
alter table public.meal_plans enable row level security;
alter table public.meal_days enable row level security;
alter table public.meals enable row level security;
alter table public.shopping_items enable row level security;

create policy profiles_select_own on public.profiles
for select using (auth.uid() = id);
create policy profiles_update_own on public.profiles
for update using (auth.uid() = id);

create policy plans_public_select on public.meal_plans
for select using (is_public = true or auth.uid() = user_id);
create policy plans_insert_own on public.meal_plans
for insert with check (auth.uid() = user_id);
create policy plans_update_own on public.meal_plans
for update using (auth.uid() = user_id) with check (auth.uid() = user_id);
create policy plans_delete_own on public.meal_plans
for delete using (auth.uid() = user_id);

create policy days_select_visible_plan on public.meal_days
for select using (
  exists (select 1 from public.meal_plans p where p.id = plan_id and (p.is_public = true or p.user_id = auth.uid()))
);
create policy days_insert_own on public.meal_days
for insert with check (
  exists (select 1 from public.meal_plans p where p.id = plan_id and p.user_id = auth.uid())
);
create policy days_delete_own on public.meal_days
for delete using (
  exists (select 1 from public.meal_plans p where p.id = plan_id and p.user_id = auth.uid())
);

create policy meals_select_visible_plan on public.meals
for select using (
  exists (select 1 from public.meal_plans p where p.id = plan_id and (p.is_public = true or p.user_id = auth.uid()))
);
create policy meals_insert_own on public.meals
for insert with check (auth.uid() = user_id);
create policy meals_update_own on public.meals
for update using (auth.uid() = user_id) with check (auth.uid() = user_id);
create policy meals_delete_own on public.meals
for delete using (auth.uid() = user_id);

create policy shopping_select_visible_plan on public.shopping_items
for select using (
  exists (select 1 from public.meal_plans p where p.id = plan_id and (p.is_public = true or p.user_id = auth.uid()))
);
create policy shopping_insert_own on public.shopping_items
for insert with check (auth.uid() = user_id);
create policy shopping_update_own on public.shopping_items
for update using (auth.uid() = user_id) with check (auth.uid() = user_id);
create policy shopping_delete_own on public.shopping_items
for delete using (auth.uid() = user_id);
```

### POST `/api/plans` 서버 순서
1. Supabase 서버 클라이언트에서 현재 user 조회
2. user가 없으면 401
3. 입력값 검증
4. Gemini 호출
5. JSON 파싱
6. 7일·끼니 수·slot 구조 검증
7. 알레르기 원어와 파생어 검증
8. 위반이면 1회 재생성
9. 또 위반이면 저장하지 않고 422 반환
10. meal\_plans → meal\_days → meals → shopping\_items 순서로 저장
11. 생성된 식단 id 반환

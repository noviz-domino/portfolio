# MealMate 개발일지

2026년 8월 7일 ~ 8월 9일 (3일)

기획서를 바탕으로 냉장고 재료 기반 AI 식단 서비스를 만들면서 남긴 기록입니다.
무엇을 했는지보다 **어디서 막혔고 왜 그렇게 정했는지**를 위주로 적었습니다.

---

## 8월 7일 (1일차) - 뼈대 세우기

### 한 일

- Next.js 프로젝트 생성, Supabase 프로젝트 연결, Vercel 배포 연결
- 회원가입 / 로그인 (LoginForm, SignupForm을 각각 다른 파일로 분리)
- 공개 식단 홈, 식단 생성 폼
- Gemini 연동해서 식단 + 장보기 목록 생성, 검증 후 DB 저장
- 식단 상세 화면

### 막힌 것 1 : 배포만 실패하는 빌드

내 컴퓨터에서는 잘 되는데 Vercel에 올리면 빌드가 깨졌습니다.

AI 토큰을 아끼려고 할 일을 단계별 todo로 쪼개두고, 프로젝트 세팅이나 파일 만드는 단순한 부분은 직접 타이핑하고 있었습니다. 그러다 파일 이름을 `signupForm.tsx`(소문자 s)로 만들어 놓고 코드에서는 `SignupForm`(대문자 S)으로 부르는 오타를 냈습니다.

Windows는 파일 이름의 대소문자를 구분하지 않아서 로컬에서는 멀쩡했습니다. Vercel은 리눅스라 구분하기 때문에 그제서야 "그런 파일 없다"고 나온 겁니다. 로컬에서는 되는데 배포만 안 되니 처음엔 원인을 짐작하기 어려웠습니다.

빌드 로그에서 문제 파일을 찾아 이름을 `SignupForm.tsx`로 바꿔 해결했습니다. 그 뒤로는 파일을 만들 때부터 이름과 import 경로의 대소문자를 맞춰 씁니다.

### 막힌 것 2 : middleware.ts가 안 먹힘

로그인 안 한 사람을 막으려고 `middleware.ts`를 만들었는데 동작하지 않았습니다.
찾아보니 Next.js 16에서는 `middleware.ts`가 더 이상 권장되지 않고 `proxy.ts`를 쓰도록 바뀌었습니다. 파일 이름과 함수 이름을 `proxy`로 바꾸니 정상 동작했습니다.

버전이 올라가면서 바뀐 부분이라, 검색해서 나오는 예전 글을 그대로 따라 하면 안 된다는 걸 알게 됐습니다.

### 막힌 것 3 : 다크모드에서 글자가 안 보임

로그인 화면 글자가 배경에 묻혀서 안 읽혔습니다. 기본 CSS에 다크모드 설정이 들어 있는데, 우리 화면은 배경을 흰색으로 고정해두고 만들어서 다크모드가 켜지면 글자만 밝아져 버린 것이었습니다.

이날은 급한 대로 글자색을 하나씩 지정해서 막았습니다.

## 8월 8일 (2일차) - 기능 채우기

### 한 일

- 다크모드 설정을 아예 제거 (아래 참고)
- 로그인 안 한 사람이 생성 화면에 오면 로그인으로 보내고, 로그인 후 원래 자리로 되돌리기
- 404 페이지
- 내 식단 목록, 공개/비공개 토글, 삭제
- 끼니 완료 체크와 실천율, 장보기 체크
- 공개 홈 목표/태그 필터, 검색
- 끼니별 조리법 생성 (기획서에 없던 기능, 직접 추가)

### 판단 1 : 다크모드를 껐다

어제 글자색을 하나씩 지정해서 막았는데, 새 화면을 만들 때마다 같은 문제가 반복됐습니다.
기획서 자체가 흰 배경 기준으로 쓰여 있어서, 다크모드 설정을 남겨두는 게 오히려 계속 사고를 내는 원인이었습니다. 그래서 `globals.css`에서 다크모드 블록을 통째로 지웠습니다.

대신 **새 화면을 만들 때 글자색을 반드시 직접 지정하기로** 규칙을 정했습니다.

### 판단 2 : 조리법 기능을 추가했다

기획서에는 없는 기능입니다. 만들다 보니 "메뉴 이름만 알려주면 결국 또 검색해야 하는데?"라는 생각이 들어서 넣었습니다.

다만 21끼 조리법을 한 번에 만들면 느리고 AI 사용량도 많이 듭니다. 그래서 **사용자가 누른 끼니 하나만** 만들고, 만든 건 DB에 저장해서 다음부터는 저장된 걸 쓰도록 했습니다.

### 막힌 것 : 로딩 스피너가 멈추지 않음

생성 버튼을 눌렀는데 스피너가 영원히 돌았습니다. 에러 메시지도 없었습니다.

원인은 서버 API에서 **어떤 갈래로 빠지면 응답을 안 돌려주고 함수가 끝나버린 것**이었습니다. 서버가 아무것도 안 보내니 화면에서 `response.json()`으로 응답을 읽으려다 에러가 나는데, 그 에러를 잡아두지 않아서 바로 아래 "로딩 꺼라"는 코드까지 가지도 못했던 겁니다.

두 겹으로 고쳤습니다.

1. API는 성공이든 실패든 **모든 갈래에서 반드시 응답을 반환**하도록
2. 화면은 `finally`를 써서 **무슨 일이 있어도 로딩이 꺼지도록**

이 뒤로 다른 기능을 만들 때도 "이 함수는 모든 경우에 뭔가를 돌려주는가"를 먼저 확인하게 됐습니다.

## 8월 9일 (3일차) - 버그 잡고 다듬기

### 막힌 것 1 : 같은 조리법을 두 번 만드는 버그

조리법 A를 만드는 중에 B를 누르고, A가 끝나기 전에 A를 다시 누르면 **A를 두 번 생성**했습니다.

원인은 "지금 생성 중인 끼니"를 값 하나로만 기억하고 있었던 것입니다. A를 누르면 그 값이 A가 되는데, B를 누르는 순간 B로 덮어써지면서 **A가 아직 진행 중이라는 사실이 지워졌습니다.** 그래서 A를 다시 눌렀을 때 중복 검사를 통과해버린 겁니다.

처음엔 재현이 안 됐습니다. 조리법 생성이 2~4초로 빨라서 클릭 간격보다 먼저 끝나버렸기 때문입니다. 그래서 응답을 일부러 20초 늦춰놓고 같은 순서로 눌러보니 바로 재현됐습니다.

"생성 중인 끼니"를 값 하나가 아니라 **끼니별로 따로 기억**하도록 바꿔서 해결했습니다. 덤으로 A가 끝날 때 B의 로딩 표시까지 같이 꺼지던 문제도 함께 없어졌습니다.

### 막힌 것 2 : 다시 시도 버튼이 재시도를 안 함

조리법 생성이 실패했을 때 뜨는 "다시 시도" 버튼이, 누르면 그냥 패널이 접히기만 했습니다.

React에서 상태를 바꾸는 코드는 그 줄에서 바로 반영되지 않고 다음 화면 그릴 때 적용됩니다. 그런데 버튼이 "패널 닫아라"를 실행한 **바로 다음 줄**에서 펼치기 함수를 부르고 있었습니다. 그 함수는 아직 옛날 값(펼쳐진 상태)을 보기 때문에 "같은 걸 또 눌렀네, 접자"로 빠져버린 것이었습니다.

생성하는 부분을 별도 함수로 떼어내서 버튼이 그걸 직접 부르게 고쳤습니다.

### 판단 : 7일 식단을 기본 3일로 바꿈

기획서는 7일 식단인데 기본을 3일로 줄이고 7일은 선택지로 남겼습니다.

- 장은 보통 2~3일에 한 번 보는데, 7일치는 뒷부분을 결국 안 지키게 됩니다
- 7일 3끼면 21끼를 AI가 한 번에 만들어야 하는데, 응답이 길어지면 중간에 잘리거나 시간이 초과될 위험이 있습니다. 3일이면 9끼라 훨씬 안정적입니다

DB에서 하루 번호를 1~7까지 허용하고 있었기 때문에 3일치도 그 안에 들어가서, 테이블은 건드리지 않고 바꿀 수 있었습니다.

### 디자인 정리

기능이 다 돌아가는 걸 확인하고 나서 화면을 손봤습니다.

- 기획서에 적힌 브랜드 색(딥그린)과 한글 폰트를 실제로 적용. 그전까지 화면이 전부 회색이었고 폰트도 한글용이 아니었습니다
- 버튼마다 배경색과 그림자를 줘서 배경에 묻히지 않게 함. 특히 배경색 없이 테두리만 있던 버튼들이 글자처럼 보였습니다
- 키보드로 조작할 때 지금 어디에 있는지 보이도록 포커스 표시 추가
- 목표별, 끼니별로 색을 나눠서 7일 21칸이 회색 덩어리로 보이지 않게 함
- 색을 정할 때 글자와 배경의 대비를 계산해서 확인. 처음 고른 색은 대비가 2:1까지 떨어져서 작은 글씨가 안 읽혔고, 어두운 색으로 바꿔 4.5:1을 넘겼습니다
- 로고를 헤더, 로그인 화면, 404, 브라우저 탭에 배치

## 3일간 배운 것

**1. 내 컴퓨터에서 되는 것과 배포에서 되는 것은 다르다**

대소문자 문제가 대표적이었습니다. 그래서 배포 전에 항상 `npm run build`를 돌려서 확인하는 습관을 들였습니다.

**2. 에러가 안 보이는 게 제일 무섭다**

무한 스피너도, 조리법 중복 생성도 화면에는 아무 문제가 없어 보였습니다. 실패했을 때 실패했다고 알려주는 코드를 처음부터 같이 짜야 한다는 걸 알았습니다.

**3. AI 응답은 그대로 믿으면 안 된다**

알레르기 재료가 섞여 나오거나 요청한 일수와 다르게 나올 수 있어서, 저장하기 전에 서버에서 검사하고 문제가 있으면 한 번 다시 만들게 했습니다. 두 번째도 실패하면 저장하지 않습니다. 이상한 데이터가 DB에 남는 것보다 안 만들어지는 게 낫다고 봤습니다.

**4. 기능을 줄이는 것도 결정이다**

7일을 3일로 줄이고, 칼로리 수치와 소셜 기능을 뺐습니다. 이틀 안에 만들어야 하는 상황에서 핵심인 "재료 넣으면 식단 나오는 것"을 확실하게 만드는 쪽을 골랐습니다.

# MealMate

냉장고 재료로 AI 주간 식단을 만드는 웹앱. 멀티캠퍼스 AIM AI Agent 과정 제출용 프로젝트입니다.

- 저장소: https://github.com/noviz-domino/mealmate (private)
- 배포: https://mealmate-inky.vercel.app
- 스택: Next.js 16 (App Router) + TypeScript + Tailwind + Supabase(Auth/Postgres/RLS) + Gemini `gemini-3.5-flash` + Vercel

## 사용자에 대해

프로그래밍 초보자이며 매뉴얼을 따라 직접 만들어보는 중입니다. 코드를 대신 짜주더라도 **어느 파일에 무엇이 왜 들어가는지** 함께 설명해 주세요. UI/UX는 직접 조절하고 싶어 하며, Tailwind를 배우는 중입니다. 설명은 한국어로 합니다.

## 이 프로젝트에서 실제로 겪은 함정

- **파일명 대소문자**: 로컬 Windows는 대소문자를 구분하지 않지만 Vercel(Linux)은 구분합니다. `signupForm.tsx`를 `./SignupForm`으로 import해서 배포가 실패한 적이 있습니다. import 경로와 실제 파일명이 정확히 일치해야 합니다.
- **`middleware.ts`는 Next 16에서 deprecated** → 이 프로젝트는 `proxy.ts` + `export async function proxy()`를 씁니다.
- **다크모드 금지**: 기획서가 흰 배경 기준이라 `globals.css`의 `prefers-color-scheme: dark` 블록을 제거했습니다. 페이지들이 `bg-white`/`bg-zinc-50`로 고정돼 있어 다크모드가 켜지면 글자만 밝아져 안 보이는 문제가 있었습니다. **새 UI를 만들 때 글자색을 반드시 명시**하세요(`text-zinc-900` 등). 색을 생략하면 같은 문제가 재발합니다.
- **API 라우트는 모든 경로에서 반드시 응답을 반환**해야 합니다. 응답 없이 끝나면 프론트의 `response.json()`이 터지면서 로딩 스피너가 무한히 돌았습니다. 폼 쪽도 `try/catch/finally`로 로딩을 반드시 해제합니다.

## 작업 방식

- 코드 수정 후 **`npm run build`로 확인**한 뒤 push합니다. 빌드 실패가 곧 배포 실패입니다.
- `main`에 push하면 Vercel이 자동 배포합니다. 별도 배포 명령이 필요 없습니다.
- 브라우저 미리보기로 실제 렌더링을 확인한 뒤 완료 보고합니다. 사용자에게 수동 확인을 떠넘기지 않습니다.
- 환경변수는 `.env.local`(로컬)과 Vercel Settings → Environment Variables(배포) **양쪽에** 있어야 합니다.

## 현재 구현 상태

완료:
- 공개 홈 `/` — `is_public=true` 식단 카드 그리드
- 인증 `/auth` — LoginForm/SignupForm 별도 컴포넌트(기획서 필수 요건), 이메일 콜백
- 생성 폼 `/plans/new` — 재료 chip 입력, 비로그인 시 `/auth?next=` 리다이렉트
- 생성 API `POST /api/plans` — 입력 검증 → Gemini → 구조·알레르기 검증(실패 시 1회 재생성) → `meal_plans`→`meal_days`→`meals`→`shopping_items` 저장
- 식단 일수 선택 — **기본 3일**, 7일은 옵션(`lib/mealPlan.ts`의 `PLAN_DAYS`). 장을 2~3일에 한 번 보는 실제 주기에 맞추고, 한 번에 만드는 끼니가 21끼→9끼로 줄어 응답 잘림·타임아웃 위험도 함께 줄어듭니다. **기획서 F-07은 "7일 식단"이라 이건 명세 이탈이며, 사용자와 합의해 정했습니다.** `meal_days.day_index` 제약이 1~7이라 3일도 그 안에 들어가므로 마이그레이션은 없습니다.
- 상세 `/plans/[id]` — 7일 식단 + 장보기 목록
- F-02 공개 홈 목표/태그 필터, 검색
- F-09 내 식단 목록 `/plans`
- F-10~F-13 끼니 완료 체크·실천율, 장보기 체크, 공개/비공개 토글, 삭제 — 상세 페이지의 소유자 전용 컨트롤
- F-16 조리법 상세 — 카드를 펼치면 그 끼니 하나만 Gemini로 생성해 `meals.recipe_*`에 저장. 두 번째부터는 저장된 값을 쓰므로 재호출이 없습니다. **조리법은 기획서에 아예 없는 기능입니다**(기능 표는 F-15에서 끝남). 공개 정책은 사용자와 합의해 정했습니다 - **이미 만들어진 조리법은 누구나(비로그인 포함) 열람 가능, 아직 없는 조리법은 소유자만 생성 가능**합니다. 로그인만 했다고 되는 게 아니라 본인 식단이어야 합니다. 화면은 `isOwner`가 아니면 API를 아예 부르지 않고, 서버도 `meal.user_id !== user.id`면 403으로 막습니다(비로그인은 401). 남이 소유자의 AI 사용량을 쓰지 못하게 하려는 것입니다.
- F-14 마크다운 복사 — 상세 페이지 상단 버튼. 회원·방문자 모두. 조리법은 넣지 않습니다(21끼면 너무 길어짐). DB·AI를 부르지 않고 이미 받은 데이터를 문자열로 바꾸기만 합니다.
- F-15 끼니 재생성 — 펼친 패널의 소유자 전용 `[다른 메뉴로]`. 그 끼니 하나만 교체하고 `is_done`과 `recipe_*`를 비웁니다(메뉴가 바뀌면 옛 조리법이 맞지 않으므로). **장보기 목록은 건드리지 않습니다** — 사용자가 체크해 둔 구매 상태가 날아가기 때문이며, 대신 안내 문구를 띄웁니다.
- 헤더, 404, MCP 설정

기획서의 P0~P2 기능은 모두 구현했습니다. F-14·F-15는 기획서에 기능 목록만 있고 화면·API 명세가 없어(구현 티켓 1~17에도 없음) 위 설계는 사용자와 합의해 정한 것입니다.

### 마이그레이션

초기 스키마는 저장소에 파일이 없고 Supabase SQL Editor에만 있습니다. 그 이후 것만 `supabase/migrations/`에 있습니다.

- `0002_meal_recipes.sql` — F-16 조리법 컬럼. **적용 완료(2026-08-08).**

라우트 이름은 기획서의 `/create` 대신 매뉴얼을 따라 `/plans/new`를 씁니다.

## 되돌려야 할 임시 설정

**Supabase의 이메일 인증(Confirm email)이 테스트 편의를 위해 꺼져 있습니다.** Authentication → Providers → Email → Confirm email. 제출·실사용 전에 반드시 다시 켜야 합니다. 꺼진 상태로는 아무 이메일로나 가입됩니다.

**Supabase MCP의 `read_only=true`를 개발 기간 동안 임시로 뺐습니다** (`.mcp.json`, 2026-08-08). 마이그레이션을 매번 사용자가 SQL Editor에 직접 붙여넣지 않아도 되도록 편의상 푼 것입니다. **제출·실사용 전에 반드시 URL 끝에 `&read_only=true`를 다시 붙여야 합니다.** 이 제한은 DB에서 읽은 사용자 생성 텍스트(재료명, 요약 등)에 prompt injection이 숨어 있어도 실수로 쓰기 작업을 실행하지 못하게 막는 안전장치입니다.

테스트 계정: `test@test.noviz` (비밀번호는 사용자에게 문의 — 저장소에 남기지 않음)

## 보안

- `.env.local`, service role key, Gemini 키를 절대 커밋하지 않습니다. `.gitignore`가 `.env*`를 막고 있습니다.
- `SUPABASE_SERVICE_ROLE_KEY`는 서버 전용입니다. 클라이언트 컴포넌트에서 쓰지 않습니다.
- RLS를 끄지 않습니다. 권한 문제는 정책으로 해결합니다.
- `.mcp.json`은 OAuth 방식이라 토큰이 없어 커밋해도 안전합니다. Supabase MCP의 `read_only` 상태는 위 "되돌려야 할 임시 설정" 참고.

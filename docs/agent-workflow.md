# AI 도구를 운용한 방식

> 이 문서는 **부록**이다. 무엇을 만들었고 어떤 판단을 했는지는 [루트 README](../README.md)와 각 프로젝트 문서에 있다.
> 여기서는 그 과정에서 AI 코딩 도구를 어떻게 다뤘는지만 다룬다.

## 전제

**도구는 도구다.** Claude Code, Codex, Gemini는 내가 지시한 범위 안에서 동작한다. 무엇을 만들지 정하고, 결과가 맞는지 확인하고, 틀렸을 때 책임지는 건 나다.

그래서 커밋에 도구를 공동저자로 적지 않는다. IDE나 컴파일러를 공동저자로 적지 않는 것과 같은 이유다.

다만 **여러 도구를 동시에 굴리면 관리 문제가 생긴다.** 지침이 어긋나고, 서로의 작업을 덮어쓰고, 같은 실수를 반복한다. 아래는 그 문제들을 겪고 만든 규칙들이다.

---

## 1. 지침의 원본을 하나로 고정한다

도구마다 읽는 파일이 다르다. Claude Code는 `CLAUDE.md`, Codex는 `AGENTS.md`를 본다. 처음에는 양쪽에 같은 내용을 복사해뒀다.

**사본이 낡았다.** 화면 하나를 지웠는데 `AGENTS.md` 쪽만 갱신을 놓쳤고, 그 뒤로 **이미 삭제된 화면을 참조하는 작업**이 나왔다.

그래서 `englishWordApp`에서는 원본을 하나만 두고 나머지는 그것을 가리키게 했다.

```
CLAUDE.md    ← 지침 원본. 여기만 고친다
AGENTS.md    ← "이 파일에는 지침을 복사하지 않는다. CLAUDE.md를 읽어라"
```

`mealmate`와 `go-eat`은 반대 방향으로 같은 원칙을 적용했다. `AGENTS.md`가 원본이고 `CLAUDE.md`는 `@AGENTS.md` 한 줄짜리 참조다.

**중복을 없애면 어긋날 수가 없다.** 문서에서도 코드와 같은 원칙이 적용된다.

## 2. 읽을 문서를 지정한다

컨텍스트에 문서를 다 넣으면 정작 중요한 걸 놓친다. `go-eat`의 `AGENTS.md`에는 이렇게 적어뒀다.

> 새 세션을 시작하면 아래 두 문서를 먼저 읽어라: `기획서.md`, `개발일지.md`
> 다른 건 안 읽어도 된다.

그리고 초보자용 해설 문서(`이게_다_뭐하는_건가요.md`)에는 **"개발 작업용이 아니다"** 라고 명시했다. 용도가 다른 문서가 섞이면 작업 판단이 흐려진다.

## 3. 세션 간 인수인계 규칙을 만든다

`englishWordApp`은 Claude Code와 Codex를 번갈아 썼다. 한쪽이 미커밋 상태로 두고 끝내면, 다음 도구가 그걸 모르고 같은 파일을 건드린다.

그래서 `AI_WORKLOG.md`를 따로 뒀다. **여기에는 "지금 미커밋 상태인 작업과 그 소유자"만 적는다.** 진행 기록이 아니라 게시판이다.

작업 순서를 규칙으로 고정했다.

```
1) AI_WORKLOG.md 읽기   ← 누가 뭘 하다 말았는지
2) git status
3) git log
4) 작업 시작
5) 커밋할 때 AI_WORKLOG.md에서 해당 항목 삭제
```

## 4. 검증한 내용을 커밋에 남긴다

"고쳤습니다"는 확인이 아니다. 그래서 커밋 메시지에 무엇을 실행해서 확인했는지 적는 형식을 정했다.

```
검증: ./gradlew test 성공
```

나중에 문제가 생겼을 때 **어느 커밋까지 실제로 검증됐는지** 되짚을 수 있다.

## 5. 재발한 실수를 문서에 쌓는다

같은 버그를 두 번 만나면 체크리스트에 넣는다. 이건 도구용이면서 동시에 나를 위한 기록이다.

**`englishWordApp` — "자주 반복된 실수"**

| 항목 | 증상 |
|---|---|
| ViewModel 프로퍼티를 `mutableStateOf`로 안 감쌈 | 값은 바뀌는데 화면이 갱신 안 됨 (2회 재발) |
| `Box` 안 clickable 레이어 순서 | 상위 레이어가 터치를 가로채 스피커·즐겨찾기 아이콘이 안 눌림 |
| R8 활성화 | `compose-group-mapping` 아티팩트 해석 실패로 릴리즈 빌드 실패 |

**`mealmate` — "이 프로젝트에서 실제로 겪은 함정"**

| 항목 | 증상 |
|---|---|
| 파일명 대소문자 | Windows에서는 되고 Vercel(리눅스)에서만 빌드 실패 |
| `middleware.ts` → `proxy.ts` 개명 | 인증 미들웨어가 조용히 무력화됨 |
| API 라우트 미반환 분기 | 로딩 스피너 무한 회전 |

## 6. 도구를 데이터 소스에 직접 연결한다

`mealmate`와 `go-eat`에는 MCP 서버를 붙여 썼다.

```json
{ "mcpServers": {
    "supabase": { "type": "http", "url": "https://mcp.supabase.com/mcp?project_ref=..." },
    "vercel":   { "type": "http", "url": "https://mcp.vercel.com" } } }
```

스키마를 물어보고 붙여넣는 왕복이 사라진다. 다만 **연결하면 잘못된 쿼리도 실제 DB에 나간다.** 읽기 위주로만 쓰고 스키마 변경은 마이그레이션 파일로 관리했다.

## 위임하지 않은 것

도구를 쓰든 안 쓰든, 아래는 사람이 해야 하는 일이라고 생각한다. 실제로도 이 부분에서 막혔고, 여기서 시간을 가장 많이 썼다.

**무엇을 만들지 정하는 것**
`replygate`는 "AI로 고객 응대를 자동화한다"가 아니라 **"AI가 지어낸 수치가 고객에게 그대로 나가면 분쟁이 된다"** 는 문제 인식에서 출발했다. 그래서 자동 발송이 아니라 사람 승인 구조가 됐다.

**측정 기준을 설계하는 것**
평가셋 50건을 유형·감정·조회필요·난이도 축으로 분산시키고, **정책 문서에 일부러 답이 없는 함정 5건**을 넣었다. 모르는 것을 모른다고 답하는지 확인하기 위해서다.

**결과가 이상할 때 원인을 찾는 것**
감정 분류에서 `중립`이 20번 중 0번 선택됐다. 정의를 고쳐도 여전히 0이었다. 결국 **감정과 조회필요가 직교하는 두 축**이라는 걸 알아내고 축을 분리했다(98% / 92%). 중간에 만든 v2는 라벨만 옮긴 가짜 개선이었고, 그 사실을 개발일지에 그대로 남겼다.

**제약 안에서 설계를 바꾸는 것**
`n8n-finance-news-briefing`이 무료 티어 한도에 걸려 `429`가 났을 때, 필터 강화·일일 상한·배치 요약을 조합해 호출을 188회에서 4회로 줄였다. 어느 조합이 요구사항을 깨지 않는지는 요구사항을 알아야 판단할 수 있다.

**요구사항과 증상을 구분하는 것**
같은 프로젝트에서 Discord 2,000자 제한에 걸렸을 때 `MIN_IMPORTANCE`를 5로 올리면 증상은 사라진다. 하지만 요청서는 4 이상을 보내라고 했으므로 그건 요구사항 위반이다. 대신 판정 기준이 느슨해져 있던 프롬프트를 원문대로 되돌렸다.

---

## 아직 잘 안 되는 것

- **긴 세션에서 초반 결정을 잊는다.** 그래서 결정 사항을 문서에 적어두고 매번 읽게 하는데, 문서가 길어지면 이번엔 그걸 다 안 읽는다. 적정 분량을 아직 못 찾았다.
- **되돌리기 어려운 작업**은 아직 도구에 맡기지 않는다. 히스토리 재작성이나 강제 푸시는 직접 확인하고 실행한다.
- **"검증했다"는 보고를 그대로 믿으면 안 된다.** 실제로 명령을 다시 돌려 확인해야 하는 경우가 있었다.

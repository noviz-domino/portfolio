# Supabase 라이브 데모 유지

`mealmate`와 `go-eat`은 Supabase 무료 플랜을 쓴다. 무료 플랜은 **DB 활동이 부족하면 프로젝트를 자동으로 일시정지**시키고, 정지되면 대시보드에서 손으로 재개해야 한다. 포트폴리오를 검토하는 중에 데모가 죽으면 안 되므로 자동화했다.

`.github/workflows/supabase-keepalive.yml`이 **매일** 각 프로젝트의 `keep_alive` 테이블에 **쓰기 요청**을 보낸다.

**읽기(SELECT)로는 막을 수 없다.** 처음에는 3일마다 조회만 보냈는데 두 차례 정지됐다. `HTTP 200`을 받은 지 두 시간 뒤에 정지 통보가 온 사례까지 있다. 경위는 아래 사고 기록 두 건에 남겨두었다.

## 최초 1회 설정

### 1. 각 Supabase 프로젝트에 `keep_alive` 테이블 만들기

Supabase 대시보드 → **SQL Editor** → 아래를 붙여넣고 실행한다. **두 프로젝트(`mealmate`, `go-eat`) 각각에서** 실행해야 한다. 여러 번 실행해도 안전하게 만들어두었다.

```sql
-- 핑 전용 테이블. 서비스 데이터는 담지 않는다.
create table if not exists public.keep_alive (
  id bigint generated by default as identity primary key,
  created_at timestamptz not null default now(),
  last_ping timestamptz not null default now()    -- 핑이 매번 갱신하는 컬럼
);

-- 이미 테이블이 있는 경우를 위해 컬럼만 따로 추가한다.
alter table public.keep_alive
  add column if not exists last_ping timestamptz not null default now();

-- 갱신 대상이 될 행 하나를 확보한다. 이미 있으면 아무것도 하지 않는다.
insert into public.keep_alive (id)
values (1)
on conflict (id) do nothing;

-- RLS를 켠다. 켜는 순간 명시적으로 허용한 동작만 통과한다.
alter table public.keep_alive enable row level security;

-- 조회 허용. 이 테이블에는 아무 정보도 없으므로 공개해도 위험이 없다.
drop policy if exists "keep_alive 조회 허용" on public.keep_alive;
create policy "keep_alive 조회 허용"
  on public.keep_alive
  for select
  using (true);

-- 갱신 허용. 대상을 id = 1 한 행으로 못박는다.
drop policy if exists "keep_alive 갱신 허용" on public.keep_alive;
create policy "keep_alive 갱신 허용"
  on public.keep_alive
  for update
  using (id = 1)          -- 어떤 기존 행을 건드릴 수 있는지
  with check (id = 1);    -- 바뀐 결과가 만족해야 하는 조건
```

**`INSERT`와 `DELETE` 정책은 일부러 만들지 않았다.** RLS는 허용하지 않은 동작을 기본 차단하므로 이것만으로 행 추가와 삭제가 막힌다.

행을 늘릴 수 있게 열어두면 `anon` 키를 아는 사람이 대량으로 밀어넣어 무료 용량 500MB를 채울 수 있다. 핑에 필요한 최소 권한만 여는 편이 안전하다.

### 2. GitHub Secrets 등록 (완료됨)

| 시크릿 | 출처 |
|---|---|
| `MEALMATE_SUPABASE_URL` | mealmate의 `NEXT_PUBLIC_SUPABASE_URL` |
| `MEALMATE_SUPABASE_ANON_KEY` | mealmate의 `NEXT_PUBLIC_SUPABASE_ANON_KEY` |
| `GOEAT_SUPABASE_URL` | go-eat의 `NEXT_PUBLIC_SUPABASE_URL` |
| `GOEAT_SUPABASE_ANON_KEY` | go-eat의 `NEXT_PUBLIC_SUPABASE_ANON_KEY` |

`anon` 키는 브라우저에 그대로 내려가는 공개 키다. 그래도 Secrets에 둔 이유는
저장소가 public이 되었을 때 워크플로 파일에 키가 박혀 있지 않게 하기 위해서다.
**`service_role` 키는 절대 쓰지 않는다.** DB 전체 권한을 가지므로 이런 용도에 부적절하다.

### 3. 동작 확인

GitHub 저장소 → **Actions** 탭 → `Supabase Keep-Alive` → **Run workflow** 로 수동 실행.

**`HTTP 200`만 보고 판단하지 않는다.** 아래 문장이 함께 찍혀야 정상이다.

```
정상. last_ping 이 2026-09-07T07:54:19 로 갱신되었습니다.
```

`200`이 와도 실제로는 아무것도 갱신되지 않는 경우가 있다. 그래서 워크플로가 보낸 시각과 저장된 시각을 초 단위로 대조한 뒤에만 이 문장을 출력한다.

## 문제가 생겼을 때

| 증상 | 원인 | 조치 |
|---|---|---|
| `HTTP 404` | `keep_alive` 테이블 없음 | 위 1번 SQL을 해당 프로젝트에서 실행 |
| `HTTP 401` / `403` | 키가 틀렸음 | 시크릿 값 재등록 |
| `갱신된 행이 없습니다` | `id = 1` 행이 없거나 `UPDATE` 정책 누락 | 위 1번 SQL 재실행 |
| `쓰기가 반영되지 않았습니다` | 저장된 값이 보낸 값과 다름 | 정책의 `with check` 조건 확인 |
| `HTTP 5xx` 또는 `exit 6` | 프로젝트가 이미 정지됨 | 대시보드에서 재개 후 워크플로 수동 실행 |

`exit 6`은 `curl`의 `Couldn't resolve host`다. 정지된 프로젝트는 호스트 이름 조회 자체가 실패하므로, HTTP 상태 코드가 찍히기도 전에 죽는다.

## 알아둘 점

- **Vercel 배포는 만료되지 않는다.** Hobby 플랜에 기간 제한이 없으므로 별도 조치가 필요 없다. 갱신이 필요한 건 Supabase뿐이다.
- GitHub Actions는 저장소에 **60일간 활동이 없으면 스케줄 워크플로를 자동으로 비활성화**한다. 이 저장소는 프로젝트가 추가될 때마다 커밋이 생기므로 실무상 문제되지 않지만, 오래 손대지 않았다면 Actions 탭에서 활성 상태인지 확인한다.
- 정지를 확실히 막는 유일한 방법은 **Pro 플랜 업그레이드**(월 $25)다. 무료 플랜에 머무는 한 이 문서의 자동화는 완전한 보장이 아니다. 그래서 README에서는 데모 링크와 함께 스크린샷을 안내한다.

## 사고 기록 - 2026-08-31 실제로 두 프로젝트가 정지됐던 일

3일마다 자동으로 핑을 보내고 있었는데도 `mealmate`, `go-eat` **두 프로젝트가 모두 실제로 일시정지됐다.** "자동으로 유지되게 만들어놨다"는 것과 "실제로 유지되고 있다"는 건 다른 문제라는 걸 확인한 사례라 남겨둔다.

### 증상

- GitHub Actions 실패 이메일 수신. workflow 로그를 보니 `curl`이 **exit code 6**(`Couldn't resolve host` - 호스트 이름 조회 자체가 실패)으로 즉시 종료됨. HTTP 상태 코드가 찍히기도 전에 죽은 것이라, 기존 문서의 "문제가 생겼을 때" 표에 있던 404/401/5xx 어느 것에도 안 걸림.
- 라이브 데모(`mealmate-inky.vercel.app`)를 직접 열어보니 화면에 `TypeError: fetch failed`. GitHub Actions만의 문제가 아니라 **실제 서비스가 죽어 있었다.**
- Supabase 대시보드에서 두 프로젝트 다 **"Project is paused"** 확인.

### 원인 - 아직 완전히 규명되지는 않았지만 유력한 설명

실행 이력을 시간순으로 보면 이상한 점이 있었다.

| 날짜 | mealmate | go-eat |
|---|---|---|
| 8/22 | HTTP 200 | HTTP 200 |
| 8/25 | HTTP 200 | **exit 6 (DNS 실패)** |
| 8/28 | exit 6 | exit 6 |

Supabase 공식 문서(`free-project-pausing`)는 "REST API를 통한 요청이면 SELECT도 활동으로 인정되고, 일주일에 며칠만 있어도 정지 안 된다"고 안내한다. 우리 워크플로는 3일마다 정확히 성공했으니 이 기준을 만족했어야 하는데도 정지됐다.

가장 유력한 설명은 **캐싱**이다. 매번 완전히 동일한 쿼리(`select=id&limit=1`)를 보냈기 때문에, PostgREST나 엣지 캐시 레이어에서 응답이 캐시되어 **HTTP 200은 정상적으로 왔지만 실제로는 Postgres compute까지 도달하지 않았을 가능성**이 있다. 이러면 겉보기엔 "핑이 성공하고 있다"고 착각하기 쉽지만, Supabase의 활동 감지기 입장에서는 진짜 DB 활동이 없었던 것과 같다. (비슷한 문제를 다룬 커뮤니티 도구들도 정지 방지용 요청에 일부러 캐시를 피하는 파라미터를 섞어 쓰는 걸 확인했다.)

두 프로젝트의 실패 시점이 3일 어긋난 것(go-eat이 먼저, mealmate가 나중)은 실제 마지막 "진짜" DB 접근 시점이 프로젝트마다 조금씩 달랐기 때문으로 추정된다.

### 조치

1. 대시보드에서 두 프로젝트 모두 수동 **Restore**
2. `.github/workflows/supabase-keepalive.yml`에 캐시 우회 로직 추가

```diff
  status=$(curl -s -o /dev/null -w '%{http_code}' \
    -H "apikey: ${SUPABASE_KEY}" \
    -H "Authorization: Bearer ${SUPABASE_KEY}" \
+   -H "Cache-Control: no-cache" \
+   -H "Prefer: no-cache" \
+   -H "X-Cache-Bust: $(date +%s)" \
    "${SUPABASE_URL}/rest/v1/keep_alive?select=id&limit=1")
```

**시행착오 하나**: 캐시버스터를 처음엔 쿼리스트링(`&_cb=$(date +%s)`)으로 넣었는데, PostgREST가 인식 못 하는 파라미터를 **존재하지 않는 컬럼 필터로 해석**해서 오히려 `HTTP 400`을 냈다. 그래서 응답 파싱에 영향 없는 **커스텀 헤더**(`X-Cache-Bust`)로 옮겨서 해결했다. REST API마다 "모르는 쿼리 파라미터"를 처리하는 방식이 다르다는 걸 실제로 겪은 사례.

### 검증 완료 - 2026-09-04 (이후 번복됨)

수정 이후 두 차례 스케줄 실행 모두 두 프로젝트 다 정상이었다.

| 실행일 | mealmate | go-eat |
|---|---|---|
| 09-01 | HTTP 200 | HTTP 200 |
| 09-04 | HTTP 200 | HTTP 200 |

**이 판단은 틀렸다.** 사흘 뒤 다시 정지됐고, 원인은 캐싱이 아니라 읽기 요청 자체였다. 아래 9/7 기록을 참고한다.

캐시 우회 헤더가 원인을 제대로 잡았다고 본다. 다만 이 문제는 Supabase나 중간 캐시 레이어의 정책 변경에 따라 재발할 수 있으므로, 같은 증상(200인데 실제로는 정지)이 다시 나오면 이 문서에 이어서 기록한다.

## 사고 기록 - 2026-09-07 읽기 핑으로는 막을 수 없다는 결론

8/31 수정(캐시 우회 헤더) 이후 9/1과 9/4 두 차례 성공해서 해결됐다고 판단했는데, **9/7에 `go-eat`이 다시 정지됐다.**

### 결정적 증거

| 시각(UTC) | 사건 |
|---|---|
| 09-07 04:44 | 스케줄 핑 실행 → `go-eat → HTTP 200` 성공 |
| 09-07 07:04 | Supabase에서 프로젝트 정지 통보 메일 도착 |

메일에 적힌 프로젝트 ID(`vpykysmsrafjvnewjubu`)가 핑이 찌르던 프로젝트와 **동일**했다. 핑은 정확한 대상에 갔고 `200`을 받았는데도 정지된 것이다.

`mealmate`는 살아남았지만 핑 덕분이라고 보지 않는다. `mealmate`는 로그인 없이 공개 식단 페이지가 열려서 방문자 트래픽이 DB까지 닿는다. 반면 `go-eat`은 로그인이 필수라 사람 트래픽이 0에 가깝다. **살아남은 쪽은 사람이 눌러준 쪽이었다.**

### 원인

두 가지가 겹친 것으로 판단했다.

**읽기는 활동으로 인정되지 않는다.** 공식 문서가 활동의 종류를 명시하지 않지만, `200`을 받고도 정지된 사례가 이 판단을 뒷받침한다. 8/31에 의심했던 캐싱은 부차적인 문제였고, 캐시를 우회해도 읽기라는 성질 자체가 문제였다.

**빈도도 부족했다.** 공식 문서는 "지난 주 동안 **매일** 몇 가지 요청"을 권장한다. 3일마다 1회는 주 2~3회로 이 기준에 못 미친다.

### 조치

1. 대시보드에서 `go-eat` 수동 **Restore**
2. `keep_alive` 테이블에 `last_ping` 컬럼과 `UPDATE` 정책 추가
3. 워크플로를 **읽기에서 쓰기(`PATCH`)로 전환**하고 **주기를 매일로** 단축
4. **응답 코드만으로 판단하지 않는 검증 단계 추가**

4번이 이번 개편에서 가장 중요하다. RLS로 갱신이 막히면 PostgREST는 오류가 아니라 `200`과 빈 배열을 돌려준다. "갱신 가능한 행이 0개였다"를 정상 처리로 보기 때문이다. 그래서 응답 코드만으로는 성공과 구별이 안 된다.

지금은 보낸 시각과 저장된 시각을 초 단위로 대조해서, 값이 실제로 바뀐 것을 확인한 뒤에만 성공으로 처리한다.

### 관찰 중

수동 실행에서 두 프로젝트 모두 `last_ping` 갱신이 확인됐다.

하지만 **아직 해결됐다고 적지 않는다.** 8/31에도 3일 연속 성공을 보고 "검증 완료"라고 적었는데 그 직후 정지됐다. 정지 판정은 주 단위로 도는 것으로 보이므로 **최소 2주는 지켜본 뒤에** 결론을 낸다.

그때까지는 데모가 죽어 있을 수 있다고 가정하고, README에서 스크린샷을 함께 안내한다.

## 2026-10-01 - 하루 1회 쓰기로도 정지 예고를 받음

9/7 개편 이후 하루도 빠짐없이 쓰기가 성공했는데(`last_ping`이 매일 갱신된 것까지 확인), 9/27에 go-eat이 "7일 넘게 활동이 부족하다"는 정지 예고 메일을 받았다. 같은 시각에 돌던 mealmate는 메일을 받지 않았다. 실제 방문자의 쿼리가 조금 더 있었던 차이로 보인다.

유지 작업이 엉뚱한 프로젝트를 깨우고 있던 건 아니다. 메일의 프로젝트 ID와 앱이 쓰는 주소가 같고, 그 프로젝트의 `keep_alive.last_ping`이 자동 작업이 쓴 시각과 일치했다.

Supabase 문서는 "지난 일주일 동안 하루 몇 건의 DB 요청"을 기준으로 든다. 하루 1건은 그 경계에 못 미친다고 보고 다음처럼 바꿨다.

| 항목 | 이전 | 이후 |
|:--|:--|:--|
| 주기 | 하루 1회 | 6시간마다 하루 4회 |
| 요청 | 쓰기(PATCH) 1건 | 쓰기 + 읽기(SELECT) + 로그인 서버 확인(`/auth/v1/health`) |

이렇게 해도 다시 예고 메일이 오면 무료 유지는 포기하고 Neon 이전이나 Pro 플랜을 검토한다.
